# 06 書く

## この章で読むこと

事故の記録を、後で読む人(自社の次の係、経営者、委託元、報告先、警察)が分かる形に残します。書く物は、追記だけの記録と、最後の報告書です。

報告書は、責める物ではなく、次に変える事を決めるための物です。人の名で原因を書かず、仕組みと手順で書きます。

## 追記だけの記録

01 から 05 までで書いてきた記録(`00-時刻と見た事.md` から `04-知らせた事.md`)は、追記だけで扱います。

- 書いた行を消さない、書き換えない。
- 間違いは、下に訂正の行を足します。

```
- 09:20 ファイルサーバーを網から外した(係)
- 10:05 訂正: 09:20 の行の「ファイルサーバー」は「ファイルサーバーの 2 台目」。1 台目は 09:40 に外した(係)
```

- 行ごとに、時刻と、書いた人の役を書きます。
- 一日の終わりに、その日の記録のファイルの sha256 を取り、別の所(紙でもよい)に書きます。後で書き換えられていないことを示せます。

```
[読む] Linux
sha256sum jiko/<2026-11-11-001>/*.md >> jiko/<2026-11-11-001>/hi-goto-sha256.txt
[読む] Windows
Get-FileHash -Algorithm SHA256 jiko\<2026-11-11-001>\*.md |
  Format-Table Hash,Path -AutoSize | Out-File -Append jiko\<2026-11-11-001>\hi-goto-sha256.txt
```

記録を Git で持つ会社は、記録の置き場を Git の作業の場所にし、追記のたびに commit すると、履歴が残ります。履歴を書き換える操作(rebase、force の push)はしません。

## 時系列

03 の時系列の表と、01〜05 の記録を合わせて、一本の時系列にします。二つの時刻を分けて書きます。

| 時刻 | 攻撃者がした事(記録から分かった事 / 推測) | 自社がした事 | 出どころ |
|---|---|---|---|
| 11-07 14:02 | VPN にログイン(分かった) | | 03、VPN の記録 |
| 11-11 09:05 | | 社員が画面の変化に気づく | 01 |
| 11-11 09:20 | | ファイルサーバーを網から外す | 02 |

「気づいた時刻」と「最初に入られた時刻」の差は、見張りを変える時の大事な数字です。

### 原因の書き方

- 「<人> がメールの添付を開いた」は原因の書き方として浅いです。「添付を開くと実行される形のファイルが、メールの仕組みで止められていなかった」「開いた後に気づく見張りが無かった」のように、仕組みと手順まで書きます。
- 原因が一つに決まらない時は、候補を並べ、それぞれの根拠を書きます。
- 03 の「分かった事と推測」の区別を、報告書でも保ちます。

### 次に変える事の選び方

変える事は、事故の流れのどこで止められたかで分けると、抜けが減ります。

| 段 | 問い | 例 |
|---|---|---|
| 入られる前 | 入口を減らせたか | 使っていない VPN のアカウント、退職者のアカウント、常に開いた業者の道(00) |
| 入られた時 | すぐ気づけたか | 外からのログインの知らせ(`skills/detection/`) |
| 中で広がる時 | 広がりを止められたか | 管理者の権限の分け方、網の分け方 |
| 消される時 | 記録と控えは残ったか | 記録を機械の外へ(R-RS-12)、網から切り離した控え |
| 戻す時 | 早く戻せたか | 戻す訓練(00)、予備の機械(R-RS-08) |
| 知らせる時 | 期限に間に合ったか | 連絡先の表、知った時刻の扱い(05) |

同じ穴が他のシステムに無いかは、`skills/system-check/` で確かめます。

## 社外へ出す時

報告書を委託元、取引先、報告先へ出す時は、社内の版から作り直します。

- 人の名、アカウントの名、番地、機械の名は、相手が要る物だけにします。
- 攻撃の手順の細かい所は、相手が直すのに要る分だけにします。
- 推測を事実として書かない。分からない事は分からないと書きます。

## 確かめていない事

- この雛形は、実際の事故の報告書として使ったことがありません。08 の訓練で一度書いて、書きにくい所を直す形を考えています。

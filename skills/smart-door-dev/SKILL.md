# スマートドアとスマートロックを、公開の仕様に沿って作る

扉の錠は、間違えると人が閉じ込められるか、他人が入れる機器です。そして一度付けると何十年も使われます。だからこのスキルは、速く書くことより、**何を満たすかを先に決め、確かめられる形で作る**ことを優先します。土台は digitaldoor の公開の要求仕様と、扉のコントローラの参照実装とテストです。文章は CC BY 4.0、コードは AGPL-3.0-or-later です。

## まず手元に置く物

```bash
git clone https://github.com/aiseed-dev/digitaldoor
cd digitaldoor
python3 -m venv .venv
.venv/bin/pip install -e ".[web,panel,mobile,dev]"
.venv/bin/python -m pytest -q          # 参照実装のテストが通ることを先に見る
python3 tools/taiou.py --check         # 要求とテストの対応(docs/適合の現在.md)
```

リポジトリが取れない環境では、文書を GitHub で読み、参照実装は写さずに、要求の番号と試験の対だけを使って自分の言語で作ります。

## 進め方

1. **立場と範囲を決める。** 扉メーカー、錠メーカー、読取機のメーカー、工事・管理会社、運営者のどれで、どの層を作るか。満たす要求の番号を選びます。全部を満たす必要はなく、満たす番号を申告する形です。立場ごとの読む所は `references/roles.md`。
2. **要求を一つずつ言葉にする。** 選んだ番号ごとに「何のための要求か、満たさないと誰がどう困るか」を短く書き出し、使う人に見せて合意します。分からない要求は推測で実装せず、問いとして残します(手順 7)。
3. **テストを仕様から先に書く。** 入力と期待値は要求と仕様の「試験の対」から決め、実装を見て決めません。実装の誤りを期待値に写さないためです。テストの docstring の先頭に要求の番号を書きます。書き方は `references/testing.md`。
4. **テストが落ちるのを見てから実装する。** まだ無い機能のテストは落ちるはずです。落ちなければテストが何も確かめていません。実装は、できればテストと別のセッションで行います。
5. **わざと壊して、テストが落ちることを確かめる。** 判断の分岐を消す、値を一つ変える、排他の外に出す。壊しても通るテストは作り直します。
6. **疑似の機器で全部の経路を通す。** 接点、錠、読取機、時計、箱(記録の出し先)を疑似に替え、正常の経路だけでなく、停電、火災、時刻のずれ、応答しない相手を毎回回します。実機は受入れ試験だけに使い、結果を同じ要求の番号の下に並べます。`references/interfaces.md`。
7. **対応を集計し、足りない物を仕様に返す。** `python3 tools/taiou.py --check` で、要求とテストの対応と未検証を出します。要求の抜け、矛盾、満たせない物、別の方法は、Issue のひな形「製造者からの質問・制約・代わりの案」で、番号と内容と確かめた日を添えて返します。番号は変えません。

## 扉で外してはいけない判断

これらは、規格(Matter、Aliro)が決めていない所で、事故と責任に直結します。実装の細部は選べますが、ここは選べません。理由とともに覚えてください。

- **判断は扉が持つ。** 火災、停電、避難、自動施錠、二人同時、強要の判断は扉側のコントローラが持ち、ネットワークやクラウドが止まっていても動きます。橋渡し(Matter、画面、アプリ)は翻訳と表示だけです。
- **火災の信号の間は、施錠の要求を受けない。** 設定(解放か保持か)に関わらず、火災中の施錠は拒みます。停電のときは設定に従い、解放の設定なら施錠の要求を拒みます。
- **扉が開いている間は自動施錠しない。** 閉じたのを見てから施錠します。自動施錠の秒数が 0 なら、自動施錠しません。
- **電源が無くても、内側から機械的に開けられる。** 非常手段の使用は記録に残します。
- **資格情報が有効かどうかは、上の層(発行者)が決める。** コントローラは「どの主体が、どの経路で、有効だったか」を受けて記録します。読取機から受けるのは判定の結果だけで、顔の画像や特徴量は受けません。
- **記録は追記だけ。** 連番(欠番が分かる)、前の記録のハッシュの連鎖、署名を付け、錠自身の操作で消せません。訂正は新しい記録として書きます。時刻が未同期の間の記録には印を付け、同期のときは前と新しい時刻を両方残します。設定の変更は、前と新しい値を残します。
- **外へ出す口の不調で、判断を止めない。** 記録の書き出し、通知、クラウドとの通信は、判断の排他(ロック)を持たない別の流れで行います。共有フォルダや回線が固まっても、自動施錠と火災の扱いは止まりません。
- **業者に扉を開ける常の権限を持たせない。** 一つの発行者の鍵が届く扉は、その発行者が管理する扉に限ります。業者が多くの顧客の発行を引き受けても、顧客ごとに別の鍵にし、秘密鍵は取り出せない場所に置き、他人と共有する機械には置きません。業者の鍵一つで全顧客の扉が開く形は、クラウドの事故(業者の認証情報の悪用)で建物ごと開く形です。集合住宅では、住戸の錠の発行者は区分所有者です(R-AC-09〜12、R-AP-38、39)。
- **錠の銘柄は接点の層かドライバに閉じる。** 判断側の記述を錠ごとに変えません。
- **秘密は手元に置く。** 錠の鍵、署名の秘密鍵、API の鍵はリポジトリに入れず、テストでは疑似の値を使います。個人情報(顔、名簿)もテストではバイト列や架空の名前で代えます。

## 終わったときに返す物

作業の終わりに、次の形で報告します。使う人が、何を確かめ、何を確かめていないかを一目で分かるようにするためです。

```
## 満たした要求
| 番号 | テスト | 壊して落ちることを確かめたか |
## 未検証の要求(理由:実機で確かめる / まだ書いていない / 問いがある)
## 仕様への問い(番号、内容、確かめた日)
## 選んだ細部(仕様が決めていない所で選んだ物と、その理由)
```

# 立場ごとに、作る物と読む所

層の名前は、ドアホン(読取機)、電子錠、扉のコントローラ、鍵の発行、業務システムとの連携を使います。

| 立場 | 作る物 | 読む文書 | 最初に選ぶとよい要求 |
|---|---|---|---|
| 扉メーカー | 扉側のコントローラ(判断と記録)、設定画面、受入れ試験 | `docs/扉コントローラ仕様書.md`、`docs/要求仕様/01_interface.md`、用途別のプロファイル(10〜30) | R-CT-05〜10(火災、停電、非常手段、二人同時、自動施錠、資格情報)、R-CT-11〜16(監査記録)、R-CT-22(設定の記録) |
| 錠メーカー、電動ラッチの部品メーカー | 接点の層の差し替え、安全側の MCU の振る舞い、性能の申告 | `docs/要求仕様/00_core.md`(R-EL、R-CM)、`05_latch.md`(R-MC) | R-CT-03、04(銘柄を接点の下に隠す)、R-EL の電子部の 2 系統、R-MC の性能の数字 |
| ドアホン、カメラ、読取機のメーカー | 判定結果をコントローラに渡す口、顔の扱い、生体検知、性能の申告 | `docs/要求仕様/02_reader.md`(R-RD)、扉コントローラ仕様書 5.2 | R-CT-19(判定結果の受け口)、R-RD-08(経路、信頼度、生体検知の結果)、R-RD-10(判定できないときの逃げ道) |
| 設備工事会社、管理会社 | ゲートウェイの管理ソフト、鍵の発行と失効、台帳、更新の配布、記録の受け取り | `docs/要求仕様/70_dev_server.md`(R-DV)、`00_core.md` の監査ログと権限モデル | R-CT-17(署名つきの伝票の受け取りと検べ)、R-CT-20(照会の口)、R-DV |
| 民泊、貸家、事業所の運営者 | 受け入れの仕組み(予約、本人確認、鍵の発行、台帳) | `digitalkey/entrance/`、`docs/使い方.md` の設計方針 | 様式(`digitalkey/entrance/forms_data/*.adoc`)が正。伝票は追記だけ |
| 施工・保守の業者、運営者の現場の人 | 据付、受入れ試験、点検、切り離し、復元、鍵の作り直しの手順と記録 | `docs/要求仕様/90_installer_program.md`(R-IP)、`00_core.md` 8.3(R-RS-07〜10)、5.4(R-NW) | R-IP-04、05(据付と受入れ試験)、R-IP-07(切り離しと復元)、R-IP-02、03(権限と鍵を持ち帰らない) |
| 後付けの錠のドライバを書く人 | 既存の製品(Sesame 等)を `digitalkey.locks` に登録するドライバ | `digitalkey/locks.py`、`drivers/digitalkey-sesame/` | 疑似の機器を先に作り、実機なしでテストを回す |

## 範囲の決め方

- 一度に全部を満たそうとしません。一つの層の、続けて確かめられる一塊(例: 火災と停電の判断、監査記録の連鎖と署名)から始めます。
- 選んだ番号は、使う人に一覧で見せて合意してから進めます。番号ごとに「疑似で確かめる」「実機で確かめる」を分けておくと、後の未検証の理由が書けます。
- 仕様に無いが要る物に気づいたら、勝手に番号を作らず、問いとして返します。要求を足すときは、理由に出どころ(Issue の番号か、使う人の困りごとの文)を書くのが、このリポジトリの約束です。

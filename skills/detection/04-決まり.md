# 04 決まりを書く

決まり(検知の規則)は、03 の普段の形から外れた物を拾う文です。一つの決まりに、次の五つを書きます。

| 欄 | 書くこと |
|---|---|
| 何を見るか | 人の言葉で一文 |
| どの記録か | 02 で集めた記録の名 |
| 調べる命令 | 記録を読む命令か問い合わせ。確かめたか、確かめていないかを付ける |
| 鳴った時に最初にする事 | 受けた人が、最初の 15 分ですること |
| 値 | 回数、時刻、量。例として書き、会社が決めた値と日付を書き直す |

## 命令の例の読み方

- **確かめた(Linux)**: 2026-11-11 に、Debian 13(systemd 257)の机の PC で、sudo なしで打ち、形が通る事を確かめた物です。sudo なしでは自分の記録しか見えないので、記録の量や中身は確かめていません。
- **確かめた(文書)**: 2026-11-11 に、learn.microsoft.com などの公式の文書で書き方を確かめた物です。Windows や Microsoft 365 では打っていません。
- **確かめていません**: 試験用のコンピューターで打って確かめてから使います。

道具の `scripts/fail_then_ok.py` と `scripts/off_hours.py` は、架空の記録(例示用の番地、架空の名前)で動きを確かめ、この机の PC の本物の journald の出力を通して落ちない事を確かめました。

## 決まり 1: 夜中や休みの日の、管理者のログイン

- **何を見るか**: 管理者のアカウントが、普段の時刻の外(例: 20 時から翌 8 時、土日)に入った。
- **どの記録か**: Linux は journald の sshd。Windows はセキュリティのイベントログ 4624(成功)と 4672(特別な権限)。
- **調べる命令**:

```bash
# Linux(確かめた): 20 時から 8 時の、aoki と suzuki の SSH の成功
journalctl _COMM=sshd --since -1d -o json --no-pager -q \
  | python3 -I skills/detection/scripts/off_hours.py --start 8 --end 20 --users aoki,suzuki --weekend
```

```powershell
# Windows(確かめた・文書): この 1 日の、特別な権限の付いたログオン
$since = (Get-Date).AddDays(-1)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4672; StartTime=$since } |
  Where-Object { $_.TimeCreated.Hour -lt 8 -or $_.TimeCreated.Hour -ge 20 }
```

- **最初にする事**: 本人に、記録とは別の道(電話、対面)で「入りましたか」と聞きます。本人でなければ、そのアカウントを止める手を出し(人が打つ)、`skills/incident-response/` に移ります。
- **値**: 時刻の幅は例です。

## 決まり 2: 国外からの VPN やクラウドへのログイン

- **何を見るか**: 普段は国内からしか入らない入口に、国外の番地から入った(成功も失敗も)。
- **どの記録か**: ルーターや VPN 機器の syslog の接続の記録。Microsoft 365 は Entra ID のサインインの記録と統合監査ログ。
- **調べる命令**: 番地から国を引くには、番地と国の対応表(GeoIP のデータベース)が要ります。どれを使うかは会社が選びます(確かめていません)。対応表が無い時は、普段の送り元(会社と社員の家の回線の事業者)の一覧を作り、それに無い番地を拾います。

```bash
# 記録のサーバーで、VPN の記録から送り元の番地を数える例(確かめていません。行の形は機種で違います)
grep -h 'VPN' /var/log/remote/router1/*.log | grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | sort | uniq -c | sort -rn | head
```

- **最初にする事**: その番地から入ったアカウントを確かめ、本人に別の道で聞きます。出張や旅行の予定は 03 の例外に書いておきます。
- **値**: どの国を「普段」とするかは会社が決めます。

## 決まり 3: 失敗が続いた後の成功

- **何を見るか**: 同じ送り元から、短い間に何度も失敗した後に、成功した(パスワードを当てられた疑い)。
- **どの記録か**: Linux は journald の sshd。Windows は 4625 の後の 4624。VPN 機器の記録。
- **調べる命令**:

```bash
# Linux(確かめた): 10 分の中に 5 回以上失敗した後の成功
journalctl _COMM=sshd --since -1d -o json --no-pager -q \
  | python3 -I skills/detection/scripts/fail_then_ok.py --fails 5 --minutes 10
```

```powershell
# Windows(確かめた・文書): この 1 日の失敗を、送り元の番地ごとに数える
$since = (Get-Date).AddDays(-1)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4625; StartTime=$since } |
  Group-Object { ([xml]$_.ToXml()).Event.EventData.Data | Where-Object Name -eq 'IpAddress' | ForEach-Object '#text' } -NoElement |
  Sort-Object Count -Descending
```

PowerShell の二つ目の書き方(XML から `IpAddress` を取り出す所)は、確かめていません。4625 の XML の欄の名(`IpAddress`、`TargetUserName`、`Status`)は learn.microsoft.com の 4625 の頁で確かめました。

- **最初にする事**: 成功したアカウントのパスワードを替える手を出し(人が打つ)、そのアカウントがその後にした事を記録で追います。SSH なら、パスワードで入れる形そのものを止めます(`skills/kagi/04-サーバーを見る.md` の「パスワードで入れる」)。
- **値**: 回数と分は例です。

## 決まり 4: 新しいアカウント、新しい管理者

- **何を見るか**: アカウントが作られた。管理者の組(Linux の `sudo`、Windows の Administrators、Domain Admins)に人が足された。
- **どの記録か**: Linux は journald の useradd、usermod、gpasswd。Windows は 4720(アカウントの作成)、4728・4732・4756(組への追加)。Microsoft 365 は統合監査ログの、ユーザーの追加と役の追加。
- **調べる命令**:

```bash
# Linux(確かめた): この 30 日のアカウントと組の変更
journalctl -t useradd -t groupadd -t usermod -t gpasswd --since -30d --no-pager -q

# Linux(確かめた): sudo の組の今の顔ぶれ(表の admins と比べる)
getent group sudo
```

```powershell
# Windows(確かめた・文書): この 7 日のアカウントの作成と組への追加
$since = (Get-Date).AddDays(-7)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4720,4728,4732,4756; StartTime=$since }
```

- **最初にする事**: 申請の記録(権限の申請の雛形があれば、その伝票)と突き合わせます。申請が無ければ、足した人に聞き、答えが無ければそのアカウントを止める手を出します。
- **値**: 無し。申請の無い追加は、一件でも鳴らします。

## 決まり 5: 表に無いポートが開いた

- **何を見るか**: ポートの表(kagi の `ports.toml`)に無いポートで、コンピューターが聞いている。
- **どの記録か**: `ss -ltnp` の出力。kagi の差。
- **調べる命令**:

```bash
# Linux(確かめた): 待ち受けているポートの一覧(プロセスの名は root でないと他人の物が見えない)
ss -ltnH

# kagi で表と比べる(skills/kagi/03-ポートを突き合わせる.md)
ss -ltnp > /tmp/db1-ss.txt
kagi check ports --host db1 --ss /tmp/db1-ss.txt
```

- **最初にする事**: そのポートのプロセスを確かめます。知っている物なら表に足し、知らない物なら止める手を出します(人が打つ)。
- **値**: 無し。

## 決まり 6: 表に無い鍵が足された

- **何を見るか**: コンピューターの `authorized_keys` に、鍵の表(kagi の `machines.toml`)に無い鍵が入った。
- **どの記録か**: kagi のサーバーのコピーの差。ファイルの変更の時刻。auditd を入れていれば、その記録。
- **調べる命令**:

```bash
# kagi で見る(skills/kagi/04-サーバーを見る.md)
kagi machine collect --host db1
kagi machine check --host db1      # 「表に無い鍵が … に入っている」が出る

# Linux(確かめた): 自分の authorized_keys が、この 1 日に変わったか
find ~/.ssh -name authorized_keys -newermt '1 day ago'
```

```
# auditd の決まりの例(確かめていません。root が要ります)
-w /root/.ssh/authorized_keys -p wa -k sshkeys
```

- **最初にする事**: 鍵の指紋を、鍵の表と在庫表で探します。誰の鍵か分からなければ、その行を消す手を出し(人が打つ)、いつ誰が足したかを記録で追います。
- **値**: 無し。

## 決まり 7: 控えが取れていない

- **何を見るか**: 控えの仕事が、決めた時刻に成功していない。
- **どの記録か**: 控えのサービスと timer の journald。控えのソフトの記録。kagi の `timers`。
- **調べる命令**:

```bash
# Linux(確かめた): timer の一覧(次に動く時と前に動いた時)
systemctl list-timers --all --no-pager

# Linux(確かめていません。backup.service という名の時): 前の 1 日の控えの記録
journalctl -u backup.service --since -1d --no-pager -q
```

kagi は、サーバーの表に `timers = ["backup"]` と書くと、止まった timer を「直す」に出します(`skills/kagi/04-サーバーを見る.md`)。

- **最初にする事**: 控えの記録の最後の行を読み、手で一度走らせる手を出します(人が打つ)。続けて落ちる時は、控えの置き場のディスクの残りと、控えの置き場に届く道を見ます。
- **値**: 何時間取れていなければ鳴らすかは会社が決めます(例: 26 時間)。

## 決まり 8: 記録が途切れた

- **何を見るか**: あるコンピューターから記録のサーバーに、決めた時間、記録が届いていない。記録を消した、監査を止めた。
- **どの記録か**: 記録のサーバーの受け取りの時刻。Windows は 1102(監査の記録が消された)と 4719(監査の方針が変えられた)。Microsoft の「Appendix L」は 4719 の重要度を「高」、1102 を「中〜高」としています。
- **調べる命令**:

```bash
# Linux(確かめた): このコンピューターの最後の記録の時刻
journalctl -n 1 -o short-iso --no-pager -q

# 記録のサーバーで、送り元ごとの最後の受け取りの時刻(確かめていません。形 A で /var/log/remote/<コンピューター>/ に置く時)
for d in /var/log/remote/*/; do printf '%s ' "$(basename "$d")"; ls -t "$d" | head -1 | xargs -I{} stat -c '%y' "$d{}"; done
```

```powershell
# Windows(確かめた・文書): 記録の消去と監査の方針の変更
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=1102,4719 } -MaxEvents 20
```

- **最初にする事**: そのコンピューターが動いているか、ネットワークが届くかを見ます。動いていて記録だけが止まっているなら、入られた疑いとして扱い、`skills/incident-response/` に移ります。
- **値**: 何分届かなければ鳴らすかは会社が決めます(例: 30 分)。夜は記録が少ないコンピューターもあるので、普段の量(03)を見て決めます。

## 決まり 9: 大きな外向きの転送

- **何を見るか**: 普段より大きな量が、外へ送られた。夜中に送られた。知らない宛先に送られた。
- **どの記録か**: ルーターの通信の記録や数え(機種による)。Windows は Sysmon の 3(ネットワークの接続。既定では切ってあります)。Microsoft 365 は統合監査ログのファイルのダウンロードと共有。
- **調べる命令**:

```bash
# Linux(確かめた): 今ある外向きの接続の数(宛先は root でないと全部は見えない)
ss -tnH state established | wc -l
```

量の数えは、ルーターや防火壁の機能に頼ります。nftables なら、宛先ごとの数え(counter)を規則に入れられます(確かめていません)。

- **最初にする事**: 送り元のコンピューターと、その時刻に入っていた人を確かめます。業務の送り出し(控えの外へのコピー、大きなファイルの納品)なら 03 の例外に書き足します。
- **値**: 量と時刻は会社が決めます(例: 一時間に 5 GB、夜中に 500 MB)。

## 決まり 10: 実行してよい物の一覧に無い物が動いた

- **何を見るか**: サーバーで、動いているべきサービスの表に無いサービスが動いている。社員の PC で、使ってよいソフトの一覧に無いプログラムが動いた。
- **どの記録か**: Linux は systemd の一覧(kagi の `services`)。Windows は 4688(プロセスの作成。監査の設定が要ります)か Sysmon の 1(親のプロセスと命令行つき)。
- **調べる命令**:

```bash
# Linux(確かめた): 動いているサービスの名の一覧
systemctl list-units --type=service --state=running --no-legend --plain | awk '{print $1}' | sort > running.txt
# 表(allowed.txt。一行に一つの名、並べ替え済み)に無い物
comm -23 running.txt allowed.txt
```

```powershell
# Windows(確かめた・文書): この 1 日に Sysmon が記録したプロセスの作成
$since = (Get-Date).AddDays(-1)
Get-WinEvent -FilterHashtable @{ LogName='Microsoft-Windows-Sysmon/Operational'; Id=1; StartTime=$since } -MaxEvents 500
```

`LogName` の `Microsoft-Windows-Sysmon/Operational` は、Sysmon の頁の置き場の名(`Applications and Services Logs/Microsoft/Windows/Sysmon/Operational`)から書いた物で、確かめていません。`Get-WinEvent -ListLog *Sysmon*` で名を確かめてから使います。

- **最初にする事**: そのプログラムの置き場、作った時、親のプロセス、誰の権限で動いたかを見ます。知らない物なら、その PC をネットワークから外す手を出し(人が打つ)、`skills/incident-response/` に移ります。
- **値**: 無し。一覧を作るのが仕事の本体です。最初は「見るだけ」で数週間記録し、一覧を育ててから鳴らします。

## 決まり 11: 新しいサービス、新しい予定されたタスク

- **何を見るか**: サービスや予定されたタスク(cron、systemd の timer、Windows のタスク スケジューラ)が新しく足された。入られた後に居座る手として使われます。
- **どの記録か**: Windows は 4697(サービスを入れようとした)と 4698(タスクが作られた)。Linux は timer の一覧と、`/etc/cron*` の変更。
- **調べる命令**:

```bash
# Linux(確かめた): timer の一覧を前の週のコピーと比べる
systemctl list-units --type=timer --all --no-legend --plain | awk '{print $1}' | sort > timers-今週.txt
diff timers-先週.txt timers-今週.txt
```

`systemctl list-timers` の最後の列は timer の名でなく、動かすサービスの名です。名の一覧は `list-units --type=timer` で取ります(確かめた)。cron の変更は `/etc/crontab`、`/etc/cron.d/`、各人の crontab を見ます(他人の crontab は root が要ります)。

```powershell
# Windows(確かめた・文書)
$since = (Get-Date).AddDays(-7)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4697,4698; StartTime=$since }
```

- **最初にする事**: 足した人と目的を確かめます。知らない物は、中身(動かす命令)を読み、止める手を出します(人が打つ)。
- **値**: 無し。

## 決まり 12: sudo の失敗と、権限の無い人の sudo

- **何を見るか**: sudo のパスワードの誤り、sudo を持たない人の sudo。
- **どの記録か**: journald の sudo。
- **調べる命令**:

```bash
# Linux(確かめた)
journalctl _COMM=sudo --since -7d --no-pager -q --grep 'incorrect password|NOT in sudoers|authentication failure'
```

- **最初にする事**: 本人に聞きます。打ち間違いなら記録に一行残して閉じます。持たない人が試していたら、そのアカウントの持ち主と目的を確かめます。
- **値**: 何回で鳴らすかは会社が決めます(例: 一日に 3 回)。

## 決まり 13: アカウントの締め出しと、居ないアカウントへの試し

- **何を見るか**: アカウントが締め出された。居ないアカウントの名で試された(名前の当て)。
- **どの記録か**: Windows は 4740(締め出し)と、4625 の状態 0xC0000064(居ないアカウント)。Linux は sshd の `Invalid user`。
- **調べる命令**:

```bash
# Linux(確かめた): この 1 日の、居ないアカウントでの試しの数
journalctl _COMM=sshd --since -1d --no-pager -q --grep 'Invalid user' | wc -l
```

```powershell
# Windows(確かめた・文書)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4740 } -MaxEvents 20
```

- **最初にする事**: 締め出されたアカウントの本人に聞きます。外部からのアクセス経路で居ないアカウントの試しが多ければ、そのアクセス経路を外から届かない形にする事(VPN の内側に入れる、送り元を絞る)を検討します。
- **値**: 会社が決めます(例: 居ないアカウントの試しが一日に 100 回)。

## 決まり 14: 時計がずれた

- **何を見るか**: コンピューターの時計が NTP と合っていない。時刻が手で変えられた。時計がずれると、記録の並びも期限の判断も崩れます。
- **どの記録か**: Linux は `timedatectl`。Windows は 4616(システムの時刻が変えられた)。
- **調べる命令**:

```bash
# Linux(確かめた): yes なら合っている
timedatectl show -p NTPSynchronized --value
```

```powershell
# Windows(確かめた・文書)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4616 } -MaxEvents 20
```

- **最初にする事**: NTP の出所に届くかを見ます。手で変えた記録があれば、誰がなぜ変えたかを聞きます。
- **値**: 何秒のずれで鳴らすかは会社が決めます。

## 決まり 15: メールの転送の規則が足された(Microsoft 365)

- **何を見るか**: メールボックスに、外のアドレスへ転送する規則や設定が足された。メールを使った詐欺で、入られた後によく使われます。
- **どの記録か**: Microsoft 365 の統合監査ログ(Exchange の操作)。
- **調べる命令**: `Search-UnifiedAuditLog` で、受信の規則の作成や、メールボックスの転送の設定の変更の操作を探します。操作の名(`New-InboxRule`、`Set-InboxRule`、`Set-Mailbox` など)は、Microsoft Purview の「監査の活動」の一覧で確かめてから使います(確かめていません)。
- **最初にする事**: 本人に聞き、知らない規則なら消す手を出します(人が打つ)。そのアカウントのパスワードとセッションを取り消し、同じ時期のサインインの記録を見ます。
- **値**: 無し。外への転送は、一件でも鳴らします。

## 決まりを Sigma の形で書く

決まりを、製品に依らない形で書いておくと、記録の置き場を変えても書き直しが少なく済みます。その形の一つが Sigma です(YAML のファイル。2026-11-11 に sigmahq.io の説明で確かめた)。

- 要る欄は `title`(何を見るか)、`logsource`(どの記録か。`product`、`service`、`category`)、`detection`(選ぶ条件と `condition`)です。
- よく使う欄に `id`(UUID のバージョン 4を勧めています)、`status`(`stable`、`test`、`experimental`、`deprecated`、`unsupported`)、`description`、`falsepositives`、`level`(`critical`、`high`、`medium`、`low`、`informational`)、`tags` があります。
- `detection` の中で、並べた値は「どれか」、並べた欄は「全部」の意味です。
- Windows のセキュリティのイベントログは `product: windows`、`service: security`、Linux の sshd は `product: linux`、`service: sshd` です。

決まり 4 を Sigma の形で書いた例です(この形を変換の道具に通して確かめてはいません):

```yaml
title: 管理者の組に人が足された
id: 00000000-0000-4000-8000-000000000000   # uuidgen などで作って入れ替える
status: experimental
description: ローカルの組か、グローバルの組か、ユニバーサルの組に人が足された。申請の記録と突き合わせる。
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID:
      - 4728
      - 4732
      - 4756
  condition: selection
falsepositives:
  - 申請のあった追加
level: high
```

Sigma の形を、自社の記録の置き場の問い合わせに直す道具もあります。どれを使うかは会社が選びます(確かめていません)。Sigma を使わない時は、上の五つの欄の表で十分です。

# 02 記録を集める

01 の一覧の「記録の名」と「記録の置き場」を埋める章です。決める事は四つです。どのコンピューターのどの記録を取るか、どこに集めるか、時刻をどう揃えるか、どれだけの期間残すか。

## 1. 集める先は、コンピューターの外に置く

入られたコンピューターの上の記録は、入った者に消されたり書き換えられたりします。記録は、出来た時にすぐ、別のコンピューターへ送ります。

- 送り先は、記録を受けるだけの一台(以下「記録のサーバー」)にします。業務のサーバーや社員の PC と兼ねません。
- 記録のサーバーに入れる人は、少なく(係の二人など)します。記録を送る側のコンピューターの管理者が、記録のサーバーでは管理者でない形にします。そうすると、一台の管理者の権限を取られても、記録は消されません。
- 記録のサーバーのディスクの残りを監視します(ディスクが一杯になると、新しい記録が入らなくなります)。
- 記録のサーバーそのものの控えを取ります。

小さな会社なら、記録のサーバーは小さな Linux のサーバー一台で足ります。クラウドの記録の置き場(SIEM と呼ばれるサービス)を使う時も、考え方は同じです。

## 2. どのコンピューターのどの記録か

### Linux(Debian 系)

| 記録 | 何が分かるか | 読む命令(このコンピューターで確かめた物) |
|---|---|---|
| journald | ほとんど全部。SSH のログイン、sudo、サービスの起動と停止、カーネルのメッセージ | `journalctl` |
| SSH のログイン | 成功(`Accepted`)、失敗(`Failed password`)、居ないアカウント(`Invalid user`) | `journalctl _COMM=sshd --since -1d --no-pager` |
| sudo | 誰が何を管理者で打ったか | `journalctl _COMM=sudo --since -1d --no-pager` |
| アカウントの変更 | アカウントや組を作った・変えた | `journalctl -t useradd -t groupadd -t usermod --since -30d --no-pager` |
| ログインの履歴 | 誰がいつ入ったか(wtmp) | `last -F -n 20` |
| 起動の履歴 | いつ再起動したか | `journalctl --list-boots --no-pager`、`who -b` |
| 失敗したサービス | 止まっている物 | `systemctl --failed --no-pager` |
| 時刻の同期 | NTP で合っているか | `timedatectl show -p NTPSynchronized` |

上の命令は、2026-11-11 に Debian 13(systemd 257)の机の PC で、sudo なしで打ち、形が通る事を確かめました。sudo なしでは自分の記録しか見えず、`adm` か `systemd-journal` の組に入っている人だけがすべてを読めます(journalctl がそう知らせます)。記録を読む係のアカウントをこの組に入れるかは、会社が決めます。

**Debian 13 では、標準で `/var/log/auth.log` がありません。** 記録は journald にだけ入ります(rsyslog が入っていないため。この机の PC でも rsyslog は入っていませんでした)。ガイドや記事に `auth.log` を読む例があったら、`journalctl` に読み替えます。

**auditd(Linux の監査)。** ファイルの読み書きや、特定の命令の実行を記録に残す仕組みです。入っていなければ記録は出ません。入れるかは会社が決めます。決まりの例(確かめていません。この机の PC に auditd は入っていませんでした):

```
# /etc/audit/rules.d/50-local.rules の例(確かめていません)
-w /etc/sudoers -p wa -k sudoers
-w /etc/sudoers.d/ -p wa -k sudoers
-w /etc/ssh/sshd_config -p wa -k sshd
-w /etc/passwd -p wa -k accounts
```

読む時は `ausearch -k sudoers` です(確かめていません。root が要ります)。

**nftables の記録。** 防火壁で落とした通信を記録に残すには、規則に `log` を足します。例(確かめていません。この机の PC に nft は入っていませんでした):

```
# 入る向きの既定の拒否の前に、落とす物を記録する例(確かめていません)
log prefix "nft-in-drop: " limit rate 10/minute
```

記録は journald にカーネルのメッセージとして入ります。落とした通信を全部記録すると量が多くなるので、`limit rate` で絞ります。値は例です。

### Windows

Windows のイベントログは、`Get-WinEvent` で読めます(2026-11-11 に learn.microsoft.com で確かめた書き方。Windows のコンピューターでは打っていません)。

```powershell
# この 1 日のログオンの失敗(4625)
$since = (Get-Date).AddDays(-1)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4625; StartTime=$since } -MaxEvents 200
```

セキュリティのイベントログで、まず見る ID(2026-11-11 に learn.microsoft.com の「Appendix L: Events to Monitor」と各イベントの頁で確かめた物):

| ID | 中身 | 見る所 |
|---|---|---|
| 4624 | ログオンに成功した | ログオンの種類(10 はリモートデスクトップ、3 はネットワークから)、送り元の番地 |
| 4625 | ログオンに失敗した | 状態の番号(0xC000006A はパスワードの誤り、0xC0000064 は居ないアカウント)、送り元の番地 |
| 4648 | 明示した資格情報でログオンを試みた | 別のアカウントの資格で動いた物 |
| 4672 | 新しいログオンに特別な権限が付いた | 管理者の権限でのログオン |
| 4688 | 新しいプロセスが作られた | 実行された物(記録には監査の設定が要ります) |
| 4697 | サービスを入れようとした | 新しいサービス |
| 4698 | 予定されたタスクが作られた | 新しいタスク |
| 4719 | システムの監査の方針が変えられた | 記録を止める操作(重要度「高」) |
| 4720 | ユーザーのアカウントが作られた | 新しいアカウント |
| 4724 | アカウントのパスワードの再設定を試みた | 他人のパスワードの再設定 |
| 4728 / 4732 / 4756 | 組(グローバル / ローカル / ユニバーサル)に人が足された | 管理者の組への追加 |
| 4740 | アカウントが締め出された | 失敗の続き |
| 1102 | 監査の記録が消された | 記録を消す操作(重要度「中〜高」) |

Microsoft の頁は、Windows の既定の記録はバージョンによって違い、多くの監査の設定が「構成されていません」のままなので、要るイベントが出るように監査の方針を整えるよう勧めています。どの ID が出ているかは、自社のコンピューターで確かめます。

**PowerShell の記録。** スクリプトブロックの記録(Script Block Logging)を入れると、PowerShell が処理した中身が記録に残ります(2026-11-11 に learn.microsoft.com の about_Logging_Windows で確かめた物)。

- PowerShell 7 では `PowerShellCore/Operational` に、ID 4104 で入ります。Windows PowerShell 5.1 では `Microsoft-Windows-PowerShell/Operational` に入ります(5.1 の置き場は、同じ頁の復号の例に出てくる名から書いた物で、5.1 の頁では確かめていません)。
- 入れ方はグループ ポリシー(管理用テンプレートの PowerShell Core の「Turn on PowerShell Script Block Logging」)か、レジストリです。
- Microsoft の頁は、スクリプトの中のパスワードなどが記録に入る事があるので、診断以外で使う時は保護されたイベントの記録(Protected Event Logging)も入れるよう勧めています。秘密鍵は記録を出すコンピューターに置かず、記録を集める側に置きます。

**Sysmon。** Microsoft の Sysinternals の道具で、プロセスの作成(ID 1、親のプロセスと命令行つき)、ネットワークの接続(ID 3。既定では切ってあります)、ファイルの作成(ID 11)、レジストリの値の設定(ID 13)、DNS の問い合わせ(ID 22)などを、`Applications and Services Logs/Microsoft/Windows/Sysmon/Operational` に記録します(2026-11-11 に learn.microsoft.com で確かめた物)。入れる命令は `sysmon -accepteula -i 設定.xml` です。どの出来事を残すかは設定のファイルで絞ります。全部を残すと量が多くなります。入れるか、何を残すかは会社が決めます。

**Windows の記録を集める。** Windows には、記録を一台に集める仕組み(Windows Event Forwarding)があります。Linux の記録のサーバーに集める時は、記録を送るソフト(エージェント)を入れます。どれを使うかは会社が選びます(このガイドでは確かめていません)。

### ルーター、VPN 機器、NAS

多くの機器は、記録を syslog で別のコンピューターへ送る設定を持っています。機器の管理画面の「syslog」「ログの送信」の欄に、記録のサーバーの番地を入れます。設定の仕方は機種ごとに違うので、機種の説明書を見ます(このガイドでは確かめていません)。見る物は、VPN のログインの成功と失敗、管理画面へのログイン、設定の変更、ファームウェアの更新です。

業者が機器を管理している時は、記録を送る設定と、記録をこちらに渡してもらう事を、業者に頼みます。頼んだ日と答えを一覧に書きます。

### Microsoft 365 などのクラウド

クラウドの記録は、クラウドの中にあります(2026-11-11 に learn.microsoft.com の「Search the audit log」で確かめた物)。

- Microsoft 365 の監査の記録(統合監査ログ)は、企業向けの契約では既定で入っています。入っているかは、Exchange Online PowerShell で `Get-AdminAuditLogConfig | Format-List UnifiedAuditLogIngestionEnabled` と打ち、`True` かで確かめます。
- 検索は Microsoft Purview の画面の「監査」か、Exchange Online PowerShell の `Search-UnifiedAuditLog` です。読むには「Audit Logs」か「View-Only Audit Logs」の役が要ります。
- 残る期間は、E5 の利用者の Entra ID、Exchange、SharePoint の記録が既定で 1 年、それ以外の利用者が 180 日です。それより長く残すなら、自社の記録のサーバーへコピーします。コピーする道として、Microsoft は Office 365 Management Activity API を挙げています。
- 記録が検索に出るまで、主なサービスで 60〜90 分ほどかかる事があります。すぐ鳴らす決まりには向きません。

Google Workspace、AWS など、ほかのクラウドにも監査の記録があります。どこにあり、何日残るかを、使っているクラウドの説明で確かめて一覧に書きます(このガイドでは確かめていません)。

## 3. 小さな会社で回る形

一台の記録のサーバー(Debian)に、全部を集める形の例です。どちらの例も、この机の PC では確かめていません(rsyslog も systemd-journal-remote も入っていませんでした)。設定の形は、各ソフトの公式の説明で確かめました(`sources.md`)。

### 形 A: rsyslog で送る

送る側(各 Linux のコンピューター)に rsyslog を入れ、journald の記録を記録のサーバーへ TCP で送ります。

```
# 送る側: /etc/rsyslog.d/90-forward.conf の例(確かめていません)
action(
  type="omfwd"
  target="log1.example.internal"
  port="514"
  protocol="tcp"
  queue.type="linkedList"
)
```

`queue.type="linkedList"` は、記録のサーバーが止まっていても送る側が止まらないようにする設定です(rsyslog の説明による)。

```
# 受ける側(記録のサーバー): /etc/rsyslog.d/10-receive.conf の例(確かめていません)
module(load="imtcp")
input(type="imtcp" port="514")
```

ルーターや VPN 機器の syslog も、同じポートで受けます。受けるポートは、記録を送るコンピューターの番地からだけ届くように、防火壁で絞ります。この形は通信が暗号化されません。社内のネットワークの外を通る時は、TLS か VPN の中を通します。

### 形 B: systemd-journal-upload で送る

Linux のコンピューターだけなら、journald の記録を journald の形のまま送れます(`systemd-journal-remote` のパッケージ)。

```
# 送る側: /etc/systemd/journal-upload.conf の例(確かめていません)
[Upload]
URL=https://log1.example.internal:19532
ServerKeyFile=/etc/ssl/private/journal-upload.pem
ServerCertificateFile=/etc/ssl/certs/journal-upload.pem
TrustedCertificateFile=/etc/ssl/certs/journal-ca.pem
```

受ける側の `systemd-journal-remote` は、既定でポート 19532 で受け、`/var/log/journal/remote/` に置きます(Debian の man の頁による)。証明書を作って配る手間があります。証明書の秘密鍵は kagi の在庫表に一件ずつ書きます(値は書きません)。

### どちらを選ぶか

Windows やルーターの記録も一か所に集めるなら、形 A が合います。Linux のコンピューターだけで、journald の形のまま読みたいなら、形 B が合います。選ぶのは会社です。選んだ形と理由を一覧に書きます。

## 4. 時刻を揃える

記録を並べて読むには、すべてのコンピューターの時計が合っている事が要ります。

- すべてのコンピューターを、同じ NTP の出所に合わせます(社内の一台か、決めた外の出所)。
- 合っているかを確かめます。Linux は `timedatectl show -p NTPSynchronized`(確かめた。`NTPSynchronized=yes` が出ます)。kagi の `machine check` も時計を見ます。
- 記録の時刻の書き方を揃えます。Sysmon は UTC で書き、Microsoft 365 の監査の記録の画面も UTC です。日本時間と UTC が混ざると、夜中の決まりが 9 時間ずれます。読む時にどちらかに直します。

## 5. 保存の期間は誰が決めるか

どれだけの期間、記録を残すかは会社が決めます。決める時の材料は次の通りです。

- 入られてから気づくまでに、時間がかかる事があります。短すぎると、気づいた時に始まりの記録が残っていません。
- 法令、業界の決まり、取引先との契約で、期間が決まっている事があります。
- 記録には社員の行動が入ります。長く残すほど、個人の情報を持つ期間も長くなります。
- ディスクの大きさと費用。

例として、「記録のサーバーに 1 年、そのうち直近 90 日はすぐ検索できる形」のように書きます。値は例です。決めた人と日付を一覧に書きます。

journald の量は `journalctl --disk-usage` で見られます(確かめた)。

## 6. 記録を AI に渡す前に伏せる

記録には、人の名前、アカウントの名、番地、メールアドレス、時には鍵やトークンが入ります。そのまま AI に渡しません。

Cyber Verification Program では、制度に入った者のデータの保持が必須です(`sources.md`)。会話に入れた記録は、相手の側に残るものとして扱います。

渡し方の順:

1. **数えて渡す。** 多くの問いは、行の中身でなく数で足ります(「この 7 日の SSH の失敗の数を日ごとに」)。数える命令を人が打ち、数だけを渡します。
2. **要る行だけを取り出す。** 時刻と種類と送り元くらいに絞ります。
3. **伏せる。** `scripts/mask.py` を通します。

```bash
# names.txt に、伏せる名前(人、アカウント、コンピューター)を一行ずつ書く
journalctl _COMM=sshd --since -1d --no-pager -q \
  | python3 -I skills/detection/scripts/mask.py --names names.txt --table 対応表.tsv \
  > 伏せた記録.txt
```

- IPv4 と IPv6 の番地、メールアドレス、names.txt の名前を、同じ物には同じ印(`IP-1`、`MAIL-1`、`NAME-1`)に置き換えます。同じ番地は同じ印になるので、「同じ所から何度も」は伏せた後でも読めます。
- 32 字以上の英数字の並び(鍵やトークンらしい物)は `KEY` に置き換えます。
- `--table` の対応表は手元だけに置き、AI に渡しません。AI の答えに `IP-1` と出たら、人が対応表で元に戻します。
- 伏せ方は完全ではありません。names.txt に無い名前、本文の中の住所や電話番号は残ります。渡す前に、伏せた物を人が目で読みます。

この道具は、2026-11-11 に架空の記録(架空の名前、例示用の番地 203.0.113.0/24 と 2001:db8::/32、架空のメールアドレス)で、名前、番地、メールアドレス、長い文字列が伏せられ、時刻(12:34:56)が番地と取り違えられない事を確かめました。

業者に預けた鍵と権限

一つの業者が破られると、多くの顧客に届く。2025年から2026年の五つの件と、扉への当てはめ

2026.10.18

2026年10月の一週間に、業者に預けた鍵や権限から多くの顧客に被害が及ぶ件が、続けて公表されました。2025年にも同じ形の件があります。この記事では五つの件を同じ項目で並べ、共通する形を取り出し、扉の鍵に当てはめます。調べたのは2026年10月18日です。会社と団体が発表したことと、報道や分析で伝えられたことは分けて書きます。どの件も、調べた時点で調査が続いています。

見方

件を二つの型に分けます。

  • 預かり型。 業者が、多くの顧客の鍵や権限を預かって常に持っている形です。顧客は、連携の手間を省くために、業者のサービスに自分の環境へ入る権限や、他社のサービスの鍵を渡しています。
  • 相乗り型。 他人と同じ機械の上で、自分の仕組みを動かしている形です。クラウド、VPS、レンタルサーバーが当たります。

それぞれの件について、預けていた物、起きたこと、顧客の側で防げたか、業者がどう止めたかを見ます。

一覧

件(時期) 型と、預けていた物 起きたこと
ConnectWise Cloud Backup(2026年10月) 預かり型。Microsoft 365 のメール、OneDrive、SharePoint、Teams を読み書きできる、バックアップのアプリの権限 業者の側にあるアプリの認証情報で、多くの顧客のテナントにサインインされた
OpenCode Console(2026年10月) 預かり型。利用者が保存した、AI の事業者(OpenAI、Anthropic、Google など)の鍵 廃止の途中の古い仕組みへの不正なアクセスで、保存された鍵が漏れたおそれ
CVE-2026-99999、PwnEscape(2026年10月) 相乗り型。同じ機械の上の仮想マシン 仮想マシンから、その機械(ホスト)のメモリを読み書きできる不具合
Commvault Metallic(2025年5月) 預かり型。Microsoft 365 のバックアップのアプリの秘密情報 顧客の環境に入るための秘密情報が盗まれた
Salesloft Drift(2025年8月) 預かり型。Salesforce につなぐ連携のトークン 多くの会社の Salesforce のデータが持ち出された

件ごとに見る

ConnectWise Cloud Backup(旧 SkyKick)

発表。 ConnectWise は、Cloud Backup の環境で「アプリケーションの ID への不正なアクセス」を見つけたと発表しました。対策として、提携先と顧客の Cloud Backup のアプリのアクセスを止め、バックアップのサービスは再開の見通しが示されないまま止まりました(2026年10月17日。BleepingComputer の報道による)。バックアップのデータが見られた兆しは無いとしています。原因は公表していません。Microsoft は、活動中のサプライチェーン攻撃と判断しました。

分析。 セキュリティ会社の Huntress の分析(2026年10月16日公開、17日更新)では、盗まれたのはバックアップのアプリの認証情報で、業者のテナントの中にありました。顧客の環境の中で何をしても防げない物です。不正なサインインは10月16日の時点で162のテナントで確かめられ、17日の更新では、約1,000のテナントで試みがあり、300を超えて成功しています。一つのテナントでは、別の ConnectWise のアプリが自分に全体管理者の権限を与え、他のアプリに秘密の鍵を足していました。データが持ち出されたかは確定していません。

OpenCode Console

発表。 AI のコーディングの道具を提供する OpenCode は、2026年10月17日に自社の X のアカウントで、前夜にセキュリティの侵害があったと公表しました。大規模な蒸留攻撃に関連し、コンソールの利用者の1.4%に影響があり、メールを受け取っていない人は影響を受けていない、としています。Anthropic、OpenAI、Google と協力して対応していて、調査が続いているため詳細は出せないとしています。

利用者へのメール(報道による)。 廃止の途中だった古い仕組みへの不正なアクセスを見つけ、作業場所に保存された外部の事業者の鍵(OpenAI、Anthropic など)が漏れたおそれがあるとして、鍵を取り消して作り直すよう求めています(OfficeChai、DEV Community、2026年10月17日〜18日)。

報道。 利用者が、身に覚えの無い利用の請求を受けたという声が伝えられています(Crypto Briefing、2026年10月17日)。金額は利用者の報告で、確かめられていません。蒸留攻撃は、一般に、他人のモデルを大量に呼び出し、その答えで別のモデルを育てる使い方を指します。盗んだ鍵がそう使われたのかを、OpenCode は説明していません。鍵がどう保存されていたかも公表されていません。

CVE-2026-99999(PwnEscape)

発表。 Linux カーネルの IPv4 の処理の不具合で、CVE の記録は2026年10月15日に公開されました。Red Hat と Linux のカーネルの CVE チームは Critical としています。

研究者の説明。 仮想マシンが細工したパケットを送ると、ホストのカーネルのメモリを読み、書き換えられます。研究者は、自分の KVM の実験環境で、ホストの root での実行まで示しました。各社の本番の環境で root を取ったとは主張していません。

告知。 AlmaLinux の告知(2026年10月16日)は、最も危ないのは他人の仮想マシンを動かす機械、つまりクラウド、VPS の事業者、コードを動かすサンドボックスだとしています。Vercel が本番のサンドボックスでメモリの漏れを示し、他の事業者に知らせたとも書いています。回避の手段は無く、直したカーネルに替えるしかありません。ホストの再起動は、その上の全部の仮想マシンを止めます。

Commvault Metallic

発表。 米国の CISA は2025年5月22日に、Commvault の Microsoft 365 のバックアップのサービス(Metallic、Azure の上で動く)の秘密情報が盗まれたおそれがあると警告しました。既定の設定と強い権限を持つ SaaS を狙う、より広い攻撃の一部と見ています。Commvault は、影響を受けたのは少数の顧客で、バックアップのデータは見られておらず、該当の顧客の秘密情報を作り直したとしています(The Record、2025年5月23日)。

Salesloft Drift

分析。 Google の脅威情報の部門と Mandiant は、2025年8月8日から18日に、Salesloft のチャットの道具 Drift が Salesforce につなぐためのトークンが盗まれ、多くの会社の Salesforce からデータが持ち出されたと公表しました。攻撃者は、データの中から AWS の鍵やパスワードなどの秘密を探していました。Salesloft は8月20日に、Drift と Salesforce の連携を全部切りました(Security Affairs、2025年8月28日)。

共通する形

  1. 預けた物が一か所に集まる。 一社が、多くの顧客の環境に入る権限や、他社の鍵をまとめて持っています。そこを一度破れば、全部の顧客に届きます。
  2. 顧客の側では防げない。 ConnectWise の認証情報は業者のテナントにあり、OpenCode の鍵は業者のサービスに保存され、PwnEscape を直せるのは機械を持つ事業者です。顧客にできるのは、知らされた後の対応だけです。
  3. 止める手段が大きい。 業者はサービスごと止める(ConnectWise のバックアップの停止)か、全員に鍵の作り直しを頼みます(OpenCode、Commvault)。相乗り型では、直すための再起動で全部の仮想マシンが止まります。
  4. 預けた権限は、用途より広い。 バックアップのためにメールの全部を読む権限を、連携のために顧客の記録を読むトークンを、便利さのために請求の起きる鍵を、業者に渡しています。

扉に当てはめると

  • クラウド型のスマートロックは、預かり型そのもの。 業者のクラウドが、全部の顧客の扉に鍵を出し、遠隔で開ける権限を常に持っています(日本のスマートロックのアプリの現状と課題)。業者が破られると、メールや請求ではなく、多くの建物の扉が開きえます。業者が被害を止めるためにサービスを止めれば、アプリで開ける扉が全部止まります。
  • 判定が扉の中で完結しても、発行者の鍵が一か所に集まれば同じ。 Aliro のように、スマートフォンと読取機だけで判定する方式でも、鍵を作る発行者の秘密鍵を一つの業者が全顧客の分まとめて持てば、その鍵一つで全部の扉の鍵が作れます。
  • 鍵の台帳を共有の機械に置くと、相乗り型の危険を負う。 発行者の秘密鍵や鍵の台帳を VPS やレンタルサーバーに置くと、隣の仮想マシンから抜かれうる不具合の影響を受けます。
  • 分譲マンションでは、住戸の錠の鍵を出すのは区分所有者。 法律上の持ち主と、鍵を出す実際の力を持つ業者がずれると、預かり型の危険が住戸にまで及びます。

このサイトの要求仕様

この形を避けるため、要求仕様に次を書いています(2026年10月18日に追加)。

番号 要求 対応する形
R-AC-09 一つの発行者の鍵が届く扉は、その発行者が管理する扉に限る。業者が多くの顧客の発行を引き受けても、顧客ごとに別の鍵にする 一か所に集まる
R-AC-10 業者と連携先に、扉を開ける常の権限を持たせない。遠隔の解錠は一回ごとに、発行者の一時の資格情報を錠が自分で確かめる。業者のサービスが止まっても、登録済みの資格情報で開く 一か所に集まる、止める手段が大きい
R-AC-11 発行者の秘密鍵は取り出せない場所に置き、他人と同じ機械を共有する環境に置かない 相乗り型
R-AC-12 錠と読取機が信頼する発行者の変更は、管理者の認証済みの操作だけで行い、記録に残す 顧客の側で防げない
R-AP-38、R-AP-39 住戸の錠の発行者は区分所有者とし、管理会社と管理組合の発行者の鍵では住戸の錠を開けられない 一か所に集まる

扉のコントローラの側では、発行者が署名した資格情報を、扉が網も発行者のサーバーも使わずに自分で確かめる形を、扉コントローラ仕様書 の 5.2a に書きました。仕様を確かめる疑似の扉(digitaldoor-controller)で、この形の試験が通っています。

使う人ができること

  • 業者に預けている鍵と権限を一覧にします。どの業者に、何への、どれだけの権限を渡しているかです。
  • 渡す権限を用途に要る分だけにし、期限を付けられる物は付けます。
  • 業者が止まったとき、止めたときにも使える手段を手元に残します。扉なら、錠に登録した暗証番号、カード、物理鍵です。
  • 預けた鍵を作り直す手順を、事前に決めておきます。
  • 秘密鍵を、他人と共有する機械に置きません。

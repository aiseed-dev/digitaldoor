サイバー攻撃に耐える扉

入られる前提で、口を減らし、本物かを確かめ、気づいて外に知らせ、切り離して戻す

2026.10.20

扉が攻撃されると、二つの壊れ方が起こりえます。開いてはいけないときに開くことと、開くべきときに開かないことです。前者は侵入を許し、後者は火災のときの避難を妨げます。電子錠やスマートドアは、網につながった時点で、この二つを攻撃者に握られる危険を抱えます。デジタルドアを実現するには、サイバー攻撃に耐えられることが前提になります。

見方

攻撃を全部防ぐことはできません。入られる前提で、次の順に重ねます。

  1. 入る口を減らす。 外に開く口、実行できる物、使う部品を少なくします。
  2. 中で動く物が本物かを確かめる。 更新のときと起動のたびに、署名で確かめます。
  3. 入られたら気づく。 実行してよい物を決めておき、増えた物と変わった物を見つけます。
  4. 知らせを機械の外に出す。 入られた機械の上の記録は消されるので、別の機械へ送ります。
  5. 切り離して戻す。 現場で線を抜き、予備に入れ替え、元に戻します。
  6. 何があっても、扉の安全側の挙動は保つ。 火災と停電のときの設定、内側からの機械の解錠は、判断の側が乗っ取られても止まっても保たれる所に置きます。

このサイトの要求仕様には、これまでに次の備えを書いてきました。

足りなかったのは、扉の中で動く物が本物かを確かめること、実行する物を見張ること、知らせを外に出すことです。2026年10月20日に、これを要求に足しました。

更新と起動を確かめる

扉の中の物が差し替えられれば、判断も記録も攻撃者の物になります。これまでの要求は、更新について「通信モジュール経由で可能であることが望ましい」(R-EL-06)としか書いていませんでした。

  • 更新は署名つきで配り、扉が確かめてから入れる(R-EL-25)。 確かめられない更新は入れず、今の版で動き続けます。署名を確かめずに入れる更新は、それ自体が攻撃の入口になります。
  • 起動のたびに確かめる(R-EL-26)。 書き換えられない起動の仕組み(ROM の起動コードかセキュアエレメント)で、ファームウェアが署名どおりかを確かめます。確かめられないときは、その系統を止め、安全側のマイコンが安全側の挙動を保ちます。
  • 古い版に戻させない(R-EL-27)。 脆弱性を直した版より古い版に戻されると、直した脆弱性が戻ります。版の下限を、書き換えられない所に持ちます。
  • 結果を記録に残す(R-EL-28)。

ETSI EN 303 645 は、網から届く更新の真正性と完全性を機器が確かめることを必須にしています(5.3-10)。EU のサイバーレジリエンス法も、プログラムと設定を許されない書き換えから守り、壊れたことを知らせるよう求めています(附属書 I)。NIST SP 800-193 は、ファームウェアの守り、検出、復旧を三つの柱にしています。

実行する物を決めて見張る

入った攻撃者は、何かを実行しないと何もできません。道具を持ち込んで動かすか、すでにある言語や命令を使います。

  • 実行してよい物の一覧を持ち、毎日照らす(R-RS-11)。 ゲートウェイ、ミニサーバー、OS を持つ扉のコントローラごとに、実行してよい物を、置き場と sha256 とパッケージの記録で一覧にします。一覧に無い物が増えたら、それが知らせになります。書き込める場所(一時ファイルの置き場など)では実行させません。
  • 実行の途中で機械語を作らない(R-RS-15)。 JIT は、動きながら機械語を作り、書き込めて実行もできるメモリに置きます。その機械語はファイルとして存在しないので、一覧と照らせません。JIT は脆弱性の大きな出どころでもあり、Microsoft の Edge の調査(2021年)は、2019年以降の V8(Chrome と Edge の JavaScript の実行の仕組み)の CVE のおよそ 45% が JIT に関わると書いています。

一覧を短く保つには、機械の役目を小さくし、置く物を減らします。運用する機械には、開発用の言語もコンパイラも置かず、組むのは手元で行います。出来上がる物は一つのバイナリにすると、照らす値が一つで済みます。

知らせを機械の外へ出す

入られた機械の上の記録と知らせは、攻撃者に消されます。改ざんの検査と見張りの知らせ、監査の記録は、その機械の外(別の機械か担当の人)へ、追記だけの形で送ります(R-RS-12)。扉のコントローラの記録を、署名つきの伝票にして外の箱へ出す(R-CT-17)のと同じ考え方です。

EU のサイバーレジリエンス法は、中の動きを記録して見張り、許されない立ち入りの疑いを知らせることを求めています(附属書 I)。

メモリを壊す欠陥を減らす

C や C++ で書いた物の脆弱性は、多くがメモリの扱いの誤りから生まれます。Google は、Android の脆弱性に占めるメモリの扱いの誤りが、2019年の 76% から 2024年の 24% に下がったと書いています。新しく書く部分を、メモリを安全に扱える言語に移していった結果です。米国の CISA と FBI は、新しい製品群をメモリを安全に扱える言語で作り、既存の製品にはその計画を公表するよう求めています。

要求仕様は、どの言語で書くかは決めません。製造者に、扉のコントローラと通信の部分について、メモリを壊す欠陥を減らす計画を公開することを求めます(R-RS-13)。新しく書く部分は、メモリを安全に扱える言語で書くか、同じ効き目の対策を示します。扉のコントローラを Rust で書く道筋は、扉のコントローラを Rust で書くに書きました。

同じソースから同じ物を組む

扉に入っている物が本物かを確かめるには、公開されたソースと手順から、同じ物を組み直せる必要があります。同じソース、同じ組む環境、同じ手順から、誰が組んでもビット単位で同じ物ができることを、再現可能なビルドと言います。

製造者は、出荷する物ごとに部品表(SBOM)を持ち、同じ物を組めるようにします(R-RS-14)。手元で組み直した値と、扉に入っている物の値を照らせば、本物かどうかが分かります。EU のサイバーレジリエンス法も、少なくとも直接の依存を含む部品表を作ることを求めています(附属書 I 第 II 部)。

0. この文書について

この文書は、会社の情報システムを守る人が、Claude を使って自社のシステムの穴を探し、確かめ、直すところまでを、一人で始めて進めるための手順です。相談に来なくても進められる詳しさで書きます。

  • 読む人。 会社の情報システム部門の人、情報システムを兼ねている総務や経理の人、業者から納められたシステムを受け入れる人。
  • 確かめた日。 Anthropic の制度(Cyber Verification Program)のサポートの頁は、2026年11月11日に取った原文と照らしました。料金の頁と、API の認証の文書も、同じ日に読みました。頁は更新されるので、申し込む前に原文をもう一度読んでください。頁は英語です。この文書では、頁の語を括弧に添えます。
  • 原文に無い事。 頁に書いてない事は「頁に書いてありません」と書きます。推測では埋めません。
  • 扱わない事。 動いているシステムへの侵入の試験と、マルウェアの解析の手順は扱いません。侵入の試験は、別の枠(Red Team Access)の仕事です(11 章)。
  • 値の決め方。 何回、何日ごと、誰が、といった値は、この文書では決めません。誰が決めるか、何の事実で決まるかを書きます。会社の大きさと、持っているシステムで決まるからです。

考え方の背景は、解説「AI で自社のシステムを確かめる」にあります。AI に読ませる手引きは skills/system-check です。出典は末尾にまとめています。

最初に知っておくこと

コードを読む確かめは、今日から始められます。 サポートの頁の頭に、日々の安全な開発には、この制度は要らないと書いてあります。ふつうに使える AI で、コードを見直す(review code)、知られた問題を直す(patch known issues)、警告を仕分ける(triage security alerts)ことができます。

制度が要るのは、守りの仕事を Claude が止める時です。頁は例として、穴が本当に使えるかを確かめる(validating exploits)ことと、許しを得た侵入の試験(running authorized penetration tests)を挙げています。

ですから、進め方は次の二本を並べて走らせる形になります。

  1. 今日から、自社のコードを読む確かめを始める(4 章を待たずに、6 章と 8 章へ進めます)。
  2. 同時に、Defense Access の申し込みを用意する(2 章から 5 章)。返事が来たら、見つけた穴を確かめる所まで進めます。

1. できる事と、枠の外の事

三つの枠

2026年10月6日の更新で、制度は三つの枠(access tiers)になりました。どの枠でも、Claude Mythos、Opus、Sonnet のモデルが使えます(頁の書き方では、Claude Mythos 5.2、Claude Mythos 5.1、Claude Opus 5.5、Claude Sonnet 5.5 から)。枠に応じて、サイバーの安全装置(cyber safeguards)の働き方が変わります。利用の方針(Usage Policy)は、どの枠でもそのまま当たります。

Defense Access Red Team Access Specialized Access
できる事 セキュリティの運用(security operations)、事故の対応(incident response)、マルウェアの解析(malware analysis)、検知の仕組みづくり(detection engineering)、穴の仕分けと確かめ(vulnerability triage and validation) 許しを得た侵入の試験、レッドチーム、攻撃者の模倣、攻める道具の開発、exploit の開発 重要なインフラへの許しを得た侵入の試験とレッドチーム、最も重い手法の研究
誰のための物か セキュリティの仕事を日常的にする部署と社員、重要なインフラの運用者、オープンソースの保守者、バグ報奨金の参加者、個人の研究者 侵入の試験の会社と、攻めを主な仕事とする社内のレッドチーム 飛行の制御、電力網、銀行間の送金の基盤のような重要なシステムを試験する組織
申し込める者 組織と個人 組織だけ 組織だけ
契約 Pro、Max、Ultra、Team、Enterprise、API Team、Enterprise、API Team、Enterprise、API
承認される人数 既定の上限は無い。個人の承認は本人だけ 75 人まで 25 人まで
返事の目安 2 日 2 週間(申し込みが多く、今は延びている) 決まっていない(米国政府と一緒に深く審査する)

この文書で扱うのは Defense Access です。自社のコードを読んで穴を探し、見つけた穴を仕分け、確かめ、検知の仕組みを作り、事が起きた時に対応する仕事は、この枠に入ります。

頁は、重要なインフラの運用者の多くには Defense Access が合う、と書いています。重要なインフラを運用しているだけでは、Specialized Access の対象にはなりません。

どの枠でも禁じられている事

頁は、どの枠でも禁じている事として、次を挙げています(「次を含む」と書いてあり、これで全部とは書いてありません)。

  • データや機器を大量に壊すこと
  • サービスを止める攻撃(DoS)
  • 物理的な世界に害を与えること
  • ゆすり
  • 選挙への介入
  • 悪い意図を述べた依頼

枠の中でも止められる事がある

頁には、認められた仕事でも、モデルが断ったり、分類の仕組みが止めたりする事がある、と書いてあります。誤って止める事を減らす作業を続けている、という書き方です。止められた時は、言い換えて押し通さずに、止まった事を記録に書いておきます(9 章)。

制度が変えるのはサイバーの安全装置だけです。ほかの分野(頁の例は生物の研究)の安全装置は、どの枠でもそのまま働きます。

申し込みが要らない仕事

0 章に書いた通り、コードの見直し、知られた問題の修正、警告の仕分けには申し込みは要りません。この文書の 6 章(渡す物を用意する)、7 章(社内の許しと業者への知らせ)、8 章(最初の一つを読む)は、申し込みの前から始められます。

2. 申し込む前に決める事

申し込みは、出した後に直したり取り消したりできません(4 章)。申し込む前に、次を決めます。決めるのは、会社の情報システムの責任者と、Claude の契約の持ち主(Owner)です。

組織として出すか、個人として出すか

  • 組織(business)。 会社、非営利の団体、大学、政府の部署などのために出します。会社の仕事として自社のシステムを確かめるなら、こちらです。
  • 個人(individual)。 自分のために出します。頁の例は、独立の研究者、オープンソースの保守者、バグ報奨金の参加者です。個人が出せるのは Defense Access だけです。

頁は、どちらで確かめを受けるかが申し込みの扱いに響くので、よく選ぶように書いています。後で上の枠(Red Team Access)へ進むのは、組織として出した場合だけです(FAQ)。

どの契約で使うか

制度は、有料の契約で使えます。無料の契約(Free)では使えません。どこで Claude を使っているかで、使える枠と、入れ方が変わります。

どこで使うか 使える枠 頁に書いてある事
Pro、Max、Ultra Defense Access 個人のための物。承認されると自動で有効になる
Team 全部 組織の全員に効く。Red Team Access は 75 席、Specialized Access は 25 席までの組織に限られる。人ごとに分けられない
Enterprise 全部 管理者が、役(custom role)ごとに割り当てる
Claude Console(API) 全部 管理者が、作業の場(workspace)ごとに割り当てる。既定の作業の場(Default workspace)には割り当てられない
Claude Platform on AWS、Claude Platform on Google Cloud、Google Cloud Agent Platform 全部 申し込む前に、クラウドのアカウントか project をつなぐ
Microsoft Foundry 全部 Claude のモデルを置いてから、契約(subscription)をつなぐ
Amazon Bedrock 全部 Enterprise Frontier Safeguards(EFS)が要る。今は、データの保持の例外を持つ組織だけ
Claude を使ったほかの会社の製品 Defense Access と Red Team Access その製品の会社に、つなぎ方を聞く

どれを選ぶかは、次の事実で決まります。

  • 今、社員がどこで Claude を使っているか。 承認は、出した組織にだけ効きます。
  • 確かめに使う人を絞りたいか。 Team は全員に効きます。人を絞るなら、Enterprise の役か、Console の作業の場で分けます。
  • 同じ組織で客の仕事をしているか。 次の項を見てください。

使い道は社内の物に限る

頁は、既定では社内の使い道(internal use)だけを認める、と書いています。

  • 社内の使い道。 自分の組織のコード、製品、基盤のセキュリティの仕事です。客のためではなく自分で行うバグ報奨金の調査と、決まりに沿った穴の届け出(coordinated disclosure)も入ります。どの枠もこれを含みます。
  • 社外の使い道(external use)。 客のための仕事、客が使う製品のための仕事です。社内の使い道で承認された後に、別の申し込みが要ります。承認なしに客へ出すと、規約に反し、制度から外される理由になる、と書いてあります。

ここから、次の事が言えます。

  • 客や他社のシステムを確かめる仕事は、この文書の範囲の外です。 業者から納められたシステムでも、自社が持ち主で、自社のために確かめるなら社内の使い道です。業者が自分の客のために確かめるなら、業者の側の社外の使い道になります。
  • 外の試験の会社に頼る組織では、試験の会社の側が申し込みます(頁では Red Team Access の所の注記)。
  • Team の契約では、社内の仕事だけに絞れません。 組織の全員に効くからです。頁は、社外の使い道の承認を得るまで、制度の入った組織から客にサービスを出さないように、と書いています。システムの開発や運用を請け負う会社は、この点を先に確かめます。
  • Console なら分けられます。 制度を割り当てた作業の場にだけ効くので、社内の仕事だけの作業の場に割り当て、客の通信は制度の無い別の作業の場に置きます。

Claude と Console は別の組織

頁は、Claude のアカウントと Claude Console のアカウントは別の組織だ、と書いています。承認は、ほかの組織には引き継がれません。Claude のアプリと Claude Code を Team や Enterprise の席で使うのか、Console の API で使うのかを決め、使う方の組織から申し込みます。違う組織で承認された時は、使う組織からもう一度申し込むか、Anthropic の担当(account team)に相談します。

一つの会社の中で部署ごとに別の枠にすることはできます。Claude の組織ごとに、別の申し込みが要ります。

メールアドレス

組織として申し込むなら、会社のドメインのアドレスのアカウントを使います(会社のドメインがある場合)。アカウントのメールアドレスは、後で変えられません。個人のアドレスで作ったアカウントから会社の申し込みをしないように、アカウントを作る時に確かめます。

誰が使うか

Defense Access は、承認される人数に既定の上限がありません。頁は、承認された後の割り当ての考え方として、次を挙げています。

  • Defense Access: セキュリティの担当者と、セキュリティやそれに近い仕事をする開発者や社員
  • 割り当てなし: それ以外の人

誰に割り当てるかは、会社の情報システムの責任者が決めます。決める材料は、誰が確かめの作業をするかと、その人の端末とアカウントが 5 章の決まりを満たすかです。頁は、人を足す時は、足す人がその枠のセキュリティの決まりを満たす必要がある、と書いています。

3. 用意する物

どの枠でも要る物

  • 正しいアカウント。 制度を使う組織から申し込みます(2 章)。
  • メールアドレス。 組織なら会社のドメインのアドレス(2 章)。
  • 申し込みは組織に一つ。 Claude のアカウントでは Owner か Primary Owner が、Console のアカウントでは Admin が出します。組織のほかの人は、別に申し込みません。
  • 確かめのための情報。 組織と、申し込む人についての情報です。

個人として確かめを受ける時:

  • 写真付きの、政府が出した身分証の現物(旅券、運転免許証、州や県の身分証、国の身分証)。写しは不可です。
  • カメラの付いた電話。その場で自分の顔を撮るように求められることがあります。

組織として確かめを受ける時は、上に加えて:

  • 組織の正式な名前、住所、事業の登録番号

日本の書類のどれがこれに当たるか(たとえば法人番号で足りるか)は、頁に書いてありません。

仕事の説明

頁は「あなたの部署が何をしていて、Claude をどう使うかを説明する」(Describe what your team does and how you'll use Claude)と書いています。字数や様式は、頁に書いてありません。申し込みの画面がどの言葉で書くことを求めるかも、頁に書いてありません。

書く時の心がけは一つです。自社の仕事を、その通りに書きます。 大きく見せる必要はありません。何を確かめるか、誰がするか、どこで使うか、何を渡さないか、を具体に書きます。例です(角括弧は自社の事実に置き換えます)。

日本語の例:

当社は、[業種] の会社で、社員は [人数] 人です。情報システムの担当は [人数] 人で、[職名] が責任者です。当社が持つシステム(基幹システムへの追加の開発、顧客の管理の仕組みの独自の拡張、システムの間をつなぐプログラム、社内の Web)のソースコードを Claude に読ませ、穴を探し、仕分け、試験用の環境で確かめ、直します。対象は当社が持ち主のシステムと、当社に納められたコードだけです。客のための仕事には使いません。Claude には、コード、設定の定義、データベースの定義を渡し、鍵やパスワードは値を伏せ、顧客の名簿や取引の中身は渡しません。

英語の例:

We are a [industry] company with [number] employees. Our in-house IT team has [number] members, led by our [title]. We will use Claude to review the source code of systems our company owns (custom extensions to our ERP and CRM, integration programs between systems, and internal web applications), triage the vulnerabilities it finds, validate them in a test environment, and fix them. We will only work on systems our company owns and code delivered to us under contract, not on systems of customers or third parties. We give Claude source code, configuration and schema definitions; secrets are redacted and we do not give it customer records or transaction data.

審査を速める証拠

頁は、審査を速める証拠として、次を挙げています。

  • 頁の側で自分で確かめられる出どころへのリンク(公の登録簿、資格の名簿、発行元の頁)。公のリンクが無い時は、日付の入った書類の全体を上げる。
  • LinkedIn の頁や画面の写しは、たいてい足りない。
  • 自社の Web サイトで足りる物もある(たとえば、資格を載せた公開の頁や、試験のサービスを説明する頁)。
  • 証拠の名前が、確かめを受ける組織や人の名前と合っていること。
  • リンクが全部、誰でも見られる形で開けること。

Defense Access の申し込みで、どの証拠が求められるかは、頁に具体的に書いてありません。頁の手順は、Defense Access では、確かめ(組織なら事業の確かめ)、仕事の説明、規約への同意の三つを挙げています。

Defense Access の決まりへの備え

組織は、次の決まりを満たしていると表明(attest)できる必要があります。中身は 5 章です。

  • 多要素認証(MFA)
  • API の鍵を、少なくとも 7 日ごとに替えること

4. 申し込みの手順と、返事の後

出す人

Claude のアカウントでは Owner か Primary Owner、Console のアカウントでは Admin です(3 章)。

出す場所と手順

申し込みは、Verification Portal で出します。画面が、確かめ、枠、枠が求める証拠、規約へと順に案内します。

Claude、Claude Code、Claude の API を Anthropic から直に使っている場合の手順は、次の通りです。

  1. Anthropic のアカウントで Verification Portal に入ります。アカウントが無ければ作り、支払いを設定します。
  2. 制度の一覧から「Cyber Verification Program」を選びます。
  3. 「Apply」を押し、申し込みを書きます。
  4. 規約に同意して、出します。

クラウド(AWS、Google Cloud、Azure)やほかの会社の製品から使う場合は、先にアカウントをつなぐ手順があります。頁の「Apply with a cloud account」「Apply through a third-party platform」を読んでください。

出した後

  • 出した後は、直すことも取り消すこともできません。出すまでは、答えを見直して直せます。
  • 申し込みと規約は、Verification Portal の制度の頁から PDF で取り出せます。社内の記録に残します。
  • 決まったこと、または追加の情報の求めが、メールで来ます。進み具合は、Verification Portal の Programs から「Cyber Verification Program」を開いて見ます。
  • 返事の目安は、Defense Access では 2 日です。目安を過ぎても、出し直しや問い合わせは要らない、と書いてあります。

通らなかった時

  • ふつうに使える AI は、そのまま使えます。承認された枠があれば、それも使えます。
  • 7 日たてば、もう一度出せます。頁は、何かが変わった時や、強い証拠を出せる時に、これが一番よい道だと書いています。
  • 正しいアカウントから出したか、正しい種類(組織か個人か)の確かめを受けたかを見直します。

通らなかった理由が知らされるかは、頁に書いてありません。

承認の後でも、方針に反する使い方があれば、Anthropic は自分の判断で、いつでも見直し、狭め、取り消すことがある、と書いてあります。

承認の後に有効にする

多くの製品では、承認だけでは制度は有効になりません。管理者が、役や作業の場に割り当てます。

どこで使うか すること
Pro、Max、Ultra、Team 何もしない。自動で有効になる。Team では全員に効く
Enterprise 制度を役(custom role)に割り当てる
Claude Console(API) 制度を作業の場(workspace)に割り当てる
Claude Platform on AWS、Claude Platform on Google Cloud、Microsoft Foundry Verification Portal の制度の頁の「Access on linked accounts」で枠を有効にする
Google Cloud Agent Platform project をつなぎ、枠を有効にし、データの共有を設定する
ほかの会社の製品 Verification Portal の制度の頁の「Access on linked accounts」で、その製品の枠を有効にする

Enterprise の手順:

  1. Owner か Primary Owner で入ります。
  2. Organization settings > Roles で、役(custom role)を足すか直します。
  3. Details の欄で、使う人の組(group)を選びます。
  4. Models の欄で、Grants の下の権限を選び、保存します。
  5. 承認された人の役の種類が Custom であることを確かめます。もともとある役(built-in roles)には効きません。

Console の手順:

  1. 組織の管理者として Console に入ります。新しい作業の場を作るか、今ある作業の場に割り当てます。既定の作業の場には割り当てられません。
  2. その作業の場には、この機能を使うべき人だけを入れます。
  3. Programs の頁で、枠のカード(「Defense Access」)を選びます。
  4. Workspaces の表で、作業の場の Access のスイッチを入れます。
  5. 作業の場の行に「Not set」「Not met」「Allowed」と出た欄があれば、選んで、示される直し方に従います。
  6. 頁にある有効な作業の場の数(たとえば「1 of 2 workspaces active」)を見ます。決まりを満たすまで、作業の場は有効になりません。

承認されたのに止められる時は、頁の FAQ の通り、管理者が割り当てたか、Console なら制度の入った作業の場に居るか、仕事が枠の中か、を順に確かめます。

5. 運用の決まり

多要素認証(MFA)

Defense Access では、組織が多要素認証を入れていると表明できる必要があります。どのアカウントに要るか(Claude のアカウントだけか、社内の全部か)は、頁に書いてありません。

2026年12月15日からの決まり

頁は、2026年12月15日から、Defense Access に次が要ると書いています。

  • フィッシングに強い多要素認証(phishing-resistant MFA)
  • 固定の API の鍵、長く使う API の鍵は不可(no longer allows static or long-lived API keys)

頁は、今のうちに Workload Identity Federation へ移ることを勧めています。

Console の手順の所には、より具体的に書いてあります。2026年12月15日までは、Defense Access の作業の場で使える API の鍵は、7 日以内に切れる鍵だけです。その日の後は、API の鍵は使えません。

フィッシングに強い多要素認証とは。 偽の画面にだまされて入力しても、その結果が攻める側で使えない認証です。米国の CISA の資料(2022年10月)は、FIDO と WebAuthn による認証(パスキーや、USB や NFC のセキュリティキー)と、公開鍵の基盤(PKI)による認証(IC カード等)を、フィッシングに強い物として挙げています。認証のアプリの使い捨ての番号、プッシュの通知、SMS や音声の番号は、フィッシングに強い物には入っていません。CVP の頁が、どの方式を認めるかを名指ししているわけではありません。どの方式で満たすかは、5 章の終わりの「誰が決めるか」を見てください。

API の鍵を 7 日以内に替える運用

ここは、Anthropic の API の認証の文書(2026年11月11日に閲覧)で確かめた事です。

  • Console で鍵を作る時に、切れるまでの長さを選びます。決まった長さ(3 時間、1 日、7 日、30 日)か、好きな長さか、切れない(Never)かです。組織に長さの上限の決まり(maximum expiration policy)があると、それより長い物と Never は選べません。長さは作る時に決まり、後で変えられません。
  • 切れた鍵で送ると、401 authentication_error が返ります。切れた鍵は戻せないので、新しい鍵を作ります。
  • 切れる前に、作った人にメールが来ます。長さが 14 日以上の鍵は切れる 7 日前に、7 日以上の鍵は切れる 1 日前に来ます。それより短い鍵は、知らせ無しで切れます。
  • Console の鍵の表と、Admin API の expires_at で、各鍵の切れる時を見られます。

7 日で回すには、鍵を誰が作り、どこに置き、どの仕組みが読み、誰が古い鍵を消すかを決めます。決める材料は、鍵を使う仕組みの数と、置き場(秘密の保管の仕組み)の有無です。頁の決まりは 2026年12月15日に「鍵は不可」へ変わるので、7 日の回し方を作り込むより、次の Workload Identity Federation へ移る準備に時間を使う方が、手戻りが少なく済みます。

Workload Identity Federation とは

ここも、Anthropic の文書(2026年11月11日に閲覧)で確かめた事です。

  • 何か。 仕組み(workload)が、自社で動かしている身元の発行元(identity provider)から短い間だけ有効な身元の札(OIDC の JWT)を受け取り、それを Anthropic の短い間だけ有効な鍵に取り替えて API を使う方式です。固定の sk-ant-... の鍵を作る、置く、替える、漏らす、が無くなります。
  • 発行元の例。 文書は、AWS、Google Cloud、Microsoft Entra ID、GitHub Actions、Kubernetes、SPIFFE、Okta の手引きを置いています。
  • Console で作る物。 三つです。サービスのアカウント(人ではない身元)、発行元の登録(federation issuer)、取り替えの決まり(federation rule。どの発行元の、どんな中身の札なら、どのサービスのアカウントとして通すか)。Console の Workload identity の頁の「Connect workload」で、三つをまとめて作れます。作るには、組織の admin、owner、primary owner の役が要ります。
  • 鍵の長さ。 取り替えの決まりで、60 秒から 86,400 秒の間で決めます(API の既定は 3,600 秒。画面の案内の初めの値は 600 秒)。SDK が、切れる前に取り替え直します。
  • 移り方。 文書は、並べて設定する → どちらの身元が使われているかを確かめる → ANTHROPIC_API_KEY を全部の置き場から消す → 古い鍵を消す、の順を示しています。ANTHROPIC_API_KEY が残っていると、そちらが先に使われるので、消し忘れに気をつけます。
  • 限り。 文書は、これだけで安全が完成するわけではなく、札を出す発行元の強さで決まる、と書いています。発行元の側の多要素認証、使える場所の制限、記録と組み合わせます。

自社にクラウドや CI の身元の発行元がまだ無い時に、どう移るかは、確かめていません。人が自分の机で Claude Code を使う時に、この決まりがどう当たるか(Team や Enterprise の席で入って使う場合を含む)は、CVP の頁に書いてありません。申し込む前に、どの使い方をするかを決め、その使い方について Anthropic の最新の文書を読みます。

データの保持

頁は、制度に入った者は全員、データの保持が必須だと書いています。サイバーの悪用を見張り、防ぐためです。

  • 保持しない扱い(ZDR)は、Claude Fable か Claude Mythos のモデルについてデータの保持の例外を持つ組織だけが、社内の使い道で使えます。
  • Enterprise Frontier Safeguards(EFS)が広く使えるようになると、条件に合う組織は、自分が管理するクラウドにデータを置けるようになる、と書いてあります。

何を、どのくらいの期間、どこに保持するかは、頁に書いてありません。保持の中身は、規約と Anthropic のほかの文書で決まります。申し込みの時に出る規約を読み、PDF で残します(4 章)。

ここから言える事は一つです。AI に読ませた物は、Anthropic に送られ、保持される物として扱います。 だから、渡す物を選びます(6 章)。

6. AI に渡す物と、渡さない物

5 章の通り、渡した物は保持されます。この前提で、渡す物を選びます。

種類 渡し方
ソースコード 渡す。確かめる範囲の物だけ
設定のファイル、データベースの定義、画面や API の定義 渡す。鍵やパスワードの値は伏せる
鍵、パスワード、トークン 値を伏せた写しを渡す。入っていた事は、一件の穴として記録する
顧客の名簿、取引、給与、健康の情報 そのままは渡さない。件数、項目の名、型、値の長さだけを、プログラムで取り出して渡す
記録(ログ) 確かめに要る行だけを切り出す。人の名前、メールアドレス、網の番地(IP アドレス)が入っていれば伏せる
業者との契約書 渡さない。コードを読んでよいかを人が確かめ、その結論だけを記録に書く

渡す前に、何を渡したかを記録に書きます(8 章の kensa/00-範囲と許し.md)。

取り出すプログラムの例

名簿や取引の CSV から、件数、項目の名、型、一番長い値の字数だけを取り出します。値そのものは出しません。Python の標準ライブラリだけで動きます。AI に渡すのは、このプログラムの出力だけです。

"""CSV から、件数・項目の名・型・字数だけを取り出す。値そのものは出さない。

使い方: python3 katachi.py 名簿.csv > 名簿の形.md
"""
import csv
import re
import sys


def kata(v: str) -> str:
    if v == "":
        return "空"
    if re.fullmatch(r"-?\d+", v):
        return "整数"
    if re.fullmatch(r"-?\d+\.\d+", v):
        return "小数"
    if re.fullmatch(r"\d{4}[-/]\d{1,2}[-/]\d{1,2}.*", v):
        return "日付"
    return "文字"


def main(path: str) -> None:
    with open(path, newline="", encoding="utf-8") as f:
        rows = csv.DictReader(f)
        names = rows.fieldnames or []
        kinds = {n: {} for n in names}
        longest = {n: 0 for n in names}
        count = 0
        for row in rows:
            count += 1
            for n in names:
                v = row.get(n) or ""
                k = kata(v)
                kinds[n][k] = kinds[n].get(k, 0) + 1
                longest[n] = max(longest[n], len(v))
    print(f"件数: {count}\n")
    print("| 項目の名 | 型と件数 | 一番長い値の字数 |")
    print("|---|---|---|")
    for n in names:
        ks = "、".join(f"{k} {c}" for k, c in sorted(kinds[n].items()))
        print(f"| {n} | {ks} | {longest[n]} |")


if __name__ == "__main__":
    main(sys.argv[1])

出力は次の形です。

件数: 2

| 項目の名 | 型と件数 | 一番長い値の字数 |
|---|---|---|
| 氏名 | 文字 2 | 5 |
| 年齢 | 整数 1、空 1 | 2 |
| 登録日 | 日付 2 | 10 |
  • 文字コードが Shift_JIS の CSV なら、encoding="cp932" にします。
  • 出力を渡す前に、人が目で読みます。項目の名そのものに、人の名前や取引先の名前が入っている事があります。
  • 取り出すプログラムは短く保ち、記録に残します(誰が読んでも、値を出していない事が分かるように)。

伏せ方の例

設定のファイルから、鍵やパスワードらしい値を伏せた写しを作ります。

"""設定のファイルから、鍵やパスワードらしい値を伏せた写しを作る。

使い方: python3 fuseru.py < app.properties > app.properties.伏せた写し
伏せた行の番号は、標準エラーに出す(穴の記録に使う)。
"""
import re
import sys

NAMES = r"password|passwd|pwd|secret|token|api[_-]?key|private[_-]?key|credential"
LINE = re.compile(rf"^(\s*[\"']?[\w.-]*(?:{NAMES})[\w.-]*[\"']?\s*[:=]\s*)(\S.*)$", re.I)

for no, line in enumerate(sys.stdin, 1):
    m = LINE.match(line.rstrip("\n"))
    if m:
        print(f"{m.group(1)}<伏せた>")
        print(f"{no} 行目を伏せました", file=sys.stderr)
    else:
        print(line, end="")

伏せる前と後:

db.password = hunter2      →  db.password = <伏せた>
API_KEY: "abc"             →  API_KEY: <伏せた>

この例は、名前に password や token が入った行だけを伏せます。接続の文字列の中(jdbc:...//user:pass@host)、コードの中の文字列、証明書の秘密鍵のファイルは拾いません。伏せた写しは、渡す前に人が目で読みます。伏せる仕組みを強くするのは、自社で使う設定の形に合わせて足していきます。

7. 社内の許しと、業者への知らせ

社内の許し

確かめを始める前に、次を決めて、記録の最初(kensa/00-範囲と許し.md)に書きます。skills/system-check の「始める前に聞くこと」と同じ項目です。

  • 範囲。 どのシステムの、どのコードを、どこまで(読むだけか、試験用の環境で動かすか)。
  • 持ち主。 自社の物か、業者から納められた物か。
  • 許す人。 システムについて決める権限を持つ人の役と、許した日付。誰が許す人かは、社内の決まり(職務の権限の表など)で決まります。
  • 渡さない物。 6 章の表の、自社の版。
  • 使う枠。 コードを読むだけか(申し込み無しでできる仕事)、Defense Access の承認の下で確かめるか。

契約でコードが納められているかの見方

手元にコードが無い物は、確かめられません。契約書と納品の記録で、次を見ます。

  • 納める物の一覧に、ソースコードが入っているか。
  • 著作権が誰にあるか。業者に残っている場合、自社が読んで直してよいか(使う権利の範囲)。
  • 秘密を守る決まりが、自社の中での確かめや、AI に読ませることを妨げないか。
  • 納品の後に直した分のコードも、納められているか。

判断が付かない時は、契約の担当や法務の担当に聞きます。読み取った結論(「読んでよい」「業者に確かめる」)を、一覧(kensa/01-一覧.md)に書きます。コードが無い部分は「確かめられない」と書き、業者にコードを求める材料にします。

業者への知らせ

確かめを始める前に、業者に知らせます。短い版は、解説 20 にある一文です。

当社は、当社のシステムと納入されたコードを、AI で確認します。実施にあたって問題点があれば回答してください。

もう少し詳しい版です。角括弧は自社の事実に置き換えます。

件名: [システムの名] の確認の実施について

[業者の名] 御中

当社は、当社が持つ [システムの名] と、貴社から納入されたソースコードについて、[開始の時期] から、AI(Anthropic の Claude)を使って、セキュリティの確認を行います。

  1. 対象: [範囲。例: 基幹システムへの追加の開発の部分、システムの間をつなぐプログラム]
  2. 方法: 当社の担当者が、ソースコードと設定の定義を読み、問題を探します。動かして確かめる場合は、試験用の環境で行い、本番の環境では行いません。
  3. AI に渡す物: ソースコードと、値を伏せた設定の定義です。顧客の情報と取引の中身は渡しません。AI に渡した物は、AI の提供元の決まりに沿って保持されます。
  4. 見つかった問題: 場所、何が起きるか、直し方の案を、貴社にお知らせします。直す分担と負担は、契約に沿って協議させてください。
  5. お願い: 契約の上で、または技術の上で、実施に問題があれば、[期日] までにご回答ください。

[会社の名] [部署] [担当の名] [連絡先]

開発中の物

開発中の物は、納品を待たずに、できた部分から確かめます。納品の時に初めて確かめて使えないと分かるのが、一番困るからです。確かめる分だけ仕事が増えるので、範囲を絞る、期日を見直す、といった協議を、知らせと同じ時に始めます。

直す負担の協議

見つかった穴を誰の負担で直すかは、契約の話です。保証の期間、瑕疵(契約に合わない所)の扱い、保守の契約の範囲で決まります。見つかってから揉めるより、確かめると決めた時に協議を始めます。

8. 最初の一つを確かめる

一つ選ぶ基準

最初は、一つのシステムの、一つの部分から始めます。選ぶ基準は次の通りです。上ほど先に見ます。

  1. コードが手元にある。 無ければ、確かめられません。
  2. 外から届く。 営業所、取引先、スマートフォン、インターネットから届く口を持つ部分。
  3. 大事なデータに直に触る。 顧客、取引、給与の表を読み書きする部分。
  4. 自社か受託業者が個別に書いた。 製品の本体は製品の会社が直しますが、個別に書いた部分は、納めた後に誰も見ていないのがふつうです。
  5. 大きすぎない。 最初の一つは、一人で一通り読み終えられる大きさにします。どのくらいの大きさかは、担当する人の時間で決めます。

作業の場所の作り方

確かめの作業は、社内の端末の、専用のフォルダーで行います。形は skills/system-check と合わせます。

確かめ-[システムの名]/
  .claude/
    skills/
      system-check/
        SKILL.md          ← skills/system-check を写した物
  読む物/
    code/                 ← 確かめる範囲のコードの写し
    設定-伏せた写し/       ← 6 章の伏せ方で作った物
    データの形/           ← 6 章の取り出すプログラムの出力
  kensa/
    00-範囲と許し.md      ← 7 章で決めた事、渡した物
    01-一覧.md            ← 確かめる物の一覧
    穴/
      2026-11-10-001-注文の照会が他人の番号で見える.md
  • 読む物/ に入れるのは、6 章で選んだ物だけです。本番のデータベースや、本物の設定のファイルは、このフォルダーに置きません。
  • kensa/ は、自社の中の置き場に残します。次に確かめる人と AI が、そのまま読める形にします。
  • 本物の鍵やパスワードを使って動かす確かめは、試験用の環境で、別の手順で行います。

Claude Code でスキルを読ませる

Claude Code は、作業のフォルダーの .claude/skills/<スキルの名>/SKILL.md を、そのフォルダーの仕事で読みます(自分の全部の仕事で使うなら ~/.claude/skills/<スキルの名>/SKILL.md)。

  1. このリポジトリの skills/system-check/ を、作業のフォルダーの .claude/skills/system-check/ に写します。
  2. 作業のフォルダーで claude を起動します。
  3. 依頼がスキルの説明に合うと、Claude が自分でスキルを読みます。/system-check と打って、明示して読ませることもできます。

Claude のアプリでスキルを読ませる

  1. 設定で、コードを動かしてファイルを作る機能を有効にします。個人の契約では Settings > Capabilities の「Code execution and file creation」(新しい画面では「Create and edit files」)です。Team では組織の既定で有効です。Enterprise では、Owner が Organization settings > Plugins & skills の Policy の欄で有効にしているかを確かめます。
  2. skills/system-check/ のフォルダーを、フォルダーごと ZIP にします。フォルダーの名は、スキルの名(system-check)と同じにします。
  3. Customize > Skills を開き、「+」→「+ Create skill」→「Upload a skill」で ZIP を上げます。
  4. 一覧に出たスキルを有効にします。

画面の名前は、2026年11月11日に Anthropic のサポートの頁で確かめた物です。画面は変わることがあります。アプリの場合は、コードと設定の写しを会話に上げて読ませます。上げた物も、5 章の通り保持されます。

ここでは system-check を例にしました。10 章の incident-response、detection、kagi も、フォルダーの名を替えるだけで、同じやり方で入れられます。

最初に Claude に言う文の例

skills/system-check の手引きに沿って、自社のシステムの確かめを始めます。対象は 読む物/code/ にある [システムの名] の [部分の名] です。kensa/00-範囲と許し.md に、範囲、持ち主、許した人と日付、使う枠、渡さない物を書いてあります。まずそれを読んで、足りない項目があれば聞いてください。次に、外から届く口を全部挙げて kensa/01-一覧.md を作ってください。穴を見つけたら、手引きの形で kensa/穴/ に一件ずつ書き、コードから読んだ事と、動かして確かめた事を分けてください。

一日目と一週目

時間の配分は、担当する人の数と、選んだ部分の大きさで決まります。目安として、次が出来ていれば進んでいます。

  • 一日目。 kensa/00-範囲と許し.md が書けている。読む物/ に、渡してよい物だけが入っている。外から届く口の一覧が出来ている。
  • 一週目。 選んだ部分を一通り読み終えて、見つけた穴が kensa/穴/ に書けている。一番重い一件について、直し方と、直した後に確かめる手順が決まっている。業者に知らせが届いている。Defense Access の申し込みを出している(出すと決めた場合)。

9. 見つけた穴の扱い

重さの付け方

一件ごとに、次の事実で重さを付けます。

  • 誰が届くか。 外から誰でも届くか、ログインの後か、社内の網からだけか。
  • 何に触れるか。 顧客の情報、取引、お金の動き、ほかのシステムの鍵。
  • 何が起きるか。 見える、変えられる、止まる。
  • 確かめの度合い。 コードから読んだだけか、試験用の環境で動かして確かめたか。

重さの段の数と名前は、会社で決めます。業者と共通の物差しを使うなら、CVSS のような公の物差しを使う事もできます。どちらにするかは、情報システムの責任者が、業者と話して決めます。

直す順

重い物から直します。重さが同じなら、直すのが小さい物から片付けると、残る件数が早く減ります。直す順と期日を誰が決めるかは、7 章で決めた分担に従います。

業者に渡す分

業者が直す物は、一件の記録のうち「どこ」「何が起きるか」「直し方」を渡します。攻める手順の細かい所は、直すのに要る分だけにします。渡した日と相手を、経過に書きます。

もう一度確かめる

  • 直したら、同じ手順でもう一度確かめ、経過に書きます。
  • 同じ形の誤りが、ほかの所に無いかをコード全体で探します。一件の穴は、たいてい同じ書き方の仲間を連れています。

AI に止められた時

穴を確かめる仕事を AI が止めた時は、止まった事、何を頼んだか、どの枠で使っていたかを記録に書きます。言い換えて押し通しません。Defense Access の承認がまだなら、承認の後にもう一度試します。承認の後でも止められる時は、4 章の終わりの順に確かめます。

続ける

  • AI が新しくなったら、同じ範囲をもう一度確かめます。前の AI が見つけなかった穴が見つかります。
  • コードが変わったら、変わった部分を確かめます。
  • 次に確かめる部分を一覧から選び、8 章からもう一度進めます。

10. 事故の対応と検知へ

Defense Access の枠には、事故の対応と、検知の仕組みづくりも入ります(1 章)。このリポジトリでは、次の手引きと道具を置いています。どれも 8 章と同じやり方で、作業のフォルダーに写して読ませます。

  • incident-response(事故の対応) — skills/incident-response。不正なアクセス、ランサムウェア、鍵やパスワードの漏れ、端末の紛失が起きた時と、起きる前の備えを、情報システムの係が Claude と一緒に進める手引きです。気づいた時の最初の一時間、止める、範囲を記録で知る、作り直す、知らせる、書く、身代金、訓練の章に、連絡先の表と記録の様式と知らせの文の雛形が付いています。
  • detection(見張り) — skills/detection。何を見張り、何を異常と見て、誰に知らせるかを、自社の機械とアカウントについて作る手引きです。見張る物の一覧、記録を機械の外に集める形、普段の形、決まりの例と調べる命令、試し方、知らせの宛先と鳴りすぎの直しを扱い、記録の名前とアドレスを伏せる道具が付いています。
  • kagi(道具の使い方) — skills/kagi。道具 kagi を使う時に読む手引きです。在庫表、記録、口の突き合わせ、機械の形、鍵、週の定例、報告の順に章があります。
  • kagi(道具) — kagi/。サーバーと業務システムの秘密の在庫表、口の表、追記だけの記録、Linux の機械の今の形を、人が書いた表と突き合わせて違いを出す道具です。扉の鍵ではありません。鍵の値を読まず、機械を変えず、直す手は文で出して人が打ちます。

11. 次の枠へ進む時

動いているシステムに侵入して確かめる試験は、Red Team Access の枠の仕事です。頁から、条件を拾います。

  • 申し込めるのは組織だけで、契約は Team、Enterprise、API です。Defense Access を組織として持っていれば、上の枠に申し込めて、審査の間も Defense Access は使えます(FAQ)。
  • 組織は、次を満たしていると表明できる必要があります。フィッシングに強い多要素認証、API の鍵を少なくとも 7 日ごとに替えること、会社のドメインのアカウント、組織が管理する端末、外向きの通信の制限、担当者の身元の確かめ(background checks)。
  • 社内のレッドチームとして申し込むなら、全部が要ります。セキュリティの取り組みの証拠(年次の報告書のサイバーセキュリティの節、有効な ISO/IEC 27001 の証明書、SOC 2 Type II の報告書、12 か月以上続けている有料のバグ報奨金のどれか。重要なインフラの運用者は、業界のセキュリティの義務でもよい)。試験の部署の名、長、おおよその人数。試験ごとに、そのシステムに権限を持つ人が先に許していることの確認。それに加えて、攻めのセキュリティの資格(OSCP、GPEN、CREST Registered Tester など)を持つ人、公開された仕事(研究や講演)、伏せた所のある社内の試験の報告書の、どれか一つ。重要なインフラの運用者は、業界の登録簿の記載も要ります。
  • 条件に合っても、承認が約束されるわけではない、と書いてあります。
  • 外の試験の会社に頼る組織では、試験の会社の側が申し込みます。
  • 返事の目安は 2 週間です。今は申し込みが多く、延びています。

ここで整える物(会社のドメインのアカウント、会社が管理する端末、外向きの通信の制限、フィッシングに強い多要素認証、担当者の身元の確かめ)は、鍵の管理を自社で持つ会社が整える物と同じです(解説「デジタルキーは管理者が自分で持つ」「デジタルドアはサイバー攻撃対策そのもの」)。Defense Access で自社のコードを確かめながら、網と認証を整えていけば、それが次の枠の準備になります。

12. 費用

制度そのもの

制度に申し込む料金が要るかは、頁に書いてありません。頁は、有料の契約で使えると書いています。

AI の費用

AI の費用は、契約の席の料金と、使った分です。2026年11月11日に Anthropic の料金の頁で確かめた値は、次の通りです(税は含まない、と書いてあります)。

契約 料金の頁の値
Pro 年払いで月 17 ドル(先に 200 ドル)、月払いで 20 ドル
Max 月 100 ドル
Team の標準の席 一人あたり月 20 ドル(年払い)、25 ドル(月払い)
Team のプレミアムの席 一人あたり月 100 ドル(年払い)、125 ドル(月払い)
Enterprise 一人あたり月 20 ドル(年払い、20 席から)。使った分は API の料金で別に払う
API(Console) 使った分。モデルと仕事で変わる

どの席で、どのモデルと Claude Code がどれだけ使えるかは、料金の頁で確かめてください。この文書では確かめていません。CVP の頁の FAQ には、Mythos のモデルについて、Pro では使った分の払い(usage credits)でだけ使えること、Max と Ultra では週の使える量の 50% までを Mythos と Fable で分け合うこと、が書いてあります。

人の時間

費用の大半は、AI ではなく、人の時間です。何を先に確かめるかを決め、渡す物を用意し、結果を読み、業者と話し、直し、もう一度確かめる人が、自社に要ります。どれだけの時間を当てるかは、確かめる範囲と、見つかる穴の数で決まります。最初の一つ(8 章)を終えた時に、かかった時間を記録しておくと、次からの見積もりの材料になります。

13. 確かめていない事

  • 実例。 この文書の手順を、会社が最初から最後まで通した記録は、まだありません。運営者自身が Defense Access に申し込み、このリポジトリのコードを確かめた記録を、後で足す予定です。
  • 頁に書いてない事。 データを何を、どのくらいの期間保持するか。制度そのものの料金。日本の書類のどれが組織の確かめに当たるか。申し込みを書く言葉。通らなかった時に理由が知らされるか。多要素認証がどのアカウントに要るか。個人の申し込みに 5 章の決まりがどう当たるか。人が机で Claude Code を使う時に、2026年12月15日からの API の鍵の決まりがどう当たるか。
  • 確かめていない事。 身元の発行元を持たない会社が Workload Identity Federation に移る道。どの席でどのモデルが使えるか。Verification Portal の画面を、実際に開いて確かめてはいません。

気づいた事、違っていた事は、Issues で知らせてください。Issues は誰でも読めるので、会社の中の事は書かないでください。自社で始める相談は、相談と教室でも受けています。

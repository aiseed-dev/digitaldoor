デジタルドア ユーザーマニュアル

このマニュアルは、ソフトウェアのコードから自動で生成しています。対象は、事業所のサーバーを運用する管理者、受付の担当者、鍵を使う利用者、保守の担当者です。

生成日: 2026-11-14

事業所サーバー

事業所サーバー — 一つの事業所(建物)の扉と鍵を運用する常駐サービス。

構成ファイル(site.toml)を読み、扉ごとのコントローラ(door)と鍵の台帳(entrance)を一つのプロセスで動かし、 管理者・受付・利用者向けの HTTP API を出す。スマートフォンアプリ(digitalkey.mobile)と業務システムはこの API を使う。 インターネットに接続していなくても動く。記録は事業所のサーバーに置く。

導入

deploy/install.sh を root で実行すると、専用ユーザーの作成、仮想環境の作成、設定の雛形の生成、systemd への登録まで行います。設定は /var/lib/digitaldoor/site.toml です。

sh deploy/install.sh
systemctl status digitaldoor-site

設定ファイル(site.toml)

digitalkey site init <ディレクトリ> で次の雛形が作られます。トークンは作ったときに一度だけ画面に出し、設定には SHA-256(token_sha256)だけを書きます。トークンを足すのは digitalkey site token --name <名前> --role <役割> です。

# digitaldoor 事業所サーバーの設定

[site]
name = "本社"
vault = "/var/lib/digitaldoor/vault"            # 台帳・監査記録・鍵の置き場(このサーバーの中)

[api]
host = "127.0.0.1"          # 構内だけに出す。外へ出すときは前段に TLS を置く
port = 8800

# 扉。lock は dummy(配線確認)か、入れた錠ドライバの種類。digitalkey-sesame を入れると sesameweb:<機器UUID>(Hub 3 経由)と sesame:<機器UUID>(BLE 直結)
[[door]]
id = "正面玄関"
lock = "dummy"
two_person = 1              # 2 にすると二人同時認証
autolock = 5.0              # 解錠から自動施錠までの秒

# 扉が自分で確かめる署名つき資格情報。有効の終わりは、鍵の終わりと「作った時刻 + max_hours」の早い方。
# ネットワークが届かない扉で失効が効くまでの最長の時間になる(R-AC-14)。値は管理者が扉ごとの事情で決める
[credentials]
max_hours = 24

# アクセストークン。role は 管理者 | 受付 | 利用者 | 保守。利用者は subject(鍵の主体名)を書く
# トークンそのものは書かず、SHA-256 だけを書く。足すのは digitalkey site token

[[token]]
name = "管理者"
role = "管理者"
token_sha256 = "6ee2b877b9f6c8c25ac821e659ad5889fb4179fd1a774887485424fd1e91cd80"

[[token]]
name = "受付"
role = "受付"
token_sha256 = "6e7ea941210b0b1a6912533c3a913e934fe576ccef14d38e4a7b07e6f788cdb0"

役割

役割 できること
管理者 サーバーの設定、鍵の発行と失効、扉の施錠、記録の閲覧と検査。
受付 鍵の発行、扉の施錠、操作の記録の閲覧。失効はできません。
利用者 自分の鍵の確認と、自分の鍵での解錠。
保守 扉の状態と監査記録の閲覧、記録の検査、施錠。

スマートフォンアプリ

スマートフォンアプリ(Flet)— 管理者と利用者が事業所サーバーを使うための画面。

利用者: 自分の鍵を見る、扉を開ける。 管理者・受付: 鍵を発行する、失効させる、扉を施錠する、操作の記録を見る。 接続先(サーバーの URL とトークン)は端末に保存する。通信は事業所サーバーの HTTP API だけ。

画面

画面:
  接続      サーバーの URL とトークンを入れて保存する。端末の保存領域に残る
  扉        扉の一覧。自分の鍵がある扉は「開ける」ボタンが出る。管理者・受付は「施錠」も
  鍵        利用者: 自分の鍵の一覧。管理者・受付: 全員の鍵と、発行(名前・扉・開始・終了)と失効
  記録      管理者・受付: 鍵の操作の記録(新しい順)

起動: digitalkey mobile [--web]。Android/iOS は `flet build` で組む(pyproject の [tool.flet])。

で信頼の一覧の変更の要求を、JSON で出します。revocation は発行者の鍵で署名した失効の一覧を JSON

扉のコントローラの動作

火災・停電・避難・二人同時・強要を、接点と記録に落とす。

判断の表(既定):

  • 火災信号: 電動部を解放する(避難のため)。閉鎖は扉のクローザーの仕事。記録「非常/火災信号」
  • 停電: 既定は解放(fail-safe)。設定で保持(fail-secure)にできる。復電で元に戻す
  • 認証済み: 有効な資格情報が来たら解錠。二人同時が要る扉では窓の秒数内に N 人揃って解錠
  • 強要: 強要の印が付いた資格情報は解錠し、記録に「強要」を残す(外への通報は上の層)
  • 自動施錠: 解錠から autolock 秒で、扉が閉じていれば施錠。0 なら自動施錠しない
  • 施錠の要求: 火災中は受け付けない。停電中は解放の設定なら受け付けない
  • 時刻: 同期のたびに前と新しい時刻を残す。同期済みから time_jump_s を超えて動いたら「異常/時刻のずれ」
  • 設定: configure で変える。項目ごとに「設定/(項目名)」に前と新しい値を残す。無い項目と許されない値は全体を拒む
  • 手動リリース・改ざん: 記録だけ
  • 故障注入(開発のときだけ): 指示を種別「試験」で記録するだけ。判断は変えない(仕様書 5.5)
  • 署名つき資格情報: present で、信頼する発行者の署名と範囲と期限を扉が確かめ、通れば上の判断(火災、二人同時、自動施錠)に渡す。 一回限りの使用済みの一覧は、起動のときに記録(資格情報/使用)から作り直す(仕様書 5.2a)
  • 信頼の一覧: change_trust で、据付のときに入れた管理者の鍵で署名した変更の要求だけを受ける。受けた変更は記録から読み戻す
  • 失効の一覧: accept_revocation で、信頼する発行者の署名と世代を確かめて受け、発行者ごとに前の一覧を丸ごと置き換える。 present に一緒に運んだ一覧(revocation)は、資格情報より先に受ける。同じ世代は「同じ」で記録しない。 起動のときは記録(設定/失効の一覧 受理)から状態を作り直す。信頼の一覧から外した発行者の状態も残す(仕様書 5.2c)
  • 失効の通知の古さ: revocation_max_age_s が 0 より大きいとき、一覧の issued_at からその秒数を過ぎた発行者の、 期限の長さがその秒数より長い資格情報を拒む。0 はこの規則を使わない(仕様書 5.2c、R-AC-14)

錠のドライバで動く接点

錠のドライバで動く接点 — 扉のコントローラの接点のインターフェースを、digitalkey.locks の錠のドライバにつなぐ。

扉のコントローラ(digitaldoor_controller)が見る錠は、`fire()`、`mains()`、`door_open()`、`bolt_out()`、`set_lock(locked)` の
束だけ(扉コントローラ仕様書 R-CT-03)。この接点は `set_lock` を、非同期の錠のドライバ(`unlock()` / `lock()`。
`digitalkey.entrance.keyring.LockDriver`)に渡す。Sesame でも `dummy` でも、錠の銘柄はこの下に隠れ、判断の側は変わらない(R-CT-04)。

- 火災・電源・扉の開閉は、SimContacts と同じく属性(`_fire`、`_mains`、`_door_open`)で持つ。HTTP の `/event` が書き換え、
  基板の入力に替えるときはここだけを差し替える。
- 非同期のドライバは、この接点が持つ専用のイベントループ(別のスレッド)で動かす。扉の側の呼びは同期で、
  HTTP のインターフェースの複数のスレッドから呼ばれてよい。同じループを使うほかの非同期の処理(鍵の台帳の `Keyring.open` など)は `run()` で渡す。

錠に届かないとき(ドライバが例外を出す、`timeout_s` の内に終わらない):
- `set_lock` は例外を出さず、錠の位置の記録(`bolt_out()`)を動かさない。位置は「届いて確かめた最後の側」で、起動のときは施錠側。
  届かなかった命令で位置を動いたことにしない。
- `failures` を一つ増やし、`last_error` に短い理由を残す。`outputs` には届いた命令だけを足す(`lock` か `unlock`)。
- 時間切れのときはドライバの処理を取り消す。取り消しの前に錠へ届いていた命令は取り消せないので、位置は確かめるまで分からない。
- 扉の判断は止めない。コントローラは命令を出した側として記録を続け、錠が動いたかは `bolt_out()` と `/state` の `bolt_out` が示す。
  命令を出した時点の `failures` と比べれば、呼び手(実演の道具など)は届かなかったことを知れる。

扉のコントローラ(digitaldoor_controller)の HTTP のインターフェース(/state /lock /unlock /event /audit /verify ほか)を、
模擬の接点ではなく、錠のドライバ(`digitalkey.locks` の登録簿)につないだ接点で開く。
パネル(`digitalkey panel`)や Matter の橋は、このインターフェースを叩いて本物の錠を動かす。

  digitalkey door-serve --lock sesame:<機器のUUID>      実機の Sesame(BLE 直結。鍵は `digitalkey sesame import` か `register` で置いておく)
  digitalkey door-serve --fake                          疑似の Sesame(実機にも Bluetooth にも触れない)
  digitalkey door-serve --lock dummy                    配線確認用の錠(何も動かさない)

引数は `digitaldoor-controller serve` と揃えてある(--dir --name --host --port --two-person --autolock --power-policy
--admin-key --trust --revocation-max-age --box)。違いは、錠の指定(--lock か --fake)と、錠に一回の命令を待つ秒数(--timeout)だけである。

しくみ: `Controller` に `digitalkey.contacts.LockDriverContacts` を差す。tools/jitsuen.py と同じ組み立てを、
実演の場面から切り離して常駐させたもの。錠の銘柄は接点の下に隠れ、扉の判断は変わらない(扉コントローラ仕様書 R-CT-03、R-CT-04)。
この命令は digitalkey(AGPL)の側にある。扉のコントローラ(Apache-2.0)は digitalkey を読み込まない。

- 錠の位置は、起動のとき施錠側として始まる。実機を読みには行かない。実機が解錠のままなら、先に施錠してから立てる。
- 錠に届かなかった命令は、扉の判断を止めず、錠の位置の記録を動かさない。`LockDriverContacts.failures` と標準エラーの行に残る。
- 実機の鍵(sesame-keys.json)はドライバが開く。この命令は鍵を読まず、出さない。

更新の配布(digitalkey update)

更新の配布 — 署名つきの包みを、段階配布の表に沿って当て、失敗したら戻す(使い方.md「更新の配布」、R-DV-30〜40)。

製造者の側:
  digitalkey update keygen --out maker.key                 署名の鍵を作る(権限 600)。公開鍵を JSON で出す
  digitalkey update pack --key maker.key --version 1.2.0 --reason 不具合 --summary "..." --from <置き場> --out x.ddupd
                       [--compat 'matter-controller=1.4,1.5'] ...
  digitalkey update index --key maker.key --serial N --entry 1.2.0:全棟[:2027-12-31] [--halt 1.1.0]
                       [--emergency 1.2.1:誰:なぜ] --out index.json     配布の表(index.json と index.sig)を作る
サーバーの側(設定は update.toml):
  digitalkey update status [--json]                        今のバージョン、サポート期限、互換の警告
  digitalkey update apply --package x.ddupd --index index.json   確かめて当てる(ネットワークの無い現場は USB から同じ命令)
  digitalkey update rollback                               直前のバージョンへ戻す
  digitalkey update notice --package x.ddupd               管理会社へ送る事前の通知の文
  digitalkey update fleet <status の JSON を集めた置き場>     サポートの切れたバージョンで動くサーバーの一覧

update.toml:
  product = "digitalkey"
  root = "/opt/digitaldoor/update"     # releases/、current、backups/、update-log.jsonl を置く
  data = "/var/lib/digitaldoor"         # 当てる前に tar で取るデータの置き場
  stage = "全棟"                         # 開発 | 試験導入棟 | 全棟
  trusted_keys = ["<製造者の公開鍵の 16 進>"]
  check = "systemctl is-active digitaldoor-site"    # 付け替えた後の確かめ(省けば確かめない)
  restart = "systemctl restart digitaldoor-site"    # 付け替えた後に回す命令(省けば回さない)
  notify = "logger -t digitaldoor-update"           # 自動で戻したとき、文を標準入力に渡す命令
  block_on_incompatible = false
  [components]                           # このサーバーの部品のバージョン(互換表と照らす)
  matter-controller = "1.4"

当てる順: 表の署名 → 表の通し番号 → 包みの署名と中身の SHA-256 → 段と止めと緊急 → 互換 → 控え → 展開 →
付け替え → 再起動 → 確かめ → (失敗なら)戻して知らせる。どこで拒んでも、置き場の current は変わらない。

usage: digitalkey update [-h] [--config CONFIG]
                         {keygen,pack,index,status,apply,rollback,notice,fleet,log} ...

更新の配布(署名、段階配布、自動で戻す)

positional arguments:
  {keygen,pack,index,status,apply,rollback,notice,fleet,log}
    keygen              製造者の署名の鍵を作る(権限 600、上書きしない)
    pack                置き場のファイルを、署名つきの包みにする
    index               配布の表(index.json と index.sig)を作る
    status              今のバージョンとサポート期限
    apply               確かめてから当てる。失敗したら直前のバージョンへ自動で戻す
    rollback            直前のバージョンへ戻す
    notice              管理会社へ送る事前の通知の文を出す
    fleet               status --json を集めた置き場から、サポートの切れたサーバーを並べる
    log                 更新の記録と、その連鎖の検査

options:
  -h, --help            show this help message and exit
  --config CONFIG

設定は update.toml。段は 開発 / 試験導入棟 / 全棟。詳しくはこのモジュールの説明

実演の道具

実演の道具 — デジタル錠の開け閉めは簡単で、鍵の管理は難しいことを、場面ごとに見せる。

    python tools/jitsuen.py --fake kantan                          # 疑似の Sesame で見せる
    python tools/jitsuen.py --lock sesame:<機器の UUID> check      # 実機の Sesame に届くか確かめる
    python tools/jitsuen.py --fake --yes all                       # Enter を待たずに全部

場面(手順は docs/使い方.md の「実演」):
  check    錠に届くことを確かめる(施錠の命令を一つ送る)
  kantan   開け閉めは部品の仕事。錠のドライバで直接、次に疑似の扉のインターフェース(POST /unlock)から開け閉めする
  sono-hi  その日の鍵。扉はネットワークが無くても、発行者の署名と期間を自分で確かめる
  kigen    止めたつもり。ネットワークの届かない扉では、台帳で失効しても、期限が来るまで開く
  keiro    経路が散る。同じ人の鍵を一つの経路で失効しても、別の経路で開く
  more     発行者の鍵が漏れたら。信頼の一覧を変えられるのは管理者の鍵だけ
  kiroku   記録で確かめる。記録の連鎖を検べ、一字の書き換えを見つける
  all      check を除く全部を順に(kantan から kiroku まで)

しくみ: 疑似の扉(digitaldoor_controller の Controller と HTTP のインターフェース)を同じプロセスの中で開き、接点に
digitalkey.contacts.LockDriverContacts を差す。錠は --fake の疑似の Sesame か、--lock の錠のドライバ
(digitalkey.locks の登録簿。`sesame:<UUID>` は BLE の実機)。一つの場面は一つの手順ずつ進み、Enter で次へ行く
(--yes なら待たない)。場面ごとに一時の置き場(扉の記録、鍵、台帳)を作り直し、終わったら消すので、どの場面からでも
何度でも始められる。時計は扉の時計を POST /time で進める。実時間は待たない。

結果は短い日本語で出す(「開きました」「拒みました: 期限の外」)。拒む理由の言葉は扉コントローラ仕様書 5.2a の言葉そのまま。
錠に届かないときは、例外を見せずに「Sesame に届きません。電源と Bluetooth を確かめてください」と出して止まる。
実機の Sesame の鍵(sesame-keys.json)は読まない。ここで作る鍵は一時の置き場の中だけで、終われば消える。

Sesame のアプリ

Sesame の鍵 — CANDY HOUSE の Sesame(SesameOS3。Sesame 5 / 6 / 6 Pro)を、Bluetooth で直接動かす画面(Flet)。

PC でもスマートフォンでも同じ画面です。複数の Sesame の鍵を持ち、選んで開け閉めし、鍵を家族などに対面で渡せます。

  digitalkey sesame app            PC の画面(BLE のアダプタが要る)
  digitalkey sesame app --web      画面をブラウザで開く(Bluetooth はこの PC のまま)
  digitalkey sesame app --fake     疑似の Sesame で試す(実機も Bluetooth も使わない。鍵は sesame-keys-fake.json)
  flet build apk / flet build ipa  スマートフォンのアプリに組む(drivers/digitalkey-sesame で)

【これは画面の歯止めで、鍵の守りではありません】
Sesame の錠が知っている鍵は 32 桁の一つだけで、錠の側では人を分けられません。以下の役の分け方は、このアプリの画面の
中の約束です。32 桁を持つ人が別の道具(このリポジトリの命令行や公開の SDK)を使えば、歯止めは通ります。防げるのは、
受け取った人がこのアプリで鍵をさらにコピーして広げることです。一人を本当に止めるには、Sesame をリセットして登録し直し、
残る人に渡し直します。

役 — 鍵ごとに「管理者」か「利用者」を持ちます。一台の端末で、ある Sesame は管理者、別の Sesame は利用者、ということがあります。
  管理者   その端末で登録した鍵、または管理者として渡された鍵。今までのバージョンで登録した鍵(役の欄が無い物)も管理者で引き継ぎます
  利用者   利用者として渡された鍵。管理者コードが無い鍵は利用者で入り、あとから管理者には上がりません

利用者の画面(最初の画面。全員)
  鍵のある Sesame     鍵のある Sesame を並べる(役つき)。押すと近くから探してつなぎ、ログインして、施錠と解錠、電池、角度を出す
  解錠、施錠、トグル    「自分の呼び名」が Sesame の履歴に残る(名乗りなので、偽ることもできる)
  鍵を削除            この端末の鍵だけを消す。ほかの端末にコピーがあれば、そちらは使える
  鍵を受け取る        渡す人の画面の QR を、このアプリのカメラで読む。読み取りが使えないときは、32 桁を打ち込む道がある(利用者として入る)

管理者の画面(管理者の鍵がある端末だけ。最初の Sesame を登録するために、鍵が一つも無い端末でも開く。利用者の鍵しか無い端末では開かない)
  探す、登録          近くの Sesame を並べる。未登録の Sesame とだけ登録でき、鍵を作ってこの端末に保存する(管理者になる)
  渡す                管理者の鍵の Sesame を、利用者として、または管理者として渡す。相手の呼び名を入れ、QR を出す。
                     PC にコピーするときは「32 桁を見せる」(管理者としてコピーするときは管理者コードも出る。`digitalkey sesame import` に入れる)
  渡した相手の控え      誰に、いつ、どの役で、どの道で渡したか。この端末から渡した分だけ。追記だけで、消さない。リセット前の行は印が付く
  リセットと渡し直し    止めたい人がいるときの順序の案内
  端末の認証           管理者の画面を開くときに、端末の認証(生体認証か PIN)を求めるか。管理者が選ぶ(スマートフォンのアプリ)

渡し方は対面で、アプリからアプリへ直接です。ネットワーク(LINE、メール、クラウド)を通しません。渡す側の画面に QR を出し(60 秒で自動で閉じて
消える)、受け取る側が自分のアプリのカメラで読みます。端末のふつうのカメラアプリや、画像を読み取るサービスは通しません。周りの人に
撮られない所で行います。受け取る側は、その Sesame にログインできたときだけ保存します(R-CM-13)。QR の中身は、バージョン、UUID、32 桁、役、
管理者コード(管理者のときだけ)で、人の名前は入れません(handoff.py)。

鍵について: 鍵は登録のときに錠と端末の間で作る 16 バイト(32 桁の 16 進)で、Sesame が知っている鍵はこの一つだけです。コピーした物は
全部同じ鍵で、持つ物は誰でもこの Sesame を開けられます。鍵はログ欄、logging、例外の文、標準出力に出しません(R-CM-12)。人が見られるのは、
管理者が確かめた上で行う「渡す」の表示だけで、閉じると消えます。

鍵の置き場: PC では ~/.config/digitalkey/sesame-keys.json(権限 600。`digitalkey sesame` の命令と共用)。スマートフォンでは端末の
安全な保管庫(Android Keystore、iOS のキーチェーン。Flet の SecureStorage)です。今までのバージョンは SharedPreferences に置いていたので、
新しいバージョンを初めて起動したときに保管庫へ移します(コピーする → 読み戻して一致を確かめる → 元を消す。途中で失敗したら元は消さず、今までの置き場のまま
動く)。移す前に、念のため鍵を PC にコピーしておくことを勧めます。保管庫はエラーのときに中身を消す設定(reset_on_error)を無効にしています。
鍵は端末のバックアップで別の端末へ移りません(Android はアプリのデータをバックアップから外し、iOS はこの端末だけの扱いにします)。

組み方、入れ方、困ったときは skills/sesame-app/SKILL.md にあります。

digitalkey sesame(命令行)

Command-line client (no GUI) for CANDY HOUSE Sesame 5/6/6 Pro over BLE via bleak.

  digitalkey sesame scan [--seconds 5]
  digitalkey sesame register <uuid-or-address> [--name 玄関]
  digitalkey sesame import <uuid-or-address> [--name 玄関]
  digitalkey sesame status|lock|unlock|toggle|version <uuid-or-address>
  digitalkey sesame keys
  digitalkey sesame --fake <command> ...      疑似の Sesame(実機も Bluetooth も使わない。鍵は sesame-keys-fake.json)
Keys are stored in ~/.config/digitalkey/sesame-keys.json (or $SESAME_KEYSTORE).

鍵(16 バイト、32 桁の 16 進)は、この Sesame を開けられる唯一の物です。ログにも標準出力にも出しません。
別の端末(スマートフォンのアプリ)の鍵をコピーするときは、アプリの管理者の画面の「渡す」で「32 桁を見せる」を選んで 32 桁を出し、
このコンピューターで `import` します(鍵は引数で受けず、伏せた入力で受けます)。

鍵には役があります。このコンピューターで `register` した鍵は管理者、`import` した鍵は、管理者コードを添えたときだけ管理者で、
コードが無ければ利用者です(コードは、スマートフォンの管理者が「管理者として渡す」ときに画面に出す 8 桁です)。
役はアプリの画面の歯止めで、鍵の守りではありません。この命令行は、役にかかわらず鍵があれば Sesame を動かせます。

digitalkey sesame import

usage: digitalkey sesame import [-h] [--name NAME] target

別の端末(スマートフォンのアプリ)で登録した Sesame の鍵を、このコンピューターの鍵の置き場に取り込む。

流れ: 伏せた入力で 32 桁を受ける → 伏せた入力で管理者コードを受ける(任意。空の Enter なら利用者) → 形を確かめる
(32 桁の 16 進でなければ断る。コードは入力があれば 16 進 8 桁) → Sesame を探して BLE でつなぐ → コードが鍵と合うか確かめる
(合わなければ断る) → その鍵でログインできることを確かめる → できたときだけ、機種(広告の model_id)と役と一緒に保存する。
コードが合ったときだけ管理者で、コードが無ければ利用者として入る。
ログインできなければ何も保存しない。確かめは必ず行う(間違った鍵を置くと、使う場面で初めて動かないと分かるため。飛ばす選択肢は置かない)。
保存した鍵は鍵の置き場の権限(600)で守られる。鍵を画面にもログにも出さない。

positional arguments:
  target       Sesame の UUID か BLE の住所

options:
  -h, --help   show this help message and exit
  --name NAME  鍵の置き場に残す名前(既定は機種名)

鍵はコマンドの引数に書かせません(シェルの履歴に残るため)。実行すると 32 桁を尋ね、続けて管理者コードを尋ねます。区切りの空白とハイフンは読み飛ばすので、アプリの「32 桁を見せる」の表示をそのまま貼れます。管理者コードは、管理者としてコピーするときだけ入れます(利用者なら空の Enter)。

# 権限の申請の雛形(下書き、2026-10-20)

## 位置づけ

社員が、どこからでも、どの PC やスマートフォンからでも、扉や部屋やシステムの権限を申請し、情報システム部門が確かめて出し、止め、記録する。その流れを、自分の機械で動かして学ぶための雛形です。

- 教材です。各社はこれを参考にして、自社の事情に合わせて独自に開発します。写して直してかまいません(コードは AGPL-3.0-or-later、文書は CC BY 4.0)。
- 問題や足りない所に気づいたら、Issues で指摘してください。流れは [つなぐ.md](つなぐ.md) にあります。
- 扉が無くても始められます。扉は、同じ権限で後からつなぎます。
- 社内では「サイバー攻撃対策の訓練」として始められます。今の仕組みを置き換えるのではなく、隣に置いて動かします。

考え方は、解説 17「デジタルキーは管理者が自分で持つ」と、解説 18「デジタルドアはサイバー攻撃対策そのもの」に書いています。

## 1. 流れ

```
社員の端末(どこからでも)
  │ サインイン(Apple ID か Google ID。ID は本人の物)
  ▼
受付(開く所): 申請を受けて並べるだけ。鍵は作れない
  ▲ 取りに行く(受付から閉じる所へは口を開けない)
  │
承認と発行(閉じる所): 管理者が確かめ、発行者の鍵で署名して出す。台帳に追記
  │
  ▼
結果と知らせ(受付を通して本人へ) / 扉(後からつなぐ)
```

本人は、自分の権限の中身(対象、期間)と、自分の権限が使われた記録を、いつでも見られます。

## 2. 申請の種類と扱い

| 申請 | 出す人 | 扱い |
|---|---|---|
| 権限の申請(扉、部屋、システム、期間) | 社員 | 管理者が確かめて承認し、発行する |
| 来客と業者の、その日だけの権限 | 受け入れる社員 | 管理者が承認する。期間が過ぎれば自動で切れる |
| 権限の延長 | 社員 | 管理者が承認する |
| 端末の紛失 | 本人(別の端末からでも出せる) | 届けた時点で、その人の全経路を自動で止める。出し直しは窓口で本人を確かめてから |
| 異動、退職、契約の終了 | 人事 | 退職と終了は届けの日に自動で止める。異動の新しい権限は承認してから |
| 自分の権限と記録の確認 | 本人 | 申請ではなく、いつでも見られる |
| 建物の信号への権限(火災報知の連動) | 管理者、設備の担当 | 信号に扉を開ける権限を与えることになるので、人の権限と同じく審査して承認する(扉コントローラ仕様書 R-CT-05)。審査の記録を台帳に残し、見直す |

扱いの原則は次の三つです。

1. 止めるのは自動でよい。間違えても「開かない」側に倒れるだけだからです。止めたことは記録に残します。
2. 出すのは人が確かめる。外の知らせから自動で出すと、偽の知らせ一つで権限が出ます(R-EB-37)。
3. 一番上の操作は人の手に残す。管理者の鍵の操作、発行者の鍵の作り直し、扉の前での戻し(R-AC-17)は自動にしません。

## 3. 開く所と閉じる所

| 部分 | 開くか閉じるか | 持つ物 | 置き場の例 |
|---|---|---|---|
| サインイン | 開く | 本人の ID(Apple、Google)とのつなぎ。PocketBase | 外から届く機械(Cloudflare の後ろ) |
| 受付 | 開く | 申請の並び。鍵は持たない | 同じく外から届く機械 |
| 承認と発行 | 閉じる | 発行者の鍵(取り出せない所、R-AC-11)、台帳、承認の画面 | 社内の別の機械。外に口を開けない(R-AC-13) |
| 記録の写し | 閉じる | 署名つきの記録の伝票 | さらに別の機械(R-RS-12) |

承認と発行の機械は、受付から申請を取りに行くだけです。受付が外から破られても、作れるのは承認されていない申請だけで、権限は出ません。

## 4. 本人と端末

- サインインは、PocketBase を通して Apple ID か Google ID で行います。ID は本人の物で、勤め先が変わっても本人が持ち歩きます。権限は会社の物で、会社の台帳が持ちます。
- 最初の一回は、窓口で本人を確かめてから登録します(対面かビデオ通話)。ここを遠隔だけにすると、成りすましの入口になります。
- 端末の鍵(パスキー)を登録し、申請に署名させる形は、部品が揃ってから足します(7 章)。資格情報を端末の鍵に結ぶ R-AC-21 と同じ考え方です。
- Entra ID とはつなぎません。退職の照らし合わせに、アカウントの一覧を読むだけにします(R-EB-34、37)。

## 5. 台帳と様式

台帳は digitalkey の追記だけの台帳(伝票、前の伝票のハッシュの連鎖)を使います。様式(adoc)が正で、画面と検査は様式から作ります。今ある様式(`鍵_発行`、`鍵_失効`、`本人確認` など)に、次の様式を足します(項目は下書き)。

| 様式 | 主な項目 | 書ける |
|---|---|---|
| 権限_申請 | 主体、対象(扉、部屋、システム)、開始、終了、理由 | 社員(本人の分)、受け入れる社員(来客と業者の分) |
| 権限_承認 | 申請の伝票、判断(承認、却下)、理由 | 管理者 |
| 権限_発行 | 主体、対象、経路、開始、終了、根拠(承認の伝票) | 管理者 |
| 権限_失効 | 主体、対象(全部を含む)、理由、根拠 | 管理者、自動(紛失、退職、統計の基準) |
| 端末_紛失 | 主体、届けた端末、届けた時刻 | 本人 |
| 人事_届け | 主体、種別(入社、異動、退職、契約の終了)、効力の日 | 人事 |

失効は伝票を消さず、失効の伝票で打ち消します。訂正も新しい伝票で書きます。

## 6. 使う部品

雛形は部品の写しを持たず、部品を立てて呼びます。立て方は各部品のスキル(`SKILL.md`)を AI に読ませて進めます。

| 部品 | 置き場 | 雛形での役 |
|---|---|---|
| ninshou(PocketBase、Apple と Google のサインイン) | aiai-tools | 入口 |
| kaiin(登録、版を付けた同意、本人が自分の記録を見て消せる) | aiai-tools | 社員の登録と、本人が確かめる画面 |
| honnin(本人確認) | aiai-tools | 最初の登録と、紛失のあとの出し直し |
| tsuuchi(取引のメールと Web Push) | aiai-tools | 承認、失効、期限切れの知らせ |
| tenken(毎朝の知らせ) | aiai-tools | 日課の自動化 |
| kagi(錠をつなぐ) | aiai-tools | 扉を後からつなぐとき |
| 台帳と様式 | digitaldoor の `digitalkey/entrance` | 申請、承認、発行、失効の伝票 |
| 署名つきの資格情報、鍵を作る命令 | digitaldoor の `controller/`(`keygen`、`issue`、`trust-change`) | 発行者の鍵と、扉に渡す資格情報 |

## 7. 足りない部品

aiai-tools の側に部品として足してもらう物(ほかの雛形からも使えるように、雛形の側で作り込まない):

1. 社員の端末のパスキー(WebAuthn)の登録と、申請への署名。PocketBase の OAuth2 の上に重ねる形か、別の小さな部品か
2. 受付の並び。開く所の機械に置き、閉じる所の機械が取りに行く口を持つ。受付は鍵を持たない
3. 人事の届けの取り込み。書式を決めた表を読み、伝票にする前に検査する

digitaldoor の側で足す物:

1. 一人の全経路を一度に止める(R-AC-15)
2. 失効が効くまでの最長の時間の表示(R-AC-14)
3. 資格情報を端末の鍵に結ぶ(R-AC-21)と、端末が運ぶ失効の一覧(R-AC-22)。扉コントローラ仕様書の 5.2a を先に直す
4. 統計の基準を超えた主体を、段階(注意、確かめる、停止)をつけて止める

## 8. 満たす要求と確かめ方

| 要求 | 雛形での形 |
|---|---|
| R-AC-10、R-AC-20 | 業者にも受付にも発行者の鍵を置かない |
| R-AC-11、R-AC-13 | 発行者の鍵は閉じる所の機械の、取り出せない所に置く |
| R-AC-14、R-AC-15 | 最長の時間を表示し、一人の全経路を一度に止める |
| R-AC-16 | 出来事ごとの手順を、申請の種類と同じ並びで持つ |
| R-AC-17 | 管理者の鍵をなくした想定の戻しを、練習に入れる |
| R-AC-19 | 管理者の機械だけで、発行と失効ができる |
| R-EB-33〜37 | 発行者は情報システム部門。人事の届けが正。退職の日に両方を止めて照らす。紛失の窓口を外に任せない。台帳は全員を載せる |
| R-RS-11、R-RS-12 | 閉じる所の機械で動く物を見張り、記録を外へ出す |

確かめ方は、各要求の「確かめ方」(要求仕様)をそのまま使います。テストは、確かめる要求の番号を docstring の先頭に書きます。

## 9. 社内での実地の練習

| 役 | 誰が | すること |
|---|---|---|
| 管理者 | 情報システム部門 | 発行者の鍵と台帳を持ち、承認、発行、失効、出来事の手当て |
| 届けを出す人 | 人事 | 入社、異動、退職の届け |
| 使う人 | 希望する社員、受け入れる社員 | 申請する。自分の権限と記録を確かめる |
| 扉と錠(つなぐとき) | 設備の担当 | 据付、電池、点検。内側からはいつでも機械で開けられるようにする |

期間は三か月ほどで、毎月一つずつ出来事を起こします。

1. 一か月目: 申請、承認、発行と、毎日の照らし合わせ
2. 二か月目: 退職と紛失を、同じ日に止める
3. 三か月目: 発行者の鍵の作り直し、網を切って戻す、管理者の鍵をなくした想定

終わりに、8 章の要求を記録で一つずつ確かめます。この記録が、その会社が「自社で運用している」証拠になります(R-RS-16)。

社員の名前と申請の記録は個人情報です。練習の目的を社員に知らせ、台帳には社員番号か仮の名前を使い、練習が終わったら消す期限を決めておきます。

## 10. 進め方

1. この仕様を直して固める
2. テストを、仕様から別のセッションで作る
3. 実装を作る。コードは `digitalkey/shinsei/` に置く
4. 7 章の部品の依頼を aiai-tools に渡す

## 11. 決まっていないこと

- 端末のパスキーと申請への署名を、どの部品で持つか(7 章の 1)
- 受付を置く機械と、閉じる所の機械が取りに行く間隔
- 統計の基準(何を、どれだけ超えたら、どの段階か)
- 画面を Flet の Web にするか、アプリにするか。どの端末のブラウザからでも使える Web を先にする案

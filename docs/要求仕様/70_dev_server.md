## 1. 何を渡すか

| 成果物 | 内容 |
| --- | --- |
| インストールイメージ | x86 ミニ PC に書き込む Linux イメージ、または既存 Linux への 1 コマンド導入スクリプト。標準版と同一 |
| 開発モード | 疑似デバイス（錠、センサー、カメラ）を起動し、実機なしで管理ソフトの全 API を動かす。`--fake` の拡張 |
| 公開 API | 管理ソフトの REST + WebSocket。OpenAPI 定義付き。ローカルのみ、クラウド前提なし |
| サンプルアプリ | 現行の Flet アプリ（PC / Android）を API クライアントとして整理したもの |
| 推奨ハード一覧 | 第 3 章。段階的に買い足せる |
| 適合試験手順 | 玄関プロファイル未決事項 8。自前 BLE と別添 B の適合を確認するスクリプト |

## 2. ミニサーバーの構成

```
 ミニ PC（x86、内蔵 BT、Ethernet）
 ├ OS: Linux（標準版と同一イメージ）
 ├ 管理ソフト（応用側）: 予約、資格情報の発行・失効、監査ログ、権限判定、Web UI、REST + WebSocket
 ├ Matter コントローラ + Thread ボーダールーター（USB Thread ドングル）  … 錠・センサー・照明
 ├ ONVIF / RTSP クライアント、録画、動体検知                                   … カメラ
 ├ 自前 BLE スタック（sesame_ble）                                              … 玄関の系統 1、既存 Sesame
 ├ 開発モード: 疑似デバイス群（第 4 章）
 └ 任意: Cloudflare Tunnel 等での外部公開（標準版の運用と同じ）
```

- 親 PC / 子 PC の構成（玄関が親、部屋や区画が子）は同じイメージの役割設定で切り替える
- クラウドは不要。開発者の LAN 内で完結する

## 3. 推奨ハード（段階的）

| 段階 | 追加するもの | できること |
| --- | --- | --- |
| 0 | 手持ちの Linux PC（VM 可） | 開発モードのみ。API、UI、予約、監査ログ、権限の開発と自動テスト |
| 1 | x86 ミニ PC（内蔵 BT） | 標準版と同じ実行環境。既存 Sesame 6 Pro を自前 BLE で実機制御 |
| 2 | USB Thread ドングル + Matter Door Lock 認証品 1 台 | Matter 経由の錠制御、Aliro 鍵登録（対応錠の場合） |
| 3 | PoE カメラ（ONVIF / RTSP）1 台 + PoE スイッチ | 録画、動体検知、玄関の通知 |
| 4 | Matter 対応の開閉センサー、スマートプラグ | 半ドア検知、威嚇ライト等の自動化 |
| 5 | ドア製造者の試作扉（玄関プロファイル） | 系統 1 / 系統 2 の受入れ試験 |

段階 0 で開発の大半ができるようにするのが本書の要点。実機は検証のために後から足す。

## 4. 開発モードの疑似デバイス

| 疑似デバイス | 実装の方向 | 再現する振る舞い |
| --- | --- | --- |
| 疑似 Sesame | 既存の `sesame_ble/fake.py` | 登録、ログイン、施解錠、状態 publish、履歴タグ |
| 疑似 Matter 錠 | Matter SDK の仮想デバイス（all-clusters-app 相当）を Door Lock として起動し、同じ LAN 上でコミッショニング | 施解錠、ユーザー・資格情報・スケジュール、イベント、Aliro 属性 |
| 疑似 玄関錠（系統 1 + 2） | 別添 A の自前 BLE と別添 B の UART を模した Python プロセス | 3 軸の物理状態、半ドア、停電、系統の抜き差し、監査ログの連鎖と署名 |
| 疑似 センサー・プラグ | Matter 仮想デバイス | 開閉、人感、On/Off |
| 疑似 カメラ | RTSP サーバーでループ動画を配信（動体あり／なしの素材） | 録画、動体検知、通知 |
| 故障注入 | 各疑似デバイスに「応答しない」「途中で切断」「時刻がずれる」を指示できる | 再接続、失効の伝播、時刻未同期時の拒否（コア R-AC-02） |

要求は次のとおり。

| ID | 要求 |
| --- | --- |
| R-DV-01 | 開発モードは実機が 1 台もない環境で起動し、公開 API の全エンドポイントが疑似デバイス相手に動作**すること** |
| R-DV-02 | 疑似デバイスは実機と同じプロトコル経路（Matter コミッショニング、BLE GATT または同等のトランスポート抽象）を通る**こと**。管理ソフト側に「疑似専用の分岐」を作らない |
| R-DV-03 | 故障注入を API から指示でき、自動テストで使える**こと** |
| R-DV-04 | 疑似デバイスの鍵・状態は実機用の保存領域と分離**すること**（既存の `devices-fake.json` と同じ方針） |
| R-DV-05 | 開発モードで作った監査ログは「疑似」フラグ付きで、実運用のログと混ざらない**こと** |

## 5. 公開 API

| ID | 要求 |
| --- | --- |
| R-DV-10 | 管理ソフトの機能はすべて REST + WebSocket の公開 API 経由で提供し、Web UI もその API のクライアントで**あること**（UI だけができることを作らない） |
| R-DV-11 | OpenAPI 定義を配布し、API の後方互換をバージョンで管理**すること** |
| R-DV-12 | 認証はローカルのトークンで行い、権限モデル（コア第 7 章）の主体に対応づける**こと** |
| R-DV-13 | 主要なリソース：錠（論理状態、物理状態、操作）、資格情報（発行・失効・期限・時間帯）、予約、監査ログ（差分取得、連鎖検証結果、書き出し）、デバイス（発見、コミッショニング、状態）、カメラ（ストリーム URL、イベント）、設備設定 |
| R-DV-14 | イベント（状態変化、認証結果、警報）は WebSocket で配信し、再接続時に取りこぼしを連番で補える**こと** |

## 6. 導入と運用（標準版と同じ）

| ID | 要求 |
| --- | --- |
| R-DV-20 | 導入はイメージ書き込みまたは 1 コマンドで完了し、初回起動時のウィザードで役割（親 / 子 / 開発）と機器登録を行える**こと** |
| R-DV-21 | 更新、バックアップ、復元、ログ書き出しはワンボタンで**あること**（応用側の保守を前提にしない） |
| R-DV-22 | 標準版は MIT で公開し、README に免責（無保証、無サポート、防火区画は対象外、金庫・書庫・薬品庫は扱わない）を明記**すること**。製品名に Sesame / CANDY HOUSE を含めない |

### 6.1 修正パッチの配布（売りながら直し続けるための要求）

販売後も継続開発は止まらない。規格（Matter、Aliro、ONVIF）の改定と依存ライブラリの更新により、バグがなくても更新は避けられない。したがって導入済みの全ミニサーバーに修正パッチを安全に当てられることを製品の要件とする。

| ID | 要求 |
| --- | --- |
| R-DV-30 | 更新は署名付きパッケージとして配布し、ミニサーバーは署名を検証してから適用**すること** |
| R-DV-31 | 更新は「開発 → 試験導入棟 → 全棟」の段階配布ができ、段階ごとに止められる**こと** |
| R-DV-32 | 更新に失敗したら直前の版へ自動で戻り、戻ったことを通知**すること**。更新前に自動バックアップを取る（R-DV-21） |
| R-DV-33 | インターネット接続のない現場では、施工業者が持ち込む媒体（USB 等）または管理会社の PC 経由で同じ署名付きパッケージを適用できる**こと** |
| R-DV-34 | 更新中も錠の解錠判定（錠内）と集合玄関の運用は止まらない**こと**。ミニサーバーの停止時間は 5 分以内を目標とする |
| R-DV-35 | 公開 API は後方互換を保ち、互換を切る場合は 1 つ前の版を最低 12 か月併存させる**こと**（クライアントと研修教材の追従期間） |
| R-DV-36 | 管理ソフトの版、Matter コントローラの版、対応する錠・コントローラのファーム版の**互換表**を配布し、ミニサーバーが自分の構成と照合して非互換を警告**すること** |
| R-DV-37 | 錠・コントローラのファーム更新（供給元が Matter OTA 等で配布）は、管理ソフトから配布の可否と時期を制御でき、系統ごとに独立して行える**こと**（コア R-EL-23） |
| R-DV-38 | 更新の内容（版、対象、理由：不具合・規格改定・セキュリティ）を管理会社に事前通知し、適用結果を監査ログの保守記録に残す**こと**（95 R-MT-04） |
| R-DV-39 | セキュリティ修正は通常の段階配布を短縮して当てられる緊急経路を持ち、その判断と記録を残す**こと** |
| R-DV-40 | 各版のサポート期間を定め（現行版と 1 つ前の版）、期限切れの版で稼働するミニサーバーを一覧で把握できる**こと** |

## 7. 開発の順序

1. 公開 API と OpenAPI 定義を先に固める（ドア事業の要求書の中核）。現行 Flet アプリをそのクライアントに作り替える
2. 開発モード：疑似 Sesame（既存）→ 疑似玄関錠（安全 MCU のファーム、2 系統、半ドア、停電）→ 疑似 Matter 錠 → 疑似カメラ → 故障注入（ラッチ担当）
3. 性能試験の自動化と、認証品のリーダーからラッチを動かす実演環境（ラッチ担当）
4. 段階 1〜3 のハードで実機検証（Sesame、Matter 錠、カメラ、試作ラッチ）と適合試験スクリプト
5. ドア事業の管理ソフトの要求書一式と、管理部門が作る販売の要求書との事前協議（ドア事業担当）
6. 商品化が決まった時点で、管理部門が要求書から管理ソフト・インストールイメージ・ウィザードを実装し、開発モードと CI で検証する

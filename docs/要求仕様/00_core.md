## 1. 目的と範囲


本書は、施解錠管理ソフトウェア（以下「管理ソフト」）から制御できる電子錠のうち、**用途によらず共通な部分**の要求を定める。

- 用語と、管理ソフトが扱う論理状態
- 電子部（安全 MCU、通信モジュールの系統 1 / 系統 2、その独立性）
- 通信・認証（自前 BLE、Matter、Aliro、有線）
- 監査ログ（何を、どう改ざん不能に残すか）
- 権限モデル（誰が、いつ、どの条件で開けられるか）
- 責任分界の原則
- ユニバーサルデザイン（誰でも開けられ、誰も閉じ込めない。全プロファイル共通）
- 安全のためのセンサー（扉が人を傷つけない、閉じ込めない、危険のときに逃げられる。全プロファイル共通）

対象外は次のとおり。

- 管理ソフト本体（Web UI、予約、履歴表示）。これは応用側が提供する
- 機構、通線、非常手段、認定・法規、受入れ試験。これらは用途で大きく変わるので各プロファイルが定める
- 金庫、書庫、薬品庫などの保管設備。今回の対象外とする

## 2. 用語

| 用語 | 定義 |
| --- | --- |
| 掛かり（latched） | 扉が閉まり、ラッチが受け（ストライク）に噛んだ状態。バネによる。電気不要 |
| 施錠（secured） | 外ハンドルがラッチから切り離され、外から開けられない状態 |
| 解錠（released） | 外ハンドルがラッチを引ける状態。時間制限付きを基本とする |
| 通行（passage） | 施錠しない設定。オートロックを切った状態 |
| 半ドア | 1 段目のラッチのみ噛んだ状態 |
| 安全 MCU | 扉本体側の、無線を持たない小さな制御器。モーター駆動とセンサーだけを担当 |
| 通信モジュール | 差し替え可能な無線・認証の基板。BLE、Thread（Matter）、NFC（Aliro）、セキュアエレメント |
| ゲートウェイ | 管理ソフトが動くミニ PC。玄関に 1 台、部屋や区画ごとに子を置く構成もある |
| 系統 1 / 系統 2 | 独立した通信モジュール。系統 1 はローカル経路（NFC + BLE、Aliro と自前 BLE）、系統 2 はネットワーク経路（Thread + Ethernet、Matter）。第 4 章 |
| 主体（principal） | 錠に対して操作を行う者または物。管理者、運用者、利用者、保守者、システム。第 7 章 |
| 資格情報（credential） | 主体が錠に提示する鍵。管理者鍵、期限付きゲスト鍵、Aliro ウォレット鍵、カード・暗証番号、有線接点。第 7 章 |
| 監査ログ | 錠内に不揮発で残る操作・事象の記録。連番とハッシュ連鎖で改ざんを検出できる。第 6 章 |

## 3. 状態モデル（抽象）

物理的な状態（扉の位置、ラッチ、ボルト、レバー）は用途で異なるので各プロファイルが定義する。管理ソフトは全用途を次の**論理状態**で扱う。プロファイルは物理状態から論理状態への対応を必ず定めること。

| 論理状態 | 意味 | 典型的な遷移のきっかけ |
| --- | --- | --- |
| `secured` | 外からは権限なしに開けられない | 閉扉・閉蓋による自動成立、または明示の施錠操作 |
| `released(n秒)` | n 秒だけ開けられる | 権限のある解錠操作 |
| `passage` | 施錠しない設定 | 管理者の設定操作。許可されないプロファイルがある |
| `ajar` | 閉まり切っていない（半ドア、半開き） | センサー |
| `fault` | 機構または電子部の異常 | 自己診断 |

| ID | 要求 |
| --- | --- |
| R-EL-30 | 錠は自身の物理状態を独立したセンサーで検出し、管理ソフトへ論理状態と物理状態の両方を報告**すること** |
| R-EL-31 | 状態変化から 200 ms 以内に安全 MCU が通信モジュールへ通知**すること** |
| R-EL-32 | 電源投入・復電時に、センサーから現在の状態を再構成して報告**すること**（記憶に頼らない） |

## 4. 電子部要求

### 4.1 構成

電子部は「本体側の安全 MCU」と「独立した 2 系統の通信モジュール」で構成する。

```
[扉本体・共通]
 安全 MCU ── モーター駆動 / センサー / 電源監視 / ウォッチドッグ
    │ ポート 1                     │ ポート 2
[系統 1: ローカル]              [系統 2: ネットワーク]
 NFC リーダー + BLE              Thread + Ethernet
 セキュアエレメント              セキュアエレメント
 Aliro / 自前 BLE                Matter Door Lock
```

**玄関錠は独立した 2 系統を持つ**（応用側の提案）。理由は次のとおり。

- 系統 1 は「その場で鍵を提示して開ける」経路で、ファームは小さく変化が少ない。系統 2 はネットワークスタックを含み、規格更新・脆弱性対応で更新頻度が高い。更新や不具合の影響を互いに及ぼさない
- 片方のモジュールを交換・停止しても、もう片方だけで玄関の運用が続く
- Aliro と Matter の認証を系統ごとに取れるので、片方の再認証がもう片方に波及しない

独立の定義(R-EL-20〜24)を満たさない「1 枚の基板に 2 つの無線を載せた構成」は 2 系統とみなさない。安全 MCU は 1 つとし、二重化しない(無線を持たない単純な制御器で、最終的な冗長は機械的脱出で担保する)。

### 4.2 安全 MCU

### 4.7 更新と起動(2026-10-20)

扉の中で動く物が本物であることを、更新のときと起動のたびに、扉が自分で確かめる。R-EL-06 の「失敗時は旧バージョンで起動」の旧バージョンは、R-EL-27 の下限より新しいバージョンに限る。

| ID | 要求 |
| --- | --- |
| R-EL-25 | ファームウェアの更新は製造者の署名つきで配り、各モジュールと安全 MCU は、署名と完全性を確かめてから入れる**こと**。確かめられない更新は入れず、今のバージョンで動き続ける。更新の署名の鍵の扱いは R-RS-03 による |
| R-EL-26 | 起動のたびに、ファームウェアが署名どおりであることを、書き換えられない起動の仕組み(ROM の起動コードかセキュアエレメント)で確かめる**こと**。確かめられないときは、その系統を止め、安全 MCU は安全側の挙動(火災と停電の設定、内側からの機械の解錠)を保つ |
| R-EL-27 | 脆弱性を直したバージョンより古いバージョンへ戻す更新を拒む**こと**。バージョンの下限は、セキュアエレメントか書き換えられない所に持つ。下限を上げたことは監査ログに残す |
| R-EL-28 | 更新と起動の検査の結果(バージョン、成否、拒んだ理由)を監査ログに残す**こと** |

足した要求の理由と確かめ方（2026-10-20）

- R-EL-25〜28
  - 出どころ：使う人の言葉「デジタルドアを実現するためには、サイバー攻撃に対応できないとだめですね」（2026-10-20）。それまでの更新の要求は R-EL-06 の「望ましい」だけで、署名と起動の検査が書かれていなかった。EU のサイバーレジリエンス法（規則 2024/2847）の附属書 I は、脆弱性を更新で直せること、プログラムと設定を許されない書き換えから守り、壊れたことを知らせることを求める。ETSI EN 303 645 の 5.3-10 は、ネットワークから届く更新の真正性と完全性を機器が確かめることを必須とする。NIST SP 800-193 は、ファームウェアの守り、検出、復旧を三つの柱とする
  - 理由：扉の中の物が差し替えられれば、判断も記録も攻撃者の物になる。署名を確かめずに入れる更新は、それ自体が入口になる。古いバージョンに戻させれば、直した脆弱性が戻る
  - 確かめ方：R-EL-25 は、署名の無い更新と、一字を書き換えた更新を渡し、入れずに今のバージョンで動き続けることを確かめる。R-EL-26 は、書き換えた像で起動し、その系統が止まり、安全 MCU が火災と停電の設定どおりに振る舞い、内側から機械で開くことを実機で確かめる。R-EL-27 は、下限より古い正しく署名されたバージョンを渡し、拒むことを確かめる。R-EL-28 は、各試験の後に監査ログに結果が残ることを確かめる

### 4.8 更新の入れ方、置き場、環境（2026-11-11）

| ID | 要求 |
| --- | --- |
| R-EL-34 | 更新を入れる時期と方法（その都度の承認、決めた時間帯に自動で入れる、など）は、管理者が設定で決める**こと**。製造者と保守者は、管理者の設定に無い入れ方で更新を入れられない。設定と、入れたことは監査ログに残す（R-EL-28） |
| R-EL-35 | 安全 MCU は、動かす錠と同じ側（錠が扉にあれば扉の中、枠にあれば枠の側の壁か、枠に付く筐体）に置く**こと**。鍵を持つ部分（各モジュールのセキュアエレメント）と安全 MCU は、扉を閉めた状態で、室内の側からだけ届く所に置く。外の側の面から届く所に置くのは、アンテナ、表示、操作の部品までとし、それらを外しても、壊しても、その配線に電圧をかけても、解錠しない（R-EL-03） |
| R-EL-36 | 製造者は、扉の中と枠の側に置く電子部（安全 MCU、通信モジュール、予備の電源）について、動く温度の範囲と、開閉の衝撃に耐える回数を、試験の方法と一緒に申告する**こと**。日の当たる扉の中の温度と、建具の開閉の回数（01_interface R-IF-10 と同じ数え方）を前提にする |

足した要求の理由と確かめ方（2026-11-11）

- R-EL-34
  - 出どころ：使う人の指示「置き場と「製造者が発行者」の案は要求仕様と食い違います。要求仕様も検証しろ」「その形で直して」（2026-11-11）と、その検証。R-EL-25 は、製造者の署名があれば更新が入る形で、入れるかを管理者が決める要求が無かった。7.1 の保守者は「ファーム更新」ができる
  - 理由：更新の署名の鍵を持つ者は、扉を開けるバージョンを配れる。入れるかを管理者が決めなければ、R-AC-06（製造者のバックドア鍵を持たない）が更新の道で破れる。配ったバージョンを公開の一覧と照らせること（R-RS-19）と合わせて、製造者の鍵一つで扉が開く形を閉じる
  - 確かめ方：管理者の設定を「その都度の承認」にした疑似の扉に、正しく署名された更新を渡し、承認の前は入らず、承認の後に入り、どちらも記録に残ることを確かめる。「決めた時間帯に自動」の設定では、時間帯の外で入らないことを確かめる
- R-EL-35、R-EL-36
  - 出どころ：同じ検証。置き場は、扉コントローラ仕様書の冒頭の一文にしか書かれておらず、扉の中の熱、開閉の衝撃、外から壊されることに答える番号が無かった
  - 理由：外の側の面は、誰でも手が届く。そこに鍵か、解錠を決める部分があれば、壊して取り出すか、線に電圧をかけて開けられる。安全 MCU を錠と同じ側に置くのは、扉と枠の間の線が切れても、火災と停電の挙動と内側からの解錠を保つためである。温度と衝撃は、扉の構造と向きで変わるので、数字は製造者が測って申告する
  - 確かめ方：R-EL-35 は、実機で、外の側の面の部品を外した状態と、その配線に電圧をかけた状態で、解錠しないことを確かめる。扉と枠の間の線を抜いた状態で、火災と停電の設定どおりに振る舞い、内側から開くことを確かめる（R-RS-07 と同じ試験）。R-EL-36 は、申告と試験の成績があることを確かめる

## 5. 通信・認証

### 5.1 対応する規格

| 規格 | 用途 | 系統 | 要求 |
| --- | --- | --- | --- |
| 自前 BLE プロトコル（別添 A） | ゲートウェイからの直接制御。Thread 環境がなくても動く | **すること** |
| Matter Door Lock（Thread） | ゲートウェイ（Matter コントローラ）、Apple Home / Google Home 等 | **すること** |
| Aliro（NFC 必須、BLE） | スマホ・ウォッチのウォレット鍵によるタップ解錠。ウォレットを通さないアプリの鍵も、同じリーダーで受ける（R-CM-17） | **すること** |
| 有線 UART / RS-485（多芯線経由） | ゲートウェイとの有線制御、無線の予備 | **すること** |

### 5.2 要求

| ID | 要求 |

| R-CM-05 | 錠内の履歴は最低 100 件を不揮発に保持し、ゲートウェイが後から取得できる**こと** |
| R-CM-06 | 登録（機密鍵の共有）は物理的な操作（本体ボタン等）を伴わないと開始できない**こと** |

| R-CM-12 | 錠との間で共有した機密鍵（登録で得た 16 バイト）と、管理者のコードは、ログ、画面の記録欄、例外の文、標準出力に出さない**こと**。人が見られるのは、持ち主が確かめた上で行う鍵の渡す・書き出しの画面だけとし、閉じたら消える |
| R-CM-13 | 機密鍵を別のコンピューターへコピーするときは、コピー先でその錠にログインできることを確かめてから保存する**こと**。ログインできなければ保存しない。鍵はコマンドの引数で受けない（シェルの履歴に残るため） |
| R-CM-14 | 機密鍵ごとに役（管理者、利用者）を持ち、探す・登録・渡す・渡した相手の控え・リセットと渡し直しの案内を持つ管理者の画面は、管理者の鍵がある端末（最初の登録のために鍵が一つも無い端末を含む）だけで開く**こと**。利用者の鍵しか無い端末では開かない。管理者として渡すときだけ管理者のコードを付け、コードの無い鍵は利用者として入って管理者には上がらない。役の欄が無い今までの鍵は管理者で引き継ぐ。画面と文書に「これは画面の歯止めで、鍵の守りではない」と書く。管理者の画面を開くときに端末の認証（生体認証か PIN）を求めるかは、管理者が選べる |
| R-CM-15 | 鍵の渡し方は、対面で、アプリからアプリへ直接とし、ネットワーク（メッセージ、メール、クラウド）を通さない**こと**。渡す側が画面に出し（時間を限り、閉じたら消す）、受け取る側が自分のアプリのカメラで読む。読み取りが使えないときは 32 桁を打ち込む道を残し、利用者として入る。受け取る側は R-CM-13 のとおり、ログインできたときだけ保存する。渡した相手の控え（誰に、いつ、どの役で）は、管理者の端末に追記だけで残す |
| R-CM-16 | スマートフォンの鍵は、端末の安全な保管庫に置く**こと**。保管庫のエラーで中身を消す設定は無効にし、鍵が端末のバックアップで別の端末へ移らない設定にする。今までの保存領域からの移し替えは、コピーする → 読み戻して一致を確かめる → 元を消す、の順で行い、途中のどこで失敗しても鍵を失わない |
| R-CM-17 | 応用側は、ウォレット（Apple、Google）を通さずに、管理者の発行者の鍵で出した資格情報を持ち、扉にかざして出せるアプリを提供する**こと**。Android では NFC と BLE、iPhone では BLE で出す。iPhone の NFC は、アプリを出す者が Apple の NFC & SE Platform の契約を結んだときに足す。アプリは、扉の製造者ごとに分けず、公開の仕様に沿う扉ならどれでも開けられる一つの物とし、仕様と参照実装を公開する。資格情報は端末の鍵に結び、端末の安全な保管庫に置く（R-AC-21、R-CM-16） |

足した要求の理由と確かめ方（2026-10-20）

- R-CM-12、R-CM-13
  - 出どころ：実演で、スマートフォンのアプリに入っている Sesame の鍵を、持ち運ぶ miniPC にコピーする作業（運営者の依頼、2026-10-20）。実装を読むと、登録のログ（アプリのログ欄と logging）と、`digitalkey sesame register` と `keys` の標準出力に、鍵が 32 桁のまま出ていた
  - 理由：32 桁を持つ人は、その錠を開けられる。ログは画面共有、貼り付け、報告に写りやすく、シェルの履歴やターミナルの記録にも残る。コピーした先で鍵が違うと、実演の場で初めて動かないと分かる
  - 確かめ方：R-CM-12 は、疑似の Sesame で登録、ログイン、書き出し、取り込みを通し、ログの全行と標準出力と標準エラーに鍵が現れないことを確かめる。R-CM-13 は、書き出した 32 桁を取り込めること、間違った鍵と形の違う入力では何も保存されないことを確かめる

足した要求の理由と確かめ方（2026-10-21）

- R-CM-14、R-CM-15
  - 出どころ：運営者の依頼（2026-10-21）「キーを送ってもらって取得した人は、その鍵の管理者画面が開かないようにする」「渡し方は対面で、アプリ間で直接」
  - 理由：Sesame の錠が知っている鍵は 32 桁の一つだけで、錠の側では人を分けられない。家族などに鍵を渡すとき、受け取った人がこのアプリで鍵をさらにコピーして広げないようにするには、受け取った鍵の側で管理者の画面（探す、登録、渡す）を閉じておく必要がある。送った先のサービス（LINE、メール、クラウド）にも鍵のコピーが残るので、渡すのは対面で、アプリからアプリへ直接とする。ただし、これは画面の歯止めで、鍵の守りではない。32 桁を持つ人が別の道具を使えば通る。一人を本当に止めるには、Sesame をリセットして登録し直し、残る人に渡し直す。そのために、渡した相手の控えを管理者の端末に残す
  - 確かめ方：疑似の Sesame と疑似の保存領域で、管理者の鍵・利用者の鍵・鍵なしの端末ごとに管理者の画面が開くか開かないかを確かめる。管理者として渡した QR からは管理者、コードの無い QR・合わないコード・32 桁の打ち込みからは利用者で入ること、今までの鍵（役の欄なし）が管理者になることを確かめる。QR を実際に読み戻して中身を確かめ、閉じたら消えること、控えが追記だけであること、ログと標準出力に 32 桁とコードが現れないことを確かめる。受け取る側はログインできた場合しか保存しないことを確かめる
- R-CM-16
  - 出どころ：運営者の依頼（2026-10-21）。実機のスマートフォンに本物の鍵が入ったまま、アプリを新しいバージョンに上書きする
  - 理由：今までのバージョンは、鍵をアプリの保存領域（SharedPreferences）に平文で置いていた。端末の保管庫（Android Keystore、iOS のキーチェーン）に移すと守りが強くなるが、保管庫は既定ではエラーのときに中身を全部消す設定で、バックアップから別の端末へ復元されると読めなくなる。移し替えの途中で失敗して鍵を失うと、Sesame をリセットして登録し直すしかなくなる。画面の歯止めの前提として、鍵そのものを失わないことが一番大事になる
  - 確かめ方：疑似の保存領域で、移し替えが成功する場合、保管庫が読めない・書けない・書いたはずが読めない・読み戻しが食い違う場合、元が消せない場合、途中で落ちた次の起動の場合に、元の鍵が残り、アプリが今までの置き場のまま動くことを確かめる。実機での保管庫・バックアップの効き方は、組んだアプリで確かめる

足した要求の理由と確かめ方（2026-11-11、ウォレットを通さないアプリ）

- R-CM-17
  - 出どころ：使う人の言葉「独自のAliro用アプリが必要になるでしょう。homeアプリでは対応できない」「一般住宅や事務所用は。どうしたらいいか公開しろ」（2026-11-11）
  - 理由：ホームアプリ（Apple のホーム、Google Home）は一つの家のための物で、会社が社員に鍵を出し、退職の日に止める使い方には合わない。ウォレットに入館の鍵を入れる制度では、制度に入った会社が鍵をスマートフォンに入れ、扉の管理者は鍵を出す側に入っていない。管理者が自分で出した鍵をスマートフォンで使うには、ウォレットを通さないアプリが要る。扉の製造者ごとにアプリが分かれると、製造者が替わるたびに使う人が入れ直すことになり、製造者がアプリをやめたときに開かなくなる（R-RS-05）。iPhone は、Apple との契約が無ければ、アプリから NFC でかざして出せないので、BLE で始める
  - 確かめ方：管理者の発行者の鍵で出した資格情報を、アプリに入れ、Android では NFC と BLE、iPhone では BLE で、疑似の扉と実機が開くことを確かめる。別の端末にコピーした資格情報では開かないこと（R-AC-21）を確かめる。同じアプリで、別の製造者の、仕様に沿う扉が開くことを確かめる

### 5.4 ルーターとネットワーク

扉、ミニサーバー、リーダー、カメラは、全部ルーターの後ろにある。ルーターを強くすることと、ルーターを信用しない作りにすることの、両方を求める。考え方は解説「ルーターは全部の前にある」に書く。

| ID | 要求 |
| --- | --- |
| R-NW-01 | 扉の系統の通信（錠、扉のコントローラ、ミニサーバー、リーダー、発行者の間）は、ルーターが乗っ取られても読まれず書き換えられないよう、端から端まで暗号化し、相手を確かめる**こと**。ルーターとネットワークを信用の前提にしない |
| R-NW-02 | 扉の系統は、来客用の Wi-Fi、家電、ほかのカメラなどと、ネットワークの上で別の区画に分ける**こと**。外部のネットワークから扉の系統へ直接入るアクセス経路（ポートの転送）を開けない |
| R-NW-03 | 扉の系統をつなぐルーターは、メーカーが更新を出す期間を公開している物を選び、更新を当て続け、期間が終わる前に替える**こと**。初めに決められたパスワードのまま使わない |
| R-NW-04 | ルーターの外部からのアクセス経路（遠隔の管理、VPN、DDNS、外からの管理画面、回線の事業者の遠隔の設定）は、要るときだけ有効にする**こと**。点検のたびに、見覚えのない設定とアカウントが無いかを確かめ、記録に残す |
| R-NW-05 | ルーターが止まっても、乗っ取られても、扉の判断と記録は扉の側で続く**こと**（R-CM-03）。ルーターの持ち主（更新、確認、交換をする人）を決める |

足した要求の理由と確かめ方（2026-10-18）

- R-NW-01〜05
  - 出どころ：使う人の問い「ルータ問題は書いていますか」（2026-10-18）。米国の司法省は、更新の止まった家庭と小さな事業所の数百台のルーターが、国家が背後にいるとされる集団に乗っ取られ、重要インフラへの攻撃の中継に使われていたとして、2023年12月に裁判所の許可を得てボットネットを止めたと発表した（2024年1月31日）。米国の FBI は、更新の止まったルーターが乗っ取られ、犯罪の中継として売られていると注意を出し、遠隔の管理を切ることを勧めた（2025年5月7日）。警視庁は、家庭用ルーターが外から操作されて VPN などの機能を有効にされ、攻撃に使われていたとして、見覚えのない設定の確認を求めた（2023年3月）。2016年11月には、通信事業者がルーターを遠隔で管理するインターフェースが狙われ、ドイツで約90万の回線がつながらなくなった（報道）。日本の端末設備等規則は 2020年4月から、新しく認証を受ける機器にアクセス制御、初期パスワードの変更を促す機能、更新の機能を求めているが、すでにある機器には届かない
  - 理由：ルーターは、扉とサーバーをコンピューターごとに分けても、その全部の前にある。更新の期間が扉より短く、終わっても使われ続け、持ち主が決まっていないことが多い。回線の事業者の遠隔の管理は、事業者が全部の利用者のルーターに常の権限を持つ形で、コア R-AC-10 と同じ危険がある
  - 確かめ方：R-NW-01 は、疑似の機器で、通り道の機器が中身を読めず、書き換えると拒まれることを確かめる。R-NW-02 は、据付の点検で、ネットワークの区画と、外部からのアクセス経路が開いていないことを確かめる。R-NW-03、04 は、点検の記録（ルーターの型番、更新の期間、当てた更新、外部からのアクセス経路の設定）で確かめる。R-NW-05 は、疑似の機器でルーターを止めても扉の判断と記録が続くことを確かめ、持ち主の名簿を点検で確かめる

## 6. 監査ログ

監査ログは保守記録と法定の入退室記録の基礎になる。玄関・室内・集合住宅で同じ仕組みを使うので、コアで定める。

### 6.1 記録する事象

| 種別 | 内容 |
| --- | --- |
| 操作 | 解錠、施錠、通行モード設定、一時解錠の開始と終了 |
| 物理 | 開扉、閉扉、半ドア、掛かり、ボルト位置の変化 |
| 認証 | 成功、拒否（理由付き：期限外、時間帯外、無効化済み、二人同時の不成立、強要コード） |
| 資格情報 | 登録、更新、失効、鍵の受け渡し（Aliro 鍵登録を含む） |
| 設定 | オートロック設定、時間帯、二人同時の要否、遅延時間、ファーム更新の開始と結果、バージョンの下限の引き上げ（R-EL-27） |
| 非常 | 非常手段の使用（給電パッド、機械キー、手動リリース、有線接点）、火災信号、停電と復電 |
| 異常 | 機構異常、通信モジュールの脱落・故障、時刻の大幅なずれ、ログ領域の上書き発生、起動の検査の失敗と署名の合わない更新・下限より古いバージョンの拒否（R-EL-25〜28） |
| 時刻 | 時刻同期（旧時刻と新時刻を両方残す） |

### 6.2 1 件の記録の内容

| 項目 | 内容 |
| --- | --- |
| 連番 | 錠ごとに単調増加。欠番は検出できること |
| 錠の時刻 | 錠内時計。同期前の記録は「未同期」フラグ付き |
| 事象種別と結果 | 上表の種別、成功・拒否、拒否理由 |
| 主体 | 資格情報の識別子（仮名化された ID）と、経路（系統 1 / 系統 2 / 有線 / 機械キー） |
| 前レコードのハッシュ | ハッシュ連鎖。先頭は錠の固有鍵から導出 |
| 署名 | セキュアエレメントの鍵による署名。毎件署名するか一定件数ごとにまとめて署名するかはプロファイルが定める |

### 6.3 要求

| ID | 要求 |
| --- | --- |
| R-LG-01 | 6.1 の事象を錠内の不揮発領域に記録**すること**。停電・電池交換で失われない**こと** |
| R-LG-02 | 保持件数は最低 100 件。プロファイルで引き上げてよい |
| R-LG-03 | 各記録は連番とハッシュ連鎖を持ち、改ざん・削除・挿入をゲートウェイ側で検出できる**こと** |
| R-LG-04 | 署名はセキュアエレメント内の鍵で行い、鍵はエクスポートできない**こと** |
| R-LG-05 | ゲートウェイは連番を指定して差分取得し、取得済みを確認応答**すること**。錠は確認応答のない記録を優先して保持し、上書きが起きたときは「上書き件数」を記録に残す**こと** |
| R-LG-06 | 錠内の記録は錠自身の操作では消去できない**こと**。工場出荷リセットでも監査ログは残す、または消去そのものを最終記録として署名付きで残す**こと** |
| R-LG-07 | 主体は仮名化 ID で記録し、人物との対応表はゲートウェイ側だけが持つ**こと** |
| R-LG-08 | ゲートウェイは取得した記録の連鎖を検証し、検証結果付きで書き出せる（CSV / JSON）**こと**。保存期間は設備の設定とする |
| R-LG-09 | 非常手段の使用は、センサーで検出できるものは自動で、できないものは管理ソフトの手動記録で残せる**こと** |

## 7. 権限モデル

### 7.1 主体

| 主体 | 例 | 典型的な権限 |
| --- | --- | --- |
| 管理者 | 施設オーナー、設備管理者 | 全操作、資格情報の登録・失効、設定変更 |
| 運用者 | 現場スタッフ、清掃、フロント | 解錠、時間帯内の通行モード、非常手段の使用 |
| 利用者 | 予約者、テナント、居住者、一時的な入館者 | 期限・時間帯内の解錠 |
| 保守者 | 設置業者、製造者のサービス | ファーム更新（入れ方は管理者の設定による。R-EL-34）、診断、設定。解錠は管理者の承認が要る |
| システム | ゲートウェイの自動処理 | 予約に基づく資格情報の発行・失効、自動施錠 |

### 7.2 資格情報の属性

| 属性 | 内容 |
| --- | --- |
| 有効期間 | 開始・終了の日時。錠が自身の時計で判定する（オフラインでも有効期限が効く） |
| 時間帯 | 曜日と時刻の範囲。複数可 |
| 回数 | 使用回数の上限（1 回限りの受け渡し用） |
| 範囲 | 対象の錠、または錠のグループ |
| 能力 | 解錠、施錠、通行モード設定、設定変更、監査ログ取得、資格情報の登録 |
| 二人同時 | この資格情報が「N 人のうちの 1 人」としてのみ有効か |

### 7.3 仕組み

| 仕組み | 内容 | 必須とするプロファイル |
| --- | --- | --- |
| 錠内での期限判定 | ゲートウェイ不通でも期限切れの鍵を拒否する | 全部 |
| 即時失効 | ゲートウェイからの失効指示を錠が受け取り次第、以後を拒否する | 全部 |
| 二人同時（N of M） | 定めた秒数以内に N 人の有効な資格情報が提示されて初めて解錠する | 緊急開錠の手順。他は任意 |
| 開扉遅延 | 認証成功から解錠まで設定した時間待ち、その間に取り消せる | 任意 |
| 強要コード | 通常どおり解錠しつつ、ゲートウェイへ無音の警報を送る | 任意 |
| 開放時間の上限 | 解錠または開扉が設定時間を超えたら警報し記録する | 任意 |
| 承認つき解錠 | 利用者の要求に対して管理者が承認してから解錠する。承認はゲートウェイ側で行い、錠は承認済みの一時資格情報だけを見る | 任意（管理ソフトの機能） |

### 7.4 要求

| ID | 要求 |
| --- | --- |
| R-AC-01 | 資格情報の有効期間・時間帯・回数・範囲・能力を錠内で保持し、錠自身が判定**すること** |
| R-AC-02 | 期限判定は錠の時計で行い、時計が未同期のときは期限付き資格情報を拒否する（管理者鍵は除く）**こと** |
| R-AC-03 | 失効はゲートウェイからの指示で即時に、ゲートウェイ不通時は有効期限で必ず効く**こと** |
| R-AC-04 | 二人同時、開扉遅延、強要コード、開放時間上限を錠内の機能として実装**すること**。有効にするかはプロファイルと設備の設定で決める |
| R-AC-05 | 資格情報の登録は、管理者鍵による認証済みセッション、または物理操作を伴う登録モードでのみ可能で**あること** |
| R-AC-06 | 保守者の解錠は、管理者が発行した一時資格情報を経由**すること**。製造者のバックドア鍵を持たない**こと** |
| R-AC-07 | 権限の判定と実行はすべて監査ログに残す**こと**（第 6 章） |
| R-AC-08 | 管理ソフトの UI から、プロファイルが禁止する設定（例：防火区画の扉の施錠固定）を作れない**こと** |
| R-AC-09 | 一つの発行者の鍵が届く扉は、その発行者が管理する扉に限る**こと**。業者や管理会社が複数の顧客の発行を引き受けるときも、顧客ごとに別の発行者の鍵とし、一つの鍵が漏れても他の顧客の扉に届かない形にする |
| R-AC-10 | 業者と連携先（クラウドのサービス、管理会社、保守者）に、扉を開ける常の権限を持たせない**こと**。遠隔の解錠は一回ごとに、その扉の発行者が出した一時の資格情報か承認（7.3 承認つき解錠）を、錠が自身で確かめて行う。業者のサービスが止まっても、止められても、錠に登録済みの資格情報で開けられる |
| R-AC-11 | 発行者の秘密鍵は、取り出せない場所（セキュアエレメント、HSM）に置く**こと**。他人と同じサーバーを共有する環境（共有の VPS、他の顧客と同じホストの上の仮想マシン）に、秘密鍵を取り出せる形で置かない |
| R-AC-12 | 錠とリーダーが信頼する発行者（公開鍵）の追加、削除、変更は、管理者の認証済みの操作だけで行い、前と新しい値を監査ログに残す**こと**（種別：設定） |
| R-AC-13 | 発行者の秘密鍵と、扉の判断と記録を担うサーバー（ミニサーバー、事業所サーバー）は、外部のネットワークに向いたサービス（ウェブ、予約や外部との連携）と同じサーバー、同じ仮想化の基盤に置かず、役割ごとに分けたサーバーに置く**こと**。一台が止まっても、ほかの扉の判断は続く。台数が増える分、同じ形の予備のサーバーと、イメージから一つの手順で戻す復元の手順を持つ |
| R-AC-14 | 扉ごと、資格情報の役ごとに、ネットワークが届かないときに失効が効くまでの最長の時間（資格情報の最長の有効期間）を決め、管理ソフトに表示する**こと**。失効の通知を最後に受け取ってから決めた時間を過ぎた扉は、その時間より長い期限の資格情報を拒む設定を選べる。製造者は、設定できる範囲を申告する |
| R-AC-15 | 台帳は、一人の主体に結びついた全経路の資格情報（スマートフォンの鍵、カード、暗証番号、後付け錠のアプリ、貸し出した機械の鍵）を一覧にし、一度の操作で全部を失効できる**こと**。機械の鍵は回収の記録を残す |
| R-AC-16 | 運営者は、出来事ごとに、何を失効し、何を作り直し、誰が確かめるかの手順を持つ**こと**。出来事は、端末の紛失、退去と退職、管理者の交代、建物の持ち主の交代、発行者の鍵の漏れとする。持ち主が替わるときは、発行者の鍵と信頼する発行者の一覧を作り直す |
| R-AC-17 | 管理者の鍵をなくしたときは、扉の前での物理の操作（R-AC-05 の登録モード）と本人の確かめで、信頼する発行者の一覧を作り直せる**こと**。この操作は遠隔ではできず、監査ログに残る |
| R-AC-18 | スマートフォンのウォレット（Apple、Google）に入れる鍵は、発行者の一つとして扱い、発行と失効を管理者の台帳から行い、台帳に記録する**こと**。ウォレットの会社のサービスが止まっても、ほかの経路（カード、暗証番号、機械の鍵）で開けられる |
| R-AC-19 | 鍵の発行の道具（台帳、発行、失効、出来事ごとの手順）は、管理者が自分のコンピューターで動かせる形で提供する**こと**。発行者の鍵と台帳を、道具を作った業者のクラウドに置かなくてよい |
| R-AC-20 | ウォレットへの載せ方を担う業者（Aliro の資格情報をウォレットに届ける業者を含む）は、発行者の秘密鍵を持たない**こと**。資格情報（Aliro では Access Document）は、管理者が自分のコンピューターか、鍵を取り出せない所（R-AC-11）で署名し、業者はそれを運ぶだけとする。リーダーと扉が信じる発行者の鍵（Aliro では IssuerKey_PubK か、その CA の証明書）は、管理者の鍵の操作でだけ入れ替える（R-AC-12） |
| R-AC-21 | 資格情報は、持ち主の端末の鍵に結ぶ**こと**。扉は、毎回違う問いかけへの、その端末の鍵の署名を確かめる。資格情報のコピーを送り直されても開かない（Aliro では Access Credential の鍵の対と、Access Document に入る公開鍵） |
| R-AC-22 | ネットワークの届かない扉は、利用者の端末が運んできた、発行者の署名つきの失効の一覧を受けて、以後の判定に使える**こと**（Aliro の Revocation Document と同じ形）。古い一覧で新しい一覧を戻せない（Aliro の ValidityIteration と同じ考え方） |
| R-AC-23 | 据付のときに、管理者の鍵とは別に、予備の管理者の鍵を作り、秘密の部分は封をして扉の持ち主に渡す**こと**。管理者の鍵の入れ直し（R-AC-17）は、室内の側の物理の操作と、予備の管理者の鍵の署名の両方がそろったときだけ受ける。R-AC-17 の「本人の確かめ」は、この予備の鍵で行う。工場出荷状態へのリセット（R-CM-07）も、同じ条件で受ける。予備もなくしたときは、管理者の公開鍵と信頼する発行者の一覧を持つモジュールを、新しい個体に替える（R-EL-10）。製造者と、施工と保守の人は、予備の鍵のコピーを持たない |
| R-AC-24 | 扉を Matter の錠として登録した先（Fabric）は、管理者のインターフェースの一つとして扱う**こと**。コミッショニングウィンドウ（機器が登録を受け付ける状態）を開ける操作は、管理者の鍵の操作か、室内の側の物理の操作に限る。今の登録先の一覧を管理者が見られ、足したことと外したことを監査ログに残す（種別：設定）。登録先の管理者から、鍵の登録（R-EL-18）と遠隔の解錠を受けるかは、プロファイルと扉の設定で決め、受けない設定の扉では、その経路を閉じる。受ける設定の扉では、登録先から入った鍵を、入れた登録先と一緒に記録し、管理者が一覧にして消せる。持ち主が替わるときは、登録先を全部外す（R-AC-16） |
| R-AC-25 | ウォレットの会社と、ウォレットに鍵を載せる会社の発行者の署名は、資格情報が本物であることの確かめにだけ使う**こと**。扉は、扉の管理者が登録した資格情報（端末の鍵の公開の部分）だけを通す。その会社の署名の鍵が漏れても、管理者が登録していない資格情報では開かない。登録と取り消しは管理者の操作で行い、資格情報をリーダーにかざして登録する形を持つ。その会社の仕組みが止まっていても、登録と取り消しができる。その会社には、誰がどの扉を通れるかの台帳と、出入りの記録を渡さない。出入りの記録は、扉と建物の側に残す（第 6 章） |

### 7.5 足した要求の理由と確かめ方（2026-10-18）

- R-AC-09、R-AC-10
  - 出どころ：使う人の問い「クラウド、VPS、レンタルサーバーを使うのが問題になってきていませんか」と、ConnectWise Cloud Backup（旧 SkyKick）の件。2026年10月15日から17日に、業者のテナントにあるバックアップのアプリの認証情報が悪用され、顧客が承認した権限（メール、OneDrive、SharePoint、Teams）で数百の Microsoft 365 のテナントにサインインされた（Huntress の分析、2026年10月16日公開。ConnectWise はアプリの ID への不正なアクセスを発表し、サービスを止めた）
  - 理由：業者が多くの顧客への常の権限を持つと、業者の鍵一つで全部の顧客に届き、顧客の側では防げない。業者が被害を止める手段はサービスの停止で、扉では多くの建物が同時に開くか、同時に使えなくなる。Aliro のように判定がリーダーの中で完結する方式でも、発行者の秘密鍵を一つの業者が全顧客の分まとめて持てば、同じ形になる
  - 確かめ方：疑似の機器で、発行者 A の鍵で発行者 B の扉が開かないこと。業者のサービスを止めた状態で、登録済みの資格情報で開くこと。業者の資格情報だけで遠隔の解錠を求めると拒まれ、記録に残ること
- R-AC-11
  - 出どころ：CVE-2026-99999（PwnEscape、2026年10月15日公開）。Linux カーネルの IPv4 の処理の不具合で、仮想マシンからホストのメモリを読み書きでき、ホストを乗っ取れる。クラウド、VPS、サンドボックスの事業者が最も危ないとされた（AlmaLinux の告知、2026年10月16日）
  - 理由：共有のサーバーでは、隣の仮想マシンから発行者の秘密鍵が漏れうる。直すのは事業者で、利用者は待つしかない
  - 確かめ方：据付と点検のときに、発行者の秘密鍵の置き場所を申告し、点検の記録に残す（実機の確認）
- R-AC-12
  - 出どころ：Aliro の検討（2026-10-18）。リーダーが信頼する発行者を変えられる者は、その扉の鍵を自由に作れる者と同じ強さを持つ
  - 確かめ方：疑似の機器で、信頼する発行者を変えると、設定の記録に前と新しい値が残ること。管理者の認証の無い変更は拒まれること
- R-AC-13
  - 出どころ：使う人の言葉「サーバーを借りるのも問題ということですよね。できるだけ、自社でも、仮想化を減らして、台数を増やす」（2026-10-18）と、CVE-2026-99999（R-AC-11 と同じ）
  - 理由：危ないのは、外部のネットワークに向いたサービスと鍵や扉の判断を、同じサーバーや同じ仮想化の基盤に同居させることである。外から破られた所から鍵まで届く。役割ごとに分ければ、一台が破られても止まっても、ほかは動き続ける。台数を増やして続けるには、予備と、誰がやっても同じ手順で戻せる復元が要る
  - 確かめ方：据付と点検のときに、サーバーの構成図で、鍵と扉の判断が外向きのサービスと分かれていることを確かめる。疑似の機器で、ミニサーバーを一台止めても、ほかの扉の判断と記録が続くこと。予備のサーバーにイメージから戻す訓練を記録に残す

### 7.6 足した要求の理由と確かめ方（2026-10-20）

- R-AC-14〜19
  - 出どころ：使う人の言葉「デジタルドアの一番の課題は、デジタルキーをどう管理するかでないですか？」「デジタルキーの管理は、受託ではしんどすぎますね。それぞれの管理者が責任をもってやることではないでしょうか？」（2026-10-20）。米国の CISA と FBI の注意喚起 AA23-320A（2023年11月16日）は、大企業と、その IT のヘルプデスクを請け負う会社を狙い、電話でヘルプデスクの担当者に成りすましてパスワードと多要素認証を作り直させる手口を挙げている
  - 理由：鍵の出来事（入居、退去、端末の紛失、掃除の人、持ち主の交代）は毎日その場で起き、本人と事情を一番よく知るのは現場の管理者である。受託の窓口は、離れた所から本人を確かめるので遅く誤りやすく、成りすましの入口になる。一つの受託先に多くの建物の鍵を集めれば、そこが破られたときに全部が開く。ネットワークの届かない扉では失効は有効期限でしか効かないので、本当の守りは有効期限の長さであり、それを扉ごとに決めて見える形にする。同じ人の鍵が経路ごとに散っていると、一つでも漏れれば失効したつもりで開く。管理者が自分でやれるように、道具は管理者のコンピューターで動く形で渡す
  - 確かめ方：R-AC-14 は、疑似の扉で失効の通知を止め、決めた時間を過ぎると長い期限の資格情報が拒まれ、短い物は通ることを確かめる。管理ソフトに最長の時間が表示されることを確かめる。R-AC-15 は、一人に複数の経路の資格情報を出し、一度の失効の後、どの経路でも開かないことを確かめる。R-AC-16 は、出来事ごとの手順書があり、年に一度、端末の紛失と持ち主の交代を想定した訓練を記録に残す。R-AC-17 は、管理者の鍵の無い状態から、扉の前の登録モードで一覧を作り直せること、遠隔からは同じ操作が拒まれること、記録が残ることを確かめる。R-AC-18 は、ウォレットの鍵の発行と失効が台帳に残ること、ウォレットの経路を止めてもほかの経路で開くことを確かめる。R-AC-19 は、道具をネットワークから切り離した管理者のコンピューターで動かし、発行と失効ができることを確かめる

### 7.7 足した要求の理由と確かめ方（2026-10-20、Aliro 1.0 を読んで）

- R-AC-20〜22
  - 出どころ：使う人の言葉「スマホをかざすだけで動くようにするのは、デジタルキーが必要」「このデジタルキーを管理を管理会社にやってもらわないといけない。委託の問題が表面化しているので、もう委託ではできない」（2026-10-20）。Aliro 1.0（CSA 文書 26-42802-001、2026年2月18日）の第 6 章は、Access Manager、Credential Issuer、Reader System Issuer を別の役として定め、同じ者か別の者かは仕様の外とする（6.1）。端末とリーダーへの載せ方と、その後の管理は仕様の外とし、ガイド（CR-31968）は会員の場で公開待ちとしている（6.2）。Access Document は Credential Issuer の秘密鍵（P-256）で署名し、リーダーはその公開鍵か CA の証明書を知っている必要がある（6.5）。端末の Access Credential の鍵の対は端末ごとに一つで、Access Document がその公開鍵を含む（6.4）。ネットワークにつながらないリーダーには、端末が発行者の署名つきの Revocation Document を運ぶ（6.6、7.6）。発行者ごとの ValidityIteration で古い世代を無効にする（7.2.3）
  - 理由：かざすだけの鍵にはウォレットの会社への載せ方が要り、その載せ方を業者に任せると、業者が発行者の鍵まで持つ形に戻りやすい。Aliro の信頼の仕組みは、決める者（発行者）と運ぶ者を分けられる作りで、載せ方は仕様の外にある。だから、分けることを要求として書く。業者が破られても、管理者の署名の無い資格情報は扉が拒む。今の 5.2a の資格情報は持っている人なら誰でも使える形なので、コピーを送り直されると開く。端末の鍵に結べば防げる。ネットワークの届かない扉の失効が有効期限でしか効かない問題（R-AC-14）は、端末が失効の一覧を運ぶ形で縮められる
  - 確かめ方：R-AC-20 は、載せ方を担う業者の仕組みに発行者の秘密鍵が無いこと（署名が管理者のコンピューターか HSM で行われること）を、構成図と署名の記録で確かめる。業者の鍵で署名した資格情報を扉が拒むことを、疑似の扉で確かめる。R-AC-21 は、正しい資格情報のコピーを別の端末から送り直し、問いかけへの署名が合わずに拒まれることを確かめる。R-AC-22 は、ネットワークを切った扉に、失効の一覧を持った端末をかざした後、失効した資格情報が拒まれること、古い世代の一覧で戻せないことを確かめる

### 7.8 足した要求の理由と確かめ方（2026-11-11）

- R-AC-23
  - 出どころ：使う人の指示「置き場と「製造者が発行者」の案は要求仕様と食い違います。要求仕様も検証しろ」「その形で直して」（2026-11-11）と、その検証。R-AC-17 は「物理の操作と本人の確かめ」で入れ直すとしていたが、本人を誰がどう確かめるかが書かれていなかった
  - 理由：物理の操作だけで入れ直せる扉は、室内に居る人を誰でも管理者にする。賃貸では、入居者が貸主の発行者を外せる。確かめを製造者や業者に任せると、製造者が全部の扉の入れ直しを許せる形になり、R-AC-06 と R-AC-10 に反する。確かめの根を、扉の持ち主の手元の物にする。全部なくしたときにモジュールを替えるのは、機械の鍵を全部なくしたときにシリンダーを替えるのと同じで、製造者の合鍵が要らない
  - 確かめ方：疑似の扉で、物理の操作だけ、予備の鍵の署名だけでは入れ直せず、両方がそろうと入れ直せ、記録に残ることを確かめる。引き渡しの受入れ試験で、売り先の管理者が自分で入れ直しを行う（R-RS-18）
- R-AC-24
  - 出どころ：同じ検証と、使う人の言葉「こちらからいうと、扉のコントローラが鍵を持つかどうかです」（2026-11-11）。R-EL-18 は Matter から Aliro の鍵の登録を受ける道を持つが、誰が扉を Matter に登録してよいか、登録先をどう見て、どう外すかが書かれていなかった。R-AC-05（鍵の登録は管理者の鍵の操作か登録モードだけ）と R-AC-12（信頼する発行者を変えるのは管理者の操作だけ）との関係も決まっていなかった
  - 理由：Matter では、錠を登録した者がその錠の管理者になり、鍵を入れ、消せる。登録先を複数にすれば、その数だけ管理者が居る。Matter の SDK の実装では、登録先を外しても、その登録先が入れた鍵は錠に残る。一方で、個人が、取り出せない所に鍵を持てる現実の形は、本人のスマートフォンの保管庫であり、スマートホーム（Matter と Aliro の道）はこれに当たる。だから、閉じるのではなく、誰が開けるかを扉の側で決め、見える形にし、扉ごとに受ける範囲を選べるようにする
  - 確かめ方：疑似の扉で、管理者の鍵の操作も物理の操作も無い状態ではコミッショニングウィンドウが開かないこと。登録先を足す、外すと記録に残り、一覧に出ること。受けない設定の扉が、登録先からの鍵の登録と解錠を拒むこと。登録先を外したあと、その登録先が入れた鍵が一覧に残っていれば、管理者が消せることを確かめる
- R-AC-20 の代わりの案（2026-11-11）
  - 出どころ：同じ検証。Apple の制度（Apple Wallet Access Program）のガイドは、資格情報を届ける者がマスター鍵を握る形を例に挙げており、建物の管理者が自分で署名できるかは書いていない（2026-11-11 に読んだ）
  - 案：ウォレットの会社の制度で、載せ方を担う業者が署名するしか道が無い場合は、その業者の鍵を、建物ごとの別の発行者として、信頼する発行者の一覧に載せる。届く扉を R-AC-09 で限り、管理者が R-AC-12 の操作で外せ、台帳には R-AC-18 の発行者の一つとして記録する。その発行者の署名は、資格情報が本物であることの確かめにだけ使い、通すかは管理者の登録で決める（R-AC-25）。管理者が署名する形を取れるようになったら、そちらへ移す
  - 確かめ方：疑似の扉で、その業者の発行者の鍵が、一覧で許した扉だけに届き、管理者が一覧から外すと、その発行者の資格情報が全部拒まれることを確かめる
- R-AC-25
  - 出どころ：使う人の言葉「認証だけを行うようになるでしょう」「一般住宅や事務所用は。どうしたらいいか公開しろ」（2026-11-11）。Apple のウォレットに入館の鍵を入れる制度（Apple Wallet Access Program）のガイドを読んだ。制度に入った会社が、鍵をスマートフォンに入れ、マスター鍵を持つ。開けるかどうかの判断には、Apple の仕組みとスマートフォンは関わらない、と書かれている
  - 理由：仕事は二つに分けられる。スマートフォンの中の鍵が本物で、コピーではないことを確かめられるようにする仕事（認証）と、その鍵をどの扉にいつ通すかを決める仕事（権限）である。Aliro 1.0 も、資格を与える者（Access Manager）と、資格の文書に署名する者（Credential Issuer）を別の役割として定めている（7.7）。ただし Aliro では、発行者が署名した文書がそのまま通してよい印になるので、分けるだけでは、その会社の署名一つで扉が開く。多くの扉が一つの会社につながるほど、その会社が攻められたときの被害が大きくなる。扉が、管理者の登録した資格情報だけを通せば、その会社の署名の鍵が漏れても扉は開かず、鍵を出す、止めるは、管理者の手に残る（R-AC-10）
  - 確かめ方：疑似の扉で、その会社の発行者の鍵で正しく署名した、登録していない資格情報を出し、拒まれることを確かめる。登録した資格情報が通り、取り消したあとは拒まれることを確かめる。その会社の仕組みを止めた状態で、かざして登録でき、取り消せることを確かめる

足した要求の理由と確かめ方（2026-10-18）

- R-RS-01〜06
  - 出どころ：使う人の言葉「ドアの製造メーカーでも、デジタルドアを製造する以上は自社で管理できる人間を育てないといけない。民泊でもおなじ」（2026-10-18）。EU のサイバーレジリエンス法（規則 2024/2847）は、利用者が脆弱性を知らせる一つの窓口を求め、悪用されている脆弱性の 24 時間以内の早期の届け出を 2026年9月11日から適用している（全体の適用は 2027年12月11日）。英国の PSTI 法は 2024年4月29日から、脆弱性の連絡先と更新の期間の公開を求めている。業者に預けた鍵と権限の事故（コア 7.5 の R-AC-09、10 の出どころ）と、アプリの提供の終了で物理鍵に戻った例（解説「日本のスマートロックのアプリの現状と課題」）
  - 理由：預けた所は顧客の側で防げず、更新が止まれば扉は物理鍵に戻るか弱いまま残る。法も、窓口と期間と届け出を製造者の責任とし始めた
  - 確かめ方：R-RS-01 は公開されていることを確かめる。R-RS-02〜04 は、手順書、目録、責任者の名簿があることを点検で確かめ、年に一度、鍵の一つを実際に作り直す訓練を記録に残す。R-RS-05 は、アプリを使えない状態で錠に登録した資格情報で開くことを受入れ試験で確かめる。R-RS-06 は、業者のサービスを止めた想定で、暗証番号やカードで開くことを確かめる
- R-RS-07〜10
  - 出どころ：使う人の言葉「AI で、人に残るのは、何を作るかを決めること、出来た物が正しいかを見て判断することと言われてきたけど間違っていた」と、その理由の文（2026-10-18）。AI で作るのが安くなれば作られる物が増え、一つずつを建物に入れて動かす人が要る。攻撃も増え、線を抜く、区画を止める、戻す作業は現場でしかできない。ネットワークが止まれば、外の AI は届かない
  - 理由：残る判断は、画面の上の正しさではなく、その場の物で確かめる判断である。現場で切り離せない作り、その場に無い予備、決まっていない人では、攻撃と事故の手当てができない
  - 確かめ方：R-RS-07 は、受入れ試験で、扉の系統の線を抜き電源を切っても、扉が設定どおりの安全側の挙動を保ち、内側から開くことを確かめる。R-RS-08 は、ネットワークを切った状態で、予備のサーバーにイメージから戻す訓練を記録に残す。R-RS-09 は、人の名簿と連絡の手段を点検で確かめる。R-RS-10 は、手順と教材があり、それを使って育てた記録があることを確かめる

足した要求の理由と確かめ方（2026-10-20）

- R-RS-11〜15
  - 出どころ：使う人の言葉「開発用の言語を絞って監視する。実行可能ファイルを監視する。これは、セキュリティ的に重要だと思いませんか」（2026-10-19）、「一つのバイナリにして、できるだけ最適化する」（2026-10-19）、「デジタルドアを実現するためには、サイバー攻撃に対応できないとだめですね」（2026-10-20）。EU のサイバーレジリエンス法の附属書 I は、攻撃の面を小さくすること、悪用を和らげる仕組みを使うこと、中の動きを記録して監視すること（第 I 部）と、少なくとも直接の依存を含む部品表を作ること（第 II 部）を求める。米国の CISA と FBI の「Product Security Bad Practices」（2.0 版、2025年1月）は、新しい製品群をメモリを安全に扱える言語で作り、既存の製品にはメモリの安全への計画を公表するよう求める。Google は、Android の脆弱性に占めるメモリの扱いの誤りが、2019年の 76% から 2024年の 24% に下がったと書く。Microsoft の Edge の調査（2021年）は、2019年以降の V8 の CVE のおよそ 45% が JIT に関わると書く
  - 理由：入った攻撃者は、何かを実行しないと何もできない。実行してよい物を決めて監視すれば、増えた物が通知になる。入られたコンピューターの上の記録は消されるので、通知は外に出す。同じソースから同じ物が組めなければ、扉に入っている物が本物かを確かめられない。JIT が作る機械語はファイルとして存在せず、一覧と照らせない
  - 確かめ方：R-RS-11 は、一覧に無い実行ファイルを一つ置き、次の照らし合わせで通知が出ること、一時ファイルの置き場に置いた物が実行できないことを確かめる。R-RS-12 は、コンピューターの上の記録を消しても、外に送った記録が残っていることを確かめる。R-RS-13 は、計画が公開されていることを確かめる。R-RS-14 は、公開された手順で手元で組み直し、扉に入っている物と sha256 が一致することを確かめる。R-RS-15 は、扉のコントローラとゲートウェイのプロセスに、書き込めて実行もできるメモリの領域が無いことを確かめる（Linux なら /proc の maps で見る）

足した要求の理由と確かめ方（2026-10-20、売る側の条件）

- R-RS-16〜18
  - 出どころ：使う人の言葉「デジタルドアを販売するとは、デジタルキーを管理することですね」「売った先で管理者を育てないといけないので、自分のところでできないようであれば売ったらいけない」（2026-10-20）。R-RS-01〜06 の出どころ「ドアの製造メーカーでも、デジタルドアを製造する以上は自社で管理できる人間を育てないといけない」（2026-10-18）を、売る側の条件に進めた物
  - 理由：デジタルドアを売るとは、買った側が鍵を管理し続けられる状態を渡すことである。売る側が鍵を管理すれば委託に戻る（R-AC-10、R-AC-20）ので、買った側の管理者を育てるしかない。人に教えられるのは自分でやったことだけで、自社で運用していない売り手は育てられず、運用を誰かに丸投げしたくなる。それが、鍵が業者に集まる始まりになる。鍵を管理できない所に入れたデジタルドアは、機械の鍵より危ない
  - 確かめ方：R-RS-16 は、売り手の自社の建物の扉と台帳、出来事ごとの手順書、鍵の作り直しと切り離しの訓練の記録を見て確かめる。R-RS-17 は、育てる人の名簿と、その人が育てた記録を確かめる。R-RS-18 は、引き渡しの受入れ試験の記録に、売り先の管理者が自分で行った発行、失効、紛失の手当て、管理者の鍵の戻しが残っていることを確かめる

足した要求の理由と確かめ方（2026-11-11、製造者が持つ物）

- R-RS-19、R-RS-20
  - 出どころ：使う人の指示「置き場と「製造者が発行者」の案は要求仕様と食い違います。要求仕様も検証しろ」「その形で直して」（2026-11-11）と、その検証。それまでの要求は、製造者が「持たない」物（扉を開ける鍵）だけを書き、製造者が何を持つかを書いていなかった
  - 理由：扉は数十年使われ、その間に、持ち主は替わり、鍵はなくなり、部品は壊れる。そのとき要るのは、どの扉にどの個体が入っているかの記録と、替えの部品である。これは鍵を持つこととは別で、製造者が持ってよく、持つべき物である。製造者が持つ物を、更新の署名の鍵（R-RS-03）、個体の台帳、交換の部品の三つに限れば、製造者が攻められても扉は開かず、製造者が無くなっても扉は開く。更新は、製造者に残る唯一の「扉の中を変えられる道」なので、配ったバージョンを公開し、誰でも同じバージョンかを確かめられる形にする
  - 確かめ方：R-RS-19 は、公開の一覧があり、扉から読んだバージョンと sha256 が一覧にあることを確かめる。R-RS-20 は、受入れ試験で、扉の製造番号とモジュールの個体の番号が、製造者の台帳と合うことを確かめる。台帳の項目に秘密の部分が無いことを、台帳の定義で確かめる

## 9. ユニバーサルデザイン（全プロファイル共通）

錠は、誰が使っても開けられ、誰も閉じ込めないことが前提である。高齢者、車いす利用者、視覚・聴覚・認知に障害のある人、子ども、けがや荷物で手が使えない人、日本語を読まない人が、玄関・室内・集合住宅のどの扉でも同じように使えることを要求する。機構と設置は製造者と設計者、認証手段とソフトの操作は応用側、運用は施設が担う。

## 10. 安全のためのセンサー（全プロファイル共通）

防犯のためのセンサー（侵入、開閉、カメラ）とは別に、**扉が人を傷つけない・閉じ込めない・危険のときに逃げられる**ためのセンサーを要求する。原則は次の 3 つ。

1. 安全に関わる判定は、ゲートウェイやネットワークに依存せず、錠内（安全 MCU または最小コントローラ）で完結する
2. 安全のための入力（火災信号、感震、挟み込み）は通信モジュールを経由せず、安全 MCU の専用入力に直接入れる（[30_fire_compartment.md](30_fire_compartment.md) 3.4 と同じ）
3. 迷ったら「開く側」「止まる側」に倒す。ただし内側からの機械的な脱出（R-MC-06、R-UD-01）が最終の担保であり、センサーはそれを補うもの

### 10.1 種類

| 分類 | センサー | 何を防ぐか | 錠の振る舞い | 適合の基準 |
| --- | --- | --- | --- | --- |
| 扉の動作による事故 | 扉間の障害物（扉と枠の間に人や物がある） | 自閉装置による挟まれ、施錠中の挟み込み | 障害物がある間は施錠モードへの切替（`secured` 成立）を保留し、半ドアとして報告。自閉装置が電動なら停止 | 扉位置センサー（R-ST-01）と、必要に応じて扉端のタッチセンサー。無電圧接点で安全 MCU へ |
| 同上 | 指はさみ（蝶番側の隙間） | 子ども・高齢者の指の挟まれ | 機構側の対策（蝶番側ガード、隙間を作らない扉形状）。センサーではなく構造で防ぐ | 製造者の設計 |
| 同上 | 閉扉力・閉扉速度 | 自閉装置による衝突・転倒 | R-UD-03 の設定範囲。速度超過を検出できる場合は警報 | 自閉装置の仕様 |
| 閉じ込め・救助 | 在室の長時間無動作（人感 + 時間） | 室内で倒れている、閉じ込められている | 施設の設定時間を超えたら通知。緊急開錠の手順へつなぐ | Matter Occupancy Sensing |
| 同上 | 転倒検知（ミリ波など） | 玄関・室内での転倒 | 通知。錠は解錠側へ倒す設定を持てる（介助者が入れるように） | 機種依存（Matter の機器種別はない）。接点またはゲートウェイ経由 |
| 同上 | 内側からの脱出要求（パニックバー、内側ボタン） | 施錠中に外へ出られない | 機械的に開くのが基本。電気的な内側ボタンを付ける場合も機械脱出を代替しない | 機構（R-MC-06） |
| 環境の危険 | 煙・熱・CO | 火災、不完全燃焼 | 火災信号で扉ごとの設定に従い解錠側へ倒すか保持。通知 | Matter Smoke CO Alarm（補助）。法定設備の信号は無電圧接点で安全 MCU へ |
| 同上 | 感震（地震） | 枠の変形で扉が開かない、施錠したまま救助が入れない | 感震で解錠側へ倒す設定を扉ごとに持てる。内側は常に機械脱出。枠の変形への追従は機構（R-MC-08）と耐震枠 | 感震センサー（接点）。Matter の機器種別はない |
| 同上 | ガス漏れ | 爆発・中毒 | 通知。錠は解錠側へ倒す設定を持てる（換気と避難のため） | 接点。Matter の機器種別はない |
| 同上 | 水漏れ、極端な温湿度 | 漏水、熱中症、凍結 | 通知のみ。錠の振る舞いは変えない | Matter Water Leak / Temperature / Humidity |
| 電子部の安全 | 過電流、過熱、モーター異常、電源低下 | 発火、誤動作 | 駆動を止めて報告。施錠モードは保持。内側は機械脱出 | R-EL-04、05（既存） |

### 10.2 要求

| ID | 要求 |
| --- | --- |
| R-SS-01 | 扉と枠の間に障害物がある状態では `secured` を成立させず、半ドアとして報告**すること**。障害物の検出は扉位置と掛かりのセンサー（R-ST-01）で行い、必要に応じて扉端のタッチセンサーを追加できる**こと** |
| R-SS-02 | 火災信号、感震、ガス漏れなどの安全入力は、安全 MCU の専用の無電圧接点入力に直接入れ、通信モジュール・ゲートウェイ・ネットワークの状態に依存せずに動作**すること** |
| R-SS-03 | 安全入力を受けたときの錠の振る舞い（解錠側へ倒す／施錠を保持する／通知のみ）は扉ごとに設定でき、設定は設計者・消防との確認に従う**こと**。設定の変更は監査ログに残す |
| R-SS-04 | 安全入力で解錠側へ倒した後は、入力が解除され、かつ権限のある人の操作があるまで自動で再施錠しない**こと** |
| R-SS-05 | 在室の長時間無動作と転倒の検知は、施設が有効にした場合に通知し、緊急開錠の手順へつなげられる**こと**。常時の映像・音声を前提にしない |
| R-SS-06 | 指はさみと閉扉力は構造と自閉装置の設定で防ぎ、センサーに頼らない**こと**（製造者の設計、R-UD-03） |
| R-SS-07 | 安全センサーの故障・断線を検出して報告し、故障中は「危険側」に倒さない（誤って施錠を強めない）**こと** |
| R-SS-08 | 安全に関わる事象（安全入力の受信、解錠側への切替、障害物による保留、センサー故障）は監査ログに残す**こと**（第 6 章） |
| R-SS-09 | 安全センサーは電池・バックアップ電源の残量を報告し、残量低下で通知**すること** |

### 10.3 プロファイルごとの重点

| プロファイル | 重点 |
| --- | --- |
| 玄関（個別住宅） | 感震・火災での解錠側設定、家族の転倒・無動作の通知、指はさみ |
| 玄関（集合住宅） | 集合玄関の障害物（ベビーカー、荷物）、火災信号の連動、住戸玄関の感震 |
| 玄関（事業所） | 火災信号と扉ごとの設定、非常口、障害物 |
| 室内扉（業務用） | 在室の無動作、障害物 |
| 室内扉（家庭用） | 子どもの指はさみ、閉じ込め、高齢者の転倒・無動作 |
| 防火区画 | 火災信号の直接入力と再施錠の禁止（R-SS-02、04） |

### 10.4 受入れ試験への追加

| 試験 | 合格条件 |
| --- | --- |
| 扉間に障害物 | `secured` が成立せず半ドアとして報告される |
| 火災信号の模擬入力 | 設定どおり解錠側へ倒れ、入力解除後も自動再施錠しない。ゲートウェイ停止中でも同じ |
| 感震の模擬入力 | 同上 |
| 安全センサーの断線 | 故障が報告され、施錠モードが変わらない |
| 無動作の通知 | 設定時間を超えたら通知される |
## 別添 A：自前 BLE プロトコル仕様（骨子）

現行の管理ソフトは CANDY HOUSE SesameOS3 のプロトコルを実装しており（リポジトリ `sesame_ble/`）、実機で登録・施解錠を確認済み。組込み錠向けの自前プロトコルはこれを土台に、次の方針で定める。詳細は別文書で確定する（未決事項 3）。

### A.1 引き継ぐもの

| 項目 | 内容 |
| --- | --- |
| トランスポート | BLE GATT。Write(no response) 1 本と Notify 1 本。20 byte 分割（1 byte ヘッダ + 19 byte） |
| 広告 | manufacturer data に機種、登録済みフラグ、履歴ありフラグ、デバイス UUID(16) |
| 登録 | ECDH（secp256r1）で 16 byte の機密鍵を共有。本体の物理操作で登録モードに入ったときのみ受け付ける（R-CM-06） |
| ログイン | 接続ごとに錠が 4 byte トークンを発行。`sessionKey = AES-CMAC(secret, token)`。以後 AES-CCM（tag 4 byte、送受別カウンタ） |
| 時刻同期 | ログイン応答で錠の時刻を返し、3 秒以上ずれていれば設定コマンド（R-CM-08） |
| 履歴 | 各コマンドに 20 byte 以内の履歴タグ（誰が操作したか） |

### A.2 組込み錠向けに変える・足すもの

| 項目 | 内容 |
| --- | --- |
| 状態報告 | サムターン角度ではなく、玄関プロファイル第 2 章の 3 軸（扉位置、掛かり、施錠モード）+ 電源状態 + 直近の異常コード |
| コマンド | `secure`（レバーを切り離し側へ）、`release(n秒)`（ポール解放）、`passage`（レバーを結合側へ）、`get_status`、`get_history`、`set_time` |
| 複数鍵 | 管理者鍵（登録で得る）に加え、期限付きのゲスト鍵を錠内に登録・失効できること |
| 常時接続 | ゲートウェイは接続を保持し切断時は自動再接続する。錠側は 1 台のゲートウェイからの常時接続を維持できること |

### A.3 サービス／キャラクタリスティック

固有の 128 bit UUID を採番する（SesameOS3 の `0xFD81` は使わない）。値は別文書で確定。

## 別添 B：安全 MCU ⇔ 通信モジュール UART 仕様（骨子）

| 項目 | 内容 |
| --- | --- |
| 物理 | 3.3 V UART、115200 bps、8N1。加えて `MODULE_PRESENT`（モジュール装着検出）と `WAKE` の GPIO 2 本 |
| フレーム | `[0xA5][len][type][payload...][CRC16]`。安全 MCU は不正フレームを無視する |
| モジュール→MCU | `SECURE`、`RELEASE(ms)`、`PASSAGE`、`GET_STATUS`、`GET_POWER`、`FW_UPDATE_BEGIN/DATA/END` |
| MCU→モジュール | `STATUS`（扉位置、掛かり、施錠モード、異常コード）、`POWER`（主電源電圧、バックアップ残量）、`EVENT`（状態変化の即時通知、R-ST-02）、`ACK/NAK` |
| 安全条件 | `RELEASE`/`PASSAGE` は直前 5 秒以内の `AUTH_OK`（モジュールが認証済みセッションであることを宣言）が無ければ NAK（R-EL-03 の実装例。製造者はより強い方式を提案してよい） |
| 起動 | MCU はモジュールの有無にかかわらず単独で起動し、センサーから状態を再構成する（R-ST-03） |

# AI で作り続ける原則

2026-09-13 のソフトウェア開発計画から、少人数と AI で作り続けるための章だけを抜いたもの。組織の体制や年次計画は含めない。「95」「90」は元の文書群の保守体制と業者育成の章、「モジュール E / I」は開発モードと納品検査、「PM」は製品定義に責任を持つ人を指す。

## 3. AI を使って少人数で成立させる原則

| 原則 | 内容 |
| --- | --- |
| 仕様が先 | 本文書群の要求 ID と OpenAPI を先に固め、AI にはそこから実装とテストを書かせる。要求 ID をテスト名に含め、対応づけを自動で集計する。ソフト担当の時間は仕様と検証に使い、コードを書く時間に使わない |
| テストが確実 | AI が書いたコードは正しいとは限らない。正しさはテストで確かめ、そのテスト自体の正しさも確かめる（3.1）。テストが通らない変更は取り込まない |
| 疑似で全部通す | 実機はコストと時間の本体。開発モード（E）でほぼ全部を検証し、実機は受入れ試験だけに使う |
| 再現できる配布 | イメージと 1 コマンド導入。復元は「誰がやっても同じ」ように作る。属人性を消すのが少人数体制の保険 |
| 文書が引き継ぎ | 担当者の不在に備え、仕様（本文書群）、OpenAPI、テスト、運用手順を常に最新にする。AI に差分から文書を更新させる |
| 作らないもの | クラウド前提の機能、独自の UI フレームワーク、独自プロトコルの拡張（Matter で足りるものは Matter）、独自ハード |
| 規格の追従 | Matter、Aliro、ONVIF の更新は年単位で来る。依存ライブラリの更新を月次で確認し、破壊的変更はテストで検出 |

### 3.1 テストの確実性（AI のコードを信用しないための仕組み）

AI が書いたコードは正しいとは限らない。AI が書いたテストも同じである。したがって「テストが確実にできる」ことを、次の仕組みで担保する。

| 仕組み | 内容 | 誰が |
| --- | --- | --- |
| テストは仕様から書く | テストの入力と期待値は本文書群の要求 ID と OpenAPI から決める。実装コードを見てテストを書かせない（実装の誤りをそのまま期待値にしてしまう） | AI が下書き、PM が期待値を仕様と照合 |
| 実装とテストを分けて作らせる | 同じ AI セッションで実装とテストを一度に作らせない。仕様 → テスト（先に固定）→ 実装、の順にする | PM が手順を守る |
| テストのテスト | 故意にコードを壊して（値を 1 つ変える、分岐を消す）テストが落ちることを確認する。落ちないテストは無効として作り直す。自動化（ミューテーション試験）を CI に入れる | AI が実行、PM が結果を見る |
| 要求 ID との対応を集計する | 各要求 ID にテストが最低 1 つ対応し、対応のない要求を一覧にする。対応のない要求は「未検証」として扱う | 自動集計、PM がレビュー |
| 疑似デバイスで全経路を通す | 開発モード（モジュール E）で、正常系だけでなく故障注入（応答なし、切断、時刻ずれ、系統の脱落）を毎回回す | 自動（CI） |
| 実機は納品検査で | 疑似で通らないもの（電波、タップ、再接続）はエレキ担当の納品検査（モジュール I）で確認し、同じ要求 ID の下に結果を並べる | エレキ担当 |
| 通らなければ取り込まない | テスト、ミューテーション試験、要求 ID の対応集計を CI の必須条件にする。PM も例外を作らない | CI |
| 本番に近い環境で復元まで試す | 更新のたびに、イメージから起動 → 復元 → 受入れ試験、を自動で通す（95 の翌営業日復旧の担保） | 自動（CI） |

ソフト担当に求める最低限の力は、テストを読んで「これは仕様のどの要求を、どの入力で、何を期待して確かめているか」を言えること、そして故意に壊したときに落ちるかを自分で確認することである。コードを書けなくてもよいが、テストを読めなければ AI の出力を検証できない。

### 3.2 継続開発と販売の両立（パッチ運用）

販売を始めた後も開発は続く。理由は 3 つで、いずれもバグの有無とは無関係に起きる。

| 更新が避けられない理由 | 例 | 頻度の目安 |
| --- | --- | --- |
| 規格の改定 | Matter は年 2 回程度の版上げ（1.4 → 1.5 → 1.5.1）、Aliro の版上げ、ONVIF プロファイルの更新。認証品のファームが新版に移ると、コントローラ側も追従が要る | 年 2〜3 回 |
| 依存の更新 | OS、Matter SDK、ライブラリのセキュリティ修正 | 月次 |
| 運用からの要求 | 保守指標（95）と管理会社の要望から出る改善 | 継続 |

したがって「完成して売る」のではなく「売りながら直し続ける」体制を最初から作る。要求は [70_dev_server.md](70_dev_server.md) 6.1（R-DV-30〜40）に置き、ここでは運用の方針を定める。

| 方針 | 内容 |
| --- | --- |
| 版の並行 | 現行版と 1 つ前の版の 2 本を保守する。3 本以上は持たない。互換を切る変更は 12 か月の併存期間を置く（R-DV-35） |
| 配布の周期 | 定期更新は四半期ごと。セキュリティ修正は緊急経路（R-DV-39）。規格改定への追従は、供給元のファーム配布に合わせて計画する |
| 段階配布 | 開発モード（CI）→ 試験導入棟（最低 2 週間）→ 全棟。各段階で保守指標が悪化したら止めて戻す（R-DV-31、32） |
| 互換表の維持 | 管理ソフト × Matter コントローラ × 錠・コントローラのファームの互換表をドア事業担当が版ごとに更新し、エレキ担当が納品検査で検証する（R-DV-36） |
| 更新の前後で試験 | 3.1 の CI（テスト、ミューテーション、要求 ID 対応、イメージ起動 → 復元 → 受入れ試験）を通らない版は配布しない |
| 現場への通知 | 更新の理由と影響を管理会社に事前通知し、結果を保守記録に残す（R-DV-38）。施工業者は研修シナリオに「更新と切り戻し」を含める（90） |
| 開発の配分 | ソフト担当の時間の目安は、新機能 5 割、規格追従と依存更新 3 割、運用からの修正 2 割。規格追従を後回しにすると認証品の新版に取り残される |

## 4. AI でも消えないもの（機構・エレキ側が責任を持つ）

| 項目 | 理由 | 責任 | ソフト担当の関与 |
| --- | --- | --- | --- |
| 実機と電波の試験 | Thread の到達、Aliro のタップ、BLE の再接続は実機でしか分からない | **エレキ担当**（納品検査） | 検査の自動化を用意して渡す（モジュール I）。検査項目はエレキ担当が書く。段階的なハード購入（70 第 3 章）はエレキ担当が発注 |
| 認証取得 | モジュール単体の技適・Matter・Aliro は供給元が取る。扉・ラッチを組み込んだ**自社の製品としての CSA 認証（Matter Door Lock、Aliro）はエレキ担当の一番の役割**。認証試験機関の期間がかかる | **エレキ担当**（自社製品の認証取得）。機構側の防火・CP は機構担当が取得 | 認証試験に通すための試験自動化と技術情報の提供。認証品を選ぶ設計（コア R-EL-19）で負担を減らす |
| 法規・契約 | 防火、個人情報、保守契約の文案 | **機構担当**（設計者・管理組合・販売元と） | 技術情報だけ出す |
| 試験導入 | 6 か月は縮まらない | **機構担当**（建物・管理組合側）、エレキ担当（機器側） | M2 までを早く終え、試験導入と並行して M4〜M5 を進める。指標（95）を管理ソフトで集計して渡す |
| 運用の相手 | 管理会社・業者との対話 | 販売元（ドア製造者） | 二次サポート（平日メール）に限定 |

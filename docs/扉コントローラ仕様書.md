# 扉コントローラ 仕様書

2026年9月16日 第1版

## 0. この文書について

扉に付く専用コントローラの仕様である。置き場は層ごとに決める(第 2 章)。公開規格(Matter・Aliro)が範囲に入れていない部分を、扉側で持つために書く。

範囲は、一枚の扉と、その扉の枠までである。読取機の中身、錠の機構、建物の縦系統配線、上位の発行者(誰に鍵を出すか)は範囲外とし、それぞれ界面で受ける。

関連する文書。

| 文書 | 関係 |
|---|---|
| [要求仕様 01_interface](要求仕様/01_interface.md) 認定の境界と標準インターフェース | 事業としての位置づけ。固定する物（切欠き、補強、コネクタ）と交換自由部、等級（R-IF-10〜12。本書の R-CT-23 が点検の測定を受け持つ） |
| 解説記事「玄関まわりの技術を層に分けて見る」（サイトの /guide/） | この機器がどの層にあたるか。上下の層との関係 |
| digitalkey（実装、この置き場） | 本書に沿って動いている試作。`door`（判断と記録）と`panel`（Matterの橋と盤） |

要求には `R-CT-nn` の番号を付ける。「〜すること」が要求、それ以外は説明である。

## 1. 位置づけ

コントローラが持つのは、規格が機器の言葉を決めた後に残る部分である。

Matterの錠(Door Lockクラスタ)が持つもの。施錠・解錠・アンボルト、利用者と資格情報、曜日と年日と休日の予定、扉位置センサー、操作の通知、操作モード、自動再施錠、警報。

Aliro 1.0が持つもの。スマートフォンと読取機の相互認証、NFC・BLE・UWB、オフラインでの失効。Aliroは読取機から後ろ(制御盤とその先)を意図して範囲外にしており、鍵の共有と監査は後の版に置いている。

この二つの外に残るものが、本書の中身である。

| # | 残るもの | 理由 |
|---|---|---|
| 1 | 火災・停電・避難のときの挙動 | 認定と消防で決まる。規格に型がない |
| 2 | 改ざんの分かる監査記録 | 通知はあるが、連番・連鎖・署名の記録がない |
| 3 | 二人同時と強要コード | 規格外 |
| 4 | 回数制限の鍵 | 予定は時間帯であって回数ではない |
| 5 | 読取機と制御盤の間の言葉 | Aliroが範囲外にした所 |
| 6 | 建物側との連動 | JEM-A、集合玄関の取り次ぎ |
| 7 | 通線路の自己診断 | 等級を点検の暦に載せるための測定 |
| 8 | 時刻の同期と未同期の記録 | 記録の証拠力に関わる |
| 9 | 非常手段の使用記録 | 給電パッド・機械キー・手動リリース |
| 10 | 保守者の権限 | 更新と診断はできて、解錠は管理者の承認が要る |

**R-CT-01** 上の10項目を扉側で持つ**こと**。

**R-CT-02** 持った機能は公開した言葉で外へ出す**こと**(第5章)。規格が後の版で同じ機能を取り込んだ場合は、その部分を規格に譲れる形にしておく**こと**。

## 2. 構成

三つに分ける。境目は接点とコネクタである。

| 層 | 中身 | 速さ |
|---|---|---|
| 安全側 | 接点の読み書き、火災と停電の一次挙動、機械的な解放 | 遅い。認定と一緒に固める |
| 判断側 | 状態の表、監査の記録、二人同時、設定 | 中。試験で固める |
| 界面側 | Matter、伝票の書き出し、読み取りの口、読取機との接続 | 速い。規格の版に合わせて動く |

置き場は、共通コア R-EL-35 による。安全側は、動かす錠と同じ側に置く。錠が扉にある玄関では扉の中、錠(ストライク)が枠にある室内扉では枠の側である(20_interior_business R-IN-20)。判断側と界面側のうち鍵を持つ部分は、室内の側からだけ届き、工具で扉を分解せずに替えられる所に置く(R-EL-10)。外の側の面に出すのは、アンテナ、表示、操作の部品までとする。動く温度の範囲と衝撃は、製造者が申告する(R-EL-36)。試作は Linux の小さな機械で動かしているが(第 9 章)、製品の大きさと置き場を表す物ではない。

**R-CT-03** 錠の銘柄は接点の下に隠す**こと**。コントローラから見える錠は、次の入出力の束とする。

| 向き | 信号 |
|---|---|
| 入力 | 火災信号、商用電源の有無、扉の開閉、デッドボルトの位置、手動リリース、改ざん検知 |
| 出力 | 解錠、施錠 |

**R-CT-04** 錠に固有の事情は、接点の層の差し替えとして書く**こと**。判断側の記述を錠ごとに変えないこと。

## 3. 状態と判断

### 3.1 状態

通常、火災、停電、通行。扉の状態(開・閉)と錠の状態(施錠・解錠)は別に持つ。

### 3.2 判断の表

| 入来事 | 既定の挙動 | 記録 |
|---|---|---|
| 有効な資格情報 | 解錠する | 認証/成功、操作/解錠 |
| 無効な資格情報 | 施錠のまま。理由を残す | 認証/拒否(理由付き) |
| 二人同時が要る扉で一人目 | 待つ。窓の秒数を過ぎた待ちは落とす。同じ人は二人と数えない | 認証/二人同時 待ち |
| 強要の印が付いた資格情報 | 解錠する | 認証/強要コード。外への通報は上の層 |
| 火災信号 入 | 設定に従い、解放するか保持する | 非常/火災信号 |
| 火災中の施錠要求 | 受け付けない | 操作/施錠 拒否(理由:火災中) |
| 停電 | 設定に従い、解放するか保持する | 非常/停電 |
| 停電中の施錠要求 | 解放の設定なら受け付けない。保持の設定なら受け付ける | 操作/施錠 拒否(理由:停電中) |
| 復電 | 通常に戻す | 非常/復電 |
| 自動施錠の時刻 | 扉が閉じていれば施錠する。開いている間は待つ | 操作/施錠(自動施錠) |
| 手動リリース | 記録する。状態は解錠 | 非常/非常手段(手段名) |
| 改ざん検知 | 記録する | 異常 |
| 時刻の同期 | 前の時刻と新しい時刻を残す。同期済みから許容を超えて動いたら、ずれも残す | 時刻/同期、異常/時刻のずれ |
| 設定の変更 | 項目ごとに前の値と新しい値を残す。無い項目と許されない値は拒み、何も変えない | 設定/(項目名) |

**R-CT-05** 火災報知と連動して解錠する機能を持つ**こと**。連動するかどうかは扉ごとに鍵の管理者が決め、運用の中で入れたり外したりできる**こと**。変更は管理者の鍵で確かめた操作に限り、R-CT-22 のとおり記録に残す。仕様はどちらにするかを決めない。連動は、火災報知の信号に、その扉を開ける権限を与えることである。そのため、連動を入れるときは、人に鍵を出すときと同じく審査し、承認を台帳に残す。審査では、誰が信号を出せるか(発信機は誰でも押せる)、どの扉が開くか、信号の配線に細工されないか、内側から機械で開くか、消防隊が外から入る手段、地域の基準を確かめる。入れた後も、管理者が決めた時期に見直す。

**R-CT-06** 停電のときの挙動を、設定で解放と保持のどちらにもできる**こと**。既定は解放とする。

**R-CT-07** 電源が失われても機械的に開けられる手段を残す**こと**。その使用を記録できる**こと**。

**R-CT-08** 二人同時の人数と窓の秒数を設定できる**こと**。窓の内に人数が揃って初めて解錠する**こと**。

**R-CT-09** 自動施錠の秒数を設定できる**こと**。扉が開いている間は施錠しない**こと**。

**R-CT-10** 資格情報が有効かどうかの判定は、上の層(発行者)から受け取る**こと**。コントローラは提示された事実と結果を記録する。

## 4. 監査の記録

**R-CT-11** 記録は連番を持ち、欠番が分かる**こと**。

**R-CT-12** 各記録は前の記録のハッシュを持ち、改ざん・削除・挿入を検出できる**こと**。

**R-CT-13** 各記録に署名を付ける**こと**。署名の鍵は取り出せない場所に置く**こと**(セキュアエレメント)。

**R-CT-14** 記録は錠自身の操作で消せない**こと**。

**R-CT-15** 連番を指定した差分の取得ができる**こと**。

**R-CT-16** 時刻が同期していない間の記録に、その旨の印を付ける**こと**。同期したときは、前の時刻と新しい時刻の両方を残す**こと**。

記録する種別は、操作・物理・認証・資格情報・設定・非常・異常・時刻とする。一件の中身は、連番、錠の時刻、同期の印、種別、事象、結果、主体(仮名化した識別子)、経路、詳細、前ハッシュ、ハッシュ、署名。

主体と人の対応表は、コントローラの外(発行者と台帳)が持つ。

## 5. 界面

三つの向きに分ける。向きを分けることで、外から入ってくる認証をほとんど持たずに済む。

### 5.1 出す(記録)

**R-CT-17** 監査の記録を、署名つきの伝票として外へ出せる**こと**。相手が検べるのは接続ではなく署名とする。

置き場は箱(フォルダか、それに相当する受け口)でよい。止まっている間は溜まり、復旧したときに続きから流れる。装置の中の形式と、箱を流れる伝票の形式が違ってよく、翻訳は境界で一度だけ行う。

この向きに鍵の配布と失効は要らない。三十年もつのは、接続に付けた認証ではなく記録に付けた署名の方である。

作った伝票の形は次のとおりである。

| 項目 | 中身 |
|---|---|
| 単位 | 一件の記録を一つのファイルにする。名前は `<扉>-<連番10桁>.json`。書きかけが見えないよう、別の名前で書いてから名前を変える |
| 欄 | `format`(`digitaldoor-audit-slip/1`)、`door`(扉の名前)、`alg`(`Ed25519`)、`key_id`(公開鍵の SHA-256 の先頭 16 桁)、`entry`(記録の各欄。第4章の一件の中身) |
| 署名 | 記録のハッシュの 16 進の文字列を、扉の秘密鍵で署名する |
| 受け手の検べ方 | `entry` から `hash` と `signature` を除いた欄を、名前の順に並べた JSON(UTF-8、ASCII 以外の文字はそのまま、区切りは既定)にして SHA-256 を取り、`hash` と比べる。`hash` の署名を公開鍵で検べる。連番が続き、前ハッシュがつながっていることを見る |
| 公開鍵 | 据付のときに受け手の台帳へ写す(`digitaldoor-controller pubkey`)。伝票には鍵の識別だけを入れ、鍵そのものは入れない。受け手は伝票の中の鍵を信じず、台帳の鍵で検べる |
| 続きから | どこまで出したかは装置の側に持つ(置き場の `export.cursor`)。箱が無い間と書けない間は進めず、戻ったら続きから出す。箱の側で取り込んだ伝票を消しても、装置の記録は変わらない |
| 判断と分ける | 書き出しは判断と別の流れ(スレッド)で、判断の排他を持たずに行う。箱が応答しなくても、判断、自動施錠、命令の受け付けは止まらない |

### 5.2 受ける(命令)

**R-CT-18** 施錠と解錠の命令を、Matterの錠として受けられる**こと**。

操作する相手の認証は、Matterのペアリングで済んでいる。同じ認証をコントローラで作り直さない。誰をペアリングしてよいかは、扉の側が決める(R-CT-26)。

**R-CT-26** Matterの登録先(Fabric)を、管理者の口として扱う**こと**(共通コア R-AC-24)。登録の窓を開ける操作を、管理者の鍵の操作か、室内の側の物理の操作に限る。今の登録先を照会で出し、足したことと外したことを、種別「設定」で記録する。登録先から受ける命令の範囲(施錠と解錠、鍵の登録)は、設定の項目とする(第 6 章)。

**R-CT-19** 読取機からの認証結果を受けられる**こと**。読取機は差し替えられる前提とし、コントローラが受けるのは「どの主体の資格情報が、どの経路で提示され、有効だったか」だけとする。

読取機がAliroの読取機であっても、ドアホンに吸収されたものであっても、この受け口は変わらない。財布に鍵を載せる会社の発行者の署名で本物と確かめた資格情報も、通すのは、管理者が扉に登録した物だけである(共通コア R-AC-25)。 読取機の側で守ること(顔の特徴量の扱い、生体検知、性能の申告)と、判定結果に含める物(経路、信頼度、生体検知の結果)は [要求仕様 02_reader](要求仕様/02_reader.md) に書く。

### 5.2a 発行者の署名つき資格情報

読取機の判定結果(R-CT-19)とは別に、発行者が署名した資格情報を、扉が自分で確かめて受ける口を持つ。発行者の判定(R-CT-10)は署名として扉に届き、扉は署名と範囲と期限を確かめる。網も発行者のサーバーも要らない。要求は共通コアの R-AC-02、R-AC-09、R-AC-10、R-AC-12 である。失効の一覧(R-AC-14、R-AC-22)は 5.2c に書き、その確かめはこの節の確かめる順番に入れる。

作った物と選んでいる物は次のとおりである。

| 項目 | 中身 |
|---|---|
| 資格情報の形 | `{"body": "<署名したバイト列そのもの。UTF-8 の JSON の文字列>", "sig": "<Ed25519 の署名の 16 進>"}`。受け手は `body` の文字列のバイト列で署名を検べてから、中を読む。並べ直しや書き直しをしないので、言語ごとの JSON の書き方の違いに左右されない |
| `body` の欄 | `format`(`digitaldoor-credential/1`)、`issuer`(発行者の公開鍵の SHA-256 の先頭 16 桁)、`id`(資格情報の識別)、`subject`(仮名化した主体)、`doors`(開けてよい扉の名前の列)、`not_before`、`not_after`(整数の unix 秒)、`once`(一回限りか) |
| 信頼の一覧 | 扉ごとに、信頼する発行者の `issuer` → 公開鍵と、その発行者に許す扉の名前の列(範囲)。発行者の鍵が届く扉は、この範囲に限る(R-AC-09) |
| 確かめる順番 | 1 形、2 発行者が一覧にあるか、3 署名、4 この扉が `doors` と一覧の範囲の両方にあるか、5 失効の一覧にあるか(その発行者の `revoked` に `id` がある。5.2c)、6 時計が同期済みか、7 期限の内か、8 失効の知らせの古さ(5.2c)、9 一回限りなら未使用か。最初に外れた所で拒む |
| 拒否の理由の言葉 | `形式が違う`、`知らない発行者`、`署名が合わない`、`範囲の外`、`失効済み`、`時刻が未同期`、`期限の外`、`失効の知らせが古い`、`使用済み` |
| 通った後 | 読取機の判定結果と同じ判断を通る(火災、二人同時、自動施錠)。記録の詳細に `issuer` と `id` を残す。強要の印は、提示の仕方(強要の暗証など)で決まる物なので、署名つき資格情報には持たせず、読取機の判定結果(R-CT-19 の強要の印)で受ける |
| 一回限り | 使った `id` を記録に残し、再起動のときは記録から使用済みの一覧を作り直す。使用の記録は詳細に `id` だけを入れ、経路は入れない(経路は認証の記録にある) |
| 経路 | `present` の `route` の既定は `遠隔`。読取機から受けたときは、読取機の経路の名前(`系統1` など)を渡す |
| 扉の名前 | 据付のときに必ず設定する。既定の `door` は試験のための物 |
| 遠隔の解錠 | 網を通した解錠は、発行者が出した一回限りで期限の短い資格情報を、この口へ送る形だけにする。業者や連携先が持つ常の解錠の権限は作らない(R-AC-10)。HTTP の `/lock`、`/unlock` は、同じ機械の中の Matter の橋のための口で、外の網には開かない。HTTP の口の既定の待ち受けは 127.0.0.1 とし、外の網に向けて待ち受けるときも、`/lock` と `/unlock` は同じ機械(ループバックの相手)からの要求だけを受け、ほかは 403 で拒んで記録に残す |
| 信頼の一覧の変え方 | 据付のときに扉へ入れた管理者の公開鍵で署名した変更の要求だけを受ける。要求は `{"body": "<JSON の文字列>", "sig": "<16 進>"}` で、`body` は `format`(`digitaldoor-trust-change/1`)、`door`(この扉の名前)、`action`(`add` / `remove`)、`issuer`、`public_key`(16 進、`add` のとき)、`doors`(範囲、`add` のとき)、`id`。署名が合わない、扉の名前が違う、同じ `id` を二度送った要求は拒み、一覧を変えない。受けた変更は種別「設定」で前と新しい一覧を残し、拒んだ要求も種別「設定」の拒否として残す(R-AC-12)。拒否の記録は、事象「信頼する発行者」、結果「拒否」、詳細に理由(`形式が違う`、`管理者の鍵が無い`、`署名が合わない`、`扉の名前が違う`、`使用済み`)。受けた要求の `id` は、同じ内容でも、消した後でも、二度と受けない。拒んだ要求の `id` は使用済みにしない。変更は時計の同期を要らない(管理者の操作のため。R-AC-02 の管理者鍵と同じ扱い) |
| 一覧の作り直し | 再起動のときは、受けた変更の記録から、最後に受けた変更の後の一覧と、受けた要求の `id` を作り直す。記録の一覧が、起動のときに渡した一覧より優先する |
| HTTP の口 | `POST /credential` `{"credential": {...}, "route": "...", "revocation": {...}}` → 結果(`revocation` は任意。5.2c)。`POST /trust` `{"request": {...}}` → 結果。`GET /trust` → 信頼の一覧(公開鍵と範囲。秘密は無い)。`POST /revocation`、`GET /revocation` は 5.2c |
| 置き場 | `controller/digitaldoor_controller/credentials.py`。発行者の側で資格情報と変更の要求を作る関数も同じ所に置く(試験と発行者の実装の見本) |
| 参照実装の口(発行者の側) | `credentials.issue(signer, *, cred_id, subject, doors, not_before, not_after, once=False) -> dict`(資格情報)、`credentials.trust_change(admin_signer, *, door, action, issuer_public_key, doors=None, req_id) -> dict`(変更の要求)、`credentials.revocation_list(signer, *, generation, issued_at, revoked) -> dict`(失効の一覧。5.2c)。`signer` と `admin_signer` は `audit.Ed25519Signer`。発行者の識別は `slips.key_id(公開鍵)` と同じ計算 |
| 参照実装の口(扉の側) | `Controller(contacts, audit, config, name="door", admin_key=None, trust=None)`。`admin_key` は管理者の公開鍵(32 バイト)、`trust` は `{issuer: {"public_key": "<16 進>", "doors": [...]}}`。`ctl.trust` は今の一覧。`ctl.present(credential, route="遠隔", *, revocation=None) -> str` は判断の結果(`解錠`、`待ち`、`強要`、`解放済み`、`拒否`)を返し、拒否の理由は記録の `result` に入る。`revocation` は端末が一緒に運んだ失効の一覧(5.2c)。`ctl.change_trust(request) -> str` は `受理` か `拒否` を返す。`ctl.accept_revocation(lst) -> str`、`ctl.revocations`、`Config.revocation_max_age_s` は 5.2c。`credentials.verify_credential(credential, *, door, trust, now, synced, used_ids, revocations=None, max_age=0.0) -> Verdict` は、足した二つの引数を省くと今までと同じに動く(`revocations` が `None` なら順番の 5 を見ず、`max_age` が 0 なら順番の 8 を見ない) |
| 記録の形 | 確かめて通った資格情報と拒んだ資格情報は、種別「認証」で、詳細に `issuer=<識別> id=<資格情報の識別>` を入れる。一回限りの資格情報を使ったら、種別「資格情報」、事象「使用」、詳細 `id=<識別>` を一件足す。再起動のときは、この記録から使用済みの一覧を作り直す。信頼の一覧の変更は、種別「設定」、事象「信頼する発行者」で、詳細に前と新しい一覧を入れる |

### 5.2b 鍵の階層

扉にかかわる鍵を、誰が持ち、その鍵で何ができ、なくしたとき、漏れたとき、持ち主が替わったときにどう作り直すかを、一つの表にする。一つの鍵には一つの役を持たせる。製造者と業者は、扉を開ける鍵(管理者の鍵、予備の管理者の鍵、発行者の鍵)を持たない(R-AC-10、20、23)。製造者が持つのは、更新の署名の鍵と、扉の個体の台帳と、交換の部品である(R-RS-20)。

| 鍵 | 持つ人 | その鍵でできること | 扉と受け手が知る形 |
|---|---|---|---|
| 管理者の鍵 | 鍵の管理者(会社は情報システム部門、民泊は経営者) | 扉が信頼する発行者の一覧を変える(R-AC-12)。扉の設定を変える(火災報知の連動など、R-CT-05)。資格情報は出せない | 据付のときに扉へ入れた公開鍵 |
| 予備の管理者の鍵 | 扉の持ち主(封をして持つ。賃貸は貸主) | 管理者の鍵を入れ直す(R-AC-23)。室内の側の物理の操作と一緒のときだけ効く。ほかのことはできない | 据付のときに扉へ入れた公開鍵 |
| 発行者の鍵 | 管理者(鍵を出す、外に口を開けない機械) | 資格情報と、失効の一覧(5.2c)に署名する。届くのは、信頼の一覧でその発行者に許した扉だけ(R-AC-09) | 扉の信頼の一覧の公開鍵 |
| 端末の鍵 | 本人の端末 | 扉の毎回違う問いかけに署名する(R-AC-21) | 資格情報の中に入れた公開鍵 |
| 扉の記録の鍵 | 扉(セキュアエレメント、R-LG-04) | 記録と伝票に署名する(R-CT-11〜17) | 据付のときに受け手の台帳へ写した公開鍵 |
| 更新の署名の鍵 | 製造者(R-RS-03) | ファームウェアの更新に署名する(R-EL-25)。入れるかは管理者が決める(R-EL-34)。配った版は公開の一覧に載る(R-RS-19) | 製造のときに扉へ入れた公開鍵 |

| 鍵 | なくしたとき | 漏れたとき | 持ち主が替わるとき |
|---|---|---|---|
| 管理者の鍵 | 室内の側の物理の操作と、予備の管理者の鍵の署名で、新しい公開鍵を入れ直す。遠隔ではできない(R-AC-17、R-AC-23) | 同じく扉の前で入れ直し、信頼の一覧と設定の記録を見直す | 新しい管理者の鍵を扉の前で入れ、前の鍵を外す(R-AC-16) |
| 予備の管理者の鍵 | 管理者の鍵の操作で、新しい予備を入れ直す。管理者の鍵も一緒になくしたときは、管理者の公開鍵と信頼の一覧を持つモジュールを替える(R-EL-10) | 管理者の鍵の操作で入れ替える。物理の操作が要るので、予備だけでは扉の外から何もできない | 封のまま引き渡すか、新しい持ち主が作り直す |
| 発行者の鍵 | 新しい鍵を作り、管理者の鍵で一覧に足し、資格情報を出し直す | 管理者の鍵で一覧から外す。その発行者の資格情報は全部効かなくなるので、新しい鍵で出し直す | 新しい持ち主の発行者を足し、前の発行者を外す |
| 端末の鍵 | 端末の紛失として、その人の全経路の資格情報を止め、本人を確かめてから新しい端末に出し直す(R-AC-15、R-EB-36) | 同じ | 端末を替えたら、新しい端末の鍵で出し直す |
| 扉の記録の鍵 | 取り出せない所にあるので、なくすことは扉の故障にあたる。扉を替え、新しい公開鍵を台帳へ写す | 記録の信用が落ちる。扉を替え、それまでの記録は外に出した伝票と照らす | 扉に付いたまま。台帳の写し先を新しい持ち主へ渡す |
| 更新の署名の鍵 | 製造者が作り直す手順を持つ(R-RS-03) | 版の下限を上げ、漏れた鍵で署名した版を拒ませる(R-EL-27) | 製造者が替わるときの引き継ぎを、製品と一緒に決める |

今の参照実装で持っている物と、まだ無い物は次のとおりである。

| 鍵 | 今の参照実装 | まだ無い物 |
|---|---|---|
| 管理者の鍵 | 公開鍵を起動のときに渡す(`admin_key`)。`digitaldoor-controller keygen` で作り、`trust-change` で変更の要求に署名する | 予備の管理者の鍵と室内の側の物理の操作で入れ直す口(R-AC-23)。扉の設定の変更を、管理者の鍵の署名で受ける口 |
| 予備の管理者の鍵 | 無い | 公開鍵を据付のときに入れ、入れ直しの要求の署名を確かめる口 |
| 発行者の鍵 | `keygen` で作り、`issue` で資格情報に署名する。秘密鍵はファイル(権限 600) | 取り出せない所に置くこと |
| 端末の鍵 | 無い | 資格情報に端末の公開鍵を入れ、問いかけへの署名を確かめる形(5.2a を先に直す) |
| 扉の記録の鍵 | ソフトの Ed25519(`audit.ed25519`) | セキュアエレメント(STSAFE)への差し替え |
| 更新の署名の鍵 | 無い(参照実装は更新を扱わない) | 製造者の側の物 |

**R-CT-27** 管理者の公開鍵、予備の管理者の鍵、信頼する発行者の一覧、Matterの登録先が、どれも入っていない状態(鍵の無い状態)を、照会で出せる**こと**。鍵を消してこの状態に戻したことを、種別「設定」で記録に残す(共通コア R-CM-07)。工事と試験のあとに、扉に誰の鍵も残っていないことを、持ち主が確かめるための口である。

### 5.2c 失効の一覧

網の届かない扉でも、期限の前に資格情報を止められるようにする口である。発行者が、失効した資格情報の `id` を並べた一覧に自分の鍵で署名し、扉は署名と世代を確かめて受け、以後の資格情報の確かめ(5.2a の順番の 5)に使う。一覧は網で届いてもよく、利用者の端末が資格情報と一緒に運んでもよい。失効した人の端末は一覧を運ばないが、同じ発行者のほかの人の端末が運んだ一覧で、その扉に効く。あわせて、一覧の知らせが古くなった扉が、長い期限の資格情報を拒む設定を持つ。要求は共通コアの R-AC-22(端末が運ぶ署名つきの一覧、古い一覧で戻せない)と R-AC-14(失効の知らせが古い扉は長い期限の資格情報を拒める)である。考え方は Aliro の Revocation Document(一覧)と ValidityIteration(世代)に当たる。形をどこまで合わせるかは確かめていない。

作った物と選んでいる物は次のとおりである。

| 項目 | 中身 |
|---|---|
| 一覧の形 | `{"body": "<署名したバイト列そのもの。UTF-8 の JSON の文字列>", "sig": "<Ed25519 の署名の 16 進>"}`。資格情報(5.2a)と同じ包み方で、受け手は `body` の文字列のバイト列で署名を検べてから、中を読む。署名するのは発行者の鍵(5.2b)で、管理者の鍵ではない |
| `body` の欄 | `format`(`digitaldoor-revocation/1`)、`issuer`(発行者の識別。5.2a と同じく公開鍵の SHA-256 の先頭 16 桁)、`generation`(世代の番号。1 以上の整数)、`issued_at`(作った時刻。整数の unix 秒)、`revoked`(失効した資格情報の `id` の列。文字列の列。空でよい)。真偽は整数として受けない。ほかの欄は読まない |
| 全部を送る | 一覧は、その発行者が失効させた資格情報の全部であり、差分ではない。扉は受理したら、その発行者の前の一覧を丸ごと置き換える。発行者は、期限を過ぎた資格情報を一覧から外してよい(期限の外として拒まれるため) |
| 扉を名指さない | 一覧は扉の名前を持たない。同じ一覧を、その発行者を信頼するどの扉に、どの端末が運んでもよい。届く扉は、信頼の一覧でその発行者を信頼している扉である |
| 受ける時の確かめる順番 | 1 形(`形式が違う`)、2 発行者が信頼の一覧にあるか(`知らない発行者`)、3 署名(`署名が合わない`)、4 世代。最初に外れた所で拒む。世代は、その発行者について扉が持つ世代と比べ、小さければ拒む(`古い世代`)。同じなら何も変えず、結果は `同じ`(拒否ではない)。大きければ受理する。まだ一覧を持たない発行者は、どの世代(1 以上)も受理する |
| 結果の言葉 | `受理`、`同じ`、`拒否`。`同じ` は、端末がかざすたびに同じ一覧を運ぶための結果で、記録にも残さない。同じ世代で中身の違う一覧も `同じ` として扱い、中身は見ない(発行者は世代を使い回さない) |
| 時計 | 一覧を受けるのに、時計の同期は要らない(信頼の一覧の変更と同じ)。順番は世代の番号で決め、時刻では決めない |
| 扉が持つ状態 | 発行者ごとに `{"generation": n, "issued_at": t, "revoked": [...]}`。受理した一覧の中身をそのまま持つ。受けた時刻は持たない |
| 信頼の一覧との関係 | 信頼の一覧から発行者を外しても、その発行者の状態は残す。外した後に足し直したときに、世代が戻らないようにするためである。外した発行者の資格情報は、順番の 2 で拒まれる |
| 資格情報の確かめに足す二つ | 5.2a の確かめる順番の 5 と 8。5 は、資格情報の `issuer` について扉が持つ `revoked` に、資格情報の `id` があれば `失効済み` で拒む。時計の同期と期限より前に見るので、時計が未同期でも、期限の外でも、失効した資格情報の理由は `失効済み` になる。8 は次の行 |
| 失効の知らせの古さ(順番の 8) | 設定 `revocation_max_age_s`(秒。0 以上。0 はこの規則を使わない。既定は 0 で、今までの動きを変えない)。この設定が 0 より大きく、その発行者の一覧をまだ一度も受理していないか、`now - issued_at > revocation_max_age_s` であり、かつ資格情報の長さ `not_after - not_before` が `revocation_max_age_s` より長いときに、`失効の知らせが古い` で拒む。長さが設定以下の資格情報は通す。`now` は扉の時計で、順番の 6 で同期済みであることを確かめた後に見る |
| 古さを量る時刻 | 古さは、扉が一覧を受け取った時刻ではなく、一覧の中の `issued_at`(発行者の署名の下にある)で量る。受け取った時刻で量ると、失効した人が前に手に入れた古い一覧を送り直すだけで、扉の知らせが新しくなってしまう。`issued_at` で量れば、新しい知らせを作れるのは発行者の鍵だけになる。そのため発行者は、失効が無くても、世代を上げて `issued_at` を新しくした一覧を、設定の秒数より短い間隔で出し続ける |
| 役ごとの値 | R-AC-14 は資格情報の役ごとに時間を決める形だが、今の資格情報の形(5.2a)に役の欄が無いので、扉ごとに一つの値にする。役ごとに分けるのは、資格情報の形に役を足すとき(5.2a の次の版)とする |
| 製造者の申告 | R-AC-14 で製造者が申告する「設定できる範囲」は、参照実装では 0 以上の秒数である |
| 端末が運ぶ | `present` に `revocation` を渡すと、扉は先に一覧を受ける確かめをし、結果が `受理`、`同じ`、`拒否` のどれでも続けて資格情報を確かめる。一覧を受理したときは、その資格情報の確かめに新しい一覧を使う。資格情報が拒まれても、受理した一覧は残る |
| 記録の形 | 受理は、種別「設定」、事象「失効の一覧」、結果「受理」、主体に発行者の識別、詳細に `issuer=<識別> generation=<n> issued_at=<t> revoked=<JSON の配列>`。JSON の配列は ASCII 以外の文字をそのまま、区切りは既定(`", "`)で書き、詳細の終わりまでとする。記録だけから状態を読み戻せる形である。拒否は、同じ種別と事象で結果「拒否」、詳細に理由(`形式が違う`、`知らない発行者`、`署名が合わない`、`古い世代`)、主体は空。`同じ` は記録しない。資格情報を `失効済み`、`失効の知らせが古い` で拒んだときは、5.2a の認証の拒否の記録(詳細に `issuer` と `id`)になる |
| 状態の作り直し | 再起動のときは、種別「設定」、事象「失効の一覧」、結果「受理」の記録を順に読み、発行者ごとに最後の状態を作り直す。信頼の一覧の作り直し(5.2a)とは別に行い、信頼の一覧に無い発行者の状態も作り直す |
| HTTP の口 | `POST /revocation` `{"list": {"body", "sig"}}` → `{"result": "受理" \| "同じ" \| "拒否"}`。`list` が無い要求は `形式が違う` の拒否として記録する。`GET /revocation` → 発行者ごとの状態 `{issuer: {"generation", "issued_at", "revoked"}}`(秘密は無い)。`POST /credential` の本文の任意の欄 `revocation` に一覧を入れると、`present` の `revocation` に渡し、応答に `"revocation": 一覧の結果` を足す(入れないときは応答にこの欄を入れない)。`/revocation` は `/credential`、`/trust` と同じ扱いで、署名で守る口とし、相手の住所は問わない。OpenAPI の定義(`/openapi.json`)に `/revocation` の二つと `/credential` の欄を足し、版の二つ目の数を上げる(`1.3.0`) |
| 置き場 | `controller/digitaldoor_controller/credentials.py`。発行者の側で一覧を作る関数も同じ所に置く |
| 参照実装の口(発行者の側) | `credentials.REVOCATION_FORMAT`(`digitaldoor-revocation/1`)。`credentials.revocation_list(signer, *, generation, issued_at, revoked) -> dict` は一覧 `{"body", "sig"}` を作る。`signer` は `audit.Ed25519Signer`、`issuer` は `slips.key_id(signer.public_key())`。`generation` が 1 より小さいときは `ValueError` |
| 参照実装の口(扉の側) | `credentials.verify_revocation(lst, *, trust, current) -> tuple[str, dict]`。`current` は発行者ごとの状態の辞書で、変えない。返すのは (理由、`同じ`、空のどれか, `body` の中身)。空なら受理してよい。拒否の理由の定数は `credentials.REVOKED = "失効済み"`、`credentials.STALE_REVOCATION = "失効の知らせが古い"`、`credentials.OLD_GENERATION = "古い世代"`。記録の詳細は `credentials.revocation_detail(body) -> str` で書き、`credentials.parse_revocation_detail(detail) -> dict \| None` で `{"issuer", "generation", "issued_at", "revoked"}` に読み戻す。`Controller.accept_revocation(lst) -> str` は `受理`、`同じ`、`拒否` を返す。`Controller.revocations` は今の状態の辞書。`Config.revocation_max_age_s`(既定 0.0)は `Controller.configure` で変えられ、R-CT-22 のとおり記録に残る。`present` は `verify_credential` に `revocations=self.revocations`、`max_age=self.config.revocation_max_age_s` を渡す |
| 命令 | `digitaldoor-controller revocation --key FILE --generation N [--ids ID[,ID...]] [--at TIME]`。発行者の鍵で署名した一覧を JSON で出す。`--ids` はコンマ区切りで、省くと空の一覧。`--at` は `issued_at` で、`issue` の `--from` と同じ書き方(unix 秒か ISO 8601)、省くと今の時刻。`keygen`、`issue`、`trust-change` と同じく置き場を使わず、網も要らず、読めない入力は短い文で止まって終了コード 1。共通の引数に `--revocation-max-age 秒`(既定 0)を足し、`serve` の `Config` に渡す |

例。発行者が世代 7 の一覧を作り、扉が受ける。

```
body: {"format": "digitaldoor-revocation/1", "issuer": "<発行者の識別>", "generation": 7, "issued_at": 1794700800, "revoked": ["c-0012", "c-0031"]}

POST /revocation {"list": {"body": "<上の body の文字列>", "sig": "<16 進>"}}      → {"result": "受理"}
記録: 設定/失効の一覧 受理 主体 <発行者の識別> 詳細 issuer=<発行者の識別> generation=7 issued_at=1794700800 revoked=["c-0012", "c-0031"]
POST /revocation 同じ一覧をもう一度                                               → {"result": "同じ"}(記録は増えない)
POST /revocation 世代 6 の一覧                                                    → {"result": "拒否"}(記録: 設定/失効の一覧 拒否 詳細 古い世代)
POST /credential {"credential": <id が c-0012 の資格情報>}                        → {"result": "拒否", ...}(記録: 認証/拒否 結果 失効済み)
POST /credential {"credential": <ほかの人の資格情報>, "revocation": <世代 8 の一覧>} → {"result": "解錠", "revocation": "受理", ...}
GET /revocation → {"<発行者の識別>": {"generation": 8, "issued_at": 1794787200, "revoked": ["c-0012", "c-0031"]}}
```

試験の値は、言語に依らない形でファイルに置く(`controller/tests/vectors/revocation-1.json`)。テストはこのファイルを読み、操作を順に行って、結果を確かめる。扉をほかの言語で書き直すときも、同じファイルで確かめられる。秘密鍵はファイルに入れない(値を作った後に捨てる)。値を作り直すと署名が変わるので、形を変えるときは新しい名前のファイル(`revocation-2.json`)にする。ファイルの形は次のとおりである。

| 欄 | 中身 |
|---|---|
| `format` | `digitaldoor-test-vectors/1` |
| `requirements` | 確かめる要求の番号の列(`["R-AC-22", "R-AC-14"]`) |
| `door` | 扉の名前(`Controller` の `name`) |
| `keys` | 試験で使う鍵の公開側。名前 → `{"public_key": 16 進, "issuer": 識別}`。信頼する発行者と、信頼しない発行者(別の鍵で署名した一覧と、信頼していない発行者の一覧を作るため)を入れる |
| `trust` | 起動のときの信頼の一覧(5.2a の形) |
| `config` | 起動のときの `Config` の項目のうち、既定と違う物(`{"revocation_max_age_s": 3600}` など) |
| `start` | `{"now": unix 秒, "synced": 真偽}`。起動の直後に `set_time` に渡す |
| `steps` | 操作の列。順に行う。各操作は `op` と、操作ごとの欄と、期待する結果を持つ |

| `op: "present"` | `credential`(資格情報)と、任意の `revocation`(一緒に運ぶ一覧)と、任意の `route` を `present` に渡す。`expect` は `present` の結果。拒否のときは `reason` に、認証の拒否の記録の結果(理由)を入れる。`revocation` を渡したときは `revocation_expect` に一覧の結果を入れる |
| `op: "time"` | `{"now": unix 秒, "synced": 真偽}` を `set_time` に渡す(時刻を進める、未同期にする) |

### 5.5 開発の口(公開 API の定義、出来事の配信、故障注入)

アプリを作る人が、実機の錠なしで扉の HTTP の口を相手に開発と自動試験をするための口である。要求は [要求仕様 70_dev_server](要求仕様/70_dev_server.md) の R-DV-03(故障注入)、R-DV-11(OpenAPI の定義と版)、R-DV-14(出来事の配信と、連番での取りこぼしの補い)。判断の表(第3章)は変えない。

| 口 | 作った物 |
|---|---|
| 定義 | `GET /openapi.json` が、扉が受ける口の全部を OpenAPI 3.1 で返す。定義にある口と扉が受ける口は一致させる(定義に無い口は作らない)。開発のときだけの口には `x-dev-only: true` を付ける |
| 版 | 応答のすべてに `API-Version` の見出しを付ける。値は定義の `info.version` と同じ。版 1 の間は、口と欄を足すだけにし、今ある口の形と意味は変えない。変えるときは版 2 にし、版 1 の口を `/v1/` の下に残して併存させる(R-DV-35) |
| 出来事の配信 | `GET /events?since=N` を WebSocket(RFC 6455)に切り替える。監査の記録の一件を一つのテキストの文にし、`/audit` の一件と同じ欄の JSON で送る。連番が `N` より後の物を順に送り、追いついた後は増えた物を順に送る。抜かさず、まとめず、同じ物を二度送らない。つなぎ直すときは、受け取った最後の連番を `since` に渡せば、間の物が全部届く。Upgrade の無い要求には 426 を返す(差分を引くだけなら `GET /audit?since=N`) |
| 配信と判断 | 配信は、判断の排他の中では記録の写しを取るだけにし、送るのは排他の外で行う。受け手が読まない、遅い、切れても、判断、自動施錠、命令の受け付けは止まらない。受け手が送る文は、ping に pong を返し、close に close を返して終える。ほかの文は読み捨てる(この口から命令は受けない) |
| 故障注入 | `POST /fault`。開発のときだけ開く(`digitaldoor-controller serve` は接点が模擬なので開く。`digitalkey door-serve` は本物の錠なので開かない。開かないときは 404)。同じ機械の相手だけを受け、ほかは 403 で拒んで記録に残す。指示できる物は次の三つで、一つの要求でいくつでも指示してよい。無い項目か許されない値が一つでもあれば 400 で、何も変えない。指示が一つも無い要求と、数の欄に真偽を入れた要求も 400 とする。400 は記録に残さない |
| 錠が応答しない | `{"lock": "応答しない"}` で、接点への施錠と解錠の命令が錠に届かなくなる。錠の位置(`bolt_out`)は動かず、届かなかった数(`failures`)が増え、届いた命令の並び(`outputs`)には足さない。本物の錠のドライバで錠に届かないときと同じ振る舞いで、判断の側は命令を出した側として記録を続ける。`{"lock": "正常"}` で戻す。錠に届かなかった間は、扉の状態(`locked`)と錠の位置が食い違ったまま残り、次に届いた施錠か解錠の命令で揃う |
| 時計がずれる | `{"clock_offset_s": 秒}` で、扉の時計(自動施錠を進める時計)を実際の時刻から秒だけずらす。次の時刻の同期(`POST /time`)で、ずれが設定の `time_jump_s` を超えていれば「異常/時刻のずれ」が残る(R-CT-16、24)。`0` で戻す |
| 錠への通信が途中で切れる | `{"lock": "途中で切断"}` で、施錠と解錠の命令は錠に届いて錠は動くが、錠からの返事が届かない。接点は届かなかった命令として扱い、届かなかった数(`failures`)を増やし、錠の位置(`bolt_out`)を動かさず、`outputs` に足さない。本物の錠のドライバで時間切れになったとき、取り消しの前に命令が届いていた場合と同じで、扉が知る位置と錠の本当の位置が食い違う。本当の位置は `GET /fault` の `actual_bolt_out` で見える(試験のための窓で、判断には使わない)。次に返事まで届いた命令で揃う。`{"lock": "正常"}` で戻す |
| 配信が途中で切れる | `{"events": "切断"}` で、今つながっている出来事の配信(`/events`)を、close の文を送らずに全部切る。一度だけの指示で、後からつなぐ相手は普通に受けられる。受け手が、受け取った最後の連番でつなぎ直して、抜けなく続きを受けられるかを試す。切った数を応答の `cut` に返す(`cut` は、この指示のときだけ応答に入る)。指示の記録は切る前に書くので、切られる受け手に届くことがある。値は「切断」だけ |
| 故障注入の記録 | 受けた指示は、種別「試験」、出来事「故障注入」で、指示の中身を記録に残す。記録だけを見て、錠の失敗が注入による物と分かるようにする。同じ機械でない相手から来て拒んだときは、同じ種別と出来事で、結果「拒否」、経路「網」、相手の住所を残す |
| 今の注入 | `GET /fault` が `{"lock", "clock_offset_s", "failures", "actual_bolt_out"}` を返す。読むだけなので、相手は問わない |
| 開発でない扉 | 定義(`/openapi.json`)は開発でない扉でも同じ物を返し、`/fault` は `x-dev-only` の印で見分ける。出来事の配信(`/events`)と定義は、開発でない扉でも開く |

選んでいる物: 配信を同時に受ける相手は 8 までとし、超えたら 503 を返す。扉の口はトークンを持たない。トークンでの認証(R-DV-12)は上の層の事業所サーバーの API が持つ(使い方.md「事業所サーバーの口とトークン」)。今の口は 127.0.0.1 で待ち受け、網へ出すときに守る物は第 5.2a 節の署名である。

## 6. 設定

据付のときに決める項目である。ルータやプリンターと同じく、機器自身が設定の画面を持つ。火災報知の連動は、運用の中でも鍵の管理者が変えられる(R-CT-05)。

| 項目 | 内容 |
|---|---|
| 火災報知の連動 | する / しない。扉ごと。鍵の管理者が変えられる |
| 停電のとき | 解放 / 保持 |
| 自動施錠 | 秒数。0で自動施錠しない |
| 二人同時 | 人数と窓の秒数 |
| 接点 | 各入力の極性、出力の型 |
| 時刻 | 同期の相手、ずれの許容(秒。既定 300) |
| 失効の知らせの古さ | 秒数(`revocation_max_age_s`)。0 でこの規則を使わない(既定)。扉ごとに一つ。失効の一覧の `issued_at` からこの秒数を過ぎた発行者の資格情報のうち、期限の長さがこの秒数より長い物を拒む(5.2c、R-AC-14) |
| Matterの登録 | 登録先から受ける命令の範囲(施錠と解錠、鍵の登録)。受けない設定では、その経路を閉じる(R-CT-26) |
| 更新の入れ方 | その都度の承認 / 決めた時間帯に自動で入れる。管理者が決める(共通コア R-EL-34) |

**R-CT-22** 設定の変更を記録に残す**こと**(種別:設定)。前の値と新しい値の両方を残す**こと**。

設定画面の守り方は、次のどれかで足りる。利用者の一覧と失効を持たずに済む形を選ぶ。

- 機器に印刷した一つの合言葉
- 工事用の網からだけ見えるようにする
- 扉を開けた状態か、内側の押しボタンを押している間だけ受け付ける

## 7. 診断

**R-CT-23** 通線路の伝送性能と給電時の温度を測り、記録に残せる**こと**。等級の試験成績を、点検のたびの測定値として続けられる形にする。

**R-CT-24** 通信モジュールの脱落、時刻の大幅なずれ、記録領域の上書きを検出し、記録する**こと**。

## 10. 規格に足すべきもの

第1章の10項目のうち、日本固有ではなく、規制のある建物なら世界のどこでも要るものを、規格側に足す候補とする。

- 火災信号・停電・避難のときの挙動の型
- 改ざんの分かる監査記録(連番・連鎖・署名・差分取得)
- 二人同時と強要コード
- 読取機と制御盤の間の秘匿通信の指針

足す先は、MatterのDoor Lockクラスタと、Aliroが後の版に置いた監査と共有の部分である。本書の要求と第8章の試験の対を、そのまま要望書に使える。

等級の測定値と試験成績は、規格に出さずに持つ。規格が「測って保証せよ」と定めるほど、測った記録を持つ者の値打ちが上がる。

# デジタルキーの管理の問題の整理(下書き、2026-10-20)

デジタルドアの一番の課題は、デジタルキーをどう管理するかです。扉と錠は買える部品になりましたが、鍵を管理する仕組みと、それを持つ人が追いついていません(解説 19)。この文書は、散らばった論点を六つの枠と二本の横の糸に分け、それぞれを「決まったこと」「決まっていないこと」「確かめていないこと」に整理します。

- 決まったこと: 要求仕様か方針になっている物
- 決まっていないこと: 誰が決めるか(運営、製造者、管理者、各社)も書く
- 確かめていないこと: 一次資料や実機で確かめる物

値(期限の長さ、時間、回数、段階)は、この文書では決めません。

## 前提

- 鍵の管理は、会社のシステムのセキュリティ管理と同じ仕事です。違うのは、扉の鍵が目に見えることだけです。
- 鍵の管理の問題は、デジタルにしたから生まれたのではありません。物理キーにも同じ問題があり、見えていなかっただけです。物理キーは、複製され、番号から作られ、錠ごと解析されます。マスターキーは一本で全部の扉が開き、止められません。デジタルキーは、正しく作り、管理すれば、止められ、記録が残り、直せます。
- 鍵の管理は受託しません。それぞれの管理者が持ちます。会社では情報システム部門です。

## 1. 鍵そのもの

問い: どんな鍵なら、写されず、止められるか。

| 区分 | 中身 |
|---|---|
| 決まったこと | 扉は発行者の署名と規則を自分で確かめる(5.2a)。期限の判定は扉の時計で行い、時計が未同期なら期限つきの資格情報を拒む(R-AC-02)。網の届かない扉では失効は期限で効く(R-AC-03)。失効が効くまでの最長の時間を扉ごとに決めて示す(R-AC-14)。資格情報を持ち主の端末の鍵に結ぶ(R-AC-21)。端末が署名つきの失効の一覧を運べる(R-AC-22) |
| 決まっていないこと | 資格情報の形の版 1(扉と鍵の管理の境目として、運営が決める)。期限の長さ(管理者)。端末の鍵の登録の仕方とパスキーとの関係(運営が案を出す) |
| 確かめていないこと | Aliro の Access Document と 5.2a の形をどこまで合わせられるか。停電の間の時計のずれと、期限の判定への響き |

## 2. 一番上の鍵

問い: 誰が持ち、なくしたら、漏れたら、どう戻すか。

| 区分 | 中身 |
|---|---|
| 決まったこと | 発行者の秘密鍵は取り出せない所に置く(R-AC-11)。信頼する発行者の変更は管理者の鍵の操作だけ(R-AC-12)。管理者の鍵をなくしたら扉の前の物理の操作で戻し、遠隔ではできない(R-AC-17)。鍵ごとに置き場、触れられる人、作り直す手順、責任者を決める(R-RS-03)。扉の設定(火災報知の連動など)の変更も管理者の鍵の操作で、審査して承認する(R-CT-05) |
| 決まっていないこと | 鍵の階層の表(扉コントローラ仕様書 5.2b に下書き。見直して固める)。複数の人で持つか(管理者)。作り直しの周期(管理者) |
| 確かめていないこと | セキュアエレメント(STSAFE)で、管理者の鍵と発行者の鍵をどこまで扱えるか |

マスターキーにあたる「一本で全部が開く鍵」は作りません。保守と緊急のときは、その時だけの権限と、決めた手順と記録で入ります(R-AC-06、10)。

## 3. 人と台帳

問い: 誰を載せ、いつ出し、いつ止めるか。

| 区分 | 中身 |
|---|---|
| 決まったこと | 扉の台帳は、鍵の要る全員(社員、派遣、アルバイト、清掃、警備、業者、来客)を載せる正の台帳(R-EB-37)。入社と退職は人事の届けが正で、アカウントと扉の鍵を同じ日に止めて照らし合わせる(R-EB-34)。一人の全経路を一度に止める(R-AC-15)。出来事ごとの手順を持つ(R-AC-16)。端末の紛失は自社の窓口で受け、本人を確かめてから出し直す(R-EB-36)。止めるのは自動、出すのは人が確かめる、一番上の操作は人の手に残す |
| 決まっていないこと | 台帳の様式の項目(雛形で例を置き、各社が決める)。統計で止めるときの基準と段階(管理者) |
| 確かめていないこと | 人事の届けの形を、各社の今の仕組みからどう受けるか |

## 4. 組織の境目

問い: 誰が何を受け持ち、境目で何を渡すか。

| 区分 | 中身 |
|---|---|
| 決まったこと | 会社の発行者は情報システム部門。設備は扉と錠の物理、人事は届け(R-EB-33)。業者に常の権限を持たせない(R-AC-10)。財布への載せ方を担う業者も発行者の鍵を持たない(R-AC-20)。売る側は、売る物と同じ管理を自社で運用し、売り先の管理者を育て、引き渡しで確かめる(R-RS-16〜18) |
| 決まっていないこと | 売った側の顧客の台帳と、買った側の取引先の台帳の間で渡す物の形(更新、脆弱性の知らせ、保守の一時の権限)。管理会社に作業の権限だけを渡す形(分譲、賃貸) |
| 確かめていないこと | 管理会社や理事が替わったときの引き継ぎを、実際にどう回すか。分譲マンションでは、扉の仕様を決め、販売と引渡しを受け持つのは分譲会社(ディベロッパー)で、管理会社がその系列のことも多い。引渡しで権限を移すことを、分譲会社とどう決めるか |

押し付け合いを防ぐには、一番上の鍵を一つの部署が持ち、境目で渡す物を決め、誰が何をしたかを記録で示します。

## 5. 外の仕組み

問い: 何を他社に頼り、何を頼らないか。

| 区分 | 中身 |
|---|---|
| 決まったこと | 扉の台帳は、ディレクトリ(Entra ID など)から自動で動かさず、照らし合わせるだけ(R-EB-37)。財布の鍵は発行者の一つとして台帳から扱い、ほかの経路でも開けられる(R-AC-18)。鍵の発行と扉の判断の機械を、外向きのサービスと同じ機械や仮想化の土台に置かない(R-AC-13) |
| 決まっていないこと | 財布の鍵に対応する時期(製造者)。認証を受ける時期(製造者) |
| 確かめていないこと | Apple と Google の財布への載せ方で、発行者の鍵を管理者が持てるか(Aliro の載せ方の手引き CR-31968 は公開待ち)。財布の認証の条件 |

一番上の層を他人に預ける所に、穴があります。Microsoft では Entra ID、借りた Linux では仮想化の土台、運用を委託した自社の機械では業者の遠隔管理の道具です。業者のバックアップのアプリの資格情報から顧客のテナントに入られた件も、同じ形です。

## 6. 売り先ごと

問い: 誰が管理し、何が難しいか。

| 売り先 | 管理する人 | 難しい所 |
|---|---|---|
| 会社 | 情報システム部門 | 外の人の扱い。Microsoft 365 の中だけでは外を管理できない |
| 分譲マンションの共用部 | 管理組合、またはその委託先 | 相手が多く毎日変わる。理事と管理会社が替わる |
| 分譲マンションの住戸 | 区分所有者 | 開け閉めと家族の鍵は Matter で足りる。持ち主の交代、賃貸に出すとき、外の人、緊急、記録、更新は残る |
| 賃貸 | 貸主の会社、個人の大家、その管理会社 | 退去のたびの出し直し。個人の大家でも回せること |
| 民泊、宿泊 | 経営者、宿の運営 | 宿泊者ごとの鍵。本人の確かめ。予約システム(予約サイト、予約をまとめる仕組み)と連携する |
| 会員証、無人販売所 | 運営 | 個人の情報、成りすまし、止めることの重さ、統計で止めるときの説明 |

決まっていないこと: 管理会社に作業の権限だけを渡す形と、引き継ぎ、個人の大家でも回せることを、集合住宅と貸家のプロファイルにどう書くか。

## 7. 物理キーとマスターキー

問い: 今ある物理キーを、どう同じ台帳で管理するか。

物理キーも、攻撃から逃げられなくなっています。合鍵は記録なしに作られ、鍵の番号や写真から注文でき、錠は型ごとに解析されます。AI がその手間をさらに下げています。マスターキーは一本で全部の扉が開き、一本の子鍵と錠から形を割り出す手口も知られています(Matt Blaze、2003年)。漏れても止める手段はシリンダーの交換しかなく、使われた記録も残りません。デジタルドアを入れる前から、物理キーの管理は始める必要があります。

| 区分 | 中身 |
|---|---|
| 決まったこと | 一人の全経路の失効に、貸し出した機械の鍵の回収の記録を含める(R-AC-15)。業者のサービスが止まったときの手段として、錠に登録した資格情報と物理鍵を手元に持つ(R-RS-06)。電源が無くても機械で開けられる手段を残し、その使用を記録できる(R-CT-07) |
| 決まっていないこと | 物理キーとマスターキーを、権限の台帳に載せる様式(誰が何本持ち、どこに置き、いつ渡し、いつ返ったか)。マスターキーの持ち出しの記録の仕方と、業者に常に持たせないための貸し出しの形(管理者)。漏れたときに錠を替える順番(管理者) |
| 確かめていないこと | 番号から合鍵を頼めない登録の仕組みの錠が、どこまで守りになるか。デジタルドアに替えるまでの間、物理キーとデジタルキーを同じ台帳でどう並べて扱うか |

## 8. スマートフォンの鍵(かざす、許可、電池)

問い: スマートフォンを鍵にするとき、何が自分ででき、何に許可が要るか。

かざすだけで開く鍵は、技術ではなく、スマートフォンの会社の許可で囲われています。かざすだけの鍵は、スマートフォンの会社が用意した管理の機能(家庭用の「ホーム」、提携した入退室管理の会社のクラウド)の中で動き、自分の台帳で出した鍵をかざすだけで使う道は、許可が無いと開きません。

| 形 | 許可 | かざすだけか | 電池が切れたとき |
|---|---|---|---|
| iPhone のアプリを開いて Bluetooth LE で近づける | 不要 | アプリを開く | 使えない |
| iPhone の NFC でかざす(NFC & SE Platform) | 要る | かざすだけ | 財布の鍵のエクスプレスモードは、予備の電力で最大 5 時間ほど使える(自分で電源を切った場合は使えない) |
| Android の自社のアプリで NFC に応える(HCE) | 不要 | アプリを開かずに応えられる(画面のロックを解くなどの条件がある) | 使えない。アプリが CPU の上で処理するので、電源が要る |
| Android のセキュアエレメントに入った鍵(財布、FeliCa など) | 提携が要る | かざすだけ | 交通の使い道では、電源が切れていても使えることが文書にある。機種と使い道による |

Apple の NFC & SE Platform は、家の鍵、会社の社員証、ホテルの鍵を使い道に含み、日本も対象です(iOS 18.1 以降)。申し込めるのは、家の鍵なら家の鍵の製造者かその提携先、社員証なら事務所の建物を運営する者かその者と契約した者です。要る物は、Apple Developer Program の会員(会社のアカウントの持ち主が申し込む)、商取引の条件と料金を含む Apple との契約、秘密保持の契約、Apple Business Register への登録、個人の情報の扱いと脆弱性の公開と直し方の書いた方針、悪用されている脆弱性や事故を遅れずに Apple に知らせる手順、スマートフォンに入れる小さなプログラム(アプレット)の、認定を受けた外部の試験所での審査です。財布(Apple Wallet)に載せる道は、これとは別の提携(Access の仕組み)で、条件は公開されていません。Google の財布の社員証も、提供する会社が Google から専用の部品を受けて作る提携の形です。

| 区分 | 中身 |
|---|---|
| 決まったこと | 財布の鍵は経路の一つで、カード、暗証番号、物理キーでも開けられる(R-AC-18)。スマートフォンを持たない人と電池切れの人のために、カードか暗証番号を受ける(R-CM-09)。財布への載せ方を担う業者は発行者の鍵を持たない(R-AC-20)。資格情報を端末の鍵に結ぶ(R-AC-21) |
| 決まっていないこと | 社員証と家の鍵の試験に申し込むか、どちらからか(協力先が決める)。申し込むと、iPhone のアプリ、アプレットと試験所の審査、鍵を載せ止めるサーバー、鍵の台帳、方針の開発を伴い、受け持つのは情報システム部門になる |
| 確かめていないこと | 日本で社員証の使い道が使えるか(使い道ごとに対象の国が違うことがある)。扉の製造者が「家の鍵の製造者」に当たるか。Android の財布の社員証が電池切れでも使えるか。Aliro の鍵を財布に載せる手引き(CR-31968)の中身 |

すぐにできる実験(許可なし)と、許可を取って行う試験は、並べて扱います。すぐにできる実験は、Android の HCE で自社のアプリでかざす形と、iPhone でアプリを開いて近づける形です。鍵の台帳から出し、止め、記録する流れを、許可を待たずに確かめられます。

## 横の糸 A. 扉との境目

扉の技術者は鍵の管理を知らなくて当然なので、扉の側は「確かめる、規則に合えば開ける、記録する」だけにし、確かめる部品と試験の値で渡します。境目の仕様は、扉の技術者向けと鍵の管理の側向けの二層で書きます。境目は回す前に決め、版を付けます。

- 決まっていないこと: 境目の仕様の版 1、言語に依らない試験の値、扉のマイコンと外の機械の二段の分け方
- 確かめていないこと: マイコンの上で、確かめる部品が電池で動き続けられるか(給電と停電の実験)

## 横の糸 B. 運用と人

- 決まったこと: 当面は、運営と AI が会社のセキュリティの管理システム(全部のシステムの権限の管理)を作って経験を積む。扉はその後で、電子錠は鍵の管理を確かめる道具として使う。協力先への提案は勉強会の形。各社は雛形を参考に自社で作る
- 決まっていないこと: 勉強会の中身と回数(協力先と決める)。権限の目録の様式
- 確かめていないこと: 自分の所で回したときに出てくる問題(回して記録する)

## 横の糸 C. ERP との連携

鍵の管理が頼る台帳は、ERP の台帳です。人(入社、異動、退職)、取引の相手(顧客、取引先、保守の業者)、資産(扉、サーバー、PC)。鍵の管理は、ERP と連携しないと成り立ちません。宿泊では、予約システムが ERP の役を受け持ちます。分譲マンションでは、最初は分譲会社の販売の仕組みとつなぎ、引渡しの後は管理組合の台帳に移ります。今の ERP の多くは、人と資産の台帳を持っていても、「誰に、どの物の、どの権限を、いつまで出したか」を業務のデータとして持っていません。

- 決まったこと: 入社と退職は人事の届けを正とする(R-EB-34)。扉の台帳は鍵の要る全員を載せる正の台帳で、ほかの台帳から自動で鍵を出さない(R-EB-37)。止めるのは自動、出すのは人が確かめる
- 決まっていないこと: ERP の人、取引の相手、資産の台帳と、権限の台帳をどうつなぐか(出来事を受ける向き、照らし合わせの手順)。宿泊では、予約、取消し、到着、出発の出来事をどう受けるか。分譲マンションでは、引渡しのときに、発行の権限を分譲会社から区分所有者と管理組合へどう移し、分譲会社と工事の会社の鍵を確実に止めるか。予約サイトとつなぐ資格情報の権限を、予約を読むだけに絞れるか。aiai-tools では ERP を Tryton にすると決めている(2026-10-12)
- 確かめていないこと: Tryton の台帳に、権限の台帳をモジュールとして足せるか。今の ERP を使う会社では、届けをどの形で受けるか

## 次に手を付ける所

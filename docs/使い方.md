# 使い方

## セットアップ・ビルド・公開

### セットアップとビルド

Python 3.12 以上が必要です。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt                       # サイトのビルド
.venv/bin/pip install -e ./controller                             # 扉のコントローラ(controller/、Apache-2.0)
.venv/bin/pip install -e ".[web,panel,mobile,dev]"                # ソフトウェア(digitalkey)を使う場合
.venv/bin/pip install -e "drivers/digitalkey-sesame[app,dev]"      # Sesame を使う場合(公開後は pip install digitalkey-sesame)
.venv/bin/pip install -e drivers/digitalkey-sesame/flet_ble       # Sesame の画面の BLE(Flet 拡張。テストにも要る)
.venv/bin/pip install -e kagi                                       # 道具 kagi(kagi/、AGPL-3.0-or-later。本体は標準ライブラリだけ)
.venv/bin/pip install -e 'kagi[app]'                               # kagi の机の画面も使う場合(flet が入ります)
```

ソフトウェアのテストは次のコマンドで実行します。

```bash
.venv/bin/python -m pytest -q                       # digitalkey 本体
.venv/bin/python -m pytest -q controller                  # 扉のコントローラ
.venv/bin/python -m pytest -q drivers/digitalkey-sesame   # Sesame ドライバ
.venv/bin/python -m pytest -q kagi                        # 道具 kagi(pip で入れていなくても回ります)
.venv/bin/python -m pytest -q tests/kanri                 # 鍵の管理だけ(digitalkey 本体のテストにも入っています)
```

鍵の管理の命令 `digitalkey kanri`(名簿、役、扉と群、権限の申請から失効まで。`digitalkey kanri --help`)の仕様は [鍵の管理ソフト設計書](鍵の管理ソフト設計書.md) の 19 章で、テストは `tests/kanri/` にあります。

機器の台帳の命令(`digitalkey kanri segment`、`device`、`access`、`vendor`。網の区画、機器の登録と変更と紛失と廃棄、据え付けと点検と廃棄の確かめ、更新の記録、管理者の口の削除、照らし合わせの知らせ、業者と連携先に渡している物の目録)の仕様は、同じ設計書の 20 章です。

失効の一覧の命令(`digitalkey kanri revocation publish`、`show`、`list`、`delivered`、`revoke --out`、`door add --revocation-max-min`。署名つき資格情報を止めた時の、発行者の鍵で署名した失効の一覧と、一覧が扉に届いた記録、扉ごとの失効が効くまでの最長の時間)の仕様は、同じ設計書の 21 章です。命令は網を使わず、一覧はファイルに出します。網の届かない扉へは、人か利用者の端末が運びます。

要求仕様の番号とテストの対応は、標準ライブラリだけで動く `tools/taiou.py` が `docs/適合の現在.md` に書き出します。扉のコントローラのテスト(`controller/tests`)も数えます。テストは、確かめる要求の番号を docstring の先頭に書きます。

```bash
python3 tools/taiou.py --check   # 文書に無い番号をテストが名指ししていたら失敗
```

```bash
.venv/bin/python tools/build_article.py --all     # 記事、一覧ページ、sitemap.xml を生成
.venv/bin/python tools/build_feed.py               # RSS フィード(feed.xml)を生成
.venv/bin/python tools/build_news.py               # news/*.adoc からニュースの頁とトップのニュース欄を生成
.venv/bin/python tools/build_manual.py             # ユーザーマニュアル(docs/manual.md と /manual/)をコードから生成
.venv/bin/python tools/build_check.py              # 確かめの始め方(docs/確かめの始め方.md → /check/)を生成
.venv/bin/python tools/serve.py --port 8000       # 開発サーバー。ファイルを保存すると自動でビルドしてブラウザを更新
```

上の並び(ナビゲーション)と奥付は `tools/build/site_nav.py` で定義し、上の道具はそこから読みます。手書きの頁(`html/index.html`、`html/consult/`、`html/license/`、`html/404.html`)は同じ形を手で書き、`tests/sitebuild/test_site_nav.py` がずれを見つけます。記事の表は、セルを一行に一つずつ書いても、最初の行のセルの数を列の数として組み直してから変換します(`tools/build/markdown.py` の `normalize_adoc_tables`)。

### スマートフォンアプリ

`digitalkey/mobile/`(管理者と利用者のアプリ)と `drivers/digitalkey-sesame/`(Sesame の登録用の画面)は、`flet build` で Android と iOS のアプリになります。配布は Google Play と App Store で行い、ビルドしたファイル(APK 等)はリポジトリに入れません(`build/` は git の対象外です)。設定は各 pyproject.toml の `[tool.flet]` にあります。

```bash
pip install flet-cli
flet build aab    # Google Play 向け
flet build ipa    # App Store 向け(macOS と Xcode が必要)
```

#### Sesame のアプリを組み直して入れる

Sesame のアプリ(「Sesame の鍵」)は、登録した Sesame の鍵を持ちます。前の版は鍵をアプリの保存領域(SharedPreferences)に置いていました。この版は、端末の安全な保管庫(Android Keystore、iOS のキーチェーン)に置きます。**初めて起動したときに、鍵を保管庫へ移します。** アンインストールすると Android の鍵は消えるので、組み直したアプリは上書きで入れます。

```bash
cd drivers/digitalkey-sesame
flet build apk
adb install -r build/apk/<組んだファイル>.apk
```

1. **移す前に、念のため鍵を PC に写しておくことを勧めます。** 前のアプリで Sesame を選び、「鍵を書き出す」で 32 桁を出し、PC で `digitalkey sesame import <UUID>` に打ちます(下の「実機の Sesame を miniPC の…」と同じ手順です)。移し替えは失敗しても元を消さない作りですが、写しがあれば何が起きても戻れます
2. 前と同じ開発機で、同じ署名の鍵で組みます。署名の鍵と証明書はリポジトリに入れず、開発機で持ちます
3. 上書きで入れます。上書きで入らない(署名が違う)ときは、アンインストールせずに止めます。前と同じ署名の鍵を探して組み直します
4. 起動して Bluetooth、カメラ、位置情報を許可します。ログ欄に「鍵の保管庫: 鍵 N 件を保管庫に移し、読み戻して確かめてから、元を消しました」が出て、一覧の Sesame に「(管理者)」が付き、開け閉めできることを確かめます。前の版の鍵は管理者として引き継ぎます
5. 「保管庫に移せなかった」と出たときは、鍵は今までの保存領域に残り、そのまま使えます(次の起動でもう一度移します)。続くときは、1 で写した鍵を PC に残したまま、人に相談します

移し替えは、写す → 読み戻して一致を確かめる → 元を消す、の順です。保管庫が読めない、書けない、書いたはずが読めない、のどれでも元は消しません。保管庫は、エラーで中身を全部消す設定(`reset_on_error`)を無効にしています。鍵は端末のバックアップで別の端末へ移りません(Android はアプリのデータをバックアップから外し、iOS は「この端末だけ」の扱いにします)。機種変更のときは、管理者から鍵を受け取り直します。

新しい版は、鍵ごとに管理者と利用者の役を持ち、鍵を家族などに対面で(QR で)渡せます。役の分け方は画面の歯止めで、鍵の守りではありません。画面の使い方はアプリのコードの先頭(マニュアルの「Sesame のアプリ」)に、組み方から困ったときまでの手引きと、実機で確かめることの一覧は `skills/sesame-app/SKILL.md` にあります。

### 公開

サイトは静的なファイル(`html/`)だけでできています。公開先は、運営の miniPC(deb2)の Caddy です。deb2 は配るだけの機械で、サイトを組むことはしません。組むのは手元の機械で、組んだ `html/` をリポジトリに含めます。

#### 流れ

1. 手元で組み、確かめて、commit し、push する(push は本人)
2. deb2 の写し(clone)が、決めた間隔でリポジトリを取りに行き、早送りできるときだけ進める
3. 点検を通ったら、`html/` を新しい版として置き、シンボリックリンクを付け替える
4. Caddy が、今の版を配る

取りに行く先は、deb2 の写しの `origin` です。GitHub でも、deb2 の Forgejo でもかまいません。道具は取りに行く先を決めません。

#### 公開の道具 `tools/publish.py`

Python の標準ライブラリと git だけで動きます。deb2 では、公開の写し(`~/dev/digitaldoor`)に miniforge(conda-forge)で作った `.venv` の python で動かします。deb2 の Python のアプリは、miniforge の環境をアプリごとの `.venv` に持ちます。apt の python3 は使いません。この `.venv` には python だけを入れます。説明は `--help` にもあります。

```bash
cd ~/dev/digitaldoor
.venv/bin/python tools/publish.py --repo ~/dev/digitaldoor --root /srv/door           # 取りに行き、点検し、切り替える
.venv/bin/python tools/publish.py --repo ~/dev/digitaldoor --root /srv/door --dry-run # 何をするかだけ見る
.venv/bin/python tools/publish.py --root /srv/door --status                           # 今の版と、置いた時刻
.venv/bin/python tools/publish.py --root /srv/door --rollback                         # 一つ前の版に戻す
```

| オプション | 内容 |
|---|---|
| `--repo` | 取りに行く写し。既定は、この道具のあるリポジトリ |
| `--root` | 置き場(必須)。例: `/srv/door` |
| `--branch` | 公開するブランチ。既定は `main` |
| `--keep` | 残す版の数(新しい順)。既定は 5。今の版と一つ前の版は、この数に関わらず消さない |
| `--dry-run` | `fetch` と点検までで、版も `www` も写しも変えない |
| `--status` / `--rollback` | 今の版を見る / 一つ前の版に戻す |
| `--debug` | エラーのとき、例外の追跡も出す |

出力の例:

```
公開しました: 4be91d40a78e(前は 0c1f2e3a4b5d)、2 版を消しました
変更なし: 今の版 4be91d40a78e
今の版: 4be91d40a78e(置いた時刻 2026-10-20 15:52:36)
エラー: 早送りできません: 写しの位置 0c1f2e3a4b5d が origin/main 4be91d40a78e の先祖ではありません(履歴が書き換えられた可能性)。何も変えていません
```

- 取りに行く: `git fetch` の後、今の位置から早送りできるときだけ進める。履歴が書き換えられていたら、何もせずに止まり、理由を出す(終了コード 1)。写しの位置が `origin/<branch>` と同じで、今の版もあるときは、何もしない(終了コード 0)
- 点検: `index.html` と `404.html` があること。`sitemap.xml` があり、その URL(`https://door.aiseed.dev/` の下)が全部ファイルとしてあること(末尾が `/` なら `index.html`)。ファイルの数が、今の版の半分を下回らないこと。`html/` の外を指すシンボリックリンクが無いこと。通らなければ切り替えず、今の版を出し続ける
- 点検に落ちたとき: 点検は写しを進める前に、`origin/<branch>` の `html/` を取り出した場所で行う。落ちたときは写しも `www` も動かさず、取り出した場所は消す。次に動かしたとき、同じ commit をもう一度点検する。直した commit が push されれば、そこへ進む
- 置き方: `/srv/door/releases/<commit の先頭 12 桁>/` に、一時の名前で写してから名前を変える。`_headers` と、名前が `.` で始まるファイルは写さない。`/srv/door/www` は一時のシンボリックリンクを作り、`os.replace` で一度に付け替える。切り替えの後に、写しを早送りする
- 残す版: `--keep` の数だけ新しい順に残す。今の版と一つ前の版は消さない。「一つ前」は、置いた時刻が今の版より前で一番新しい版
- 戻す: `--rollback` は `www` を一つ前の版に付け替えるだけで、写しの位置は動かさない。続けて戻すと、さらに前の版へ行く。origin に新しい commit が無いうちは、次に動かしても何もせず、戻した版が出続ける。戻す先が無ければ、0 以外で終わる
- 同時に二つ動かない(`/srv/door/.publish.lock`)。動いているときは「別の公開が動いています」と出して終わる
- 結果は短い日本語で出す。エラーのときは、終了コードを 0 以外にする

#### Caddy の設定の見本 `deploy/web/door.aiseed.dev.caddy`

deb2 の `/etc/caddy/Caddyfile` に写すのは本人です。

- `root * /srv/door/www`、`file_server`。前に置いている設定の束(`import cf`)を使う
- 応答ヘッダは、今の `html/_headers` と同じ物を出す(HSTS、nosniff、X-Frame-Options、Referrer-Policy、Permissions-Policy、COOP、CORP)。CSP は各 HTML の `<meta>` で出している
- 見つからないときは `/404.html` を返す
- キャッシュの長さは例として置き、運用で決める
- アクセスの記録(`log`)は書かない。計測は本人が決め、プライバシーポリシーの頁と一緒に入れる

#### 本人の作業(root と、アカウントが要る物)

deb2 で公開を動かすまでの順です。ニュースは deb2 では作りません(「ニュースの仕組み」)。版、間隔、置き場の名前は例です。決めるのは運営者です。deb2 の作業は dev で行い、`sudo` と書いた所だけ root の権限を使います。

1. 置き場を作り、dev が書けるようにする: `sudo mkdir -p /srv/door && sudo chown dev:dev /srv/door`
2. 公開の写しを置く: `git clone https://github.com/aiseed-dev/digitaldoor.git ~/dev/digitaldoor`
3. 公開の写しの `.venv` を miniforge で作る: `~/miniforge3/bin/conda create -y -p ~/dev/digitaldoor/.venv python=3.13`(`tools/publish.py` は標準ライブラリだけで動くので、python だけを入れます)。確かめ: `cd ~/dev/digitaldoor && .venv/bin/python tools/publish.py --root /srv/door --dry-run`
4. Caddy に見本を写し、`sudo caddy validate --config /etc/caddy/Caddyfile` で確かめてから `sudo systemctl reload caddy`
5. Cloudflare の DNS に door.aiseed.dev を足す
6. ログの置き場を作り(例: `mkdir -p ~/log/digitaldoor`)、`crontab -e` で一行を足す。見本は `deploy/web/crontab.example` です
   - 公開(間隔は例): `*/10 * * * * cd ~/dev/digitaldoor && .venv/bin/python tools/publish.py --repo ~/dev/digitaldoor --root /srv/door >> ~/log/digitaldoor/publish.log 2>&1`

選んでいる物: 写しの取りに行く先は、今は GitHub を https で読む形です。公開の写しの `origin` は `https://github.com/aiseed-dev/digitaldoor.git` で、deb2 からは読むだけで push しません。deb2 の Forgejo(git.aiseed.dev)に替えるときは、写しで `git remote set-url origin <Forgejo の URL>` を行います。道具は取りに行く先を決めません。

### ディレクトリの構成

| ディレクトリ・ファイル | 内容 |
|---|---|
| `articles/guide.adoc` | 解説記事。規格と機器の説明。番号順に並び、`/guide/` に公開されます |
| `articles/blog.adoc` | ブログ記事。時事のノート。日付順に並び、`/blog/` に公開されます |
| `articles/assets/blog/<記事ID>/` | 記事で使う画像や PDF |
| `news/` | ニュース。`SKILL.md`(手引き)、`好み.adoc`(分野、まず見る所、件数)、`tsukuru.py`(AI の CLI に今日の分を書かせる)、`YYYY-MM-DD.adoc`(1 日 1 つのニュース) |
| `html/` | 公開する HTML。`index.html`、`404.html`、`license/`、`_headers`、`css/`、`images/` は手で編集します。`guide/`、`blog/`、`news/`、`sitemap.xml`、`feed.xml` はビルドで自動生成されます。`check/` は `tools/build_check.py` が `docs/確かめの始め方.md` から作ります |
| `tools/` | ビルドスクリプト。ビルドの仕組みは aiseed.dev のサイトと同じものです |
| `site.json` | サイトの設定(サイト名、URL、記事のシリーズ) |
| `skills/` | AI に読ませる手引き(スキル)。`smart-door-dev/`(扉のソフトウェアを作る)、`sesame-app/`、`door-minipc/`、`system-check/`(コードを読んで穴を見つける)、`incident-response/`(事故の対応と備え)、`detection/`(見張りを作る。道具は `scripts/`)、`kagi/`(道具 kagi の使い方) |
| `kagi/` | 道具 kagi(別パッケージ digitaldoor-kagi、AGPL-3.0-or-later)。扉の鍵ではなく、サーバーと業務システムの秘密の在庫・口・記録・機械の形を表と突き合わせます。説明は `kagi/README.md`、設計は `kagi/docs/設計書.md` |

記事は AsciiDoc 形式で、1 つのファイルに全記事を書きます。日本語だけで書けます。英語版を付ける場合は `ifdef::lang-en[]` のブロックを追加します。

## 記事の書き方


記事は `// ===== article: <記事ID> =====` という行で区切ります。その後にフロントマター(`slug`、`date`、`title.ja`、`subtitle.ja`、`description.ja`、`category.ja`)を書き、`ifdef::lang-ja[]` から `endif::[]` の間に本文を書きます。出典は記事の末尾に「== 出典」という見出しでまとめ、誰がいつ書いた記事かが分かるようにします。

## ニュースの仕組み

ニュースは、aiai のニュース(https://aiai.aiseed.dev/news/)と同じ作り方です。開発機の AI の CLI(Claude Code など)が、手引きと好みに沿って元の記事を開いて確かめ、1 日 1 つの adoc を書きます。人が読んで直し、commit します。サイトに載るのは、commit した adoc だけです。サーバー(deb2)と GitHub Actions では作りません。API キーも置きません。CLI は、その PC でログインした物を使います。

| ファイル | 中身 |
|---|---|
| `news/SKILL.md` | 手引き。守ること、毎日の手順、adoc の書き方。チャットの AI にも、CLI にも読ませられる |
| `news/好み.adoc` | このサイトの好み。分野(層の名前)と分野ごとの見る目、まず見る所、地域、言葉、件数、扱わない物。件数や分野を変えるときは、このファイルを直す |
| `news/tsukuru.py` | 手引きと好みと前の数日の見出しから頼み文を組み、選んだ AI の CLI を動かして、今日の adoc を書かせる。できたファイルの形も確かめる。標準ライブラリだけ |
| `news/YYYY-MM-DD.adoc` | 1 日 1 つのニュース。1 件が 1 つの `==` の節で、分野、国・地域、種別(発表、報道など)、本文、出典(資料の名前、日付、URL、確かめた日)が入る |

```bash
.venv/bin/python news/tsukuru.py --ai claude      # Claude Code で今日の分を書かせる
.venv/bin/python news/tsukuru.py --ai gemini      # Gemini CLI で
.venv/bin/python news/tsukuru.py --ai codex       # Codex CLI で
.venv/bin/python news/tsukuru.py --prompt-only    # 頼み文だけを出す(CLI の無い AI に貼る)
.venv/bin/python news/tsukuru.py --check news/2026-11-11.adoc   # 書いた adoc の形を確かめる
```

毎日の流れ:

1. `news/tsukuru.py --ai claude` で今日の下書きを書かせる(数分かかる)。書く物が無い日は、ファイルを作らない
2. 人が読んで直す。載せない件は節ごと消す。発表と報道の書き分け、出典の URL と日付を見る
3. ビルドする: `.venv/bin/python tools/build_news.py`(ニュースの頁とトップのニュース欄)、続けて `tools/build_feed.py`。確かめは `tools/serve.py`
4. commit する。push は本人が内容を確かめてから行う。push した main を、deb2 の `tools/publish.py` が取りに行って公開する(「公開」の節)

書くときの決まりは `news/SKILL.md` の「守ること」にあります。会社が正式に発表したことと、報道されただけのことを分け、誰が、いつ、どこに書いたかを添えます。製品名と会社名は原文のまま書き、個人名は公開の報道にある物だけを書きます。

## 実演(デジタル錠の開け閉めは簡単、鍵の管理は難しい)

どこでも同じ手順で見せられる実演です。伝えることは二つです。デジタル錠を開け閉めするのは簡単で、誰でも作れること。難しいのはデジタルキーの管理で、それは各管理者が自分で持つ仕事であること(解説 17)。

### 持ち物と前提

- miniPC 一台(Debian、Bluetooth のアダプタ)と、CANDY HOUSE の Sesame。網はつながない。扉の判断も鍵の確かめも、その場の機械だけで行う
- 実機が無いときは疑似の Sesame(`--fake`)で同じ手順を見せる
- Sesame の鍵(`sesame-keys.json`)は miniPC の手元だけに置く

### miniPC の準備

miniPC には Debian 13 を最小構成で入れます。手引きは `skills/door-minipc/SKILL.md` にあり、一般の作法は連載「Claudeと一緒に育てるDebian サーバー」(https://aiseed.dev/debian-server/ )に沿います。順は次のとおりです。

1. netinst で入れる。tasksel は「SSH server」と「standard system utilities」だけ。root のパスワードは空欄にし、一般のユーザーに sudo を与える。ロケールは英語
2. SSH を鍵だけにする(`/etc/ssh/sshd_config.d/99-hardening.conf`)
3. `sudo apt install bluez avahi-daemon avahi-utils python3-venv git ufw unattended-upgrades needrestart`。開発の道具(コンパイラーなど)は入れない
4. digitaldoor を取ってきて `.venv` に入れる(下の「準備」)
5. ファイアウォールを、入りも出も既定は拒否にし、SSH、Matter(5541/udp)、mDNS(5353/udp)、盤の画面(8798/tcp)だけを同じ網から許す。扉の HTTP の口(8797/tcp)は開けない
6. 実演の前の日に、更新、`bluetoothctl show`、`tools/jitsuen.py check`、ホームアプリで盤の QR を読めることを確かめる

root の作業は本人が行います。画面を付けるか、網のつなぎ方、ディスクを暗号化するか、扉と盤を手で起動するか systemd にするかは、持ち主が選び、その miniPC の覚え書きに書きます(リポジトリには入れません)。持ち運ぶ miniPC には、実演用の Sesame の鍵だけを入れます。

### 準備

```bash
.venv/bin/pip install -e ./controller -e . -e "drivers/digitalkey-sesame[app]"
bluetoothctl show                                     # アダプタがあること
.venv/bin/python tools/jitsuen.py check --lock sesame:<機器の UUID>   # 錠に届くこと
```

### 道具

`.venv/bin/python tools/jitsuen.py (--fake | --lock sesame:<UUID>) [--yes] <場面>`。`--fake` か `--lock` のどちらか一つを指定します。`--yes` は Enter を待たずに進めます(テストで使います)。場面は `check`(錠に届くことの確認)、`kantan`、`sono-hi`、`kigen`、`keiro`、`more`、`kiroku`、または `all`(`kantan` から `kiroku` まで順に全部)。一つの場面は一つの手順ずつ進み、Enter で次へ行く。結果は「開きました」「拒みました: 期限の外」のような短い日本語で出す。場面ごとに一時の置き場を作り直すので、どの場面からでも、何度でも始められる。錠に届かないときは、例外を見せずに「Sesame に届きません。電源と Bluetooth を確かめてください」と出す。

| 場面 | 見せること | 起きること |
|---|---|---|
| `kantan` 開け閉め | 開け閉めは部品の仕事。数行で書け、AI でも書ける | 錠のドライバで直接、開ける、閉める。次に疑似の扉の口(`POST /unlock`)から開ける。どちらでも Sesame が動く |
| `sono-hi` その日の鍵 | 扉は網が無くても、発行者の署名と期間を自分で確かめる | 清掃の人に 9〜12 時の資格情報を出す。時計を 10 時にして提示すると開く。13 時にすると「期限の外」で拒む |
| `kigen` 止めたつもり | 網の届かない扉では、失効は有効期限でしか効かない(R-AC-03、R-AC-14) | 辞めた人に 30 日の資格情報を出してある。台帳で失効しても、扉に届かないので、時計を 10 日進めて提示すると開く。1 日の資格情報を毎日出し直す形なら、翌日には「期限の外」で拒む |
| `keiro` 経路が散る | 一人の鍵が経路ごとに散ると、止め漏れが起きる(R-AC-15) | 受け入れの台帳で、同じ人に「スマートフォン」と「暗証番号」の二つの経路の鍵を出す。スマートフォンの鍵だけ失効する。暗証番号の経路で解錠すると開く |
| `more` 発行者の鍵が漏れたら | 発行者の鍵を持つ者は、誰にでも鍵を出せる。信頼を変えられるのは管理者の鍵だけ(R-AC-11、R-AC-12) | 漏れた発行者の鍵で、知らない人の資格情報を作ると開く。管理者の鍵で、その発行者を信頼の一覧から外す。同じ資格情報は「知らない発行者」で拒む。一字書き換えた資格情報は「署名が合わない」で拒む |
| `kiroku` 記録で確かめる | 起きたことは、改ざんの分かる記録に残る(R-CT-11〜16) | ここまでの記録の連鎖を検べて「連鎖は正しい」と出す。記録の写しを一字書き換えて検べると、何番で壊れたかを出す |

### 作った物

- 扉コントローラの命令 `keygen`、`issue`、`trust-change`(扉コントローラ仕様書 第9章)。controller の側(Apache-2.0)。説明は `digitaldoor-controller <命令> --help`
- 錠のドライバで動く接点 `digitalkey/contacts.py` の `LockDriverContacts`(`digitalkey` の側、AGPL)。扉のコントローラの接点の口(`fire`、`mains`、`door_open`、`bolt_out`、`set_lock`)を満たし、`set_lock` を `digitalkey.locks` の錠のドライバ(非同期の `unlock()` / `lock()`)につなぐ。錠の銘柄は接点の下に隠れる(R-CT-03、R-CT-04)。錠に届かないときは、例外を出さず、錠の位置の記録を動かさず、`failures` と `last_error` に残す(詳しくは `digitalkey/contacts.py` の docstring)
- `tools/jitsuen.py`。上の場面を順に進める道具。疑似の扉は同じプロセスの中で、錠のドライバで動く接点を差して開く。説明は `tools/jitsuen.py --help`。疑似の Sesame は `drivers/digitalkey-sesame` の `FakeSesameLock`
- テスト。疑似の Sesame で、場面ごとの結果(開いた、拒んだ、拒んだ理由)が上の表のとおりになること(`tests/jitsuen/`)。鍵の命令は `controller/tests/test_cli_keys.py`

```bash
.venv/bin/python tools/jitsuen.py --fake --yes all      # 疑似の Sesame で全部を、Enter を待たずに
.venv/bin/python tools/jitsuen.py --fake keiro          # 一つの場面を、Enter で進めながら
```

`keiro` の台帳の経路は、様式 `鍵_発行` の名前に合わせ、スマートフォンの鍵を「遠隔解錠」で出します。`all` は `check` を含みません(`check` は準備の確認です)。

### 実機の Sesame を miniPC の Matter の電子錠として見せる

スマートフォンのアプリに入っている Sesame の鍵を miniPC に写し、miniPC を Matter の電子錠として見せます。スマートフォンの鍵は残したまま使えます。流れは、32 桁を見せる → 取り込む → 扉を立てる → 盤を開く → ホームアプリで QR を読む、です。

#### miniPC に要る物

- Bluetooth(BLE)のアダプタ。USB の物でよい。`bluetoothctl show` で見えること
- `avahi-utils`(Matter の広告に `avahi-publish-service` を使います)と、動いている `avahi-daemon`。入れるのは root の作業です(`sudo apt install avahi-utils`)。`systemctl status avahi-daemon` で動作を確かめます。無いまま `digitalkey panel` を起動すると、直し方を標準エラーに出して止まります
- Python の環境。`.venv/bin/pip install -e ./controller -e ".[panel]" -e "drivers/digitalkey-sesame[app]"`
- miniPC とスマートフォンが、同じ網に載っていること。広告(mDNS)が届けばよく、網の作り方(会場の Wi-Fi、持ち込みのルーター、テザリング)は会場で選びます。前の節の実演の道具は網を使いませんが、Matter のペアリングは同じ網のスマートフォンが相手です

#### 手順

1. スマートフォンのアプリの管理者の画面で、「渡す」から Sesame を選び、相手の呼び名(「miniPC」など)を入れて「32 桁を見せる」を押す。確かめのあとに 32 桁が出て、閉じると消える。人に見せず、チャットやメールに貼らない。(前の版のアプリなら、Sesame を選んで「鍵を書き出す」)
2. miniPC で Sesame の UUID を調べる。`digitalkey sesame scan`
3. miniPC で取り込む。`digitalkey sesame import <UUID> --name 玄関`。32 桁を入力し(画面に出ない)、続けて管理者の符号を尋ねられるので、利用者のままなら空の Enter、管理者として写すなら画面に出た符号を入力する。その鍵でログインできることを確かめてから保存する。ログインできなければ何も保存しない。扉を立てるだけなら役はどちらでもよい(役は画面の歯止めで、命令行は鍵があれば動かせる)
4. 錠に届くことを確かめる。`.venv/bin/python tools/jitsuen.py check --lock sesame:<UUID>`(施錠の命令を一つ送る)
5. 扉を立てる。`digitalkey door-serve --lock sesame:<UUID> --name genkan --dir <置き場>`。`digitaldoor-controller serve` と同じ引数に、錠の指定を足した命令で、扉の HTTP の口(既定 `http://127.0.0.1:8797`)を開く。自動施錠の秒数は `--autolock` で選ぶ(0 なら自動施錠なし)。失効の一覧が届かない間に長い期限の資格情報を拒ませる時は、`--revocation-max-age <秒>` で失効の知らせの古さの上限を選び(既定 0 はこの規則を使わない)、鍵の管理の台帳にも同じ値を分で書く(`digitalkey kanri door add --name genkan ... --revocation-max-min <分>`。秒 = 分 × 60)。台帳はこの値で、失効が扉で効くまでの時刻を見立てる
6. 別のターミナルで盤を開く。`DIGITALKEY_DOOR_DIR=<置き場> digitalkey panel`。盤の画面(既定 `http://127.0.0.1:8798`)に Matter の QR が出る
7. スマートフォンのホームアプリで、アクセサリを追加して盤の QR を読む。試験用の証明書で動かしているので、未認証のアクセサリと表示されることがある。追加を続ける
8. ホームアプリから解錠・施錠すると、Sesame が動く。盤の画面の状態と記録にも残る

終わるときは、盤と扉を Ctrl-C で止めます。盤は、止めるときに広告の子プロセス(`avahi-publish-service`)も終わらせます(SIGTERM と SIGHUP でも同じ)。SIGKILL で落とした場合は、`pkill -f avahi-publish-service` で消し、`fuser -k 5541/udp 8797/tcp 8798/tcp` で口を空けます。

#### 選んだこと

- 取り込みの確かめ(ログイン)は必ず行い、飛ばす選択肢は置いていません。間違った鍵を置くと、実演の場で初めて動かないと分かるためです
- 鍵の 32 桁は、「32 桁を見せる」の画面で 4 桁ずつ空白で区切って出します。取り込みは空白とハイフンを読み飛ばすので、そのまま打てます
- 扉は、起動のとき錠の位置を読まず、施錠側として始まります。Sesame が解錠のままなら、先に施錠してから立てます
- 錠への一回の命令を待つ秒数は `--timeout` で選びます(BLE は探して、つないで、送るので、短くしすぎないこと)。錠に届かなかった命令は、扉の判断を止めず、標準エラーに一行ずつ出ます
- 鍵の置き場(`sesame-keys.json`)は miniPC の手元だけに置き、権限は 600 です。ログと標準出力には鍵を出しません。`digitalkey sesame keys` も鍵を出しません

## ソフトウェア(digitalkey)の設計方針

台帳・鍵の発行・本人確認(entrance)の設計判断です。扉のコントローラ(door)は [扉コントローラ仕様書.md](扉コントローラ仕様書.md) を参照してください。

2026-09-16 の対話で決めたことを、コードの前提として並べる。由来は案件メモ(akiya-minpaku-system)。

### 作らないもの
- 読取機。顔はドアホン、身分証は客のスマートフォン、鍵は錠の暗証番号か財布(Aliro)が受ける
- 機器。ドアホン(Nest/Ring、将来Apple)、後付け錠(Sesame/Matter)、火災報知(特定小規模施設用)は買う
- 画面。客のチェックイン一枚だけ。経営者は台帳と依頼で回す

### 構造で保証する三つ
1. 伝票を運ぶ — 一枚が自己完結の AsciiDoc。表題・属性(様式・番号・発行者・宛先・発行日時・根拠・前ハッシュ)・項目
2. 記録を変えない — ファイルは `x` で作り読み取り専用にする。訂正は新しい伝票で、前の番号を根拠に書く。連鎖(前ハッシュ)で改ざん・削除・挿入を検出
3. 持ち主以外に書かせない — 様式の `:書ける:` に名前か役割。門(web)と CLI だけが書く

検査するのは構造(様式の制約・権限・追記)だけ。内容の正しさは事後の突合(依頼)に回す。
様式の check 制約のうち評価するのは数の範囲だけ。他は台帳に書いて人と AI が読む。

### 様式
- 唯一の定義は AsciiDoc(`項目:: [SQL語彙] 説明`)。aiseed-migration-kit DESIGN §5 の流儀
- 型と制約は SQL の語彙。独自の型体系は作らない
- 修復は制約から一意に導けるものだけ(NFKC、和暦→ISO、全角数字)。導けないものは受理しない
- 表示の都合は属性にせず、説明文に日本語で書く

### 本人確認
- 要領の A(顔と旅券が鮮明)を客のスマートフォンが、B(届出住宅か近傍から発信)をドアホンと位置情報と時刻差が受け持つ
- 判定は AI社員 でよい(要領は人の目を求めていない)。迷うものは保留、人が判定し直した伝票を足す。判定者の名前は必ず残す
- 顔の照合は差し替え(Matcher)。同梱の StubMatcher は配線確認用
- 画像は金庫の `画像/` に内容のハッシュ名で置き、伝票にはハッシュだけ書く

### 箱を置かない構成もできる(2026-09-16)
- 家に箱を置くかどうかは決めていない。置かない構成が取れるように、錠の駆動を Web API 経由でも組めるようにした
- 置かない構成: 家にあるのは機器と回線だけ(ドアホンは三社のクラウド、錠は Sesame + Hub 3 で Wi-Fi に載り CANDY HOUSE の Web API か Matter で外から操作、火災報知、ルーター)。entrance は経営者の自宅 PC か経営者名義の VPS。客のチェックイン画面には公開の住所が要る
- 置く構成: 家の小さな機械で entrance を動かし、錠は BLE 直結。網が無い家や、記録を家の中に置きたい場合
- 錠の駆動は三択で差し替え: `SesameWebLock`(Web API、Hub 3 経由、既定)/`SesameLock`(BLE 直結、家に箱を置く場合や網が無い場合の逃げ道)/Matter(制御機が家にあるとき)
- どちらにするかは家ごとに経営者が決める

### 鍵
- 鍵は伝票。発行(主体・錠・経路・開始・終了)と失効(鍵番号・理由)。解錠は「発行済み・未失効・窓の中」だけを見る
- 解錠の結果(成功・拒否・失敗)は必ず伝票に残す。機器の失敗も

### 事業所サーバーの口とトークン(2026-11-11)

開発用ミニサーバーの要求 R-DV-12(認証はローカルのトークンで行い、権限モデルの主体に対応づける)を、事業所サーバー(`digitalkey/site`)の HTTP API で満たす。扉のコントローラの HTTP の口は同じ機械の中の口で、トークンを持たない(扉コントローラ仕様書 5.2、5.5)。

- トークンは事業所サーバーの中だけで作り、確かめる。外のサービス(ID の提供者、クラウド)を通さない
- 役割と、要求仕様の共通コア 7.1 の主体の対応は次のとおり。`GET /me` が、名前、役割、主体、鍵の主体名を返す

| 役割(site.toml の role) | 主体(共通コア 7.1) | できること |
|---|---|---|
| 管理者 | 管理者 | 全部。鍵の発行と失効、扉の記録、記録の検査 |
| 受付 | 運用者 | 鍵の発行、解錠と施錠、鍵の操作の記録 |
| 利用者 | 利用者 | 自分の鍵の一覧と、自分の鍵での解錠 |
| 保守 | 保守者 | 状態、施錠、扉の記録、記録の検査。解錠は管理者が発行した鍵で行う(R-AC-06) |

- 設定(site.toml)にはトークンの SHA-256(`token_sha256`)を書き、トークンそのものは書かない。トークンは作ったときに一度だけ画面に出す。前からの設定の `token`(そのままの値)も読む
- トークンを足すのは `digitalkey site token --config site.toml --name <名前> --role <役割> [--subject <主体名>]`。設定の末尾に一つ足し、同じ名前は足さない。止めるときは設定からその行を消して、サーバーを起動し直す
- 届いたトークンは SHA-256 にしてから照らす。違うトークンは 401、役割の外の操作は 403 で、応答にトークンを入れない
- どの役割に何を許すかの表は、`digitalkey/site/api.py` の先頭に書き、テストで役割ごとに全部の口を叩いて確かめる

### 予約と資格情報の発行の口(2026-11-11)

開発用ミニサーバーの要求 R-DV-13 の主要なリソースのうち、予約と資格情報(発行、失効、期限)を、事業所サーバーの HTTP API に置く。記録は台帳の伝票で、追記だけで扱う。

| 口 | 役割 | 中身 |
|---|---|---|
| `POST /reservations` `{subject, layer, arrival, departure, door, contact}` | 管理者、受付 | 様式「予約」の伝票を書く。受付符号を作って返す |
| `GET /reservations` | 管理者、受付 | 予約の一覧。取り消した物は `cancelled` に取り消しの伝票の番号が入る |
| `GET /reservations/{id}` | 管理者、受付 | 一件と、その予約で出した鍵の一覧 |
| `POST /reservations/{id}/keys` `{route}` | 管理者、受付 | 予約の主体、錠、到着から出発までで、様式「鍵_発行」の伝票を書く。予約番号と根拠に予約の番号を入れる。取り消した予約には出さない(409) |
| `POST /reservations/{id}/cancel` `{reason}` | 管理者、受付 | 様式「予約_取消」の伝票を書き、その予約で出した、まだ失効していない鍵を全部失効する(様式「鍵_失効」、理由「予約の取消」)。二度目は 409 |
| `POST /keys/{id}/credential` `{once}` | 管理者、受付 | 鍵から、扉が自分で確かめる署名つき資格情報(扉コントローラ仕様書 5.2a)を作って返す。様式「資格情報_発行」の伝票を残す。失効した鍵、期限の外の鍵には出さない(409) |
| `GET /issuer` | 管理者、受付、保守 | 発行者の公開鍵と識別、資格情報の最長の有効時間。扉の信頼の一覧に入れるときに使う(秘密は無い) |
| `POST /doors/{id}/credential` `{credential}` | トークンを持つ全員 | 資格情報をその扉のコントローラに見せる。扉が署名、範囲、期限、一回限りを自分で確かめる |

- 資格情報の有効の終わりは、鍵の終わりと、作った時刻に最長の有効時間を足した時刻の、早い方にする。網が届かない扉で失効が効くまでの最長の時間(R-AC-14)を、この値で決める。最長の有効時間は site.toml の `[credentials] max_hours` で設定し、`GET /issuer` が返す
- 発行者の鍵(Ed25519)は事業所サーバーの金庫(`<vault>/発行者.ed25519`、権限 600)に置き、初めて使うときに作る。取り出せない所(R-AC-11)に移すときは、`digitaldoor_controller.audit.Ed25519Signer` と同じ口(`sign`、`public_key`)で差し替える
- 事業所サーバーの中の扉のコントローラは、扉の名前を設定の `id` にし、この発行者を信頼する(範囲は設定にある扉の全部)。外の扉に入れるときは、管理者の鍵で信頼の一覧の変更の要求を作る(`digitaldoor-controller trust-change`)
- 伝票を書く名前は、トークンの名前とする(受付の名前で書けない様式には書かない。台帳の `:書ける:` が正)
- 時間帯(曜日と時刻)の制限は、まだ資格情報に入れていない。今の資格情報は開始と終了だけを持つ

### 更新の配布(2026-11-11)

開発用ミニサーバーの要求 R-DV-30〜40(売りながら直し続けるための更新)を、`digitalkey update`(`digitalkey/update.py`)で満たす。対象は事業所サーバーとミニサーバーのソフト(この版の置き場)で、錠と扉のコントローラのファーム(R-DV-37、供給元の Matter OTA など)は扱わない。

| 物 | 作った物 |
|---|---|
| 更新の包み(`.ddupd`) | tar の中に、`manifest.json`、その署名 `manifest.sig`(Ed25519 の 16 進)、`files/` の下の中身。manifest は `format`(`digitaldoor-update/1`)、`product`、`version`、`reason`(不具合 / 規格改定 / セキュリティ)、`summary`、`files`(相対の道とその SHA-256)、`compat`(部品の名前と、合う版の一覧) |
| 配布の表(`index.json` と `index.sig`) | 製造者が署名する。版ごとに、届ける段(`開発` / `試験導入棟` / `全棟`)、止めたか(`halted`)、サポートの終わり(`support_until`)、緊急の経路の判断(`emergency`: 誰が、なぜ)を持つ。表には通し番号(`serial`)を付け、前より小さい表は受けない |
| 署名を確かめてから当てる(R-DV-30) | 当てる前に、表の署名、包みの署名、中身の SHA-256 を全部確かめる。信じる公開鍵は、そのサーバーの設定(`update.toml` の `trusted_keys`)にある物だけ。一つでも外れたら何も変えない |
| 段階配布(R-DV-31) | サーバーは自分の段を設定に持つ。`開発` は全部の段の版を、`試験導入棟` は試験導入棟と全棟の版を、`全棟` は全棟の版だけを受ける。表で `halted` の版は、どの段でも当てない。製造者は表の段を書き換えて進め、`halted` で止める |
| 緊急の経路(R-DV-39) | 表の版に `emergency` があれば、段を待たずに全部のサーバーが受ける。判断(誰が、なぜ)を表に書き、当てた記録にも写す |
| 当て方と戻し方(R-DV-32、R-DV-21) | 版ごとに `releases/<版>/` に展開し、`current` の記号リンクを一度に付け替える。付け替える前に、データの置き場を `backups/` に tar で取る。付け替えた後に確かめの命令(設定の `check`。無ければ確かめない)を回し、失敗したら直前の版へ自動で戻して、戻したことを記録に残し、知らせの命令(設定の `notify`)を呼ぶ |
| 網の無い現場(R-DV-33) | 包みと表を USB などで持ち込み、`digitalkey update apply --package <包み> --index <表>` で当てる。確かめは網があるときと同じ |
| 止まる時間(R-DV-34) | 付け替えと確かめにかかった秒を記録に残す。錠の解錠の判断は錠と扉のコントローラの中にあり、更新はそれを止めない |
| 互換表(R-DV-36) | サーバーは自分の部品の版(Matter のコントローラ、錠のファームなど)を設定の `components` に持つ。包みの `compat` と照らし、合わない部品を警告として出し、記録に残す。警告で止めるかは設定の `block_on_incompatible` で選ぶ |
| 事前の知らせと記録(R-DV-38) | `digitalkey update notice` が、版、対象、理由、要約を、管理会社へ送る文として出す(送るのは人)。当てた結果、戻した結果、拒んだ結果は、更新の記録(`update-log.jsonl`、前の行のハッシュを持つ追記だけの記録)に残す |
| サポート期間(R-DV-40) | 表の `support_until` を過ぎた版で動いているかを `status` が示す。`status --json` を集めた置き場を `digitalkey update fleet <置き場>` に渡すと、期限切れの版で動くサーバーを一覧にする |

選んでいる物: 段の名前は要求仕様の三つ。署名は Ed25519(扉の伝票と同じ)。サーバーが表を取りに行く先と回数、知らせの送り先は、運営者がサーバーごとに決めて設定に書く。

### 金庫と控え
- 記録は経営者の箱。控えは経営者の箱で gpg(AES256、合言葉は経営者)してから経営者名義の国内 VPS へ rsync
- 保存年限(様式の `:保存年限:`)を過ぎた伝票は候補として挙げるだけ。消すのは経営者

### 三層と WWOOF
- 同じ家に会議室(時間)・民泊(1泊〜)・貸家(1ヶ月〜)が重なる。仕組みは一つ、様式が三組
- WWOOF は宿泊料ゼロで両法の外。手伝いは1日6時間が基本、お金は渡さない、保険と在留資格は台帳に

### Apple の認証(2026-09-16 整理)
- パスキー(WebAuthn): 可。許可も費用も要らない。客の iPhone の Face ID が端末の中で鍵を開き、こちらには署名だけ届く。
  用途は初回の本人確認の後の「同じ人・同じ端末」の証明(二回目以降の解錠・退去まで)。法律上の本人確認(顔と旅券)の代わりにはならない
- Sign in with Apple: 可だが開発者アカウント(App ID + Services ID)が要り、得られるのはメールと名前だけ
- iPhone のマイナンバーカード(2025-06〜): 日本人の本人確認に有力。ただしスマホ JPKI は主務大臣の認定、Wallet の提示はデジタル庁への申請が要る。
  現実解は認定済みの eKYC 事業者(サイバートラスト iTrust、LIQUID eKYC)を通す(一回いくら)。要領 2024-12 改正で確認書類の例にマイナンバーカードが入った
- Apple Wallet の鍵(Home Key / Aliro): 今は無理。Apple との契約と Aliro 読取機が要り、日本に Aliro 錠が無い。Face ID の生体そのものは外に出ない
- Apple Wallet Access Program の構造(2026-09-16 公式ガイドで確認): 役割は三つ。Credential Manager(アクセス基盤の提供者。Apple Access platform と統合し、pass の配布と一生を管理)、
  Credential Provider(暗号要素を握る読取機・錠の製造者)、Participating Provider(物件の所有者・管理者。Participating Provider Agreement に署名し、Credential Manager 経由で参加)。
  Credential Manager の要件: 稼働率 99.99%、p90 2.2 秒以下、複数リージョンの active-active、P1 は 15 分以内、QA/負荷/本番の三環境、経営幹部のスポンサー、読取機の Apple IOT 認証。
  入口は access-partnerships@group.apple.com への問い合わせ → 質問票 → 事業・技術の審査 → Apple Business Register。
  帰結: 家(民泊・貸家)は Participating Provider として、日本で Credential Manager になった事業者の顧客になる形で届く。自分が Credential Manager になるのは別会社・別の規模の話

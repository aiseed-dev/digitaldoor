# 鍵の管理ソフト 設計書(下書き、2026-11-11)

## 0. この文書について

鍵の管理者が自分の機械で動かす、鍵の管理のソフトウェアの設計です。誰に、どの扉とどの機器の権限を、いつまで出し、いつ止め、何が起きたかを、一つの台帳で扱います。

名前は「鍵の管理」ですが、扱うのは扉の鍵だけではありません。網につながる機器(PC、スマートフォン、プリンター、ルーター、センサー、カメラ、扉と錠と読取機)も、同じ台帳に載せて管理します(7a 章、2026-11-11 に運営者が決めた事)。機器を管理するとは、その機器の持ち主と置き場を知り、誰がその管理者の権限を持つかを決め、更新を当て続け、使い終えたら権限と中身を消すことで、人に鍵を出して止める仕事と同じ形をしています。

- **状態。** 設計の下書きです。実装はまだありません。運営者が読んで直してから、仕様、テスト、実装の順に進めます(17 章)。
- **書き方。** 「選んでいる物」は、この設計で形を決めた物です。「作る時に選ぶ物」は、実装の時に決めて、ここに書き足します。「管理者が設定する物」は、ソフトが値を持たず、使う会社や家の管理者が決めます。値(期限の長さ、回数、時間、段階)は、この文書では決めません。
- **元にした文書。**
  - 要求: [要求仕様 00_core](要求仕様/00_core.md) の第 6 章(R-LG)、第 7 章(R-AC-01〜22)、8.3(R-RS-01〜18)、[12_entrance_business](要求仕様/12_entrance_business.md) の R-EB-33〜37、[11_entrance_apartment](要求仕様/11_entrance_apartment.md) の R-AP-24、33、35、38、39
  - 扉との境目: [扉コントローラ仕様書](扉コントローラ仕様書.md) の 5.1(記録の伝票)、5.2a(署名つき資格情報)、5.2b(鍵の階層)
  - 整理と筋書き: [鍵の管理の問題の整理](鍵の管理の問題の整理.md)、[鍵の管理の開発のシナリオ](鍵の管理の開発のシナリオ.md)、[権限の申請の雛形](権限の申請の雛形.md)
  - 役、物、鍵、機械、出来事の流れの並べ方は、運営者の別のリポジトリ(seed)に 2026-11-05 に書いた「層 2 発行と台帳」の設計を取り込みました。この文書が、digitaldoor の側の正になります。
- **新しい要求は足していません。** 今ある要求を、一つの動くソフトウェアの形に並べた物です。足りない要求に気づいた所は 18 章に挙げます。

## 1. 何を作り、何を作らないか

### 作る物

管理者が、網から切り離した自分の機械でも動かせる(R-AC-19)、次の七つの働きを持つソフトウェアです。

| 働き | 中身 |
|---|---|
| 名簿 | 鍵の要る全員を載せる正の台帳(R-EB-37)。社員、派遣、清掃、警備、業者、来客、住人、宿泊者 |
| 機器の台帳 | 網につながる機器の全部を載せる正の台帳。PC、スマートフォン、プリンター、ルーター、センサー、カメラ、扉と錠と読取機。責任者、置き場、網の区画、版と更新の期限、管理者の権限、廃棄(7a 章) |
| 権限 | 誰が、どの扉(または群、システム)に、いつからいつまで、どの時間帯に入れるか。申請、承認、発行、失効の伝票 |
| 発行 | 承認された権限を、経路ごとの形(署名つき資格情報、暗証番号、カード、物理キーの貸し出し、アカウント)にして出す |
| 失効 | 一人の全経路を一度の操作で止め(R-AC-15)、止まったことを経路ごとに確かめる |
| 記録 | 追記だけの台帳。扉から届く署名つきの記録の伝票を受け取り、検べ、台帳と結ぶ |
| 出来事の手順 | 紛失、退去と退職、管理者の交代、持ち主の交代、鍵の漏れの手順(R-AC-16)を、段ごとに進めて記録する |

### 作らない物

- 読取機、錠、ドアホン。買う物です。
- スマートフォンの財布に鍵を載せる基盤。載せ方を担う業者は運ぶだけで、署名は管理者の機械でします(R-AC-20)。このソフトは、財布を「発行者の一つ、経路の一つ」として扱う口だけを持ちます(R-AC-18)。
- 多くの会社の鍵を一か所で預かる仕組み。一つの動かす単位は、一人の管理者(一つの発行者)の分だけです(R-AC-09)。
- 本人を確かめる ID の提供者。サインインは部品(aiai-tools の ninshou)を使い、最初の一回は窓口で人が確かめます。
- ディレクトリ(Entra ID など)や ERP から権限を自動で出す仕組み。読むのは、照らし合わせのためだけです(R-EB-34、37)。

## 2. 使う人と役

| 役 | 誰 | できること | できないこと |
|---|---|---|---|
| 管理者 | 鍵の管理者(会社は情報システム部門、分譲の共用部は管理組合、住戸は区分所有者、民泊と貸家は経営者) | 扉が信頼する発行者の一覧を変える(R-AC-12)。発行者の鍵を足す、外す。扉の設定の変更を承認する(R-CT-05)。出来事の手順を始める | 資格情報に自分の鍵で署名すること(管理者の鍵は発行に使いません。5.2b) |
| 名簿の係 | 人事、総務、経営者 | 主体を足す、変える、止める。人事の届けを入れる | 承認、署名 |
| 承認する人 | 管理者が決めた人 | 申請を確かめて承認する、却下する | 自分の申請の承認(一人で回す所のために、管理者が設定で許した時を除く。許した事と、自分で承認した事は記録に残る。19.7) |
| 発行者(機械) | 閉じる機械の中の働き | 承認の伝票がある権限だけに、発行者の鍵で署名する。失効の一覧を作る | 承認の無い発行 |
| 運用 | 機械を動かす人 | 起動、控え、復元、更新 | 鍵を読むこと、台帳を書き換えること |
| 監査 | 記録を読む人 | 記録と検査の結果を読む | 書くこと |
| 本人 | 鍵を使う人 | 申請する。自分の権限と、自分の権限が使われた記録を見る。端末の紛失を届ける | 他人の記録を見ること |

- 一人が複数の役を兼ねる所(個人の大家、小さな会社)では、役は分けたまま、同じ人が役を切り替えて入ります。記録には役が残ります。
- どの操作を二人で行うか(一人が行い、もう一人が確かめる)は、管理者が設定する物です。ソフトは、操作ごとに「確かめる人が要る」の印を持てる形にします。
- 保守の業者と製造者は、役を持ちません。入る時は、管理者が出した一時の権限で入ります(R-AC-06、10)。

## 3. 置き方

機械の分け方は、管理者が選びます。ソフトは、同じ部品を次の三つの形に置けるようにします。

| 形 | 向く所 | 機械 |
|---|---|---|
| 一台 | 個人の大家、民泊、練習 | 管理者の PC か小さな機械一台に、台帳、発行、扉の門番をまとめる。外から届く口は開けない |
| 二台 | 扉が離れた所にある家、小さな事業所 | 閉じる機械(台帳と発行)と、扉のそばの門番(扉のコントローラか、錠のドライバで動く口) |
| 分ける | 会社、集合住宅 | 閉じる機械、開く機械(申請の受付)、記録の写しの機械、扉の門番、管理者の端末 |

選んでいる物は次のとおりです。

- **閉じる機械は、外からの口を持ちません。** 申請は、閉じる機械が開く機械へ取りに行きます。開く機械が破られても、作れるのは承認されていない申請だけです(権限の申請の雛形 3 章、R-AC-13)。
- **発行者の鍵と台帳は、閉じる機械に置きます。** 外の網に向いたサービス、借りた機械、仮想化の土台を共にする機械には置きません(R-AC-11、13)。
- **記録の写しは、別の機械へ追記だけで送ります**(R-RS-12)。
- **同じ形の予備と、控えから戻す手順を持ちます**(R-AP-24、R-RS-08)。戻す訓練をした日を台帳に残します。
- **閉じる機械で動く物の一覧を持ち、毎日照らします**(R-RS-11)。道具は `kagi/` を使います。

管理者が設定する物: 機械の台数と置く部屋、管理者の端末から閉じる機械への道(同じ机の上か、WireGuard か)、控えの置き場と回数。

## 4. 物(台帳に載る物)

台帳は、`digitalkey/entrance` の追記だけの台帳(一枚が自己完結した伝票、前の伝票のハッシュの連鎖、様式が正)をそのまま使います。SQLite は索引で、正は伝票のファイルです。訂正と失効は、新しい伝票で前の伝票を打ち消します。

| 物 | 中身 | 書く役 |
|---|---|---|
| 主体 | 一人、または一つの機械。呼び名、種別(社員、業者、住人、客など)、状態(有効、停止、退出)、仮名の識別 | 名簿の係 |
| 端末 | 主体の持つ端末と、その公開鍵(R-AC-21)。登録の時に本人を確かめた伝票を根拠に持つ | 名簿の係(本人の確かめの後) |
| 扉と群 | 扉の名前、扉の記録の公開鍵、据え付けた日、扉の群。扉ごとの「失効が効くまでの最長の時間」(R-AC-14) | 管理者 |
| 機器 | 網につながる機器の一台ずつ。種類、責任者、置き場、網の区画、版、更新の期限、状態(7a 章)。扉、錠、読取機も機器の一つで、扉の欄(記録の公開鍵、最長の時間)は機器の欄に重ねて持つ | 管理者(登録と廃棄)、機器の責任者(点検の記録) |
| システム | 機器の上で動く、権限を出す相手(Web の管理画面、クラウドの管理者、業務のシステム)。機器と合わせて、権限の目録の対象になる(R-RS-04) | 管理者 |
| 権限 | 主体 × 対象(扉、群、システム)× 期間 × 曜日と時間帯 × 能力(共通コア 7.2)。申請、承認、発行、失効の伝票の組で表す | 本人(申請)、承認する人、発行者 |
| 経路の実体 | 一つの権限を、ある経路で形にした物。署名つき資格情報、錠に登録した暗証番号やカード、貸し出した物理キー、アカウントや SSH の鍵。一つの権限に複数あってよい | 発行者、名簿の係(物理キー) |
| 失効の一覧 | 失効した資格情報の識別と世代の番号。発行者の署名つき(R-AC-22) | 発行者 |
| 鍵の目録 | 管理者の鍵、発行者の鍵、扉の記録の鍵、台帳の記録の鍵、機械の鍵。置き場、触れられる人、作った日、作り直す手順、責任者(R-RS-03)。値は載せない | 管理者 |
| 手順と実施 | 出来事ごとの手順(R-AC-16)と、実際に進めた段の記録 | 管理者 |
| 届け | 人事の届け(入社、異動、退職、契約の終了)、端末の紛失の届け | 名簿の係、本人 |

選んでいる物は次のとおりです。

- **権限と経路の実体を分けます。** 止める時は権限を止め、そこから全部の経路の実体を止めます。これが R-AC-15 の「一人の全経路を一度に」の元になります。
- **主体は、扉と記録では仮名の識別で扱います。** 人と仮名の対応は名簿だけが持ちます(R-LG-07)。
- **様式は、今ある `鍵_発行`、`鍵_失効`、`鍵_操作`、`本人確認` を生かし、権限の申請の雛形 5 章の様式(権限_申請、権限_承認、権限_発行、権限_失効、端末_紛失、人事_届け)と、主体、端末、扉、鍵の目録、手順の実施の様式を足します。** 項目の名前と制約は、様式のファイルを書く時に決め、様式が正になります。
- **台帳の伝票に署名を足します。** 今の台帳はハッシュの連鎖だけです。扉の記録(`controller/` の `audit.py`)と同じ形で、台帳の記録の鍵で署名します。

管理者が設定する物: 主体の種別、扉の群の分け方、保存の期限、台帳に本名を載せるか社員番号にするか。

## 5. 鍵

扉コントローラ仕様書 5.2b の表が正です。このソフトが触る鍵と、置き場の選び方を並べます。

| 鍵 | このソフトでの使い方 | 置き場 |
|---|---|---|
| 管理者の鍵 | 信頼の一覧の変更の要求に署名する(`trust-change`)。発行者の鍵の追加と削除。年に数回の操作 | 網から外した所。使う時だけつなぐ。このソフトは、署名の要求を出して署名を受け取る口だけを持ち、秘密鍵を預かりません |
| 発行者の鍵 | 資格情報と失効の一覧に署名する。日々の操作 | 閉じる機械の、取り出せない所(R-AC-11)。無い間は、権限を絞ったファイルと、OS の資格情報の仕組みで渡す |
| 端末の鍵 | 公開鍵を台帳に載せ、資格情報に入れる | 本人の端末の安全な保管庫(R-CM-16)。このソフトは秘密鍵に触れません |
| 扉の記録の鍵 | 公開鍵を台帳に写し、届いた記録の伝票を検べる | 扉(R-LG-04) |
| 台帳の記録の鍵 | 台帳の伝票に署名する | 閉じる機械。発行者の鍵と分ける |
| 機械の鍵 | 管理者の端末、開く機械、扉の門番と、閉じる機械の間の道 | それぞれの機械 |

選んでいる物は次のとおりです。

- **一つの鍵に一つの役。** 発行者の鍵で台帳に署名しません。管理者の鍵で資格情報を出しません。
- **署名は、差し替えられる口(Signer)を通します。** 今あるソフトの Ed25519 から、取り出せない所の鍵へ差し替えられる形にします(CLAUDE.md「署名の口は後で差し替える」)。
- **鍵の値を、画面、記録、命令の引数に出しません**(R-CM-13)。
- **鍵を作る、作り直す、外す操作は、必ず鍵の目録の伝票を伴います。**

作る時に選ぶ物: 取り出せない所に何を使うか(TPM、セキュアエレメント、HSM)。署名の方式(今は Ed25519。Aliro は P-256 なので、境目の版を固める時に、方式の欄を持つかを決めます)。

## 6. 流れ

### 申請から失効まで

```
申請 → 確かめ → 承認 → 発行 → 配る → 使う → 記録が届く → 照らす
                  ↓                              ↑
                 却下         失効 → 経路ごとに止める → 止まったことを確かめる
```

| 段 | 何が起きるか | 残る伝票 |
|---|---|---|
| 申請 | 本人、または受け入れる人が、対象と期間と理由を書く。閉じる機械が、開く機械から取りに行く | 権限_申請 |
| 確かめ | 主体が名簿にあるか、本人の確かめが済んでいるか、対象が申請できる物か、期間が扉の最長の時間に収まるかを、ソフトが調べて並べる | (申請に付く検査の結果) |
| 承認 | 承認する人が判断する。自分の申請を自分で承認できるのは、管理者が設定で許した所だけで、その印が伝票に残る | 権限_承認 |
| 発行 | 承認の伝票を根拠に、経路ごとの実体を作る(7 章) | 権限_発行、経路ごとの発行の伝票 |
| 配る | 資格情報を本人の端末へ、信頼の一覧と失効の一覧を扉へ | 配った記録 |
| 使う | 扉が自分で確かめて開ける。門番を通す錠では、門番が確かめて錠を動かす | 扉の記録(扉に残り、伝票で届く) |
| 記録が届く | 扉の記録の伝票を受け取り、署名と連鎖を検べ、台帳の権限と結ぶ | 受け取りの記録 |
| 失効 | 9 章 | 権限_失効、経路ごとの失効の伝票 |
| 照らす | 12 章 | 照らし合わせの結果 |

### 扱いの原則

権限の申請の雛形の三つを、ソフトの作りにします。

1. **止めるのは自動でよい。** 期限、紛失の届け、退職の届けで、人を待たずに止めます。間違えても「開かない」側に倒れます。止めたことは記録に残り、本人に知らせます。
2. **出すのは人が確かめる。** 発行の関数は、承認の伝票の番号を受け取らないと動かない作りにします。外からの知らせ(ディレクトリ、予約の仕組み、人事の届け)は、申請を作る所までで、発行はしません。
3. **一番上の操作は人の手に残す。** 管理者の鍵の操作、発行者の鍵の作り直し、扉の前での戻し(R-AC-17)は、自動にしません。ソフトは手順を示し、済んだ段を記録します。

宿泊のように数が多く毎日変わる所で、承認を一件ずつ人がするか、管理者が先に決めた条件(本人の確かめが済み、予約があり、期間が予約の内)に合う物をまとめて承認するかは、管理者が設定する物です。まとめて承認する時も、条件を決めた人と日付が承認の伝票に残ります。

## 7. 経路

一つの権限は、経路ごとに違う形で扉やシステムに届きます。経路ごとに、同じ四つの働きを持つ差し替え口を作ります。

| 働き | 中身 |
|---|---|
| 出す | 承認された権限から、その経路の実体を作る |
| 止める | 実体を止める。自動で止められない経路は、人のする作業を作業票として出す |
| 効くまで | 止めてから実際に開かなくなるまでの最長の時間を答える(R-AC-14) |
| 照らす | 扉やシステムに今入っている物を読み、台帳と比べる |

| 経路 | 出す | 止める | 効くまで | 今ある物 |
|---|---|---|---|---|
| 署名つき資格情報(扉が自分で確かめる) | 発行者の鍵で署名し、本人の端末へ渡す | 失効の一覧に足して扉へ配る。網の届かない扉は、端末が運ぶ一覧(R-AC-22)と期限で効く | 網が届く扉は一覧が届くまで。届かない扉は資格情報の残りの期限まで | 5.2a の資格情報と信頼の一覧、`issue`、`trust-change` |
| 門番を通す錠(後付け錠を、錠のドライバで動かす) | 門番が権限を確かめてから錠を動かす。錠の鍵は門番だけが持つ | 台帳で止めれば、次の要求から開かない | 門番が台帳の変更を受け取るまで | `digitalkey door-serve`、`digitalkey/site`、Sesame のドライバ |
| 錠に登録する暗証番号、カード | 錠の口(Matter の錠の利用者と資格情報、機種ごとの口)で登録する | 同じ口で消す。口が無い錠は、作業票を出して人が消す | 消す操作が錠に届くまで | Matter の橋は扉を錠として見せる側。登録の口はまだ無い |
| 財布の鍵、Aliro | 口だけを空ける。発行者の一つとして台帳から扱う(R-AC-18、20) | 台帳から失効を出す | 確かめていない | 無い |
| 物理キー | 貸し出しを台帳に書く(誰に、何番を、いつ) | 回収を台帳に書く。戻らない時は、錠の交換を作業票にする | 回収か交換まで | 無い |
| システムの権限(アカウント、SSH の鍵、管理者の役) | 作業票を出し、人が機械で行う。行った結果を照らして台帳に書く | 作業票を出す。`kagi` の直す文を使える | 人の作業が済むまで | `kagi/`(機械の形を表と突き合わせる) |

選んでいる物は次のとおりです。

- **どの経路でも開けられる別の道を残します。** 財布や業者のサービスが止まっても、カード、暗証番号、物理キーで開けられます(R-AC-18、R-RS-06)。スマートフォンを持たない人と電池の切れた人のための経路を持ちます(R-CM-09)。
- **システムの権限では、ソフトは機械を変えません。** 作業票と照らし合わせだけを受け持ちます。機械を変えるのは人です(`kagi` と同じ線)。
- **経路は、錠の登録簿(`digitalkey.locks`)と同じく、登録簿から選ぶ形にします。** 機種ごとの物は別のパッケージにします。

管理者が設定する物: どの扉でどの経路を使うか。経路ごとの期限の上限。

## 7a. 機器の管理

網につながる機器は、一台ずつが入口です。台帳に無い機器、持ち主の決まっていない機器、更新の止まった機器から入られます。人の名簿と同じ考えで、機器の全部を載せる正の台帳を持ちます。

### 載せる機器

| 種類 | 例 | その種類で特に見ること |
|---|---|---|
| PC、サーバー | 机の PC、ノート PC、社内のサーバー、小さな機械 | OS の更新、管理者の権限を持つ人、盤の暗号化、入れてよい鍵と開いている口(`kagi/` の機械の表) |
| スマートフォン、タブレット | 会社の端末、仕事に使う個人の端末 | OS の更新、画面の鍵、なくした時に止める手順。扉の資格情報を持つ端末は、名簿の「端末」と結ぶ(4 章) |
| プリンター、複合機 | 事務所の複合機、ラベルの印刷機 | 管理の画面のパスワード、中に残る印刷とスキャンの控え、外へ送る設定、廃棄や返却の時の消去 |
| ルーター、網の機器 | ルーター、スイッチ、無線の親機、VPN の機器 | 全部の機器の前にある事。更新の期間、外からの口、回線の事業者の遠隔の設定、見覚えのない設定とアカウント(R-NW-03、04、05) |
| センサー | 開閉、人感、温度、火災や漏水の知らせ | 電池、版、どの区画につなぐか、知らせの宛先 |
| カメラ、ドアホン | 見守りのカメラ、ドアホン | 初めのパスワード、映像の置き場と見られる人、外のサービスへ送るか、版 |
| 扉、錠、読取機 | 扉のコントローラ、後付け錠、読取機 | 扉との境目(8 章)。記録の公開鍵、信頼の一覧 |
| そのほか | 録画の機械、NAS、テレビ会議の機器、設備の制御の機器 | 上と同じ |

どこまでを載せるかは、管理者が決めます。決める材料は「その網につながるか」です。つながる物は、小さくても載せます。

### 機器ごとに持つ事

| 欄 | 中身 |
|---|---|
| 名前と種類 | 台帳の中で一つに決まる名前。上の表の種類 |
| 責任者 | その機器の更新、点検、交換をする人(名簿の主体)。責任者のいない機器を残さない(R-NW-05 の「持ち主を決める」を、全部の機器に広げた物) |
| 置き場と、網の区画 | 部屋や建物。どの区画につなぐか(扉の系統、事務、来客、設備。R-NW-02) |
| 見分ける物 | 製造者、型、製造番号、網の上の番号(MAC アドレスなど)。照らし合わせで、網に見えた物と台帳を結ぶために使う |
| 版と更新 | 今の版、確かめた日、製造者が更新を出す期限、更新を自動で当てるか人が当てるか |
| 管理者の口 | 管理の画面や遠隔の口があるか、外から届くか、初めのパスワードを替えたか。パスワードや鍵の値は載せず、秘密の在庫表(`kagi/`)の番号で結ぶ |
| 記録の送り先 | その機器の記録を、機械の外のどこへ送っているか(R-RS-12) |
| 状態 | 準備、使用、休止、紛失、廃棄 |
| 中に残る物 | 個人の情報、鍵、設定が中に残るか。廃棄や返却の時に消す物 |

### 機器の一生

| 段 | すること | 残る伝票 |
|---|---|---|
| 入れる | 台帳に載せ、責任者と区画を決める。初めのパスワードを替え、要らない外からの口を閉じ、版を確かめる。確かめた事を一つずつ記録する | 機器の登録、据え付けの確かめ |
| 権限を出す | 管理者の口に入れる人を、人の権限と同じ流れ(申請、承認、発行)で決める。業者には要る間だけ(R-AC-10) | 権限の四つの伝票(対象が機器) |
| 点検する | 版、設定、見覚えのないアカウント、開いている口を確かめ、結果を残す | 点検の記録 |
| 更新する | 版を上げた事、上げられなかった理由を残す。更新の期限が近い機器を、期限の前に替える予定に入れる | 更新の記録 |
| なくした、盗まれた | 状態を紛失にし、その機器が持つ鍵と、その機器から入れる所を止める(9 章の全経路の失効と同じ形) | 機器の変更、失効 |
| 廃棄する、返す | 中に残る物を消し、その機器への権限を全部止め、区画から外した事を確かめる | 廃棄の確かめ |

### 人の権限とのつなぎ

- **機器は、権限の対象になります。** 「誰が、この機器の管理者の口に入れるか」は、扉の権限と同じ伝票で扱います。人を止める時(9 章)は、その人の扉の鍵と、機器の管理者の権限を、同じ一枚の進み具合で見ます。
- **機器は、鍵を持つ主体にもなります。** 機器が別の機器やサービスに入るための鍵(機械の鍵、API の鍵)は、秘密の在庫表(`kagi/`)に載せ、機器の台帳と名前で結びます。機器を廃棄する時、紛失した時に、その鍵を止めます。
- **人の端末は、名簿と機器の台帳の両方に出ます。** 扉の資格情報を持つスマートフォンは、名簿の「端末」(公開鍵)であり、機器の台帳の一台でもあります。同じ名前で結びます。

### 照らし合わせ

台帳が正で、網に見える物は台帳と比べるだけです(12 章)。

- **台帳に無い機器。** ルーターが持つ、つながっている機器の一覧(番号を貸した記録など)を読み、台帳に無い物を知らせにします。
- **台帳にあるのに見えない機器。** 決めた間、網に現れない機器を知らせにします(置き忘れ、紛失、止まったセンサー)。
- **弱点の知らせ。** 公表された弱点の一覧と、台帳の製造者、型、版を突き合わせます(aiai-tools の tenken と同じ形)。
- **更新の期限。** 期限を過ぎた機器、近い機器を挙げます。
- **Linux の機械の中。** 入れてよい人、鍵、開いている口は `kagi/` が機械の表と突き合わせます。機械の表は、機器の台帳から作るか、機器の台帳と名前で照らします。

選んでいる物は次のとおりです。

- **このソフトは、機器を変えません。** 設定を替える、更新を当てる、中を消すのは、責任者が行います。ソフトは、する事を作業票として出し、済んだ事を記録します(7 章のシステムの権限、`kagi/` と同じ線)。
- **網を調べるのは、自分の網の中だけです。** 一覧は、ルーターや機器が出す物を読むか、責任者が取った出力を渡す形にします。ソフトが自分で網を探って回る働きは、最初は作りません。
- **値を載せません。** パスワード、鍵、暗証番号は台帳に載せず、置き場と番号だけを載せます。
- **スマートフォンをまとめて管理する仕組み(MDM)の代わりにはしません。** すでに使っている所では、その仕組みの一覧を、照らし合わせの相手の一つとして読みます。

管理者が設定する物: 載せる範囲、区画の分け方、点検の回数、見えない機器を知らせるまでの長さ、更新の期限の何日前に知らせるか、仕事に使う個人の端末を載せるか。

## 8. 扉との境目

扉の側は「確かめる、規則に合えば開ける、記録する」だけを受け持ちます(問題の整理 横の糸 A)。境目を流れる物は四つです。形は扉コントローラ仕様書が正で、変える時は仕様書を先に直します。

| 流れる物 | 向き | 今 | 足す物(仕様書に入れる案) |
|---|---|---|---|
| 資格情報 | 管理 → 端末 → 扉 | `digitaldoor-credential/1`。持っている人なら誰でも使える | 端末の公開鍵を入れ、扉の毎回違う問いかけへの端末の署名を確かめる形(R-AC-21)。主体の役(住人、客、保守)と世代の番号の欄 |
| 信頼の一覧の変更 | 管理 → 扉 | `digitaldoor-trust-change/1`。管理者の鍵の署名 | 扉の前の物理の操作で管理者の鍵を入れ直す口(R-AC-17) |
| 失効の一覧 | 管理 → 扉、または端末が運ぶ | 無い | 発行者の署名つきの一覧と世代の番号。古い一覧で新しい一覧を戻せない(R-AC-22)。失効の知らせを最後に受けてからの時間で、長い期限の資格情報を拒む設定(R-AC-14) |
| 記録の伝票 | 扉 → 管理 | `digitaldoor-audit-slip/1` | 変えない |

- **試験の値を、言語に依らない形で置きます。** 資格情報、変更の要求、失効の一覧、伝票について、通る例と拒まれる例(理由つき)を JSON のファイルにし、扉の側と管理の側の両方のテストが同じファイルを読みます。扉を Rust で書き直す時も、同じ値で確かめられます。
- **Aliro との対応は、形を合わせられる所まで合わせます。** 資格情報は Access Document、失効の一覧は Revocation Document、世代の番号は ValidityIteration に当たります。どこまで合わせられるかは、確かめていない事です(18 章)。

## 9. 失効

一人の全経路を一度に止める操作(R-AC-15)は、次の順に進みます。

1. **台帳で止める。** 主体の権限の全部に、失効の伝票を書きます。ここから先、門番を通す錠は開きません。
2. **経路ごとに止める。** 7 章の「止める」を、その主体の全部の実体に行います。自動で済む物は済ませ、人の作業が要る物は作業票にします。
3. **進み具合を一枚に出す。** 実体ごとに「止まった」「待ち(効くまでの最長の時間つき)」「人の作業が要る」を並べます。
4. **止まったことを確かめる。** 経路ごとの「照らす」で、扉やシステムに残っていないことを見ます。全部が済んだら、確かめた人と時刻を伝票に書きます。
5. **物理キーは回収を記録する。** 戻っていない物は、一覧に残り続けます。

- **端末の紛失は、本人が別の端末から届けた時点で 1 と 2 を自動で行います。** 出し直しは、窓口で本人を確かめてからです(R-EB-36)。
- **退職と契約の終了は、人事の届けの効力の日に 1 と 2 を自動で行います。** 同じ日に、アカウントの停止との照らし合わせの結果を残します(R-EB-34)。アカウントの側は、このソフトから自動で動かしません。
- **扉ごとの「失効が効くまでの最長の時間」を、画面に出します**(R-AC-14)。権限を出す時にも、この扉ではここまでの期限しか出せない、と示します。値は管理者が設定します。

## 10. 出来事の手順

出来事ごとの手順(R-AC-16)を、読むだけの文書ではなく、進められるデータにします。

| 出来事 | 手順が扱うこと |
|---|---|
| 端末の紛失 | 全経路の失効、本人の確かめ、出し直し |
| 退去、退職、契約の終了 | 全経路の失効、物理キーの回収、アカウントとの照らし合わせ |
| 管理者の交代 | 新しい管理者の鍵を扉の前で入れ、前の鍵を外す。鍵の目録の責任者を替える |
| 建物の持ち主の交代、引渡し | 発行者の鍵と信頼の一覧の作り直し。前の持ち主と工事の会社の鍵が残っていないことの確かめ |
| 発行者の鍵の漏れ、作り直し | 新しい鍵を作る、信頼の一覧に足す、出し直す、前の鍵を外す(5.2b の順) |
| 管理者の鍵をなくした | 扉の前の物理の操作と本人の確かめで入れ直す(R-AC-17) |
| 閉じる機械の故障 | 予備に控えから戻す(R-AP-24)。その間、扉は最後に受け取った一覧で動く |
| 業者の保守の立ち入り | 要る間だけの権限を出し、済んだら止める(R-AC-06、10) |
| 機器を入れる | 台帳に載せる、責任者と区画を決める、初めのパスワードを替える、要らない口を閉じる、版を確かめる(7a 章) |
| 機器の紛失、盗難 | その機器が持つ鍵と、その機器から入れる所を止める。人の端末なら、端末の紛失の手順へ |
| 機器の弱点の公表 | 当たる機器を台帳から挙げ、直す版があるか、当てるまでどう守るか(区画から外す、口を閉じる)を決め、当てた事を残す |
| 機器の廃棄、返却、入れ替え | 中に残る物を消す、その機器への権限を止める、区画から外した事を確かめる。更新の期限が切れる機器は、切れる前に替える(R-NW-03) |

選んでいる物は次のとおりです。

- **手順は段の並びです。** 段ごとに、ソフトが行うか人が行うか、誰が確かめるかを持ちます。進めた段は、行った人と時刻と結果を伝票に残します。
- **訓練の印を持ちます。** 訓練で進めた記録は、本番の記録と分けて読めます。年に一度の訓練(R-AC-16 の確かめ方)と、引き渡しの時に売り先の管理者が自分で行う試験(R-RS-18)の記録になります。
- **手順の文面は、雛形を置き、管理者が自分の所に合わせて直します。** 直した版と日付が台帳に残ります。

## 11. 記録

- **台帳は追記だけです。** 伝票ごとに、連番、前のハッシュ、台帳の記録の鍵の署名を持ちます。検査の命令で、連鎖と署名を端から確かめます。
- **扉の記録は、扉が署名した伝票で受け取ります**(R-CT-17)。受け取る側は、台帳に写してある扉の公開鍵で検べ、連番の抜けと連鎖の切れを見ます(R-LG-03、05、08)。
- **本人は、自分の権限と、自分の権限が使われた記録を見られます。** 住戸の記録は住人の物で、管理する側が見られる範囲は権限で分けます(R-AP-35)。
- **非常の手段(物理キー、内側からの解錠)を使った記録を、人の手で足せます**(R-LG-09)。
- **記録を書き出せます**(CSV、JSON。検査の結果つき。R-LG-08)。

管理者が設定する物: 保存の期限(期限を過ぎた物は候補として挙げ、消すのは管理者)、記録の写しの送り先。

## 12. 照らし合わせ

台帳が正で、ほかの所は台帳と比べるだけです。違いは知らせにし、自動では直しません。

| 比べる相手 | 見ること | 道具 |
|---|---|---|
| 扉の信頼の一覧 | 台帳に無い発行者が入っていないか | 扉の口(`GET /trust`) |
| 錠に登録された暗証番号とカード | 台帳に無い物、止めたはずの物が残っていないか | 経路の「照らす」 |
| 扉の記録 | 権限の無い主体、止めた後の解錠、連番の抜け | 伝票の受け取り |
| 機械のアカウント、SSH の鍵、開いている口 | 表に無い人、鍵、口 | `kagi/` |
| ディレクトリのアカウントの一覧 | 退職した人のアカウントが残っていないか。名簿に無い人がいないか | 一覧を読むだけ |
| 人事の届け | 届けがあるのに止まっていない権限、届けが無いのに止まった権限 | 届けの様式 |
| 物理キー | 貸し出したままの物 | 台帳 |
| 鍵の目録 | 作り直しの時期を過ぎた鍵、責任者のいない鍵 | 台帳 |
| 網につながっている機器の一覧 | 台帳に無い機器、台帳にあるのに見えない機器 | ルーターや網の機器が出す一覧を読む(7a 章) |
| 公表された弱点の一覧 | 台帳の製造者、型、版に当たる知らせ | aiai-tools の tenken と同じ形 |
| 機器の版と更新の期限 | 期限を過ぎた機器、近い機器、長く点検していない機器、責任者のいない機器 | 台帳 |
| ルーターの設定 | 外からの口、見覚えのない設定とアカウント(R-NW-04) | 責任者の点検の記録 |

回数は管理者が設定します。毎日の分は、朝の知らせにまとめます(aiai-tools の tenken と同じ形)。

## 13. 画面と命令

- **命令を先に作ります。** `digitalkey` の下に置き、どの働きも命令で行えるようにします。テストは命令と関数を相手にします。
- **管理の画面は、命令と同じ関数を呼びます。** 画面だけにある働きを作りません。画面は Flet で、管理者の端末で動かします。
- **申請の画面は、開く機械の側の物です**(権限の申請の雛形)。どの端末からでも使える形にします。
- **説明は、コードの docstring と `--help` に書きます。** ユーザーマニュアルは `tools/build_manual.py` がそこから作ります。

管理の画面に置く物の例(作る時に選ぶ物): 承認を待つ申請、名簿、権限の一覧と期限の近い物、一人を止める、扉ごとの最長の時間、出来事の手順、照らし合わせの違い、鍵の目録、記録の検査。

## 15. このソフト自身の守り

鍵を出すソフトは、攻められた時に一番困る所です。

- **外からの口を持ちません**(3 章)。
- **頼る部品を少なくします。** 標準ライブラリと、署名の部品に絞ります。画面の部品は管理者の端末の側だけに置きます。
- **実行の途中で機械語を作る仕組みを使いません**(R-RS-15)。動く物を一覧と sha256 で確かめられる形に保ちます(R-RS-11)。
- **同じソースから同じ物が組めるようにします**(R-RS-14)。
- **出すことができるのは、承認の伝票がある権限だけです**(6 章)。これは関数の形とテストで確かめます。
- **このコードを、公開している手引きで確かめます。** [確かめの始め方](確かめの始め方.md)と `skills/system-check/` の順で運営者が確かめ、見つけた物と直した記録を残します。各社が自分で確かめる時の実例になります。
- **核になる所(署名を確かめる、失効を判定する)は、言語を替えても同じ試験の値で確かめられる形にします**(8 章)。

#### 様式の読み方と台帳

- 様式は `digitalkey/kanri/forms_data/*.adoc` の 14 枚だけを `digitalkey.entrance.forms.load_file` で読み、`{様式の名: FormSpec}` にします。受け入れ(entrance)の様式は混ぜません。
- 台帳は `digitalkey.entrance.ledger.Ledger(<置き場>/台帳, roles=..., form_set=<上の 14 枚>)` を使います。受け入れの台帳とは別の置き場です(18 章の仮の決め)。
- 書く時は、その操作で使う役だけが通るように `Ledger.roles` を `{by: {role}}` にしてから `Ledger.append` を呼びます。機械の伝票(権限_発行、実体_発行、実体_失効)は、`issuer="発行者"` で書きます(`:書ける: 発行者` に名前がそのまま合います)。
- 状態は台帳の伝票の組から毎回導きます。別の表やファイルに状態を持ちません。同じ置き場をもう一度 `Unit.open` で開くと、同じ状態が読めます。
- 様式に合わない値は、`Ledger.append` が出す `ValueError` を `Refused(FORM, 詳細)` にして返します(詳細は `ValueError` の文のうち「様式に合いません: 」の後)。

#### 実装の人が足す所(このファイルの外)

- `digitalkey/cli.py` の振り分けに `kanri` を足し、`digitalkey.kanri.cli.main(argv)` を呼ぶ。
- `pyproject.toml` の `[tool.setuptools.package-data]` に `"digitalkey.kanri" = ["forms_data/*.adoc"]` を足す。

### 19.2 動かす単位と、データの型

#### 動かす単位(R-AC-09)

一つの置き場(ディレクトリ)が、一人の管理者、一つの発行者の鍵、一つの台帳の分です。二つの発行者を扱う時は、置き場を二つ作ります。置き場の中は次のとおりです。

| 物 | 中身 |
|---|---|
| `kanri.json` | `{"形式": "digitalkey-kanri/1", "発行者": "<公開鍵の識別>", "公開鍵": "<16 進>", "鍵のファイル": "<発行者の秘密鍵のファイルの絶対パス。無ければ空>"}`。秘密鍵の値は入れません |
| `鍵/発行者.key` | 置き場を作る時に `--issuer-key` を渡さなかった時だけ作る。32 バイトの Ed25519 の秘密鍵そのもの、権限 600(`digitaldoor-controller keygen` の `--out` と同じ形)。`鍵/` は権限 700 |
| `台帳/` | `Ledger` の置き場(`伝票/` と `ledger.sqlite`) |

発行者の識別は `digitaldoor_controller.slips.key_id(公開鍵)`(公開鍵の SHA-256 の先頭 16 桁)です。

```python
Unit.create(root, *, admin: str, admin_name: str, admin_kind: str = "社員",
            issuer_key: str | Path | None = None, signer=None, routes=None) -> Unit
Unit.open(root, *, signer=None, routes=None) -> Unit
```

- `create` は `root` を作り(あってよい)、`kanri.json` があれば `Refused(ALREADY_CREATED)`。発行者の鍵は、`signer` を渡せばそれを使い(鍵のファイルは作らず、`鍵のファイル` は空)、`issuer_key` を渡せばそのファイルを読み(読めない時と 32 バイトでない時は `Refused(NO_KEY)`。道を絶対パスで `鍵のファイル` に書く)、どちらも無ければ `鍵/発行者.key` を作ります。
- `create` は最初の二枚を書きます。`主体_登録`(識別 `admin`、呼び名 `admin_name`、種別 `admin_kind`、業者 いいえ、役 `初期化`)と、`役_割当`(主体 `admin`、割り当てる役 `管理者`、判断 `付与`、理由 `置き場を作った`、役 `初期化`)。どちらも伝票の発行者(`:発行者:`)は `admin` です。様式の `:書ける:` に `初期化` は無いので、書く時の `Ledger.roles` には、その様式の書ける役(主体_登録は `名簿の係`、役_割当は `管理者`)を `admin` に与え、項目 `役` には `初期化` を書きます。役 `初期化` で書けるのは、この二枚だけです。
- `open` は `kanri.json` が無ければ `Refused(NO_UNIT)`。`signer` を渡せば、その公開鍵が `kanri.json` の `公開鍵` と違う時 `Refused(WRONG_KEY)`。渡さなければ `鍵のファイル` から読み、空か読めなければ `Refused(NO_KEY)`。
- `signer` は `sign(data: bytes) -> str` と `public_key() -> bytes` を持つ物(`digitaldoor_controller.audit.Ed25519Signer` と同じ口)。後で取り出せない所の鍵に差し替えます。
- `routes` は `{経路の名: Route}`。省けば 19.8 の登録簿の三つです。`register_door` と `issue_entity` の経路の確かめ(`UNKNOWN_ROUTE`)の相手は、この `unit.routes` です。
- 属性: `unit.root`、`unit.ledger`(`Ledger`)、`unit.issuer`(発行者の識別)、`unit.public_key`(bytes)、`unit.signer`、`unit.routes`。

例: `u = Unit.create(tmp/"A", admin="adm", admin_name="管理者A", signer=Ed25519Signer.generate())` の後、`u.subject("adm").持つ役 == {"管理者", "本人"}`、台帳の伝票は 2 枚。

#### データの型(`model.py`)

属性の名前は様式の項目の名前をそのまま使います。どれも `dataclass(frozen=True)` です。日時はすべて様式の形の文字列(19.5)、扉の列は `list[str]` です。

| 型 | 属性 |
|---|---|
| `Subject` | `識別`、`呼び名`、`種別`、`業者`(bool)、`状態`(`有効`/`停止`/`退出`)、`仮名`、`持つ役`(set[str]) |
| `Door` | `名前`、`経路`(list[str])、`場所`、`記録の公開鍵`、`状態`(`使用`/`撤去`) |
| `Group` | `名前`、`扉`(list[str])、`状態`(`使用`/`廃止`) |
| `Permission` | `番号`(権限の番号 = 権限_申請の伝票の番号)、`主体`、`対象の種類`、`対象`、`開始`、`終了`(空は期限なし)、`理由`、`出どころ`、`申請者`(申請の伝票の発行者)、`状態`(19.7)、`承認`(判断の伝票の番号か空)、`発行`(権限_発行の番号か空)、`扉`(発行の伝票の扉の列。発行前は空の列)、`失効`(権限_失効の番号か空) |

#### 拒否

拒む時は `Refused` を投げます。`class Refused(ValueError)` で、属性 `理由`(19.11 の言葉のどれか)と `詳細`(空でよい)を持ち、`str(e)` は詳細があれば `理由(詳細)`、無ければ `理由` です。拒んだ時は、台帳に何も書きません(一枚も増えません)。

### 19.3 役と操作

役の名は設計書 2 章の名です。人に割り当てるのは `管理者`、`名簿の係`、`承認する人`、`運用`、`監査` で、`本人` は有効な主体の全員が持ちます。`発行者` は機械の役で、人には割り当てず、`role` に渡すこともできません。`初期化` は置き場を作る時の二枚だけの印で、`role` に渡すと、どの操作も `ROLE_NOT_ALLOWED` です。

書くメソッドは、どれもキーワード引数 `by`(操作する人の識別。名簿の主体)と `role`(この操作で使う役)を取ります。確かめる順番は、どの操作も次のとおりで、最初に外れた所で拒みます。

1. `role` が、その操作のできる役の一つか。外れたら `ROLE_NOT_ALLOWED`
2. `by` が名簿にあるか。外れたら `BY_UNKNOWN`
3. `by` の状態が `有効` か。外れたら `BY_INACTIVE`
4. `by` が `role` を持つか(`持つ役` に入るか)。外れたら `NO_ROLE`
5. 書く値が様式に合うか(日時の読み、選べる値、長さ)。外れたら `FORM`
6. 操作ごとの確かめ(19.6〜19.10)

持つ役は、`役_割当` の伝票を台帳に書いた順(`Ledger.select` が返す順)に読み、主体と役の組ごとに最後の判断が `付与` の物と、主体が有効なら `本人` です。

| 操作(メソッド) | できる役 | 書く伝票 | 伝票の発行者 |
|---|---|---|---|
| `register_subject`、`change_subject` | 名簿の係 | 主体_登録、主体_変更 | `by` |
| `assign_role` | 管理者 | 役_割当 | `by` |
| `register_door`、`register_group`、`set_setting` | 管理者 | 扉、群、設定 | `by` |
| `request` | 本人、名簿の係 | 権限_申請 | `by` |
| `import_requests` | 名簿の係 | 権限_申請 | `by` |
| `decide` | 承認する人 | 権限_承認 | `by` |
| `issue` | 管理者 | 権限_発行 | `発行者` |
| `issue_entity` | 管理者(経路が物理キーの時は 管理者、名簿の係) | 実体_発行 | `発行者` |
| `revoke_permission`、`revoke_subject` | 管理者、名簿の係 | 権限_失効、実体_失効 | 権限_失効は `by`、実体_失効は `発行者` |
| `return_physical` | 名簿の係、管理者 | 物理キー_回収 | `by` |
| `confirm_stopped` | 管理者 | 失効_確認 | `by` |

どの伝票も、項目 `役` に `role` を書きます。発行者の書く伝票は、項目 `操作者` に `by` を書きます。読むメソッド(`subject`、`subjects`、`doors`、`groups`、`permission`、`permissions`、`entities`、`progress`、`may_open`、`trust_entry`、`reconcile`)は、段 1 では役を取りません(読む範囲を役で分けるのは段 5)。

例: 名簿の係を持たない `adm` が `register_subject(..., by="adm", role="名簿の係")` を呼ぶと `NO_ROLE`。`role="発行者"` なら、どの操作も `ROLE_NOT_ALLOWED`。

### 19.4 伝票の組

| 様式 | 宛先(`to`) | 根拠(`basis`) |
|---|---|---|
| 主体_登録、主体_変更 | 主体の識別 | なし |
| 役_割当 | 主体の識別 | なし |
| 扉、群、設定 | 空 | なし |
| 権限_申請 | 主体 | なし |
| 権限_承認 | 主体 | [申請] |
| 権限_発行 | 主体 | [申請, 承認] |
| 権限_失効 | 主体 | [申請] |
| 実体_発行 | 主体 | [権限_発行] |
| 実体_失効 | 主体 | [実体_発行, この失効の時に書いた権限_失効(あれば)] |
| 物理キー_回収 | 主体 | [実体_発行] |
| 失効_確認 | 主体 | 確かめた実体_発行の番号の列 |

今ある `鍵_発行`、`鍵_失効`、`資格情報_発行`(entrance)は生かして変えず、段 1 では使いません。理由は三つです。`鍵_発行` は一つの錠と予約に結んだ鍵で、事業所サーバー(`digitalkey/site`)と `door-serve` がその形を読んでいます。書ける役が受け入れの役(経営者、AI社員)で、設計書 2 章の役と違います。一人の全経路(R-AC-15)を一つの一覧にするには、どの経路の物も同じ様式(`実体_発行`、`実体_失効`)で権限に結ぶほうが、一覧と止め方が一つで済みます。物理キーの貸し出しも `実体_発行`(経路 `物理キー`、識別に鍵の番号)で書き、回収だけを `物理キー_回収` にします。

### 19.5 時刻

- 様式の日時は地方時の `YYYY-MM-DDTHH:MM`(分まで、時差なし)です。メソッドの日時の引数(`start`、`end`、`until`)は、この形の文字列か `datetime` を受けます。文字列は様式の修復(和暦、全角、空白)を通します。時差つきの文字列は読めず `FORM` です。`datetime` は、時差があれば地方時に直し、秒を落として同じ形にします。
- 期限なしは `end=""` です。`until=None` は「権限の終了のまま」です。
- 権限と実体は `開始 <= 時刻 < 終了` の間だけ効きます。終了の時刻ちょうどで切れます。
- 読むメソッドの `at` は `datetime | None` で、None は今です。時差つきなら地方時に直して比べます。
- 失効は、伝票を書いた時から効きます。`at` に失効より前の時刻を渡しても、失効は失効として読みます(台帳は今の状態を表し、`at` は期間の判定だけに使います)。
- unix 秒への直し方は `int(datetime.fromisoformat(様式の日時).timestamp())`(地方時として読む。`digitaldoor-controller` の `parse_time` と同じ読み方)です。

### 19.6 名簿、役、扉と群、設定

```python
u.register_subject(ident, name, kind, vendor: bool, *, by, role) -> Slip      # 主体_登録
u.change_subject(ident, *, reason, by, role, name=None, kind=None,
                 vendor: bool | None = None, state=None) -> Slip               # 主体_変更
u.subject(ident) -> Subject          # 無ければ Refused(SUBJECT_UNKNOWN)
u.subjects() -> list[Subject]        # 主体_登録を台帳に書いた順
u.assign_role(subject, role_name, grant: bool = True, *, reason, by, role) -> Slip   # 役_割当
u.register_door(name, routes: list[str], *, by, role, place="", audit_key="", state="使用") -> Slip  # 扉
u.register_group(name, doors: list[str], *, by, role, state="使用") -> Slip  # 群
u.doors() -> list[Door]              # 今の値。撤去した扉も入る。最初の伝票を台帳に書いた順
u.groups() -> list[Group]            # 今の値。最初の伝票を台帳に書いた順
u.set_setting(item, value: str, *, reason, by, role) -> Slip                 # 設定
u.setting(item) -> str               # 今の値。書いていなければ空(自己承認だけは 許さない)
u.trust_entry() -> dict
```

- `register_subject`: 識別に「,」があれば `NAME_HAS_COMMA`。同じ識別があれば `DUPLICATE_SUBJECT`。仮名は `secrets.token_hex(8)`(16 桁)で作り、置き場の中で重ならない物にします。
- `change_subject`: 主体が無ければ `SUBJECT_UNKNOWN`。`name`、`kind`、`vendor`、`state` が全部 None なら `NOTHING_TO_CHANGE`。項目ごとに、空でない最後の値が今の値です。
- `assign_role`: 主体が無ければ `SUBJECT_UNKNOWN`。`role_name` が選べる値に無ければ `FORM`。`grant=False` は判断 `解除`。
- `register_door`: 名前に「,」があれば `NAME_HAS_COMMA`。`routes` の一つでも `unit.routes`(19.2。省いた時は 19.8 の登録簿の三つ)に無ければ `UNKNOWN_ROUTE`(詳細に経路の名)。`routes` が空なら `FORM`。経路は「, 」でつないで書きます。同じ名前の二枚目は、今の値を置き換えます。
- `register_group`: 名前に「,」があれば `NAME_HAS_COMMA`。`doors` の一つでも、この置き場の `使用` の扉でなければ `UNKNOWN_DOOR`(詳細に扉の名)。`doors` が空なら `FORM`。
- `set_setting`: 項目は `業者の最長の日数` と `自己承認`(様式の選べる値。ほかは `FORM`)。`業者の最長の日数` の値は空か 1 以上の整数の文字列、`自己承認` の値は `許す` か `許さない`。ほかは `BAD_SETTING`。理由は要ります(様式の not null)。変えた人(伝票の発行者)、日時、理由は伝票に残ります。
- 設定 `自己承認` を書いていない置き場は、`許さない` として扱います(止める側に倒す)。値は、確かめるたびに台帳の最後の `設定` の伝票から読みます。
- `trust_entry()` は `{unit.issuer: {"public_key": unit.public_key.hex(), "doors": [状態が使用の扉の名前、最初の扉の伝票を台帳に書いた順]}}`。扉コントローラの `Controller(trust=...)` と `trust-change` の `doors` にそのまま使える形です(R-AC-09)。扉に入れるのは、管理者の鍵で署名した変更の要求で、このソフトは管理者の鍵を持ちません(5 章)。

例: `u.register_door("玄関", ["署名つき資格情報", "門番を通す錠", "物理キー"], by="adm", role="管理者")` → 伝票 `扉`、項目 `経路` は `署名つき資格情報, 門番を通す錠, 物理キー`。`u.register_group("事務所", ["玄関", "倉庫"], ...)` で倉庫が無ければ `Refused(理由="この発行者の扉ではありません", 詳細="倉庫")`。

### 19.7 権限

#### 状態の導き方

権限の番号は、権限_申請の伝票の番号です。状態は、その番号に結ぶ伝票から、上の行から順に当てはめて決めます。

| 順 | 条件 | 状態 |
|---|---|---|
| 1 | 権限_失効(項目 `権限` がこの番号)がある | `失効` |
| 2 | 最初の権限_承認(項目 `申請` がこの番号。台帳に書いた順(`Ledger.select` が返す順)で最初の一枚)の判断が `却下` | `却下` |
| 3 | 権限_発行(項目 `権限` がこの番号)があり、終了が空でなく `at >= 終了` | `期限切れ` |
| 4 | 権限_発行がある | `発行済み`(開始の前も含む) |
| 5 | 最初の権限_承認の判断が `承認` | `承認` |
| 6 | 上のどれでもない | `申請中` |

```python
u.permission(pid, *, at=None) -> Permission     # 申請の伝票でなければ Refused(PERMISSION_UNKNOWN)
u.permissions(subject=None, *, at=None) -> list[Permission]   # 申請を台帳に書いた順
```

#### 申請

```python
u.request(subject, kind, target, start, end, reason, *, by, role) -> Slip   # 権限_申請、出どころ 手入力
```

確かめ(19.3 の 1〜5 の後、この順): 主体が名簿に無ければ `SUBJECT_UNKNOWN`。主体が有効でなければ `SUBJECT_INACTIVE`。`kind` が `扉` で、`target` がこの置き場の `使用` の扉でなければ `UNKNOWN_DOOR`(R-AC-09)。`kind` が `群` で、`target` が `使用` の群でなければ `UNKNOWN_GROUP`。群の中の `使用` の扉が一つも無ければ `UNKNOWN_DOOR`。終了が空でなく `終了 <= 開始` なら `BAD_PERIOD`。主体が業者で終了が空なら `VENDOR_NO_END`。主体が業者で、設定 `業者の最長の日数` が N で、`終了 - 開始` が N 日を超えれば `VENDOR_TOO_LONG`(ちょうど N 日は通る)。

本人の役では、自分の分も、受け入れる来客や業者の分も書けます。申請者は伝票の発行者(`by`)として残ります。

#### 承認

```python
u.decide(request_id, decision, reason="", *, by, role) -> Slip   # 権限_承認。decision は 承認 か 却下
```

確かめ(この順): `request_id` が権限_申請の伝票でなければ `NO_REQUEST`。権限の状態が `失効` なら `REVOKED`。もう判断の伝票があれば `ALREADY_DECIDED`。設定 `自己承認` が `許さない`(書いていない時を含む)で、`by` が申請者なら `SELF_REQUEST`、`by` が申請の主体なら `SELF_SUBJECT`。

通れば権限_承認を書きます。項目 `自己承認` は、`by` が申請者か申請の主体なら `はい`、どちらでもなければ `いいえ` です(判断が `却下` の時も同じ)。

例: 設定 `自己承認` が `許す` の置き場で、`adm` が自分を主体に書いた申請を `adm` が `decide(..., by="adm", role="承認する人")` すると、権限_承認が書かれ、`自己承認` は `はい`、`役` は `承認する人`。同じ事を設定の無い置き場ですると `SELF_REQUEST`。

#### 発行(承認が無いと出せない)

```python
u.issue(approval_id, subject, kind, target, start, end, *, by, role, at=None) -> Slip   # 権限_発行
```

発行は、承認の伝票の番号を一つ目の引数に取り、その承認と申請の値が渡した値と同じ時だけ書きます。`at` は期限の確かめに使う時刻(None は今)です。確かめ(19.3 の 1〜5 の後、この順):

1. `approval_id` が空、無い番号、権限_承認でない伝票(申請の番号を渡した時を含む)、またはその申請の最初の判断の伝票でない → `NO_APPROVAL`
2. 判断が `却下` → `REJECTED`
3. 承認の伝票の発行者が申請者か申請の主体と同じ時は、**今の**設定 `自己承認` が `許す` で、かつ承認の伝票の項目 `自己承認` が `はい` の時だけ通ります。ほかは、発行者が申請者と同じなら `SELF_REQUEST`、主体と同じなら `SELF_SUBJECT`。`decide` を通らずに台帳へ直に書かれた印の無い承認(`自己承認` が `いいえ`)は、設定が `許す` でも拒みます。設定が `許す` の間に書かれた自己承認でも、発行の時に設定が `許さない` に戻っていれば拒みます。発行者が申請者でも主体でもない時は、項目 `自己承認` を見ずに通ります
4. 申請の値と渡した値を、主体、対象の種類、対象、開始、終了の順に比べ、違えば `MISMATCH`(詳細に項目の名)。日時は 19.5 の形に直してから比べます
5. 状態が `失効` → `REVOKED`。権限_発行がもうある → `ALREADY_ISSUED`
6. 主体が名簿に無い → `SUBJECT_UNKNOWN`。有効でない → `SUBJECT_INACTIVE`
7. 業者の確かめ(申請と同じ。今の名簿と設定で確かめ直す) → `VENDOR_NO_END`、`VENDOR_TOO_LONG`
8. 対象から扉の列を作る。扉はその扉(`使用` でなければ `UNKNOWN_DOOR`)。群は今の群の `使用` の扉(群が `使用` でなければ `UNKNOWN_GROUP`、扉が一つも無ければ `UNKNOWN_DOOR`)
9. 終了が空でなく `at >= 終了` → `EXPIRED`

通れば権限_発行を、項目 `扉` に 8 の列を「, 」でつないで書きます。権限の扉の列は、この時に決まり、後で群を変えても変わりません。

#### 外の一覧の取り込み(R-EB-37)

```python
u.import_requests(rows: Iterable[dict[str, str]], source_name: str, *, by, role) -> ImportResult
```

- `rows` の一行は `{"識別", "対象の種類", "対象", "開始", "終了", "理由"}` の辞書です(ディレクトリ、予約の仕組み、人事の届けの書き出しを、この形に直して渡します)。
- 19.3 の 1〜4 は全体に一度だけ確かめ、外れたら `Refused` を投げて何も書きません。`source_name` が空なら `FORM`。
- 行ごとに、`request` と同じ確かめをします。通った行は権限_申請(出どころ `外の一覧`、一覧の名 `source_name`)を一枚書きます。外れた行は書かずに `飛ばした` に(行の番号, 理由)を足します。辞書の鍵が足りない行は `FORM`。
- 名簿に無い識別の行は `SUBJECT_UNKNOWN` で飛ばします。主体_登録、役_割当、権限_承認、権限_発行、実体_発行は、どの行からも書きません。外の一覧から作れるのは申請までで、人も鍵も増えません。

### 19.8 経路の差し替え口

経路は、どれも同じ四つの働き(7 章)を持つ差し替え口です。経路は伝票を書かず、結果を返し、伝票は `Unit` が書きます。

```python
class Route(Protocol):
    name: str
    def issue(self, unit, perm: Permission, *, doors: list[str], start: str, end: str,
              once: bool, key_number: str) -> RouteIssue: ...          # 出す
    def stop(self, unit, entity: Entity, *, at: datetime) -> Stop: ...  # 止める
    def effective_by(self, unit, entity: Entity) -> EffectiveBy: ...    # 効くまで
    def reconcile(self, unit, entity: Entity, *, at: datetime) -> Reconcile: ...  # 照らす
```

登録簿は `digitalkey.kanri.routes.available() -> dict[str, Route]` です。段 1 の三つを組み込みで持ち、ほかの経路は entry point の群 `digitalkey.kanri.routes` で足します(錠の登録簿 `digitalkey.locks` と同じ形。暗証番号、カード、財布、システムの権限は段 6)。経路の名の定数は `CREDENTIAL = "署名つき資格情報"`、`GATE = "門番を通す錠"`、`PHYSICAL = "物理キー"` です。

| 働き | 署名つき資格情報 | 門番を通す錠 | 物理キー |
|---|---|---|---|
| 出す | `credentials.issue(unit.signer, cred_id=<secrets.token_hex(8)>, subject=<主体の仮名>, doors=doors, not_before=<開始の unix 秒>, not_after=<終了の unix 秒 - 1>, once=once)`。`RouteIssue(識別=cred_id, 発行者=unit.issuer, 資格情報=<その dict>)`。終了が空なら `NEED_END` | `RouteIssue(識別=<secrets.token_hex(8)>, 発行者="", 資格情報=None)`。錠の鍵は門番だけが持ち、本人には何も渡しません | `key_number` が空なら `NEED_KEY_NUMBER`。同じ鍵の番号の物理キーで回収の無い実体があれば `KEY_LENT`。`RouteIssue(識別=key_number, 発行者="", 資格情報=None)` |
| 止める | `at >= 終了` なら `Stop("止まった", "", "")`。ほかは `Stop("待ち", 終了, "")`(段 1 は失効の一覧が無いので、期限まで効きます) | `Stop("止まった", "", "")`(門番は台帳を読むので、次の要求から開けません) | 回収があれば `Stop("止まった", "", "")`。ほかは `Stop("人の作業が要る", "", "鍵番号 <識別> を回収する。戻らない時は錠を交換して回収の伝票に書く")` |
| 効くまで | `EffectiveBy("期限まで", 終了)` | `EffectiveBy("即時", "")` | `EffectiveBy("人の作業まで", "")` |
| 照らす | `Reconcile("照らせない", "扉の記録の受け取りは段 2")` | `Reconcile("一致", "")` | 進み具合の状態が `人の作業が要る` なら `Reconcile("違い", "貸し出したまま")`、ほかは `Reconcile("一致", "")` |

`not_after` を終了の 1 秒前にするのは、扉の判定(`not_before <= now <= not_after`)と台帳の判定(`開始 <= 時刻 < 終了`)を同じ時刻で切るためです。例: 終了 `2027-01-01T00:00` の資格情報は、地方時の 2026-12-31 23:59:59 まで通り、2027-01-01 00:00:00 に `期限の外` で拒まれます。

#### 実体を出す

```python
u.issue_entity(pid, route, *, by, role, until=None, once=False, key_number="", at=None) -> Issued   # 実体_発行
u.entities(subject=None) -> list[Entity]     # 実体_発行を台帳に書いた順。一人の全経路の一覧(R-AC-15)
u.reconcile(entity_id, *, at=None) -> Reconcile
```

確かめ(この順): `route` が `unit.routes` に無ければ `UNKNOWN_ROUTE`。19.3 の 1〜5(できる役は経路で変わります)。`pid` が申請の伝票でなければ `PERMISSION_UNKNOWN`。状態が `失効` なら `REVOKED`、`申請中`、`承認`、`却下` なら `NOT_ISSUED`、`期限切れ` なら `EXPIRED`。主体が有効でなければ `SUBJECT_INACTIVE`。権限の扉の列のうち、今 `使用` で、扉の経路にこの経路を持つ扉が一つも無ければ `NO_DOOR_FOR_ROUTE`。`once` が真で経路が署名つき資格情報でなければ `ONCE_CREDENTIAL_ONLY`。`until` があり、権限の終了が空でなく `until > 権限の終了` なら `UNTIL_TOO_LATE`。実体の終了(`until`、無ければ権限の終了)が空でなく `<= 開始` なら `BAD_PERIOD`。その後に経路の「出す」(上の表の拒否)。

通れば実体_発行を書きます。項目は、権限、主体、経路、扉(経路で絞った列)、識別、発行者、開始(権限の開始)、終了(`until` か権限の終了)、一回限り、操作者、役です。資格情報そのものは台帳に書かず、`Issued.資格情報` で返すだけです。

例: 扉 `玄関`(三つの経路)と `倉庫`(物理キーだけ)の群の権限から、`issue_entity(pid, "署名つき資格情報", ...)` を出すと、資格情報の `doors` は `["玄関"]`、実体_発行の扉は `玄関` です。

### 19.9 門番を通す錠

門番(`digitalkey door-serve`、事業所サーバーなど、錠の鍵を持つ物)が台帳に聞く口です。

```python
u.may_open(subject, door, *, at=None) -> GateVerdict
u.relay(ctl, subject, *, at=None) -> str
```

`may_open` は、その主体が、その扉を、その時刻に開けてよいかを答えます。確かめの順:

1. `door` がこの置き場の `使用` の扉でない → `UNKNOWN_DOOR`
2. 主体が名簿に無い → `SUBJECT_UNKNOWN`。有効でない → `SUBJECT_INACTIVE`
3. 主体の、経路が門番を通す錠で、扉の列に `door` を持つ実体が無い → `GATE_NO_PERMISSION`(`権限がありません`)
4. その実体の全部が、権限の状態 `失効` か実体_失効あり → `GATE_REVOKED`(`失効しています`)
5. 残りの実体のどれも `開始 <= at < 終了`(終了が空なら `開始 <= at`)でない → `GATE_OUT_OF_PERIOD`(`期間の外`)

通れば `GateVerdict(True, "", <通した実体の番号。当てはまる中で、台帳に書いた順(`Ledger.select` が返す順)で最初>)`。

`relay` は、疑似の扉と門番をつなぐ口です。`at` が None なら `datetime.fromtimestamp(ctl.now)` を使い、`may_open(subject, ctl.name, at=...)` の結果で `ctl.on_auth(<主体の仮名。名簿に無ければ空>, route="門番", valid=<ok>, reason=<理由>, detail=<"実体=<番号>" か空>)` を呼び、その戻り値(`解錠`、`拒否` など)を返します。拒んだ時は、扉の記録に種別 `認証`、事象 `拒否`、結果に理由が残ります。

### 19.10 失効と進み具合

```python
u.revoke_permission(pid, reason, *, by, role, at=None) -> Revocation
u.revoke_subject(subject, reason, *, by, role, at=None) -> Revocation
u.progress(subject, *, at=None) -> Sheet                                      # 名簿に無い主体は Refused(SUBJECT_UNKNOWN)
u.return_physical(entity_id, result="回収", note="", *, by, role) -> Slip      # 物理キー_回収
u.confirm_stopped(subject, *, by, role, at=None) -> Slip                      # 失効_確認
```

`revoke_subject` は、設計書 9 章の 1〜3 を一度の呼び出しで行います。

1. **台帳で止める。** 主体が名簿に無ければ `SUBJECT_UNKNOWN`(停止、退出の主体も止められます)。その主体の権限のうち、状態が `申請中`、`承認`、`発行済み` の物の全部に、権限_失効(範囲 `一人の全経路`)を一枚ずつ書きます。ここから門番を通す錠は開かず、承認を待つ申請も発行できません。
2. **経路ごとに止める。** その主体の実体のうち、**実体_失効がまだ無く、終了を過ぎておらず(実体の終了が空か `at < 終了`)、物理キーなら回収の伝票が無い物**の全部に、経路の「止める」を `at` で呼び、結果を実体_失効(結果、効くまで、作業、理由、操作者、役)に書きます。経路ごとに止めた記録を全部の経路に残すため、門番を通す錠の実体にも、結果 `止まった` の実体_失効を一枚書きます(1 の権限_失効で門番はもう開きませんが、記録は経路ごとに残します)。終了を過ぎた実体と、回収済みの物理キーには書きません。
3. **進み具合を一枚に出す。** `Revocation.進み具合` に `progress(subject, at=at)` を入れて返します。

`revoke_permission` は、一つの権限について同じ 1〜3 を行います(範囲 `一つの権限`。番号が申請でなければ `PERMISSION_UNKNOWN`。進み具合はその権限の主体の物)。状態が `却下`、`期限切れ`、`失効` の権限に呼んだ時は、権限_失効を書かず、その権限の実体のうち 2 の条件に当たる物だけを止めます。期限切れの権限の実体は、終了を過ぎているので 2 の条件に当たらず、実体_失効は書かれません。期限切れの権限の、回収されていない物理キーは、進み具合の表で `人の作業が要る` のまま残り、回収の伝票で止まります。

二度目の呼び出しは伝票を増やしません。1 は状態が `失効` の権限に書かず、2 は実体_失効がもうある実体に書かないためです。その時の `Revocation.権限_失効` と `Revocation.実体_失効` は空の列で、どちらの列にも、その呼び出しで書いた伝票だけが入ります。`進み具合` は今の物です。

#### 進み具合の状態

実体ごとに、`at` で次の表を当てはめます。「終了を過ぎた」は、実体の終了が空でなく `at >= 終了` のことです。

| 経路 | 状態 |
|---|---|
| 門番を通す錠 | 実体_失効がある、権限が `失効`、または終了を過ぎた → `止まった`。ほか → `効いている` |
| 署名つき資格情報 | 終了を過ぎた → `止まった`。実体_失効がある、または権限が `失効` → `待ち`(効くまで = 実体の終了)。ほか → `効いている` |
| 物理キー | 回収がある → `止まった`。実体_失効がある、権限が `失効`、または終了を過ぎた → `人の作業が要る`(作業 = 19.8 の文)。ほか → `効いている` |

`効くまで` は `待ち` の行だけに入り、`作業` は `人の作業が要る` の行だけに入ります。`Sheet.済み` は、全部の行が `止まった` の時に真です。

#### 物理キーの回収と、失効の確認

- `return_physical`: 実体が無ければ `ENTITY_UNKNOWN`、経路が物理キーでなければ `NOT_PHYSICAL`、もう回収があれば `ALREADY_RETURNED`。`result` は `回収` か `錠を交換`。回収の伝票の後、その行は `止まった` です。失効の前の返却にも使えます(R-AC-15「機械の鍵は回収の記録を残す」)。
- `confirm_stopped`(設計書 9 章の 4): 主体が無ければ `SUBJECT_UNKNOWN`。`progress(subject, at=at).済み` が偽なら `NOT_ALL_STOPPED`(詳細に止まっていない実体の番号を「, 」でつなぐ)。通れば失効_確認に、実体の番号の列(無ければ `なし`)を書きます。照らし合わせの結果を確認に入れるのは段 3 です。

#### 例

主体 `s1` に、扉 `玄関` の権限(開始 `2026-12-01T09:00`、終了 `2027-01-01T00:00`)から、署名つき資格情報(実体 E1)、門番を通す錠(E2)、物理キー 鍵番号 `K-7`(E3)を出し、`2026-12-10T12:00` に `revoke_subject("s1", "退職", ...)` を呼ぶと、権限_失効が 1 枚、実体_失効が 3 枚(E1 待ち・効くまで `2027-01-01T00:00`、E2 止まった、E3 人の作業が要る)増え、進み具合は次のとおりです。

| at | E1 | E2 | E3 | 済み |
|---|---|---|---|---|
| 2026-12-10T12:00 | 待ち(2027-01-01T00:00) | 止まった | 人の作業が要る | 偽 |
| E3 の回収の後、2026-12-20T00:00 | 待ち | 止まった | 止まった | 偽 |
| 2027-01-01T00:00 | 止まった | 止まった | 止まった | 真 |

| `GATE_OUT_OF_PERIOD` | 期間の外 | `may_open` |

### 19.12 命令 `digitalkey kanri`

`digitalkey kanri <命令> [引数]` で、19.6〜19.10 のメソッドを呼びます。命令は網を使わず、置き場のファイルだけで動きます(R-AC-19)。

共通の引数:

- `--dir DIR` 置き場。省けば環境変数 `DIGITALKEY_KANRI_DIR`。どちらも無ければ終了コード 2。
- `--by ID`、`--role 役` 書く命令では要ります(無ければ終了コード 2)。読む命令では要りません。
- `--json` 出力を JSON 一つにします(UTF-8、`ensure_ascii=False`)。

鍵の値は、どの引数でも受けません(R-CM-13)。発行者の鍵は `init --issuer-key FILE` のファイルの道か、置き場の `鍵/発行者.key` で渡します。`--audit-key` は扉の記録の公開鍵(秘密でない値)です。

| 命令 | 引数 | 呼ぶ物 |
|---|---|---|
| `init` | `--admin ID --admin-name 名 [--admin-kind 種別] [--issuer-key FILE]`(`--by`、`--role` は要らない) | `Unit.create` |
| `subject add` | `--id ID --name 名 --kind 種別 [--vendor]` | `register_subject` |
| `subject change` | `--id ID [--name] [--kind] [--vendor はい\|いいえ] [--state 有効\|停止\|退出] --reason R` | `change_subject` |
| `subject list` | | `subjects` |
| `role grant` / `role remove` | `--subject ID --name 役 --reason R` | `assign_role` |
| `door add` | `--name N --routes 経路,経路 [--place P] [--audit-key HEX] [--retire]` | `register_door`(`--retire` で状態 撤去) |
| `door list` | | `doors` |
| `group add` | `--name N --doors 扉,扉 [--retire]` | `register_group`(`--retire` で状態 廃止) |
| `setting set` | `--item 項目 --value V --reason R`。項目は `業者の最長の日数`(値は整数か空)と `自己承認`(値は `許す` か `許さない`) | `set_setting` |
| `trust-entry` | | `trust_entry`(いつも JSON) |
| `request` | `--subject S (--door D \| --group G) --from T [--until T] --reason R` | `request` |
| `import` | `--file CSV --source 名` | `import_requests` |
| `decide` | `--request N (--approve \| --reject) [--reason R]` | `decide` |
| `issue` | `--approval N --subject S (--door D \| --group G) --from T [--until T] [--at T]` | `issue` |
| `permission list` | `[--subject S] [--at T]` | `permissions` |
| `entity issue` | `--permission N --route 経路 [--until T] [--once] [--key-number K] [--out FILE] [--at T]` | `issue_entity` |
| `entity list` | `[--subject S]` | `entities` |
| `physical return` | `--entity N [--result 回収\|錠を交換] [--note X]` | `return_physical` |
| `may-open` | `--subject S --door D [--at T]` | `may_open` |
| `revoke` | `(--subject S \| --permission N) --reason R [--at T]` | `revoke_subject` / `revoke_permission` |
| `progress` | `--subject S [--at T]` | `progress` |
| `confirm` | `--subject S [--at T]` | `confirm_stopped` |
| `verify` | | `Ledger.verify_chain` |

- 時刻 `T` は 19.5 の形です。`--at` は `datetime.fromisoformat` で読める物(時差つき可)で、省けば今です。`issue`、`entity issue`、`revoke`、`confirm`、`permission list`、`may-open`、`progress` が受け、メソッドの `at` にそのまま渡します。
- `import` の CSV は UTF-8(先頭の BOM は読み飛ばす)で、一行目が `識別,対象の種類,対象,開始,終了,理由` の見出しです。
- `entity issue --route 署名つき資格情報` は `--out` が要ります(無ければ終了コード 2)。資格情報の JSON(`{"body": ..., "sig": ...}`)を `--out` のファイルへ権限 600 で書き、標準出力には出しません。`--out` のファイルが既にあれば、実体を出す前に `OUT_EXISTS` で拒みます。

出力の形:

| 場合 | 人が読む形(標準出力) | `--json` |
|---|---|---|
| 伝票を書いた | `<様式> <番号>` を一行。一回で複数書いた時は一枚一行 | `{"ok": true, "様式": "...", "番号": "..."}` |
| `init` | `発行者 <識別>` と `公開鍵 <16 進>` の二行 | `{"ok": true, "発行者": "...", "公開鍵": "...", "台帳": "<置き場>/台帳"}` |
| `entity issue` | `実体_発行 <番号>` | `{"ok": true, "様式": "実体_発行", "番号": "...", "経路": "...", "識別": "...", "扉": [...], "開始": "...", "終了": "...", "資格情報のファイル": "<--out か空>"}` |
| `import` | 書いた申請を一枚一行、飛ばした行を `飛ばした <行> <理由>` で一行ずつ | `{"ok": true, "申請": ["<番号>", ...], "飛ばした": [{"行": 1, "理由": "..."}]}` |
| `revoke` | 書いた伝票を一枚一行、続けて進み具合 | `{"ok": true, "権限_失効": [...], "実体_失効": [...], "進み具合": <progress の形>}` |
| 一覧(`list`) | 一件一行。属性をタブでつなぐ | `{"ok": true, "items": [<型の属性を鍵にした辞書>, ...]}`(set と list は列) |
| `may-open` | `開けてよい` か `拒否 <理由>` | `{"ok": true, "開けてよい": bool, "理由": "...", "実体": "..."}` |
| `progress` | 一行目 `<主体> <時刻> 済み` か `<主体> <時刻> 未了`、続けて実体ごとに `<状態>\t<経路>\t<識別>\t<扉>\t<効くまで>\t<作業>` | `{"ok": true, "主体": "...", "時刻": "...", "済み": bool, "実体": [<行>, ...]}`。行は鍵 `実体`、`経路`、`識別`、`扉`(列)、`状態`、`効くまで`、`作業` の辞書。`時刻` は 19.5 の形 |
| `verify` | `連鎖 正常 <件数>` か `連鎖 異常 <理由>` | `{"ok": bool, "件数": n, "理由": "..."}` |
| 拒否(`Refused`) | 標準エラーに `拒否: <理由>` か `拒否: <理由>(<詳細>)` | 標準出力に `{"ok": false, "理由": "...", "詳細": "..."}` |

終了コード:

| コード | 場合 |
|---|---|
| 0 | できた。`may-open` は開けてよい。`progress` は済みでも未了でも 0 |
| 1 | 拒否(`Refused`)。`may-open` の拒否。`verify` の異常 |
| 2 | 引数の誤り(argparse の誤り、`--dir` が無い、書く命令に `--by` か `--role` が無い、署名つき資格情報に `--out` が無い) |
| 3 | 置き場を開けない、作れない(`NO_UNIT`、`NO_KEY`、`WRONG_KEY`。`init --issuer-key` のファイルが読めない時の `NO_KEY` を含む)。標準エラーに理由。`ALREADY_CREATED` は 1 |

例:

```
$ digitalkey kanri init --dir /srv/kanri --admin adm --admin-name 管理者A
発行者 3f2a9c0d1e4b5a67
公開鍵 8c1f...(64 桁)
$ digitalkey kanri issue --dir /srv/kanri --by adm --role 管理者 --approval 20261111T101500-a1b2c3 \
    --subject s1 --door 玄関 --from 2026-12-01T09:00 --until 2027-01-01T00:00
権限_発行 20261111T101612-d4e5f6
$ digitalkey kanri issue --dir /srv/kanri --by adm --role 管理者 --approval 20261111T101400-0f0f0f ...   # 申請の番号を渡した
拒否: 承認がありません          (標準エラー、終了コード 1)
```

### 19.13 要求ごとの確かめ方

テストは `tests/kanri/` に置き、docstring の先頭の行に要求の番号を書きます。置き場は `tmp_path` に作り、発行者の鍵は `Ed25519Signer.generate()` を `signer` で渡します。名前は架空の物にします。疑似の扉は次の形で作ります。

```python
from digitaldoor_controller.audit import Audit, Ed25519Signer
from digitaldoor_controller.contacts import SimContacts
from digitaldoor_controller.controller import Controller

ctl = Controller(SimContacts(), Audit(Ed25519Signer.generate()), name="玄関", trust=u.trust_entry())
ctl.set_time(<unix 秒>, synced=True)
```

`ctl.present(credential)` は `解錠` か `拒否` を返し、拒否の理由は `ctl.audit.entries[-1].result` に入ります。

共通の下ごしらえ(例): `adm`(管理者、名簿の係を兼ねる)、`apr`(承認する人)、`s1`(社員)、扉 `玄関`(三つの経路)を作り、`s1` の申請を `adm` が書き、`apr` が承認し、`adm` が発行します。

**R-AC-09(発行者 A の資格情報で発行者 B の扉が開かない)**

1. 置き場 A と B を、別の鍵で作る。どちらにも扉 `玄関` を登録する。
2. A で `s1` に `玄関` の権限と署名つき資格情報を出す。
3. B の扉 `ctl_b = Controller(..., name="玄関", trust=B.trust_entry())` に A の資格情報を出すと `拒否`、記録の結果は `知らない発行者`。A の扉(`trust=A.trust_entry()`)では `解錠`。
4. A に登録していない扉 `倉庫` への `request` は `UNKNOWN_DOOR`。A の群に `倉庫` を入れる `register_group` も `UNKNOWN_DOOR`。
5. `A.trust_entry()` の鍵は A の発行者の識別だけで、`doors` は A の `使用` の扉だけ。

**R-AC-10(業者と連携先に常の権限を持たせない)**

要求の文の「常の権限を持たせない」を、段 1 では「業者の主体には、終了の無い権限と、管理者の決めた日数を超える権限を出さない」と「業者の鍵で署名した資格情報を扉が拒む」で確かめます。

1. 業者 はい の主体 `v1` の、終了が空の `request` は `VENDOR_NO_END`。
2. `set_setting("業者の最長の日数", "<N>")` の後、N 日を 1 分超える申請は `VENDOR_TOO_LONG`、ちょうど N 日は通る。N の値はテストが選ぶ。
3. 社員として申請し承認した後に、`change_subject(..., vendor=True)` で業者に変えると、終了が空の権限の `issue` は `VENDOR_NO_END`。
4. 業者が自分で作った鍵(`Ed25519Signer.generate()`)で `credentials.issue` した資格情報を、`trust=u.trust_entry()` の扉に出すと `拒否`、記録の結果は `知らない発行者`(遠隔の解錠の要求が拒まれ、記録に残る)。
5. 発行者の出した一回限りの資格情報(`issue_entity(..., once=True)`)は、置き場の `Unit` を閉じた(参照を捨てた)後でも扉で一度だけ `解錠` し、二度目は `使用済み`(業者のサービスや管理のソフトが止まっても、扉は自分で確かめて開ける)。

**R-AC-15(一人の全経路を一覧にし、一度の操作で全部を失効できる。機械の鍵は回収の記録を残す)**

1. `s1` に、同じ権限 P1 から署名つき資格情報、門番を通す錠、物理キー(鍵番号 `K-7`)を出す。`entities("s1")` が三つの経路を返す。失効の前に、`s1` の別の申請を二つ作る。P2 は承認まで進めて発行しない。P3 は申請のまま(判断を書かない)。
2. 失効の前: 資格情報は `ctl.present` で `解錠`、`u.relay(ctl, "s1")` で `解錠`。進み具合は三つとも `効いている`。
3. `revoke_subject("s1", "退職", ...)` を一度呼ぶ。権限_失効が、その主体の開いた権限(申請中、承認、発行済み)の数だけ増える(この筋書きでは P1、P2、P3 の 3 枚)。実体_失効は 3 枚増える(E1 待ち、E2 止まった、E3 人の作業が要る)。
4. 失効の直後: `u.relay(ctl, "s1")` は `拒否`、記録の結果は `失効しています`。`may_open` は `GATE_REVOKED`。進み具合は 19.10 の例のとおり(署名つきは `待ち` で効くまでに権限の終了、物理キーは `人の作業が要る`)。`済み` は偽で、`confirm_stopped` は `NOT_ALL_STOPPED`。
5. 「待ち」の物は期限を過ぎると開かない: 扉の時計を権限の終了の unix 秒にして `ctl.present` は `拒否`、記録の結果は `期限の外`。終了の 1 秒前は `解錠`(段 1 の限界をテストに残す)。
6. `return_physical(<E3>, "回収", ...)` の後、物理キーの行は `止まった`。`at` を権限の終了にした進み具合は `済み` が真で、`confirm_stopped` が失効_確認を書く。
7. 二度目の `revoke_subject` は伝票を増やさず、`Revocation.権限_失効` と `.実体_失効` は空の列。失効の後、P1 の `issue_entity` は `REVOKED`。承認済みで発行前だった P2 の `issue` は `REVOKED`。申請中だった P3 の `decide` は `REVOKED`(19.7 の `decide` の確かめ)。

**R-AC-19(管理者が自分の機械で、網から切り離して動かせる)**

1. `socket.socket` と `socket.create_connection` を、呼ばれたら例外を投げる物に差し替える(monkeypatch)。
2. その中で、命令 `digitalkey kanri` を `digitalkey.kanri.cli.main([...])` で順に呼ぶ(番号は `--json` の出力から読む): `init`、`role grant`(`adm` に名簿の係)、`subject add`(`apr`、`s1`)、`role grant`(`apr` に承認する人)、`door add`、`request`、`decide`(`--by apr --role 承認する人`)、`issue`、`entity issue`(署名つき資格情報を `--out` へ、門番を通す錠)、`revoke --subject s1`、`progress --json`、`verify`。全部の終了コードが 0 で、`progress` の JSON に実体が二つあり、門番を通す錠の行が `止まった`、署名つき資格情報の行が `待ち`。
3. 置き場の外にファイルを書かない(書くのは `--dir` の下と `--out` だけ)。

**R-EB-37(扉の台帳が正。ディレクトリから鍵を出し入れしない)**

1. ディレクトリに居ない人(種別 `清掃` の `c1`、種別 `来客` の `g1`)を `register_subject` で名簿に載せ、申請、承認、発行、門番を通す錠の実体を出すと、`may_open` が通る。
2. 名簿に無い識別の行を持つ一覧を `import_requests` に渡すと、その行は `飛ばした` に `名簿にありません` で入り、`subjects()` の数は変わらず、台帳の伝票は一枚も増えない。
3. 名簿にある `s1` の行を取り込むと、増えるのは権限_申請(出どころ `外の一覧`、一覧の名つき)だけで、状態は `申請中`、`may_open` は `GATE_NO_PERMISSION`。権限_承認、権限_発行、実体_発行は増えない。
4. 取り込みは名簿の係の役だけ。`role="本人"` では `ROLE_NOT_ALLOWED`。

**設計書 6 章の原則(出すのは人が確かめる)の確かめ**(番号は R-EB-37 と R-AC-10 の確かめに入れる)

1. `issue` に、空、無い番号、申請の番号、却下の判断の番号を渡すと、それぞれ `NO_APPROVAL`、`NO_APPROVAL`、`NO_APPROVAL`、`REJECTED`。
2. 承認と違う主体、対象、開始、終了で `issue` すると `MISMATCH`(詳細に項目の名)。
3. (a) 設定 `自己承認` を書いていない置き場で、申請者が `decide` すると `SELF_REQUEST`、申請の主体が `decide` すると `SELF_SUBJECT`。テストが `Ledger.append` で直に書いた「申請者と同じ人の承認」(`自己承認` は `いいえ`)を `issue` に渡すと `SELF_REQUEST`(直に書く時は `u.ledger.roles = {"<人>": {"承認する人"}}` にしてから書きます)。
   (b) 一人で回す置き場: `adm` 一人に、管理者(作った時の物)、名簿の係、承認する人を `assign_role` で割り当て、`set_setting("自己承認", "許す", reason=..., by="adm", role="管理者")` を書く。`adm` が `adm` を主体にした申請を書き(役 名簿の係)、承認し(役 承認する人)、発行し(役 管理者)、実体を出すまで、拒否なしに進む。権限_承認の `自己承認` は `はい`、`役` は `承認する人`、設定の伝票に発行者 `adm` と理由が残る。
   (c) `許す` の置き場でも、`Ledger.append` で直に書いた `自己承認` が `いいえ` の自己承認を `issue` に渡すと `SELF_REQUEST`。
   (d) `許す` で `adm` が自己承認した後、発行の前に `set_setting("自己承認", "許さない", ...)` を書くと、その承認での `issue` は `SELF_REQUEST`。もう一度 `許す` に戻すと通る。
   (e) `set_setting("自己承認", "はい", ...)` は `BAD_SETTING`。
4. 拒んだ時は台帳の伝票の数が変わらない。
5. 止めるのは承認なしで済む: `revoke_subject` は承認の伝票を要らない。

### 19.14 段 1 で仮に決めた事(作る時に選ぶ物)

- 置き場は `digitalkey/kanri/`、台帳は受け入れの台帳と別(`<置き場>/台帳`)。
- 権限の番号は権限_申請の伝票の番号。権限の扉の列は発行の時に決め、発行の伝票に書く。
- 操作する人(`by`)は名簿の主体。名簿の係や承認する人も名簿に載せる(R-EB-37 の「全員」に合わせる)。役は `役_割当` の伝票で付ける。最初の管理者だけは置き場を作る時に役 `初期化` で載せる。
- 発行者(機械)の書く伝票は、伝票の発行者を `発行者`、動かした人を項目 `操作者` にする。
- 自分の申請と、自分が主体の申請の承認は、設定 `自己承認` が `許す` の時だけ通し、権限_承認に `自己承認 はい` の印を残す。発行の時にも今の設定と印を確かめる。設定が無ければ `許さない`。
- 失効は書いた時から効き、`at` に左右されない。期間は `開始 <= 時刻 < 終了`。署名つき資格情報の `not_after` は終了の 1 秒前。
- 署名つき資格情報は終了が要る(期限なしの権限から出す時は `until` を渡す)。R-EB-35 の「網が届く時に延ばす」は、段 2 で実体を出し直す形で足す。
- 業者の上限は台帳の `設定`(項目 `業者の最長の日数`)。値は管理者が書き、書かなければ上限は「終了が要る」だけ。
- 仮名と資格情報の識別と門番の実体の識別は `secrets.token_hex(8)`。
- 物理キーの貸し出しは `実体_発行`、回収は `物理キー_回収`(結果 `回収` か `錠を交換`)。
- 曜日と時間帯、回数、能力(共通コア 7.2)は段 1 の様式に入れない。今の資格情報の形(`digitaldoor-credential/1`)が運べないため。境目の版を固める時に、申請の様式に項目を足す。
- 読む操作は役を問わない(読む範囲の分け方は段 5)。

### 19.15 段 2 以降へ渡す口

- **失効の一覧(段 2)。** 署名つき資格情報の「止める」を、一覧に足して `待ち(一覧が届くまで)` を返す形に替える。`Route` の形は変えない。
- **扉の最長の時間(段 2)。** `扉` の様式に項目を足し、`issue_entity` の確かめと `EffectiveBy` に入れる。
- **台帳の伝票の署名(段 2)。** `Ledger` の側に足す。kanri の伝票の組は変えない。
- **照らす(段 2、3)。** `Route.reconcile` の結果を `confirm_stopped` と照らし合わせの命令に入れる。

### 20.1 考え方と置き場

#### 考え方

- **台帳は事実を写します。** 機器の状態(準備、使用、休止、紛失、廃棄)は、権限を出す時の機器の有無の確かめ(20.8)のほかは門にしません。責任者がいない、区画が決まっていない、据え付けの確かめが無い、といった足りない物は、登録と変更で拒まずに、照らし合わせの「知らせ」(20.9)に挙げます。もう使っている機器をまとめて載せる時に、台帳が実際と違う形にならないようにするためです。
- **止めるのは自動、機械を変えるのは人です。** 機器を紛失か廃棄にすると、その機器を対象にした開いた権限を、同じ操作の中で自動で失効にします(20.6)。機器の中のアカウントを消すのは人で、消した記録(`管理者の口_削除`)が出るまで、進み具合に `人の作業が要る` で残ります。物理キーの回収と同じ形です。

- **日数は管理者の設定です。** 点検の間と、更新の期限の何日前に知らせるかは、様式 `設定` の項目で、ソフトは既定の値を持ちません。設定を書いていない間は、その知らせを出しません。

### 20.5 区画

```python
u.register_segment(name, *, by, role, note="", state="使用") -> Slip      # 区画
u.segments() -> list[Segment]       # 今の値。廃止した区画も入る。最初の伝票を台帳に書いた順
```

- `register_segment`: 名前に「,」があれば `NAME_HAS_COMMA`。`state` は `使用` か `廃止`(ほかは `FORM`)。同じ名前の二枚目は今の値を置き換えます(`群` と同じ)。
- 廃止した区画を載せている機器は、そのまま残ります。使用の機器なら `F_NO_SEGMENT` に挙がります(20.9)。

例: `u.register_segment("扉", note="錠、扉のコントローラ、小さなサーバー", by="adm", role="管理者")` → 伝票 `区画`、状態 `使用`。

### 20.6 機器の台帳

#### 登録

```python
u.register_device(name, kind, state, *, by, role, owner="", place="", segment="", door_system=False, door="",
                  maker="", model="", serial="", net_id="", version="", support_until="", update_mode="",
                  secret_ref="", log_to="", holds="") -> Slip                 # 機器_登録
u.device(name) -> Device             # 無ければ Refused(UNKNOWN_DEVICE)
u.devices() -> list[Device]          # 機器_登録を台帳に書いた順。廃棄も入る
```

引数と様式の項目の対応:

| 引数 | 項目 | 引数 | 項目 |
|---|---|---|---|
| `name` | 名前 | `serial` | 製造番号 |
| `kind` | 種類 | `net_id` | 網の番号 |
| `state` | 状態 | `version` | 版 |
| `owner` | 責任者 | `support_until` | 更新の期限(`年-月-日` の文字列か `date`。様式の修復を通す) |
| `place` | 置き場 | `update_mode` | 更新の当て方 |
| `segment` | 区画 | `secret_ref` | 秘密の在庫の番号 |
| `door_system` | 扉の系統(bool) | `log_to` | 記録の送り先 |
| `door` | 扉 | `holds` | 中に残る物 |
| `maker` | 製造者 | `model` | 型 |

- `state` は既定を持ちません。登録の時に必ず渡します。`準備`、`使用`、`休止` のほか(`紛失`、`廃棄` を含む)は `FORM` です。
- 確かめ(19.3 の 1〜5 の後、この順):
  1. 名前に「,」がある → `NAME_HAS_COMMA`
  2. 同じ名前の機器がある(廃棄した機器を含む) → `DUPLICATE_DEVICE`(「同じ名前の機器があります」)
  3. `owner` が空でなく、名簿に無い → `SUBJECT_UNKNOWN`。有効でない → `SUBJECT_INACTIVE`
  4. `segment` が空でなく、状態が `使用` の区画でない → `UNKNOWN_SEGMENT`(「登録されていない区画です」。詳細に区画の名)
  5. `door` が空でなく、この置き場の `使用` の扉でない → `UNKNOWN_DOOR`(詳細に扉の名)
- 種類と扉の系統の組み合わせ、種類と扉の組み合わせは確かめません(台帳は事実を写す)。

例: `u.register_device("ルーター1", "ルーター", "使用", owner="t1", segment="事務", support_until="2027-03-31", by="adm", role="管理者")` → 伝票 `機器_登録`、`u.device("ルーター1").扉の系統 is False`、`版` は空。

#### 変更、紛失、廃棄

```python
u.change_device(name, *, reason, by, role, at=None, kind=None, owner=None, place=None, segment=None,
                door_system: bool | None = None, door=None, maker=None, model=None, serial=None, net_id=None,
                version=None, support_until=None, update_mode=None, secret_ref=None, log_to=None, holds=None,
                state=None) -> DeviceChange                                 # 機器_変更
```

- 渡した項目だけが変わります。空の文字列は None と同じ(前のまま)です。`door_system` は None なら前のまま、bool なら `はい` か `いいえ` を書きます。`state` は `準備`、`使用`、`休止`、`紛失`、`廃棄` です。
- 確かめ(19.3 の 1〜5 の後、この順):
  1. 機器が無い → `UNKNOWN_DEVICE`(「この台帳の機器ではありません」。詳細に機器の名)
  2. 今の状態が `廃棄` → `DEVICE_RETIRED`(「廃棄した機器です」)
  3. 変える項目(`reason` と `at` のほかの引数)が一つも無い → `NOTHING_TO_CHANGE`
  4. `owner`、`segment`、`door` は、渡した時だけ登録と同じ確かめ(`SUBJECT_UNKNOWN`、`SUBJECT_INACTIVE`、`UNKNOWN_SEGMENT`、`UNKNOWN_DOOR`。この順)
- 通れば機器_変更を一枚書きます。
- **状態を紛失か廃棄にした時**(`state` に `紛失` か `廃棄` を渡した時。紛失から廃棄へ変える時も)は、同じ呼び出しの中で、機器_変更の後に、次を書きます。
  1. その機器を対象にした権限(対象の種類 `機器`、対象がこの名前。主体を問わない)のうち、状態(`at` で読む)が `申請中`、`承認`、`発行済み` の物の全部に、権限_失効(範囲 `機器の停止`、理由は `reason`)を一枚ずつ。並びは権限_申請を台帳に書いた順です。
  2. その機器を対象にした権限の実体の全部のうち、19.10 の 2 の条件(実体_失効がまだ無く、終了を過ぎておらず、回収の伝票が無い)に当たる物に、経路の「止める」を `at` で呼び、結果を実体_失効(理由は `reason`、操作者は `by`、役は `role`)に書きます。並びは実体_発行を台帳に書いた順です。
  3. `DeviceChange(伝票=機器_変更, 権限_失効=1 で書いた列, 実体_失効=2 で書いた列)` を返します。
- `at` は 2 の「止める」と期限の判定に渡す時刻です(`datetime | None`。None は今)。
- 紛失から `使用` などへ戻せます。戻しても、失効した権限は戻りません(申請し直します)。廃棄からは変えられません(上の 2)。
- 機器を紛失か廃棄にしても、その機器の責任者や権限の主体の、扉の権限は止めません。人を止めるのは `revoke_subject` です。

例: 機器 `ルーター1` に、`t1` の発行済みの機器の権限 P1(管理者の口の実体 E1)と、`v1` の申請中の機器の権限 P2 がある時、`u.change_device("ルーター1", reason="なくした", state="紛失", by="adm", role="管理者")` は、機器_変更 1 枚、権限_失効 2 枚(P1、P2。範囲 `機器の停止`)、実体_失効 1 枚(E1、結果 `人の作業が要る`)を書きます。

### 20.7 確かめと更新

#### 確かめ(据え付け、点検、廃棄)

```python
u.check_device(name, scene, results: dict[str, str], *, by, role, note="", at=None) -> Slip   # 機器_確かめ
u.checks(name) -> list[Check]        # その機器の確かめを、台帳に書いた順。機器が無ければ Refused(UNKNOWN_DEVICE)
```

- `scene` は様式の `場面`(`据え付け`、`点検`、`廃棄`)、`results` は `{確かめの項目の名: 良い|悪い|当たらない}`、`note` は `所見` です。`at` は確かめた日時(19.5 の形の文字列か `datetime`。None は今)で、様式の `日時` に書きます。
- 確かめの項目は九つで、様式の項目の順は次のとおりです: `初めのパスワード`、`外からの口`、`見覚えのない設定とアカウント`、`版`、`区画`、`権限`、`記録の送り先`、`中に残る物`、`網から外した`。どれも空でよく、空は「見ていない」です。
- 確かめ(19.3 の 1〜5 の後、この順):
  1. 機器が無い → `UNKNOWN_DEVICE`
  2. 本人の役で、`by` がその機器の責任者でない → `NOT_OWNER`
  3. 機器が廃棄で、場面が `廃棄` でない → `DEVICE_RETIRED`
  4. `results` の鍵が九つの項目に無い → `FORM`(詳細にその鍵)
  5. `results` の値が全部空で、`note` も空 → `FORM`(詳細 `確かめの項目か所見が要ります`)
  6. 場面ごとに要る項目が空 → `NEED_ITEM`(「確かめの項目が足りません」。詳細に、足りない最初の項目の名。項目の順は上の順)

| 場面 | 要る項目 |
|---|---|
| 据え付け | `初めのパスワード`(R-NW-03) |
| 点検(種類が `ルーター` の機器) | `外からの口`、`見覚えのない設定とアカウント`(R-NW-04「点検のたびに確かめ、記録に残す」) |
| 点検(ほかの種類) | なし |
| 廃棄 | `中に残る物`、`網から外した` |

- 「要る」は空でない事で、`当たらない` でも通ります。値の良し悪しは拒まず、`悪い` は知らせ `F_BAD_ITEM` に挙がります(20.9)。
- 項目の「今の値」は、その機器の確かめのうち、その項目が空でない最後の一枚(台帳に書いた順)の値です。

例: `u.check_device("ルーター1", "据え付け", {"初めのパスワード": "良い", "外からの口": "悪い"}, note="遠隔の管理が開いていた", at="2026-12-01T09:00", by="t1", role="本人")`(`t1` が責任者)→ 伝票 `機器_確かめ`。`u.checks("ルーター1")[-1].結果 == {"初めのパスワード": "良い", "外からの口": "悪い"}`。

#### 更新

```python
u.record_update(name, version, *, by, role, result="当てた", reason="", at=None) -> Slip   # 機器_更新
```

- `version` は `後の版`、`result` は `当てた` か `当てられなかった`、`at` は日時(None は今)です。`前の版` は、書く時の台帳の今の版(空でよい)をソフトが書きます。
- 確かめ(19.3 の 1〜5 の後、この順): 機器が無い → `UNKNOWN_DEVICE`。本人の役で責任者でない → `NOT_OWNER`。機器が廃棄 → `DEVICE_RETIRED`。`result` が `当てられなかった` で `reason` が空 → `NEED_REASON`(「理由が要ります」)。
- `当てた` の後は、`後の版` が機器の今の版です。`当てられなかった` の時は版は変わらず、理由が台帳に残ります。

### 20.8 機器を対象にした権限と、経路「管理者の口」

機器の権限は、その機器の管理者の口(管理の画面、遠隔の管理、SSH など)に入る権限です。申請、承認、発行、失効の伝票は、扉の権限と同じ物を使います(設計書 7a 章「人の権限とのつなぎ」)。

#### 申請と発行

- `request(subject, "機器", <機器の名前>, start, end, reason, ...)`: 19.7 の確かめの「扉か群」の所で、対象が、状態が `準備`、`使用`、`休止` の機器でなければ `UNKNOWN_DEVICE`(詳細に対象の名)。そのほかの確かめ(主体、期間、業者の `VENDOR_NO_END`、`VENDOR_TOO_LONG`)は扉と同じに当たります(R-AC-10「業者には要る間だけ」)。`import_requests` の行も同じです。
- `issue`: 19.7 の 8 で、対象の種類が `機器` なら同じ確かめ(`UNKNOWN_DEVICE`)をし、扉の列は空です。権限_発行の `扉` は空で、`Permission.扉` は空の列です。
- `may_open` と `trust_entry` は機器の権限を見ません。機器の権限で開く扉はありません。

#### 実体を出す

```python
u.issue_entity(pid, route, *, by, role, until=None, once=False, key_number="", account="", at=None) -> Issued
```

- `account` は口の名(アカウントの名や鍵の名)です。秘密の値ではありません。`account` は経路が管理者の口の時だけ使います。
- 確かめは 19.8 の順のまま、「主体が有効でなければ `SUBJECT_INACTIVE`」の後を、経路が管理者の口の時は次にします。
  1. 権限の対象の種類が `機器` でない → `DEVICE_ONLY`(「管理者の口は機器の権限だけです」)
  2. 対象の機器の状態が `準備`、`使用`、`休止` でない → `UNKNOWN_DEVICE`
  3. (`NO_DOOR_FOR_ROUTE` は確かめない)
  4. その後は 19.8 のまま: `ONCE_CREDENTIAL_ONLY`、`UNTIL_TOO_LATE`、`BAD_PERIOD`、経路の「出す」(`account` が空なら `NEED_ACCOUNT`「口の名が要ります」)
- 機器の権限に、ほかの三つの経路を渡すと、扉の列が空なので 19.8 のとおり `NO_DOOR_FOR_ROUTE` です。
- `Route.issue` の形は変えません。`Unit` は、経路が管理者の口の時、`account` を差し替え口の引数 `key_number` で渡します(`key_number` は、人が渡す識別の口として使います)。19.3 の 5 では、`account` を実体_発行の `識別`(varchar(64))に照らします。
- 実体_発行は、`扉` が空、`機器` が機器の名前、`識別` が口の名です。`発行者` は空、`一回限り` は いいえ です。
- 一つの口を複数の人が使う機器(管理者のアカウントが一つだけのプリンターやルーター)があるので、同じ機器と同じ口の名の実体を、何人分でも出せます(拒みません。知らせ `F_SHARED_ACCOUNT` に挙がります)。

例: `t1` の機器 `ルーター1` の発行済みの権限 P から `u.issue_entity(P, "管理者の口", account="admin", by="adm", role="管理者")` → 実体_発行(経路 `管理者の口`、扉 空、機器 `ルーター1`、識別 `admin`)。`Issued.資格情報` は None。

#### 経路「管理者の口」の四つの働き

| 働き | 管理者の口 |
|---|---|
| 出す | `key_number`(= `account`)が空なら `NEED_ACCOUNT`。`RouteIssue(識別=account, 発行者="", 資格情報=None)` |
| 止める | 削除の伝票がある(`entity.回収` が空でない)なら `Stop("止まった", "", "")`。ほかは `Stop("人の作業が要る", "", "機器 <機器> の管理者の口 <識別> を止める。分けられない口はパスワードを替えて、削除の伝票に書く")` |
| 効くまで | `EffectiveBy("人の作業まで", "")` |
| 照らす | 進み具合の状態が `人の作業が要る` なら `Reconcile("違い", "口が残ったまま")`。ほかは `Reconcile("照らせない", "機械の中との照らし合わせは段 6")` |

進み具合の状態(19.10 の表に足す行):

| 経路 | 状態 |
|---|---|
| 管理者の口 | 削除の伝票がある → `止まった`。実体_失効がある、権限が `失効`、または終了を過ぎた → `人の作業が要る`(作業 = 上の文)。ほか → `効いている` |

#### 削除

```python
u.remove_access(entity_id, result="消した", note="", *, by, role) -> Slip   # 管理者の口_削除
```

- `result` は `消した`、`パスワードを替えた`、`機器を初期化`、`機器が無い`(ほかは `FORM`)、`note` は `備考` です。書く値は、実体、機器(実体の `機器`)、口の名(実体の `識別`)、結果、備考、役です。
- 確かめ(19.3 の 1〜5 の後、この順): 実体が無い → `ENTITY_UNKNOWN`。経路が管理者の口でない → `NOT_ACCESS`(「管理者の口ではありません」)。本人の役で、`by` がその機器の責任者でない → `NOT_OWNER`。もう削除の伝票がある → `ALREADY_REMOVED`(「削除済みです」)。
- 失効の前にも書けます(人が先に口を消した時)。機器が廃棄でも書けます。削除の後、その行は `止まった` です。
- 物理キーの実体に `remove_access` は `NOT_ACCESS`、管理者の口の実体に `return_physical` は `NOT_PHYSICAL` です。

#### 失効、進み具合、確認

`revoke_subject`、`revoke_permission`、`confirm_stopped` は 19.10 のままで、機器の権限と管理者の口の実体にも同じに当たります。一人を止めると、扉の鍵と機器の口が同じ一枚の進み具合に並びます(設計書 7a 章)。削除の伝票が出るまで `済み` は偽で、`confirm_stopped` は `NOT_ALL_STOPPED` です。

例: `s1` に扉 `玄関` の権限から門番を通す錠(E1)、機器 `ルーター1` の権限から管理者の口 `admin`(E2)を出し、`revoke_subject("s1", "退職", ...)` を呼ぶと、権限_失効 2 枚(範囲 `一人の全経路`)、実体_失効 2 枚(E1 止まった、E2 人の作業が要る)が増え、進み具合の人が読む行は次のとおりです。

```
s1 2026-12-10T12:00 未了
止まった	門番を通す錠	<E1 の識別>	玄関			
人の作業が要る	管理者の口	admin			機器 ルーター1 の管理者の口 admin を止める。分けられない口はパスワードを替えて、削除の伝票に書く	ルーター1
```

### 20.9 台帳だけでできる照らし合わせ(知らせ)

```python
u.device_findings(*, at=None) -> list[Finding]     # Finding(機器, 知らせ, 詳細)
```

- 並びは、機器_登録を台帳に書いた順、同じ機器の中では下の表の順です。
- 「今日」は `at`(None は今。時差つきは地方時に直す)の地方時の日付です。
- 「見る状態」に当たらない機器には、その知らせを出しません。
- 知らせは拒否ではありません。命令は、知らせがあっても無くても終了コード 0 です。

| 定数 | 知らせ | 条件 | 見る状態 | 詳細 | 要求 |
|---|---|---|---|---|---|
| `F_NO_OWNER` | 責任者がいません | 責任者が空 | 準備、使用、休止、紛失 | 空 | R-NW-05 |
| `F_OWNER_INACTIVE` | 責任者が有効ではありません | 責任者の主体の状態が `有効` でない | 準備、使用、休止、紛失 | 責任者の識別 | R-NW-05 |
| `F_NO_SEGMENT` | 区画が決まっていません | 区画が空か、その区画が `廃止` | 使用 | 区画の名か空 | R-NW-02 |
| `F_MIXED_SEGMENT` | 扉の系統とほかの機器が同じ区画です | 扉の系統が いいえ で、区画が空でなく、同じ区画に、状態が使用で扉の系統が はい の機器がある | 使用 | 区画の名 | R-NW-02 |
| `F_NO_SUPPORT_END` | 更新の期限が分かりません | 更新の期限が空 | 使用 | 空 | R-NW-03 |
| `F_SUPPORT_ENDED` | 更新の期限を過ぎています | 今日 > 期限(期限の日は内) | 使用 | 期限 | R-NW-03 |
| `F_SUPPORT_NEAR` | 更新の期限が近づいています | 設定 `更新の期限の知らせの日数` が N で、0 <= 期限 - 今日 <= N 日 | 使用 | 期限 | R-NW-03 |
| `F_NO_INSTALL_CHECK` | 据え付けの確かめがありません | 場面が `据え付け` の確かめが一枚も無い | 使用 | 空 | R-NW-03 |
| `F_BAD_ITEM` | 確かめの結果が悪いままです | 確かめの項目の今の値(20.7)が `悪い`。項目ごとに一つ、様式の項目の順 | 使用 | 項目の名 | R-NW-02〜04 |
| `F_CHECK_OVERDUE` | 点検の間が空いています | 設定 `点検の間の日数` が N で、場面が `据え付け` か `点検` の確かめの `日時` のうち一番遅い物から `at` までが N 日を超える(ちょうど N 日は挙げない)。そのような確かめが一枚も無い時も挙げる | 使用 | 一番遅い確かめの日時か `確かめなし` | R-NW-04 |
| `F_SHARED_ACCOUNT` | 一つの口を複数の人が使っています | この機器の管理者の口の実体のうち、進み具合の状態(`at` で読む)が `止まった` でない物が、同じ口の名で、主体が二人以上。口の名ごとに一つ、その口の名の最初の実体_発行を台帳に書いた順 | 使用 | 口の名 | R-RS-04 |
| `F_NO_DISPOSAL_CHECK` | 廃棄の確かめがありません | 場面が `廃棄` の確かめが一枚も無い | 廃棄 | 空 | 設計書 7a 章 |
| `F_ACCESS_LEFT` | 止まっていない口があります | この機器の管理者の口の実体に、進み具合の状態(`at` で読む)が `止まった` でない物がある | 紛失、廃棄 | 実体の番号を、実体_発行を台帳に書いた順に「, 」でつなぐ | R-AC-15 |

- 設定 `点検の間の日数`、`更新の期限の知らせの日数` を書いていない間(最後の設定の伝票の値が空の時を含む)は、`F_CHECK_OVERDUE` と `F_SUPPORT_NEAR` を出しません。
- 期限と今日の差は日付の差(日数)、点検の間は日時の差(`at - 日時 > timedelta(days=N)`)です。

例: 設定の無い置き場で、使用のルーター `ルーター1`(責任者 空、区画 空、更新の期限 空、確かめなし)の知らせは、`F_NO_OWNER`、`F_NO_SEGMENT`、`F_NO_SUPPORT_END`、`F_NO_INSTALL_CHECK` の 4 件で、この順です。

### 20.10 業者と連携先に渡している物の目録(R-RS-04)

```python
u.vendor_inventory(*, at=None) -> list[Held]
# Held(主体, 権限, 対象の種類, 対象, 開始, 終了, 状態, 残り: list[Row])
```

- 今の名簿で `業者` が はい の主体の権限のうち、状態(`at` で読む)が `発行済み` の物か、その権限の実体に進み具合の状態が `止まった` でない物がある権限を、権限_申請を台帳に書いた順に並べます。
- `残り` は、その権限の実体の進み具合の行(19.10、20.8)のうち `止まった` でない物で、実体_発行を台帳に書いた順です。
- 扉、群、機器の権限のどれも入ります。失効した後でも、管理者の口や物理キーが残っている間は目録に残ります(渡したままの物が見えます)。
- R-RS-04 の「漏れたときに作り直す順番」は、段 3 の出来事の手順で扱います。段 1b の目録は、作り直す物を挙げる所までです。

### 20.11 拒否の理由と知らせの言葉

`digitalkey.kanri.reasons` に足す定数です。テストは言葉で比べてかまいません。

| 定数 | 言葉 | 出る所 |
|---|---|---|
| `DUPLICATE_DEVICE` | 同じ名前の機器があります | `register_device` |
| `UNKNOWN_DEVICE` | この台帳の機器ではありません | `device`、`checks`、`change_device`、`check_device`、`record_update`、機器の権限の `request`、`issue`、`issue_entity`(詳細に機器の名) |
| `UNKNOWN_SEGMENT` | 登録されていない区画です | `register_device`、`change_device`(詳細に区画の名) |
| `DEVICE_RETIRED` | 廃棄した機器です | `change_device`、`check_device`(場面が廃棄でない時)、`record_update` |
| `NOT_OWNER` | この機器の責任者ではありません | 本人の役の `check_device`、`record_update`、`remove_access` |
| `NEED_ITEM` | 確かめの項目が足りません | `check_device`(詳細に項目の名) |
| `NEED_REASON` | 理由が要ります | `record_update`(当てられなかった) |
| `DEVICE_ONLY` | 管理者の口は機器の権限だけです | `issue_entity` |
| `NEED_ACCOUNT` | 口の名が要ります | `issue_entity`(管理者の口) |
| `NOT_ACCESS` | 管理者の口ではありません | `remove_access` |
| `ALREADY_REMOVED` | 削除済みです | `remove_access` |

知らせの言葉(拒否ではなく、`Finding.知らせ` に入る言葉)も、同じ `reasons.py` に置きます。

| 定数 | 言葉 |
|---|---|
| `F_NO_OWNER` | 責任者がいません |
| `F_OWNER_INACTIVE` | 責任者が有効ではありません |
| `F_NO_SEGMENT` | 区画が決まっていません |
| `F_MIXED_SEGMENT` | 扉の系統とほかの機器が同じ区画です |
| `F_NO_SUPPORT_END` | 更新の期限が分かりません |
| `F_SUPPORT_ENDED` | 更新の期限を過ぎています |
| `F_SUPPORT_NEAR` | 更新の期限が近づいています |
| `F_NO_INSTALL_CHECK` | 据え付けの確かめがありません |
| `F_BAD_ITEM` | 確かめの結果が悪いままです |
| `F_CHECK_OVERDUE` | 点検の間が空いています |
| `F_SHARED_ACCOUNT` | 一つの口を複数の人が使っています |
| `F_NO_DISPOSAL_CHECK` | 廃棄の確かめがありません |
| `F_ACCESS_LEFT` | 止まっていない口があります |

`Refused.詳細` は、表で「詳細に」と書いた物と、`FORM`(20.7 の 4、5 を含む)に入れ、ほかは空です。

### 20.12 命令 `digitalkey kanri`(足す物)

共通の引数、出力の形、終了コードは 19.12 のとおりです。書く命令には `--by`、`--role` が要ります。

| 命令 | 引数 | 呼ぶ物 |
|---|---|---|
| `segment add` | `--name N [--note X] [--retire]` | `register_segment`(`--retire` で状態 廃止) |
| `segment list` | | `segments` |
| `device add` | `--name N --kind K --state S [--owner ID] [--place P] [--segment S] [--door-system] [--door D] [--maker M] [--model M] [--serial S] [--net-id X] [--version V] [--support-until 年-月-日] [--update-mode 自動\|人] [--secret-ref R] [--log-to X] [--holds X]` | `register_device`(`--door-system` で扉の系統 はい) |
| `device change` | `--name N --reason R [--kind K] [--owner ID] [--place P] [--segment S] [--door-system はい\|いいえ] [--door D] [--maker M] [--model M] [--serial S] [--net-id X] [--version V] [--support-until 年-月-日] [--update-mode 自動\|人] [--secret-ref R] [--log-to X] [--holds X] [--state 準備\|使用\|休止\|紛失\|廃棄] [--at T]` | `change_device` |
| `device list` | | `devices` |
| `device checks` | `--name N` | `checks` |
| `device check` | `--name N --scene 据え付け\|点検\|廃棄 [--item 項目=結果]... [--note X] [--at T]` | `check_device` |
| `device update` | `--name N --version V [--failed] [--reason R] [--at T]` | `record_update`(`--failed` で結果 当てられなかった) |
| `device findings` | `[--at T]` | `device_findings` |
| `access remove` | `--entity N [--result 消した\|パスワードを替えた\|機器を初期化\|機器が無い] [--note X]` | `remove_access` |
| `vendor list` | `[--at T]` | `vendor_inventory` |

- `device add` の `--state` は要ります。無ければ終了コード 2 です。`--state`、`--scene`、`--update-mode`、`device change` の `--door-system` は、選べる値のほかを argparse の誤り(終了コード 2)にします。`access remove --result` は `physical return --result` と同じく様式で確かめます(外れは `FORM`、終了コード 1)。
- `device check --item` は何度でも書けます。値は最初の `=` で項目と結果に分けます。`=` の無い物は終了コード 2 です。同じ項目を二度書いた時は後の値です。
- `--at` は 19.12 と同じく `datetime.fromisoformat` で読める物(時差つき可)で、省けば今です。`device change`、`device check`、`device update`、`device findings`、`vendor list` が受けます。
- 段 1 の命令に足す物: `request` と `issue` の `(--door D | --group G)` を `(--door D | --group G | --device D)` にします(`--device` は対象の種類 `機器`)。`entity issue` に `--account A`(口の名)を足します。`import` の CSV は `対象の種類` に `機器` を書けます。`setting set` の `--item` は `業者の最長の日数`、`自己承認`、`点検の間の日数`、`更新の期限の知らせの日数` です。

出力の形(19.12 の表に足す物):

| 場合 | 人が読む形(標準出力) | `--json` |
|---|---|---|
| `device change` | 書いた伝票を一枚一行(`<様式> <番号>`)。機器_変更、権限_失効、実体_失効の順 | `{"ok": true, "様式": "機器_変更", "番号": "...", "権限_失効": ["<番号>", ...], "実体_失効": ["<番号>", ...]}` |
| `segment list`、`device list`、`vendor list`、`device checks`、`device findings` | 一件一行。属性をタブでつなぐ(19.12 の一覧と同じ) | `{"ok": true, "items": [<型の属性を鍵にした辞書>, ...]}` |
| `progress`、`revoke` の進み具合 | 実体ごとに `<状態>\t<経路>\t<識別>\t<扉>\t<効くまで>\t<作業>\t<機器>` | 行の辞書に鍵 `機器` が増える |

- `device findings` の一行は `<機器>\t<知らせ>\t<詳細>` です。知らせが無ければ何も出さず、終了コード 0 です。
- `device checks` の人が読む形の `結果` は、`項目=結果` を様式の項目の順に「, 」でつなぎます。`--json` の `結果` は辞書です。
- `vendor list` の人が読む形の `残り` は、行ごとの `<実体>(<状態>)` を「, 」でつなぎます。`--json` の `残り` は、`progress --json` の行と同じ形の辞書の列です。

例:

```
$ digitalkey kanri device add --dir /srv/kanri --by adm --role 管理者 --name ルーター1 --kind ルーター --state 使用
機器_登録 20261201T090000-1a2b3c
$ digitalkey kanri device findings --dir /srv/kanri
ルーター1	責任者がいません	
ルーター1	区画が決まっていません	
ルーター1	更新の期限が分かりません	
ルーター1	据え付けの確かめがありません	
$ digitalkey kanri device check --dir /srv/kanri --by adm --role 管理者 --name ルーター1 --scene 据え付け --item 外からの口=良い
拒否: 確かめの項目が足りません(初めのパスワード)          (標準エラー、終了コード 1)
```

### 20.13 要求ごとの確かめ方

テストは `tests/kanri/` に置き、docstring の先頭の行に要求の番号を書きます。置き場、鍵、名前の決め方は 19.13 と同じです。知らせは一つの機器に複数出るので、テストは `知らせ` の言葉で絞って比べます。

共通の下ごしらえ(例): 19.13 の `adm`(管理者、名簿の係)、`apr`(承認する人)に、`ops`(運用)、`t1` と `t2`(社員)、`v1`(業者 はい)を足す。扉 `玄関`(三つの経路)。区画 `扉`、`事務`、`来客`。機器 `ルーター1`(ルーター、使用)、`玄関の錠`(錠、使用、扉の系統 はい、扉 `玄関`、区画 `扉`)、`複合機1`(プリンター、使用)。日時は 2026-12-01 以後の架空の物を、テストが選ぶ。

**R-NW-02(扉の系統をほかの機器と別の区画に分け、外から扉の系統へ直接入る口を開けない)**

1. `複合機1` を区画 `扉` に載せる(`change_device(..., segment="扉")`)と、`複合機1` に `F_MIXED_SEGMENT`(詳細 `扉`)。`玄関の錠` には出ない。
2. `複合機1` を区画 `事務` に変えると、`F_MIXED_SEGMENT` が消える。
3. 区画の無い使用の機器は `F_NO_SEGMENT`(詳細 空)。区画 `来客` を `register_segment(..., state="廃止")` にすると、そこに載せた使用の機器は `F_NO_SEGMENT`(詳細 `来客`)。廃止の区画への `register_device` と `change_device` は `UNKNOWN_SEGMENT`。
4. 確かめで `区画` か `外からの口` を `悪い` と書くと `F_BAD_ITEM`(詳細に項目の名)。後の確かめでその項目を `良い` と書くと消える。後の確かめでその項目が空なら、`悪い` のまま残る。
5. 限界: 台帳で確かめられるのは載せ方までで、実際のつなぎ方とポートの転送は、人の点検の記録(項目 `区画`、`外からの口`)で照らします。網を読む照らし合わせは段 6 です。この限界をテストの docstring に残す。

**R-NW-03(更新の期限を公開している物を選び、当て続け、期限の前に替える。初めのパスワードのまま使わない)**

1. 使用の `ルーター1` の更新の期限が空 → `F_NO_SUPPORT_END`。
2. 期限 `2027-03-31` で、`at` の日付が `2027-03-31` なら `F_SUPPORT_ENDED` は出ず(期限の日は内)、`2027-04-01` なら出る(詳細 `2027-03-31`)。
3. 設定 `更新の期限の知らせの日数` を `30` にすると、`at` の日付が `2027-03-01`(残り 30 日)と `2027-03-31`(残り 0 日)で `F_SUPPORT_NEAR`、`2027-02-28`(残り 31 日)と `2027-04-01` では出ない。設定を書いていなければ、どの日も出ない。設定 `更新の期限の知らせの日数` に `0`、`-1`、`三十` は `BAD_SETTING`。
4. 据え付けの確かめに `初めのパスワード` が無いと `NEED_ITEM`(詳細 `初めのパスワード`)で、伝票は増えない。`当たらない` は通る。
5. 据え付けで `初めのパスワード` を `悪い` と書くと `F_BAD_ITEM`。替えた後の点検で `良い` と書くと消える。据え付けの確かめが一枚も無い使用の機器は `F_NO_INSTALL_CHECK`。
6. 版 `1.0` で登録し、`record_update("ルーター1", "1.1", ...)` の後、`device("ルーター1").版 == "1.1"`、機器_更新の `前の版` は `1.0`。`record_update(..., "1.2", result="当てられなかった", reason="製造者の更新が止まっている")` の後も版は `1.1` で、理由が伝票に残る。`当てられなかった` で理由が空なら `NEED_REASON`。

**R-NW-04(ルーターの外からの口を要る時だけにし、点検のたびに見覚えのない設定とアカウントを確かめ、記録に残す)**

1. 種類 `ルーター` の点検で、`外からの口` か `見覚えのない設定とアカウント` が空なら `NEED_ITEM`(詳細に足りない最初の項目)。種類 `プリンター` の点検は、どちらが空でも通る。
2. 二つを書いた点検は、`checks("ルーター1")` の最後の `Check` に、場面 `点検`、`日時`、`結果`、`書いた人` が残る。
3. 設定 `点検の間の日数` を `90` にし、最後の点検の日時を `2026-12-01T09:00` にすると、`at=2027-03-01T09:00`(ちょうど 90 日)では `F_CHECK_OVERDUE` は出ず、`2027-03-01T09:01` で出る(詳細 `2026-12-01T09:00`)。確かめの無い使用の機器は、詳細 `確かめなし` で出る。
4. 設定を書いていない置き場では、どれだけ間が空いても出ない。設定の値を空に書き直すと、また出なくなる。

**R-NW-05(ルーターの持ち主を決める)**

1. 責任者のいない使用の `ルーター1` に `F_NO_OWNER`。準備、休止、紛失の機器にも出る。廃棄の機器には出ない。
2. `change_device("ルーター1", owner="t1", ...)` で消える。
3. `change_subject("t1", state="退出", ...)` の後、`F_OWNER_INACTIVE`(詳細 `t1`)。退出の `t1` を責任者にする `change_device` は `SUBJECT_INACTIVE`、名簿に無い識別は `SUBJECT_UNKNOWN`。
4. 責任者を `t2` に替えると消える。
5. 要求の「ルーターが止まっても、乗っ取られても、扉の判断と記録は扉の側で続く」は、扉のコントローラのテストの持ち分です(このテストでは確かめない)。

**R-RS-04(業者と連携先に渡している権限と鍵の目録を持つ)**

1. `v1` に `ルーター1` の機器の権限(終了つき)を申請、承認、発行し、管理者の口 `maint` を出す。`v1` に扉 `玄関` の権限と門番を通す錠も出す。`t1` にも `ルーター1` の機器の権限と管理者の口を出す。
2. `vendor_inventory()` は `v1` の二つの権限だけを返す(権限_申請を書いた順)。機器の権限の `残り` は管理者の口の行一つで状態 `効いている`。`t1` の権限は載らない。
3. `revoke_subject("v1", "契約の終了", ...)` の後: 扉の権限は門番を通す錠の行が `止まった` なので目録から消える。機器の権限は状態 `失効` で目録に残り、`残り` の行は `人の作業が要る`。
4. `remove_access(<maint の実体>, by="ops", role="運用")` の後、目録は空。
5. 業者の物理キー(貸し出したまま)も、回収まで目録に残る。

**R-AC-15(一人の全経路を一覧にし、一度の操作で全部を失効できる。機器の口も同じ一枚)**

1. `s1` に、扉 `玄関` の権限から門番を通す錠(E1)、機器 `ルーター1` の権限から管理者の口 `admin`(E2)を出す。`entities("s1")` が二つを返し、E2 の `機器` は `ルーター1`、E1 の `機器` は空。
2. `revoke_subject("s1", "退職", ...)` を一度呼ぶ。権限_失効 2 枚、実体_失効 2 枚(E1 止まった、E2 人の作業が要る)。
3. 進み具合は同じ一枚に二行が並び(20.8 の例)、`済み` は偽。`confirm_stopped` は `NOT_ALL_STOPPED`(詳細に E2 の番号)。E2 の `reconcile` は `Reconcile("違い", "口が残ったまま")`。
4. `remove_access(E2, "消した", by="adm", role="管理者")` の後、E2 の行は `止まった`、`済み` は真、`confirm_stopped` が失効_確認を書く。二度目の `remove_access` は `ALREADY_REMOVED`。
5. 命令 `progress` の人が読む行は 7 列で、E2 の行の末尾は `ルーター1`。`--json` の行に鍵 `機器`。

**R-AC-10(業者と連携先に常の権限を持たせない。機器の権限も同じ)**

1. 業者 `v1` の、終了が空の機器の権限の `request` は `VENDOR_NO_END`。
2. 設定 `業者の最長の日数` を N にすると、N 日を 1 分超える機器の権限の申請は `VENDOR_TOO_LONG`、ちょうど N 日は通る。

**機器の紛失と廃棄**(番号は R-AC-15 と R-NW-05 の確かめに入れる)

1. `ルーター1` に、`t1` の発行済みの機器の権限(管理者の口 E1)、`v1` の承認だけの機器の権限、`t2` の申請中の機器の権限を作る。`t1` には扉 `玄関` の門番を通す錠の権限も出す。
2. `change_device("ルーター1", reason="なくした", state="紛失", ...)` の `DeviceChange` は、権限_失効 3 枚(範囲 `機器の停止`、理由 `なくした`)と、実体_失効 1 枚(E1、人の作業が要る)。三つの権限の状態は `失効`。`t1` の扉の権限は `発行済み` のままで、`may_open("t1", "玄関")` は通る。
3. `device_findings` に `F_ACCESS_LEFT`(詳細に E1 の番号)。`remove_access(E1, ...)` の後に消える。
4. 状態を `使用` に戻しても、三つの権限は `失効` のまま。前の権限の `issue_entity` は `REVOKED`。新しい申請は通る。
5. 状態を `廃棄` にすると、`F_NO_DISPOSAL_CHECK`。場面 `廃棄` の確かめ(`中に残る物`、`網から外した`)で消える。廃棄の機器への `change_device` と `record_update` と場面 `点検` の `check_device` は `DEVICE_RETIRED`。廃棄の機器を対象にした `request` は `UNKNOWN_DEVICE`。廃棄の時に失効した権限の `issue_entity` は `REVOKED`。

**一つの口を複数の人が使う機器**(番号は R-RS-04)

1. `複合機1` の機器の権限を `t1` と `t2` に出し、どちらにも管理者の口 `admin` を出す(拒まない)。`F_SHARED_ACCOUNT`(詳細 `admin`)が一つ出る。
2. 一人の口に `remove_access(..., "パスワードを替えた", ...)` を書くと、止まっていない `admin` の主体が一人になり、知らせが消える。

**拒否と役**(番号は R-NW-05 と R-RS-04 の確かめに入れる)

1. 拒んだ時は、台帳の伝票の数が変わらない(`NAME_HAS_COMMA`、`DUPLICATE_DEVICE`、`UNKNOWN_SEGMENT`、`NEED_ITEM`、`NOT_OWNER`、`DEVICE_RETIRED`、`DEVICE_ONLY`、`NEED_ACCOUNT` のそれぞれで)。
2. 本人の役で、責任者でない `t2` の `check_device("ルーター1", ...)` は `NOT_OWNER`。責任者の `t1` は通る。運用の `ops` は責任者を問わず通る。`register_device` を運用の役で呼ぶと `ROLE_NOT_ALLOWED`。
3. 扉の権限から `issue_entity(..., "管理者の口", account="admin", ...)` は `DEVICE_ONLY`。機器の権限から門番を通す錠は `NO_DOOR_FOR_ROUTE`。機器の権限から `account` の無い管理者の口は `NEED_ACCOUNT`。
4. 機器の権限から実体を出すのは管理者だけ。名簿の係の役では `ROLE_NOT_ALLOWED`。

### 20.14 段 1b で仮に決めた事(作る時に選ぶ物)

- 機器の名前は、廃棄した機器を含めて台帳の中で一つ(廃棄した機器の名前は使い直さない)。
- `Entity.機器` と `Row.機器` は、どちらも最後の属性にする(段 1 の並びを変えない)。
- `change_device` の空の文字列は None と同じ(前のまま)。項目を空に戻すことは、段 1b ではできない。
- 紛失と廃棄の時に止める実体は、その機器を対象にした権限の実体の全部のうち、19.10 の 2 の条件に当たる物(`revoke_subject` と同じく、権限の状態で絞らない。開いた権限の実体と同じ結果になる)。`state` に紛失か廃棄を書くたびに行い、二度目は伝票を増やさない。
- `check_device` と `record_update` の `at` は、19.5 の形の文字列か `datetime` を受ける(様式の `日時` に書くため)。`change_device`、`device_findings`、`vendor_inventory` の `at` は `datetime | None`。
- `check_device` の `results` の知らない鍵は `FORM`(詳細にその鍵)、全部が空で所見も空の時の詳細は `確かめの項目か所見が要ります`。「要る項目」は空でない事で、`当たらない` も通す。
- `F_CHECK_OVERDUE` の「最後の確かめ」は、据え付けと点検の確かめの `日時` のうち一番遅い物(確かめの日時は後から書けるため、台帳に書いた順ではなく日時で選ぶ)。
- `F_MIXED_SEGMENT` は、区画の状態(使用、廃止)を問わず、同じ区画の名で比べる。
- `F_SHARED_ACCOUNT` の並びは、口の名ごとの最初の実体_発行を台帳に書いた順。
- 知らせの `詳細` は、期限は `YYYY-MM-DD`、日時は 19.5 の形、実体の番号は「, 」でつなぐ。
- `UNKNOWN_DEVICE` の詳細は機器の名(申請と発行では対象の名)。`DUPLICATE_DEVICE`、`DEVICE_RETIRED`、`NOT_OWNER`、`NEED_REASON`、`DEVICE_ONLY`、`NEED_ACCOUNT`、`NOT_ACCESS`、`ALREADY_REMOVED` の詳細は空。
- `checks` は、機器が無ければ `UNKNOWN_DEVICE`(`device` と同じ)。
- `issue_entity` の `account` は経路が管理者の口の時だけ使い、その時は `key_number` を使わない。ほかの経路では `account` を使わない。
- 管理者の口の実体_発行の `発行者` は空、`一回限り` は いいえ。
- 扉の経路に `管理者の口` は書けない。`register_door` の `routes` に `管理者の口` があれば、`unit.routes` にあっても `UNKNOWN_ROUTE`(詳細 `管理者の口`)で拒む。管理者の口は機器の権限だけの経路で、扉の経路の一覧に並ぶと、扉で使える経路に見えるため。
- 命令の `--state`、`--scene`、`--update-mode`、`device change --door-system` は argparse の選べる値にし、外れは終了コード 2。`access remove --result` は `physical return` と同じく様式で確かめる。
- `device check --item` は最初の `=` で分け、同じ項目は後の値。
- `device checks` の人が読む形の `結果` は `項目=結果` を「, 」でつなぐ。`vendor list` の人が読む形の `残り` は `<実体>(<状態>)` を「, 」でつなぐ。

## 21. 段 2a の仕様: 失効の一覧(2026-11-11)

17 章の段 2 のうち、失効の一覧と扉の最長の時間の表示を、19 章、20 章と同じ細かさに落とします。テストはこの章と 19 章、20 章と様式のファイル(`digitalkey/kanri/forms_data/*.adoc`)だけを読んで書き、実装はそのテストを通します。様式のファイルが項目の名前と制約の正で、この章と 19 章、20 章が振る舞いの正です。この章に書いていない所は、19 章と 20 章のとおりです。扉の側の一覧の形と確かめは、扉コントローラ仕様書 5.2c が正です。

段 2a で作る物は、失効の一覧を作って台帳に書く事、一覧を扉へ配った記録、扉に届いた世代から読む署名つき資格情報の進み具合、扉ごとの「失効が効くまでの最長の時間」の台帳への記入と表示、命令 `digitalkey kanri` の足す所です。確かめる要求は R-AC-22、R-AC-14 で、R-AC-15 と R-AC-19 の確かめを失効の一覧に広げます(21.13)。

### 21.1 考え方と置き場

#### 考え方

- **一人の全経路を止める一度の操作で、失効の一覧まで作ります。** R-AC-15 の「一度の操作」に、署名つき資格情報の経路も入れます。`revoke_subject`、`revoke_permission`、`change_device` が署名つき資格情報の実体を止めた時は、同じ呼び出しの中で一覧を一枚作ります。一覧を扉へ配るのは別の操作で、配った事を台帳に記録します。
- **扉に届いたと分かるまでは「待ち」のままです。** 届いた記録が実体の扉の全部にそろうか、遅くとも効く時刻を過ぎたら「止まった」にします。
- **命令は網を使いません**(R-AC-19)。一覧はファイルに出し、扉へ運ぶのは人、利用者の端末、別の道具です。網の届く扉へ送る道具は、閉じる機械の外で動かします。
- **扉ごとの最長の時間は、管理者が台帳に書く値です**(R-AC-14)。ソフトは既定を持ちません。値は、扉に据付で入れた `revocation_max_age_s` を分で写した物で、進み具合の「効くまで」の見立てと、出す時の表示に使います。発行の時には拒みません(網が届く扉では、長い資格情報も一覧が届く間は使えるため)。
- **署名は台帳に持ちません。** 一覧の中身(世代、発行時刻、識別)を台帳に書き、署名つきの一覧は、そのつど発行者の鍵で組み立て直します。Ed25519 の署名は、同じ鍵と同じ入力で同じ値になります。

### 21.3 役と操作、伝票の組

|---|---|---|---|
| `publish_revocations` | 管理者、運用 | 失効_一覧 | `発行者` |
| `record_delivery` | 管理者、運用 | 失効_配布 | `by` |

|---|---|
| `Published` | `伝票`(失効_一覧の `Slip`)、`世代`(int)、`一覧`(署名つきの一覧の dict `{"body", "sig"}`) |
| `RevList` | `番号`(失効_一覧の伝票の番号)、`世代`(int)、`発行時刻`(int。unix 秒)、`識別`(list[str]。台帳の値を「, 」で分けた列。空なら空の列) |

段 1・1b の型に足す属性:

| 型 | 足す属性 |
|---|---|
| `Door` | `失効の最長の分数`(最後の属性。int か None。空は None) |
| `Revocation` | `失効_一覧`(最後の属性。その呼び出しで作った 失効_一覧 の `Slip` か None) |
| `DeviceChange` | `失効_一覧`(最後の属性。同じ) |
| `EffectiveBy` | `分数`(最後の属性。int か None、既定 None。種類が `最長の時間まで` の時だけ数が入る) |

### 21.5 様式

| 様式 | 書ける | 項目 |
|---|---|---|
| `扉`(足す項目) | 管理者 | `失効の最長の分数`(integer、`check (失効の最長の分数 >= 1)`、空でよい) |
| `失効_一覧` | 発行者 | `世代`(integer、not null、`check (世代 >= 1)`)、`発行時刻`(integer、not null。unix 秒。一覧の `issued_at`)、`識別`(text。失効した資格情報の識別を「, 」でつなぐ。空でよい)、`操作者`(varchar(40)、not null)、`役` |
| `失効_配布` | 管理者、運用 | `扉`(varchar(40)、not null)、`世代`(integer、not null、`check (世代 >= 1)`)、`日時`(datetime、not null。扉が受けたと確かめた日時)、`備考`(varchar(200)。運び方など)、`役` |

- `扉` の `失効の最長の分数` は、その扉に据付で入れた `revocation_max_age_s` を分で書きます(秒 = 分 × 60)。空は「決めていない(扉はその規則を使っていない)」です。`扉` は同じ名前の二枚目が今の値を置き換える様式なので、二枚目で省くと空に戻ります。
- `役` の選べる値は、ほかの様式と同じ七つです。

### 21.6 一覧を作る

```python
u.publish_revocations(*, by, role, at=None) -> Published     # 失効_一覧。Published(伝票, 世代, 一覧)
u.revocations() -> list[RevList]                              # 台帳に書いた順
u.revocation(generation=None) -> dict                         # 署名つきの一覧 {"body", "sig"}。None は最後の世代
```

#### 一覧の中身

- **識別。** 経路が署名つき資格情報の実体のうち、実体_失効があるか権限の状態が `失効` で、`at` で終了を過ぎていない物(19.10 の「終了を過ぎた」に当たらない物)の識別です。主体を問わず、置き場の全部の実体から選び、実体_発行を台帳に書いた順に並べます。
- **世代。** 台帳の最後の 失効_一覧(台帳に書いた順で最後の一枚)の世代 + 1 です。一枚も無ければ 1 です。
- **発行時刻。** `int(local(at).timestamp())` です(`at` が None なら今。時差つきは地方時に直す。秒の端数は切り捨て)。ただし、台帳の最後の 失効_一覧 の発行時刻以下になる時は、その発行時刻 + 1 にします。発行時刻は、世代の順に必ず増えます。時計がずれた機械や、前より古い `at` でも、一覧を作る事と失効の操作は拒みません(止める操作を時刻で止めないため)。進み具合の見立て(21.8、21.10)は、台帳に書いた発行時刻で行います。
- **一覧。** `digitaldoor_controller.credentials.revocation_list(unit.signer, generation=<世代>, issued_at=<発行時刻>, revoked=<識別の列>)` で作ります。失効が一件も無くても作れます(識別は空の列)。扉の知らせを新しく保つためです(扉コントローラ仕様書 5.2c の「古さを量る時刻」)。

#### `publish_revocations`

- 確かめ: 19.3 の 1〜5 だけです(できる役は 管理者、運用)。
- 通れば 失効_一覧(世代、発行時刻、識別、操作者 `by`、役 `role`)を、伝票の発行者 `発行者` で書き、`Published(伝票, 世代, 一覧)` を返します。

#### `revocations`、`revocation`

- `revocations()` は、失効_一覧の全部を台帳に書いた順に `RevList` で返します。
- `revocation(generation)` は、台帳のその世代の 失効_一覧 の値から、上と同じ `revocation_list` で一覧を組み立て直して返します。`generation` が None なら、台帳に書いた順で最後の一枚です。
- 一覧が一枚も無い → `NO_REVOCATION_LIST`(「失効の一覧がありません」)。その世代の一覧が無い → `UNKNOWN_GENERATION`(「その世代の一覧がありません」。詳細に世代の数)。

#### 失効の操作の中で作る一覧

- `revoke_subject`、`revoke_permission`、`change_device`(紛失、廃棄)は、その呼び出しの 2(19.10、20.6)で、経路が署名つき資格情報の実体に実体_失効を一枚でも書いたら、同じ呼び出しの中で、同じ `at` で一覧を一枚作ります。書く順は、権限_失効、実体_失効、失効_一覧 です。
- `Revocation.失効_一覧`(`DeviceChange.失効_一覧`)に、その 失効_一覧 の `Slip` を入れます。書かなかった時(二度目の呼び出し、署名つき資格情報の実体が無い時、止めたのがほかの経路だけの時)は一覧を作らず、None です。
- `Revocation.進み具合` は、一覧を書いた後の `progress(subject, at=at)` です。

例: 19.10 の例(`s1` の E1 署名つき資格情報、E2 門番を通す錠、E3 物理キー `K-7`。`2026-12-10T12:00` に `revoke_subject`)では、権限_失効 1 枚、実体_失効 3 枚の後に、失効_一覧 1 枚(世代 1、発行時刻は `2026-12-10T12:00` の unix 秒、識別は E1 の識別)が増えます。`Revocation.失効_一覧` はその伝票です。

### 21.7 配った記録

```python
u.record_delivery(door, generation, *, by, role, at=None, note="") -> Slip    # 失効_配布
u.door_generation(door) -> int        # その扉に届いたと記録された一番大きい世代。無ければ 0
```

- できる役は 管理者、運用です。伝票の発行者は `by` です。
- `at` は扉が受けたと確かめた日時(19.5 の形の文字列か `datetime`。None は今)で、様式の `日時` に書きます。`note` は `備考` です。
- 確かめ(19.3 の 1〜5 の後、この順): `door` がこの置き場の `使用` の扉でない → `UNKNOWN_DOOR`(詳細に扉の名)。その世代の 失効_一覧 が台帳に無い → `UNKNOWN_GENERATION`(詳細に世代の数)。
- 前に記録した世代より小さい世代も書けます(拒みません)。`door_generation` は記録の中の一番大きい世代を返すので、今の世代は下がりません。扉も古い世代を拒むので(扉コントローラ仕様書 5.2c)、同じ見方です。
- `door_generation` は、台帳に無い扉の名前、撤去した扉にも、記録の中の一番大きい世代(無ければ 0)を返します。
- この記録は人が確かめて書く物です(扉の `GET /revocation` の応答の、その発行者の `generation` や、扉の画面を見て書きます)。扉の記録の伝票(種別「設定」、事象「失効の一覧」、結果「受理」)から自動で読むのは、記録の伝票の受け取り(段 2 の残り)で足します。

例: `u.record_delivery("玄関", 1, note="受付の端末で運んだ", by="ops", role="運用")` → 伝票 `失効_配布`、根拠は世代 1 の 失効_一覧。`u.door_generation("玄関") == 1`。

### 21.8 進み具合と、経路「署名つき資格情報」の四つの働き

#### 言葉

- **止めてある。** 実体_失効があるか、権限の状態が `失効` であることです。
- **g0。** その実体の識別を `識別` に入れた 失効_一覧 のうち、台帳に書いた順で最初の一枚の世代です。**t0** はその一覧の発行時刻(unix 秒)です。
- **実体の長さ。** `unix(終了) - unix(開始)`(秒)です。署名つき資格情報の終了は空になりません(19.8 の `NEED_END`)。
- **扉ごとの時刻 T(扉, t)。** 扉の今の `失効の最長の分数` が M で、実体の長さが `M × 60` 秒より長ければ `min(unix(終了), t + M × 60)`、そうでなければ(M が None、または長さが `M × 60` 秒以下)`unix(終了)` です。
- **時刻の書き方。** 上の時刻(unix 秒)を地方時の `datetime` に直し、秒があれば次の分に切り上げて、19.5 の形(`YYYY-MM-DDTHH:MM`)にします。

#### 進み具合の状態(19.10 の表の、署名つき資格情報の行を置き換える)

実体ごとに、`at` で上から当てはめます。

| 順 | 条件 | 状態 | 効くまで |
|---|---|---|---|
| 1 | 終了を過ぎた(`at >= 終了`) | `止まった` | |
| 2 | 実体_失効が無く、権限も `失効` でない | `効いている` | |
| 3 | 止めてあるが、その識別を入れた一覧がまだ一枚も無い | `待ち` | 実体の終了 |
| 4 | 実体の扉の列の全部で `door_generation(扉) >= g0` | `止まった` | |
| 5 | ほか | 効くまでの時刻(分に切り上げた、表に出す時刻)が `at` 以前なら `止まった`、後なら `待ち` | 届いていない扉(`door_generation(扉) < g0`)ごとの T(扉, t0) のうち一番遅い物 |

- 5 の `止まった` は、21.1 の「遅くとも効く時刻を過ぎたら止まった」です。扉の最長の分数が空の扉が一つでもあれば、効くまでは終了で、1 と同じ時刻に `止まった` になります。
- 5 の根拠: 扉は、その発行者の一覧を最後に受けてから、その一覧の `issued_at` から M × 60 秒を過ぎると、長さが M × 60 秒より長い資格情報を `失効の知らせが古い` で拒みます(扉コントローラ仕様書 5.2c の順番の 8)。g0 より前の一覧しか持たない扉は、その一覧の `issued_at` が t0 以下なので、遅くとも t0 + M × 60 の後にその資格情報を拒みます。長さが M × 60 秒以下の資格情報は、扉が古さで拒まないので、終了まで効きます。終了の時刻には、扉は `期限の外` で拒みます(`not_after` は終了の 1 秒前。19.8)。
- 5 の時刻は、扉の設定(`revocation_max_age_s`)が台帳の `失効の最長の分数` と同じである前提の見立てです。扉の設定と台帳の値の照らし合わせは段 3 で足します。
- `Sheet.済み` は 19.10 のまま、全部の行が `止まった` の時に真です。全部の扉に届いた記録がそろえば、期限の前でも `済み` になり、`confirm_stopped`(19.10 のまま)が通ります。
- 実体の扉の列は、実体_発行の `扉` です。撤去した扉も列に残り、届いた記録が無ければ 5 に当たります。

#### 経路の四つの働き(19.8 の表の、署名つき資格情報の列を置き換える)

| 働き | 署名つき資格情報 |
|---|---|
| 出す | 19.8 のまま |
| 止める | `at >= 終了` なら `Stop("止まった", "", "")`(19.8 のまま)。ほかは、実体の扉の列の全部について T(扉, `int(local(at).timestamp())`)を取り、一番遅い物を時刻の書き方で書いて `Stop("待ち", <その時刻>, "")` |
| 効くまで | 実体の扉の全部に `失効の最長の分数` があり、実体の長さがそのどれの `× 60` 秒よりも長い時は `EffectiveBy("最長の時間まで", "", 分数=<その中の一番大きい M>)`。ほかは `EffectiveBy("期限まで", 終了)`(19.8 のまま。`分数` は None) |
| 照らす | 進み具合の状態が `止まった` で、止めてある物 → `Reconcile("一致", "")`。止めてあって `待ち` → 一覧がまだ無ければ `Reconcile("違い", "失効の一覧に入っていない")`、あれば `Reconcile("違い", "扉に届いていない: <届いていない扉を、実体の扉の列の順に「, 」でつなぐ>")`。ほか → `Reconcile("照らせない", "扉の記録の受け取りは段 2")`(19.8 のまま) |

- 止める の時刻は、失効の操作の中で作る一覧と同じ `at` から作るので、ふつうは作った直後の進み具合の 5 と同じ時刻になります。発行時刻を前の世代 + 1 に進めた時(21.6。同じ秒に二度目の失効を行った時や、前より古い `at` を渡した時)は、進み具合の 5 のほうが後の時刻になることがあります。正は、台帳の発行時刻から読む進み具合です。実体_失効の `効くまで` は、止めた時点の見立てとして残ります。後で `扉` の最長の分数を書き換えた時は、進み具合の 5 が今の値で読み直します。
- `Route` の形(19.8)は変えません。止める、効くまで、照らすは、`unit` から台帳の一覧、配った記録、扉の今の値を読みます。

#### 例

19.10 の例(扉 `玄関` は `失効の最長の分数` が空)の E1 は、次のとおりです。

| at と、その前の操作 | E1 | 済み |
|---|---|---|
| 2026-12-10T12:00、`revoke_subject` の直後(一覧 世代 1) | 待ち(2027-01-01T00:00) | 偽 |
| E3 の回収と、`record_delivery("玄関", 1)` の後、2026-12-11T09:00 | 止まった | 真 |

扉 `通用口` を `失効の最長の分数` 1440(1 日)で登録し、`s2` に `通用口` の署名つき資格情報(開始 `2026-12-01T09:00`、終了 `2027-01-01T00:00`。長さは 1440 分より長い)を出し、`2026-12-10T12:00` に `revoke_subject("s2", ...)` を呼ぶと(この置き場の最初の一覧で、世代 1。扉はその前の時刻の一覧を受けている)、実体_失効は `待ち`、効くまで `2026-12-11T12:00` です。進み具合は、届いた記録が無い間、`at` が `2026-12-11T11:59` までは `待ち(2026-12-11T12:00)`、`2026-12-11T12:00` からは `止まった` です(扉は、失効より前に受けた一覧の古さで、その時刻に拒みます)。`record_delivery("通用口", 1)` の後は、その時刻の前でも `止まった` です。`effective_by` は `EffectiveBy("最長の時間まで", "", 1440)` です。

### 21.9 扉の最長の時間の表示(R-AC-14)

```python
u.register_door(name, routes, *, by, role, place="", audit_key="", state="使用",
                revocation_max_min: int | None = None) -> Slip                 # 扉
```

- `revocation_max_min` は様式の `失効の最長の分数` に書きます。None は空です。1 より小さい値と整数でない値は、19.3 の 5 で `FORM` です。
- `Door.失効の最長の分数` は、今の値(同じ名前の最後の 扉 の伝票の値)です。空なら None です。
- 発行の時には、最長の分数で拒みません。`issue_entity` は 19.8、20.8 のままです。命令 `entity issue --json` に鍵 `効くまで` を足し、出す時に見えるようにします(21.12)。

### 21.10 時刻の端の確かめ

扉の判定と台帳の見立てが同じ時刻で切れることを、式で確かめます。M は分、扉の設定は `revocation_max_age_s = M × 60` です。

- **長さ。** 扉が見る長さは `not_after - not_before = unix(終了) - 1 - unix(開始)` です。開始と終了は分の時刻なので、`unix(終了) - unix(開始)` は 60 の倍数です。台帳の「長さが `M × 60` より長い」は「`unix(終了) - unix(開始) >= M × 60 + 60`」と同じで、このとき扉の長さは `M × 60 + 59` 以上で、`M × 60` より長い(扉は古さで拒む)です。台帳の長さがちょうど `M × 60` のとき、扉の長さは `M × 60 - 1` で、扉は古さで拒みません。台帳の「M 以下は終了まで」と合います。
- **終了。** 扉は `now > not_after = unix(終了) - 1`、つまり `now >= unix(終了)` で `期限の外` で拒みます。台帳の効くまでが終了の時、その時刻ちょうどに扉は拒みます。
- **古さ。** 扉は `now - p > M × 60`(p は扉が持つ一覧の `issued_at`、整数の秒)で拒みます。つまり `now >= p + M × 60 + 1` です。台帳の効くまでは `T = (t0 + M × 60 を分に切り上げた時刻)` です。
  - `p < t0` の時: `T >= t0 + M × 60 >= p + M × 60 + 1` なので、時刻 T に扉は拒みます。
  - 扉がその発行者の一覧を一度も受けていない時: 扉は M を入れた時からずっと長い資格情報を拒みます。
  - `p >= t0` にはなりません。扉が g0 より前の世代しか持たない時、その一覧の発行時刻は t0 より小さいためです(21.6。発行時刻は世代の順に必ず増える)。同じ秒に二枚作った時も、前より古い `at` を渡した時も、後の世代の発行時刻は前の世代 + 1 以上になります。
- そのため、扉が g0 より前の世代しか持たない間は、`効くまで` の時刻に扉は必ず拒みます。進み具合の 5 が効くまでの時刻に `止まった` と読むのは、この上の見立てです。残る前提は、扉の設定が台帳の `失効の最長の分数` と同じである事と、扉の時計が合っている事です(照らし合わせは段 3)。

### 21.11 拒否の理由の言葉

`digitalkey.kanri.reasons` に足す定数です。テストは言葉で比べてかまいません。

| 定数 | 言葉 | 出る所 |
|---|---|---|
| `NO_REVOCATION_LIST` | 失効の一覧がありません | `revocation`、命令 `revocation show` |
| `UNKNOWN_GENERATION` | その世代の一覧がありません | `revocation`、`record_delivery`(詳細に世代の数) |

`NO_REVOCATION_LIST` の詳細は空です。

### 21.12 命令 `digitalkey kanri`(足す物)

共通の引数、出力の形、終了コードは 19.12 のとおりです。書く命令には `--by`、`--role` が要ります。`NO_REVOCATION_LIST` と `UNKNOWN_GENERATION` の終了コードは 1 です。

| 命令 | 引数 | 呼ぶ物 |
|---|---|---|
| `revocation publish` | `[--out FILE] [--at T]` | `publish_revocations` |
| `revocation show` | `[--generation N] [--out FILE]`(`--by`、`--role` は要らない) | `revocation` |
| `revocation list` | | `revocations` |
| `revocation delivered` | `--door D --generation N [--note X] [--at T]` | `record_delivery` |
| `door add`(足す引数) | `--revocation-max-min N` | `register_door` の `revocation_max_min` |
| `revoke`(足す引数) | `--out FILE` | 一覧を作った時に、その一覧を書く |

- `--at` は 19.12 と同じく `datetime.fromisoformat` で読める物(時差つき可)で、省けば今です。
- `--out` のファイルが既にあれば、何かを書く前(`revoke` は失効の前、`revocation publish` は一覧を作る前)に `OUT_EXISTS` で拒みます。一覧は秘密ではないので、ファイルの権限は既定のまま(umask)です。中身は署名つきの一覧の JSON(`{"body", "sig"}`)です。
- `revoke --out`: 一覧を作らなかった時は、ファイルを作りません。
- `--generation`、`--revocation-max-min` は argparse の `int` で読み、整数でない値は終了コード 2 です。`--revocation-max-min` の 1 より小さい値は様式で確かめ、`FORM`(終了コード 1)です。

出力の形(19.12 の表に足す物):

| 場合 | 人が読む形(標準出力) | `--json` |

### 21.13 要求ごとの確かめ方

テストは `tests/kanri/` に置き、docstring の先頭の行に要求の番号を書きます。置き場、鍵、名前の決め方は 19.13 と同じです。疑似の扉は次の形で作ります。

```python
from digitaldoor_controller.audit import Audit, Ed25519Signer
from digitaldoor_controller.contacts import SimContacts
from digitaldoor_controller.controller import Config, Controller

ctl = Controller(SimContacts(), Audit(Ed25519Signer.generate()), Config(...), name="玄関", trust=u.trust_entry())
ctl.set_time(<unix 秒>, synced=True)
```

`ctl.present(credential, revocation=<一覧>)` は一覧を先に受けてから資格情報を確かめます。一覧だけを渡すのは `ctl.accept_revocation(<一覧>)` で、`受理`、`同じ`、`拒否` を返します。一覧の拒否の理由は、増えた記録(種別「設定」、事象「失効の一覧」、結果「拒否」)の `detail` に入ります(扉コントローラ仕様書 5.2c の記録の形)。資格情報の拒否の理由は 19.13 と同じく `ctl.audit.entries[-1].result` です。

共通の下ごしらえ(例): 19.13 の `adm`、`apr`、`s1` に、`ops`(運用)、`s2`(社員)を足す。扉 `玄関`(三つの経路、最長の分数は空)。日時は 2026-12-01 以後の架空の物を、テストが選ぶ。

**R-AC-22(網の届かない扉が、端末の運んだ署名つきの失効の一覧を使う。古い一覧で戻せない)**

1. `s1` と `s2` に、`玄関` の署名つき資格情報を出す。扉は `Config()`(最長の時間を使わない)で立てる。
2. 失効の前に `publish_revocations` を一度呼び、世代 1(識別は空)を作る。
3. `revoke_subject("s1", ...)` の後、`Revocation.失効_一覧` が世代 2 の伝票で、`u.revocations()[-1].識別` は `s1` の資格情報の識別だけ。
4. 一覧を渡さない扉(網の無い扉)では、`s1` の資格情報はまだ `解錠`(段 1 の限界が残っている事)。
5. `ctl.present(cred_s2, revocation=u.revocation())` は `解錠`。その後 `ctl.present(cred_s1)` は `拒否`、記録の結果は `失効済み`(期限の前)。
6. 一つ前の世代の一覧 `u.revocation(1)` を `ctl.accept_revocation` に送ると `拒否`(記録の詳細は `古い世代`)で、`ctl.present(cred_s1)` は `拒否`(`失効済み`)のまま。
7. 別の置き場 B の発行者が作った一覧(`B.publish_revocations(...)`)を扉に送ると `拒否`(`知らない発行者`)。
8. `u.revocation()` と `u.revocation(2)` と、置き場を開き直した後の `u.revocation(2)` は同じ dict。`publish_revocations` が返した `Published.一覧` も、その世代の `u.revocation(世代)` と同じ dict(組み立て直しで同じ署名になる)。一覧の無い置き場の `revocation()` は `NO_REVOCATION_LIST`、無い世代は `UNKNOWN_GENERATION`。

**R-AC-14(扉ごとに最長の時間を決めて表示する。知らせが古い扉は長い期限の資格情報を拒む)**

1. `door add --revocation-max-min M` で扉を登録すると、`door list` の行の末尾に M、`--json` の項目の `失効の最長の分数` に M。省いた扉は空の欄と null。`register_door(..., revocation_max_min=0)` は `FORM`。二枚目で省くと None に戻る。M の値はテストが選ぶ。
2. 扉を `Config(revocation_max_age_s=M*60)` で立て、失効より前の時刻 t1 で `publish_revocations(at=t1)` を作って `ctl.accept_revocation` で一度受けさせる。
3. 長い資格情報(長さが M 分より長く、t0 + M 分より後に終了する物)と、長さがちょうど M 分の資格情報を出す。長い資格情報の `entity issue --json` の `効くまで` は `{"種類": "最長の時間まで", "時刻": "", "分数": M}`、M 分の物は `{"種類": "期限まで", "時刻": <終了>, "分数": null}`。
4. 時刻 t0(t1 より後。分ちょうどの時刻)に、長い資格情報の主体を `revoke_subject` し、その 1 分後に、もう一人の主体を `revoke_subject` する(同じ秒に二度行うと、二枚目の一覧の発行時刻が 1 秒進むため。それは 9 で確かめる)。扉には新しい一覧を渡さない。
5. 長い資格情報の進み具合の `効くまで` は、t0 + M 分を 21.8 の書き方にした時刻。その 1 分前の `at` の進み具合は `待ち`、その時刻の `at` では `止まった`。扉の時計をその時刻の unix 秒にすると、長い資格情報は `拒否`、記録の結果は `失効の知らせが古い`。それより前の時刻に解錠する事があるのは、扉の持つ一覧の古さによる物で、ここでは試さない。
6. 長さが M 分の資格情報の `効くまで` は終了。扉の時計を終了の 1 秒前にすると `解錠`、終了で `拒否`(`期限の外`)。
7. 最長の分数が空の扉に出した資格情報の `効くまで` は終了で、`effective_by` は `期限まで`。
8. 限界: 見立ては扉の設定が台帳の値と同じ前提で、照らし合わせは段 3。この限界をテストの docstring に残す。
9. 発行時刻は世代の順に必ず増える(21.6): 同じ `at` で `publish_revocations` を二度呼ぶと、二枚目の発行時刻は一枚目 + 1。前の一覧より古い `at` を渡しても、発行時刻は前の一覧 + 1 で、拒まれない。同じ `at` で二人を続けて `revoke_subject` した時、二人目の資格情報の進み具合は、二枚目の一覧の発行時刻(+1 秒)から読む。扉が一枚目の一覧だけを持つ時、二人目の `効くまで` の時刻に、扉は二人目の長い資格情報を拒む。

**R-AC-15(一人の全経路を一度の操作で失効できる。署名つき資格情報も同じ一度の操作で一覧に入る)**

19.13 の筋書きに足します。

1. 3 の `revoke_subject` で、失効_一覧 が 1 枚でき、`Revocation.失効_一覧` に入る。一覧の識別は E1 の識別。
2. 一覧を扉に渡す(`ctl.accept_revocation(u.revocation())`)と、期限の前に `ctl.present(E1 の資格情報)` が `拒否`、記録の結果は `失効済み`。
3. E1 の `reconcile` は、届いた記録の前は `Reconcile("違い", "扉に届いていない: 玄関")`、`record_delivery("玄関", <世代>, ...)` の後は `Reconcile("一致", "")`。
4. `record_delivery` と E3 の `return_physical` の後、期限の前の `at` でも `progress("s1").済み` が真で、`confirm_stopped` が失効_確認を書く。
5. 二度目の `revoke_subject` は 失効_一覧 も増やさず、`Revocation.失効_一覧` は None。署名つき資格情報の無い主体(門番を通す錠だけ)の `revoke_subject` も 失効_一覧 を作らない。
6. `record_delivery` に撤去した扉か台帳に無い扉を渡すと `UNKNOWN_DOOR`、無い世代は `UNKNOWN_GENERATION` で、台帳の伝票の数は変わらない。名簿の係の役の `record_delivery` は `ROLE_NOT_ALLOWED`。

**R-AC-19(網から切り離して動かせる)**

19.13 の筋書きの網を塞いだまま、続けて `revoke --subject s1 --out FILE`、`revocation publish --out FILE2`、`revocation show`、`revocation list`、`revocation delivered --door 玄関 --generation 1` を `main([...])` で呼ぶ。全部の終了コードが 0 で、`--out` のファイルに `{"body", "sig"}` の JSON がある。書くのは `--dir` の下と `--out` だけ。既にある `--out` は `OUT_EXISTS` で、台帳の伝票の数は変わらない。

**R-EB-35(期限を網が届く時に自動で延ばす)** は、この段では確かめません(21.15)。

### 21.14 段 2a で仮に決めた事(作る時に選ぶ物)

- 様式 `失効_一覧` と `失効_配布` の `世代` に `check (世代 >= 1)` を付ける(扉の一覧の世代が 1 以上のため)。
- `失効_一覧` の `識別` は `text`(長さの上限を付けない。一覧の大きさの上限は次の段)。
- 一覧の世代は台帳の最後の 失効_一覧 の世代 + 1 で、台帳に書いた順の最後の一枚から読む。
- 発行時刻は `int(local(at).timestamp())`(秒の端数は切り捨て)。進み具合と止めるの時刻は、秒があれば分に切り上げる(扉が拒んだ後の時刻を見立てにするため)。
- 扉ごとの時刻 T は、扉の今の `失効の最長の分数` で読む(止めた時の値ではない)。
- 進み具合の 5 で、効くまでの時刻が `at` 以前なら `止まった` にする(21.1 の「遅くとも効く時刻を過ぎたら止まった」。21.10 の前提の上の見立て)。
- 撤去した扉も実体の扉の列に残し、届いた記録が無ければ `待ち` の理由にする(撤去した扉がまだ動いている事があるため)。撤去した扉への `record_delivery` は `UNKNOWN_DOOR` なので、撤去の前に記録を書くか、終了を待つ。
- `door_generation` は、台帳に無い扉にも 0 を返す(拒まない)。
- `record_delivery` は、前より小さい世代も書ける。`at` は 19.5 の形の文字列か `datetime`。
- `revocation(generation)` の `UNKNOWN_GENERATION` の詳細は世代の数。`NO_REVOCATION_LIST` の詳細は空。
- 照らすの「扉に届いていない」の扉の並びは、実体の扉の列の順。
- 照らすの「ほか」の詳細は段 1 の言葉(`扉の記録の受け取りは段 2`)のまま。
- `change_device` も同じ規則で一覧を作り、`DeviceChange.失効_一覧` に入れる。機器の権限には扉の列が無く、署名つき資格情報を出せない(`NO_DOOR_FOR_ROUTE`)ので、今の様式ではいつも None。
- 命令 `revocation show` は `--out` が無ければ、`--json` でも一覧の JSON をそのまま出す(`trust-entry` と同じく、扉や道具にそのまま渡せる形)。
- 命令 `revocation list` の人が読む形の発行時刻は unix 秒のまま(扉の `GET /revocation` の `issued_at` と照らせる)。
- 命令 `revoke --json` に `一覧のファイル` を足す(`entity issue` の `資格情報のファイル` と同じ流儀)。
- `door list` の人が読む形で、None は空の欄にする。
- `--out` の確かめは、何かを書く前に行う。一覧のファイルの権限は既定のまま。
- `--generation` と `--revocation-max-min` は argparse の `int`。

### 21.15 段 2 の残りと、次へ渡す口

- **記録の伝票の受け取り(段 2 の残り)。** 扉の記録の伝票(種別「設定」、事象「失効の一覧」、結果「受理」、詳細の `generation`)を受け取って検べ、`失効_配布` を手で書かずに「届いた」を読む。`door_generation` の読み元に足し、`失効_配布` は人の記録として残す。
- **台帳の伝票の署名(段 2 の残り)。** `Ledger` の側に足す。
- **扉の設定と台帳の値の照らし合わせ(段 3)。** 扉の `revocation_max_age_s` と台帳の `失効の最長の分数` を照らす。21.8 の 5 の見立ての前提を確かめる所。
- **期限を自動で延ばす事(R-EB-35)。** 網が届く時に実体を出し直す形で足す。最長の分数を書いた扉の長い資格情報を、短い資格情報の出し直しに替える所。
- **資格情報の役ごとの時間(R-AC-14)。** 資格情報の形に役を足す時(扉コントローラ仕様書 5.2a の次の版)に、`扉` の最長の分数を役ごとにする。
- **一覧を扉へ送る道具。** 網を使う物は、閉じる機械の外で動かす。`revocation show` の出力をそのまま `POST /revocation` の `list` に入れられる。
- **一覧の大きさの上限。** 期限を過ぎた識別は一覧から外れるので、上限は実際の大きさを見てから決める。
- **発行者の鍵の差し替え。** 取り出せない所の鍵が ECDSA になると、署名が毎回変わり、組み立て直した一覧の署名が前と違う値になる(扉は世代で受けるので、働きは変わらない)。その時は、一覧の署名を台帳に持つか、組み立て直しで足りるかを決める。

### 21.16 段 2a で作った物と、作る時に選んだ事

#### モジュール

| モジュール | 中身 |
|---|---|

| `routes/credential.py` | 止めるは `unit._credential_stop`、効くまでは扉の今の最長の分数から `最長の時間まで` か `期限まで`、照らすは止めてあるかと進み具合から `一致`、`違い`、`照らせない` |
| `revoke.py` | 進み具合の行で、署名つき資格情報は `_credential_row` で読む。`_revoke` は 2 の後に `_list_after_stop` を呼び、`Revocation.失効_一覧` に入れる |
| `devices.py` | `change_device` も `_list_after_stop` を呼び、`DeviceChange.失効_一覧` に入れる |
| `roster.py` | `register_door` の `revocation_max_min`(様式の `失効の最長の分数`)、`Door.失効の最長の分数` |
| `reasons.py` | `NO_REVOCATION_LIST`、`UNKNOWN_GENERATION` |
| `model.py` | `Published`、`RevList`、足した属性(`Door`、`Revocation`、`DeviceChange`、`EffectiveBy`)、時刻の書き方 `minute_up` |
| `unit.py` | `Unit` が六つ目の `RevocationsMixin` を継ぐ。台帳は 22 枚の様式で開く |
| `cli.py` | 命令 `revocation publish`、`show`、`list`、`delivered`。`door add --revocation-max-min`、`revoke --out`、`revoke` と `device change` の `失効_一覧` の行と鍵、`entity issue --json` の `効くまで`、`door list` の末尾の列 |
| `digitalkey/door_serve.py` | `--revocation-max-age 秒`(負の値は引数の誤り)を `Config(revocation_max_age_s=...)` に渡す。引数を読む所を `parse_args` にまとめた |

#### 選んだ事

- 一覧の列(`RevList`)と、識別ごとの最初の一覧(g0、t0)は、台帳の伝票から一度だけ作り、`Book` の中に覚えます。名簿、実体、機器と同じく、台帳の枚数が変わるまで使い回します。
- 一覧の識別は、`entities()` の順(実体_発行を台帳に書いた順)に、経路が署名つき資格情報で、実体_失効があるか権限_失効がある物のうち、`at` で終了を過ぎていない物を選びます。
- 失効の操作の中で一覧を作るかは、その呼び出しで書いた実体_失効の `経路` が署名つき資格情報の物が一枚でもあるかで決めます。役の確かめは失効の操作の役で済ませ、`publish_revocations` の役の表(管理者、運用)は見ません。
- `revocation` は、`NO_REVOCATION_LIST` を世代の確かめより先に見ます(一覧の無い置き場では、世代を渡しても `NO_REVOCATION_LIST`)。
- `record_delivery` は、19.3 の 5 で 扉、世代、日時、備考、役 を様式に照らします(世代が 1 より小さい、整数でない物は `FORM`)。根拠は、その世代の 失効_一覧 の伝票です。`at` が None の時は、呼んだ時の地方時を `日時` に書きます。
- 進み具合の 5 の「効くまでの時刻が `at` 以前」は、分に切り上げた時刻の文字列を `datetime` に戻して `at` と比べます。
- T(扉, t) の扉が台帳に無い時(名前が消えた時)は、最長の分数を空として終了を返します。実体の扉の列が空の時は、一番遅い時刻を終了とします。
- 効くまでの `最長の時間まで` は、実体の扉の最長の分数の一番大きい物 M で、実体の長さが `M × 60` 秒より長い時です(どの扉の値よりも長い事と同じ)。
- 照らすの「止めてあって 止まった」は、進み具合の行(`_row`)で読みます。終了を過ぎて止まった物も `一致` です。
- 命令の `--out` は、新しく作るファイルだけに書きます(`open(..., "x")`)。中身は署名つきの一覧の JSON 一つに改行を付けた物で、権限は既定(umask)のままです。`revoke --out` は、一覧を作った時に、その世代を `revocation(世代)` で組み立て直して書きます。
- `revocation show --out` は、`--out` の確かめを一覧を読む前に行います。
- 人が読む形の一覧(`door list` ほか)で、値が None の欄は空にします。
- `revoke --json` の `世代` は、一覧を作らなかった時に null、`失効_一覧` と `一覧のファイル` は空です。

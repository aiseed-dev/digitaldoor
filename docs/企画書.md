# digitaldoor 企画書

2026-10-17。aiai の企画の側(Fable)が書き、開発は digitaldoor のプロジェクトの側で進めます。この文書は、何を、どの順で、何を守って作るかを決めた物で、作り方は書きません。公開のリポジトリに置くので、提案先の会社の名前は書きません。

## 1. 目的

扉と鍵の公開の仕様と参照実装とテストを置き、次の三つを一つの場所で成り立たせます。

1. 扉を使う人と、扉を作る製造者をつなぐ。使う人の困りごとが要求の番号になり、製造者の制約が同じ番号の下に残り、確かめるのはテストと記録です([つなぐ.md](つなぐ.md))
2. 各社(扉メーカー、錠と電動ラッチの部品メーカー、ドアホンとカメラと読取機のメーカー、設備工事会社、管理会社、民泊や貸家の運営者)が、公開の仕様と参照実装を土台に、自分の AI で自社のソフトウェアを作れるようにする([../SKILL.md](../SKILL.md))
3. 扉の製造者への提案に、公開の文書として指せる物を揃える。製造者が持つ物は、認定の境界、開口と通線と給電、等級と台帳です。読取機と機器とソフトは買う物で、載せる場所と条件を決める側に立ちます([要求仕様/01_interface.md](要求仕様/01_interface.md)、[要求仕様/02_reader.md](要求仕様/02_reader.md))

## 2. 持ち主が決めたこと(2026-10-17)

- 製造者向けの物(要求仕様、扉のコントローラー、Matter、読取機)を先に充実させる。受け入れの側(民泊・貸家)と aiai の事例の記事は後にする
- 提案先の会社の名前は、文書にも記事にもコミットメッセージにも書かない
- 読取機は顔認識を必要とする。顔のほかに、衣服、名札・ワッペン、全身、行動の認識も使う。これらは「誰か」ではなく「何が写っているか」を読む物なので、属性として上の層の規則の材料にし、資格情報とは分ける
- 映像を読む機器は電気を使い続けるので電池では持たない。扉と枠を渡る有線給電と通線を標準で持つ扉だけが、この機器を載せられる。これが扉の製造者の有利な点で、提案の筋にする
- digitaldoor は公開で、各社が AI でソフトウェアを作る土台にする。開発の間も、使う人と製造者の間に立つ
- 企画は aiai の側(Fable)が書き、開発は digitaldoor の側でやる

## 4. 進める順

### 段 1: 提案に向けて揃える(いま)

1. 今日の作業ツリーをコミットして push する(本人)。GitHub にラベル「要望」「製造者」「不具合」「新しい情報」を作る
2. ライセンスを決める。`LICENSE` はコードを AGPL-3.0-or-later とし、`70_dev_server.md` の R-DV-22 は「標準版は MIT で公開」と書いていて食い違っている。各社に組み込んでもらうなら、参照実装の許諾をどうするかが効く。決めたら、どちらかを直す
3. テストを全部動かす環境を作る(pytest、pytest-asyncio、httpx、fastapi、uvicorn、pydantic、python-multipart、circuitmatter)。導入は許しを得てから
4. 02_reader の未決事項を埋める。個人識別符号の基準(個人情報保護委員会規則)、要配慮個人情報の範囲(法第 2 条第 3 項)、カメラ画像の扱いの指針の原文を読み、R-RD-03、04、22 の文言を直す
5. 参照実装の `/auth` に、経路、信頼度、生体検知の結果の欄を足し、R-RD-08 と R-RD-18 のテストを書く(仕様、テスト、実装の順)
6. サイトに 1 本書く。使う人の困りごとが要求になり製造者に届く道があること(つなぐ)。記事のビルドの部品(pyasciidoc、pywashi)が要る
7. 提案の送り状は、非公開の側(engagements)に書く。公開の文書(01_interface、02_reader、扉コントローラ仕様書、適合の現在、SKILL.md)を指す短い物にする。CSA のニュース欄にある 2026-10-14 の Apple の Home Collection(Matter、Thread、Aliro 対応)と UWB の錠の記事は、Aliro の読取機が家庭に入り始めた材料として使える(中身は未読)

### 段 2: 製造者が一度通す

- 提案先が最初の一社になるなら、SKILL.md を読ませて、扉のコントローラーの一部(たとえば R-CT-05〜09 の判断の表)を自社の AI で作ってもらう。小さく、実機なしで、疑似の接点で
- 出てきた質問と制約を Issue「製造者」で受け、同じ番号の下に書き足す。`適合の現在` を作り直す
- ここで分かった「AI に読ませても伝わらない所」が、仕様の直しになる

### 段 3: 使う人の道を開く

- 最初の数件は、持ち主自身の民泊・貸家の困りごとを Issue「要望」に書く。要求の理由が使う人の言葉に置き換わり始める
- 1 軒で使う(家、錠、経営者を決める)。`entrance` と Sesame の Web API の道で、予約、本人確認、鍵の発行、解錠、失効、台帳を回す。aiai の `kiji/` の事例の記事は、ここが通った後
- 現場の当たり外れを Issue「不具合」と台帳に残し、直した結果を使う人の言葉で返す

### 段 4: 読取機

- 構内のゲートウェイで VLM を動かし、属性(衣服、名札、全身、行動)と信頼度と根拠の短い説明を上の層に渡す試作。モデルは差し替えられる形(同じ入力、同じ出力)
- ドアホンの取り込み(Matter 1.5 の Doorbell か ONVIF)。顔の照合の実装(`Matcher` の差し替え)
- 読取機からコントローラーへ渡す判定結果の形を公開し、扉コントローラ仕様書第 10 章「規格に足すべきもの」の候補に入れる

### 段 5: 各社が実機なしで作れる環境

- `70_dev_server.md` が求める物のうち、公開 API の OpenAPI、WebSocket の配信、故障注入の API、疑似デバイス群。ここができると、各社の AI が実機を買う前に全部通せる
- 英語版の文書は、国内の一社が通った後

## 5. 守ること

- 読取機、機器、独自の無線、クラウド前提の機能は作らない。買う物の載る場所と条件を決める
- 要求を足すときは理由に出どころ(Issue の番号か、使う人の困りごと)を書く。番号は変えない。製造者の制約は消さず、同じ番号の下に残す
- 仕様が先、テストは仕様から、実装は別のセッション、疑似で全部通す、実機は受入れ試験だけ(AI で作り続ける原則 3.1)
- 顔の特徴量は個人識別符号として扱う。構内で照合し、持ち主が一覧と削除をでき、来訪者の顔は照合後に保持しない。要配慮個人情報に当たる物は推定しない
- 公開する物に、提案先の会社の名前と、公開されていない技術・契約の情報を書かない
- 数字と事実には出典と確かめた日を付ける。変わっていたら Issue「新しい情報」から直す

## 10. システムの確かめと教室を足す(2026-11-10)

持ち主が決めたことです。扉と鍵の仕様に、次の二つを足して、三つの柱で進めます。

| 柱 | 中身 | 公開の側に置く物 |
|---|---|---|
| システムを AI で確かめる | 守る側の会社が、自社のシステムと納められたコードを、自社の人が AI で確かめる。こちらは始め方と急所を伝える | 解説 20、手引き `skills/system-check/`、サイトの「相談と教室」 |
| AI 教室 | 会社の人も、介護や福祉の現場の人も、自分の仕事を持ってきて Claude と進める | サイトの「相談と教室」 |
| デジタルキーの発行と管理 | 民泊と空き家から。段 3 の「1 軒で使う」がこれに当たる | これまでの仕様と参照実装 |

### なぜ足すか

- 2026-10-06 から、守る側の会社が申し込めば、AI で自社のシステムの穴を確かめられるようになった(Anthropic の Cyber Verification Program)。確かめる枠(Defense Access)は数日で返事が来る
- 鍵の管理の仕組みを攻撃して試す枠(Red Team Access)の条件は、会社のアカウント、会社が管理する端末、外向きの通信の制限、フィッシングに強い多要素認証です。これは、鍵の管理を自社で持つ会社が整える物(解説 17、18)と同じ物です。システムを確かめることが、デジタルドアを入れる下地になります
- 順は、鍵より先にシステムの確かめです。鍵は、準備を進めて、発売は急ぎません

# 鍵の管理のシステムを開発するシナリオ(下書き、2026-10-20)

デジタルドアの一番の課題は、デジタルキーをどう管理するかです。このシナリオは、鍵の管理のシステムを、誰が、どの順で作り、どこで確かめるかを書きます。期間や値は書きません。

## 誰が作るか

今、鍵の管理のシステムを作れるのは、digitaldoor の運営と AI だけです。

- 扉の製造者は、鍵の管理を知りません。扉の側の部品を組み込むことはできます。
- 各社の情報システム部門は、まだ準備ができていません。
- 業者に作らせると、業者が鍵を持つ形になり、委託に戻ります。

| 誰が | すること |
|---|---|
| AI | 仕様の下書き、実装(Sonnet)、テスト(別のセッションで仕様から)、調べもの |
| 運営 | 何を作るかを決める。出来た物を自分の扉で動かして確かめる。一番上の鍵と commit を持つ |

運用する人が AI と一緒に自分で作る、という形を、まず運営がやってみせます。その記録が、各社が後から同じことをするときの手本と雛形になります。

## 1. 作る

運営と AI が、実証に持っていける物を作ります。

| 作る物 | 中身 | 今あるもの |
|---|---|---|
| 鍵の管理の仕組み | 申請、承認、発行、失効(一人の全経路を一度に)、台帳、記録の受け取り。管理する物は、顧客、サーバー、Web、PC、デジタルドア。網が無くても建物の中で動く | 受け入れの台帳、鍵を作る命令、権限の申請の雛形(下書き) |
| 扉の側 | 資格情報を確かめて開け、記録する。錠のドライバで本物の錠を動かす | 疑似の扉、錠のドライバで動く接点、Sesame のドライバ |
| 実演 | 開け閉めは簡単なこと、鍵の管理に課題があることを見せる | 実演の道具 |
| 実証の手順と記録の様式 | 何を、どの要求の番号で確かめるか | 要求の確かめ方 |

自分の所の扉(Sesame と miniPC)で、出来事(入社、退職、紛失、鍵の作り直し、管理者の鍵をなくした想定)を起こして確かめてから、実証に持っていきます。

## 2. 協力先に、顧客、サーバー、Web、PC、デジタルドアの管理の仕組みを自分で作ってもらう

協力してくれる扉の製造者に、実証実験をしてもらいます。扉の製造者は、売る物と同じ管理を自社で運用していることが、売る側の条件です(R-RS-16〜18)。実証は、その最初の一歩になります。

実証の題材は、扉から始めなくてかまいません。顧客、サーバー、Web、PC の管理も、誰に、どの物の、どの権限を、いつまで出し、いつ止め、何が起きたかを記録するか、という同じ問いです。デジタルドアの管理は、その中に必ず含めます。扉を売る会社にとって、売った扉の管理は、顧客の管理と切り離せないからです。

| 管理する物 | 鍵にあたる物 |
|---|---|
| 顧客 | 顧客の台帳を見る、直す権限。売った扉ごとの管理者の連絡先、更新を出す期間、脆弱性の知らせの宛先(R-RS-01、02、05)。顧客の扉の鍵は持たない |
| サーバー | SSH の鍵、管理者のアカウント、root |
| Web | 管理画面のアカウント、API のトークン |
| PC | 管理者の権限、サインインのアカウント |
| デジタルドア、入退室 | 自社の扉: 署名つきの資格情報、発行者の鍵、管理者の鍵。売った扉: 更新の署名の鍵(R-RS-03)。保守のときの一時の権限は、顧客の管理者が出す(R-AC-06、10) |

基幹システムは、とりあえず別にします。

進め方は、協力先が決めます。例えば次の形があります。

- 協力先の情報システム部門が、雛形と aiai-tools の部品(kaiin、server、ninshou、tenken、router)を参考に、AI と一緒に自分で作る
- 今の仕組みを置き換えず、横に置いて始める。最初の仕事は権限の目録(誰がどの機械の管理者の権限を持つか、業者は何を持つか、R-RS-04)
- 退職した人の鍵とアカウントを一度に止める、紛失に手当てする、業者には要る間だけの権限を出す
- 実行してよい物を見張り、記録を機械の外に出す(R-RS-11、12)
- 扉と入退室は、同じ台帳と同じ手順の上につなぐ。売った扉は、顧客の台帳と結び、更新と脆弱性の知らせを、顧客の管理者に届ける
- 顧客の情報は個人情報を含む。扱う人と目的を決め、AI に渡すのは学習に使わないと確かめたサービスか、自分の機械の AI に限る

運営のサーバー(公開用の miniPC)でしていること(root の作業は本人だけ、実行してよい物の見張り、中で動く物を減らす、アプリごとに閉じた環境と一覧)は、そのまま見本になります。

### 買った側も同じ

デジタルドアを買った側も、同じ形で管理します。買った側にとっても、扉の管理は、顧客、取引先、サーバー、Web、PC の管理の中の一つです。

| | 売った側(扉の製造者) | 買った側(会社、マンション、民泊) |
|---|---|---|
| 顧客の台帳 | 扉を買った会社と、その扉の管理者 | 社員、入居者、宿泊者、来客 |
| 取引先の台帳 | 部品の仕入れ先 | 扉の製造者、保守の業者 |
| 持つ鍵 | 更新の署名の鍵 | 扉の発行者の鍵、管理者の鍵 |
| 相手に渡す物 | 署名した更新、脆弱性の知らせ | 保守のときの一時の権限(要る間だけ) |

二つの台帳は、向かい合ってつながります。売った側の顧客の台帳と、買った側の取引先の台帳です。更新と脆弱性の知らせは、売った側から買った側へ流れます。買った側は、署名を確かめてから入れます(R-EL-25)。保守の権限は、買った側から売った側へ、要る間だけ流れます(R-AC-06、10)。どちらも、相手の鍵は持ちません。

実証で出た問題は、要求の番号に整え、仕様と雛形に返します。

## 3. 各社が自分で作る

実証で確かめた物を雛形として公開します。各社の情報システム部門は、時期が来たら、雛形と SKILL.md を自社の AI に読ませて、自社の鍵の管理を自分で作ります。扉の製造者は、確かめる部品を製品に組み込みます。

## 並行して詰める物

| 物 | 鍵の管理との関わり |
|---|---|
| 給電と停電(有線の給電と、扉の中の電池) | 停電の間も、確かめと記録を続ける |
| 時刻 | 期限の判定の元。停電の間の時計と、ずれたとき |
| カメラ(補助) | 記録と映像を、時刻と番号で結ぶ |
| 財布の鍵の載せ方 | Apple と Google の仕組みで、発行者の鍵を管理者が持てるか |

== 利用者の声

日付順に要約します。個人名は書きません。

* 2026年3月。バージョン2.1.4からドアノブでの施錠・解錠ができるようになった一方、車内でBluetoothの接続待ちになることが増えた。2年半使ってみて、スマートフォンだからという理由でセキュリティのロックをかけすぎている。使いやすさを優先してほしい。
* 2026年4月。物理鍵がある自宅から100km離れた場所で突然接続できなくなった。サポートに相談したが、物理鍵がないとどうにもならなかった。自宅から鍵を持ってきて帰った。書かれている不具合は再現性が高い。
* 2026年8月。ときどき車と接続できなくなり、解錠できなくなる。アプリのデータを削除して再起動し、鍵のデータをサーバーから再取得する再設定で使えるようになるが、数日するとまた接続できなくなる。「リモコンキーを持ち歩きましょう」。

== 読み取れること

*ローカルで動作しないと、物理鍵は手放せません。* 利用者自身が「リモコンキーを持ち歩け」と書いています。鍵のデータをサーバーから再取得する再設定が復旧手順であることは、認証が手元で完結していないことを示しています。電子錠は追加の機器になり、鍵は二つに増えました。

*認証が一社に集中しています。* 接続が切れたときの相談先はサポートであり、サポートにできることはありませんでした。扉(この場合は車)が自ら判定する構造であれば、サーバーの状態に関わらず鍵は使えます。

*不具合を直せない構造があります。* 3月と4月に同じ不具合が報告され、6月の更新は「軽微な不具合を修正」で、8月に同じ不具合が再び報告されています。同じ会社の他のアプリは4.4から4.6の評価なので、開発力の問題ではありません。外から見える範囲で言えば、車両側、スマートフォンアプリ、サーバーが別々の組織にあり、修正のたびに三者の見積もり、検証、車両の認証を経る必要があります。使う人と直す人が分かれていて、不便が直す人に届きません。業務用アプリが高価で使いにくい理由と同じ構造が、日本最大の企業にもあります。

== 利用者、アプリ開発者、製品開発者の間の対話

利用者、アプリを作る人、製品を作る人の間には、対話があるべきです。現状では、その対話を少数の人が握っています。窓口の担当者、要件をまとめる人、見積もりを出す人が間に立ち、利用者の言葉は要約されてから届き、開発者の答えは翻訳されてから返ります。このアプリのページでは、利用者は3月から8月まで同じことを書き続け、開発側からは「軽微な不具合を修正しました」の一行が返りました。人が間に立つ構造では、これが普通です。

AIの能力が上がった今、この部分は改善できます。利用者の言葉をそのまま読み、手元の記録と照合し、開発者に渡せる形に整え、修正結果を利用者の言葉で返す。これをAIが休みなく行えます。少数の人が握っていた席を、誰でも通れる道に変える。このサイトが公開仕様、読める実装、テストを置いているのは、その道を通れるようにするためでもあります。

== AIで直せる仕組みの条件

* 仕様は「何を満たすか」だけを書く。直す人は仕様を読めば、何を壊してはいけないかが分かる。
* 参照実装はPythonで、読める大きさにする。AIが読み、直し、説明できる。
* テストがある。修正後にテストが通れば直っている。AIが直した物を人が確認する基準がテストになる。
* 記録は手元にある。不具合の原因を示す証拠が、サーバーの向こうではなく自分の手元にある。
* 判定は扉が持つ。アプリもサーバーも止まっていてよい。
* 直す人と使う人が同じ。事業者が自分の扉の不便を、その日に直せる。見積もりも稟議も三者間の調整も不要。

さらに一つ。不具合の報告をAIが受け取る仕組みです。利用者が「接続が切れた」と言えば、AIが記録を読み、原因の候補と修正案を出し、テストを通してから管理者に提示する。このアプリのページで「サポートにできることがなかった」場面に、手元の記録と修正できるコードがあれば、できることがあります。

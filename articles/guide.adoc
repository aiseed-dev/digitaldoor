= Matterとは何か

Matter(マター)は、家庭用のスマートホーム機器を、メーカーを問わず共通の方法で接続するための規格です。電子錠、照明、センサー、スピーカーなどが、同じ手順で状態を伝え、操作を受け付けます。この記事では、まずMatterで何ができるかを説明し、そのうえで、業務用の扉に適用する場合の課題を整理します。

== 概要

Matterは、Connectivity Standards Alliance(CSA、旧Zigbee Alliance)が策定する規格で、バージョン1.0は2022年10月に公開されました。Apple、Google、Amazon、Samsungが揃って策定に参加している点が、それ以前のスマートホーム規格との大きな違いです。

* 通信はIPネットワーク上で行います。Wi-Fi、Ethernet、および低消費電力の無線規格であるThreadに対応しています。Bluetooth LEは、機器を最初にネットワークへ登録するときにだけ使います。
* 仕様は公開されており、参照実装(SDK)もオープンソースで公開されています。
* Matter対応製品として販売するには、CSAの認証を取得する必要があります。各機器は製造者の証明書(DAC)を持ち、登録時に検証されます。

バージョンは年に1〜2回更新されています。CSAの発表によると、1.2(2023年)で冷蔵庫や洗濯機などの家電、1.3(2024年)でエネルギー管理、1.4(2024年末)で家庭用ルーターと、電子錠向けのAliro資格情報への対応、1.5(2025年11月)でカメラが追加されました。

== 仕組み

Matter機器は、「ファブリック」と呼ばれる管理者のネットワークに登録して使います。登録は、機器のQRコードまたは手動コードを管理者アプリで読み取って行います。管理者となるのは、Apple Home、Google Home、Amazon Alexa、Samsung SmartThingsなどのアプリや、Home Assistantのように自分で運用するコントローラーです。

1台の機器を複数の管理者に登録することもできます。たとえば、同じ電子錠をApple HomeとGoogle Homeの両方から操作できます。

== 電子錠向けの機能

Matterの電子錠(Door Lockクラスタ)は、家庭用の玄関に必要な機能を一通り備えています。

* 施錠、解錠、ラッチのみの解除
* ユーザーと認証情報の管理。暗証番号、カード、指紋、顔、Aliroの鍵
* 曜日、日付、休日ごとのスケジュール
* ドアの状態検知。開、閉、半開き、こじ開け、ラッチの引っかかり
* 操作の通知
* 動作モード。通常、不在、プライバシー、遠隔操作の禁止、通行モード
* 自動再施錠と警報

== 業務用の扉に向かない理由

ここからは筆者の評価です。家庭用の玄関にはMatterで十分ですが、業務用の扉に適用するには、次の三点が課題になります。

*接続の経路。* Matter機器は管理者のネットワークに登録しないと動作しません。業務システムから扉を操作しようとすると、管理者であるプラットフォーム企業のアカウントと同意画面を経由することになります。Appleにはサーバーから呼び出すAPIがなく、Googleは自社の家庭向けの枠組みの中でだけ他社アプリに開放しています。自前のコントローラーを立てる方法はありますが、それでも得られるのは「施錠・解錠・状態」という機器レベルの操作だけで、誰が承認し、何が記録され、どの権限で操作したかという業務上の情報は含まれません。

*主導権。* ファブリックの鍵を持つのは管理者であり、実質的にApple、Google、Amazonのアプリです。通信規格は公開されていても、実際に使うには三社のいずれかのネットワークに入る必要があります。扉の側から見ると、ソフトウェアの主導権が三社に集まる構造です。

*情報の保存場所。* Matterの通信自体はローカルネットワーク内で完結します。しかし管理者アプリは、遠隔操作や音声操作のために、機器の状態と操作履歴を自社のクラウドに同期します。扉の場合、誰がいつどこを通ったかという記録が、個人向けアカウントを通じて外部のサーバーに保存されることになります。企業では、従業員の出退勤や来客の記録が特定の一社のサーバーに集まることになり、情報管理の面で受け入れにくい構造です。

また、業務用の扉に求められる次の機能は、Matterの範囲外です。火災や停電、避難時の動作、改ざんを検出できる監査記録、二人同時認証や強要時の通報、リーダーとコントローラー間の暗号化通信、建物設備との連動、保守作業者の権限管理。

== まとめ

Matter対応のセンサーやスピーカーは、周辺機器として活用できます。一方で、扉の制御判断、記録、鍵の発行は、Matterとは別に、扉の側で管理する仕組みが必要です。扉側に認証・監査・権限管理を含むAPIを用意し、Matterはその入力の一つとして扱うのが現実的です。

= Aliroとは何か

Aliro(アリロ)は、スマートフォンやスマートウォッチを鍵として使い、電子錠のリーダーに本人であることを提示するための規格です。規定しているのはリーダーとの通信までで、リーダーから先の制御は規定していません。この記事では、規定している範囲としていない範囲、扉の側から見た利点、そして導入時の課題を説明します。

== 概要

Aliroは、Matterと同じConnectivity Standards Alliance(CSA)が策定する規格で、バージョン1.0は2026年2月26日に公開されました。策定には、Apple、Google、Samsungといったスマートフォン側の企業と、ASSA ABLOY、Allegion、HIDといった錠・リーダー側の企業が参加しており、参加企業は220社を超えます。

それまで、スマートフォンを鍵にする仕組みは企業ごとに分かれていました。たとえばAppleのHome Keyは、iOS 15(2021年)でNFCによる鍵をWalletに追加し、iOS 18(2024年)でUWBによる近接解錠に対応しましたが、Home Key対応の錠でしか使えませんでした。Aliroは、この部分を共通化する規格です。

== 規定している範囲

* スマートフォンとリーダーの間の相互認証。楕円曲線暗号P-256、AES-256-GCM、圧縮X.509証明書を使います。
* 入館資格を示すデータの形式(mdoc)。
* 通信方式は三つ。NFC(かざす)、Bluetooth LE(近づく)、UWB(手を触れずに通る)。
* 認証はリーダーの中で完結します。インターネットに接続していなくても、スマートフォンとリーダーの二者だけで解錠できます。
* オフラインでの資格情報の失効。

== 規定していない範囲

Aliroは、規定する範囲を意図的に絞っています。

* リーダーから先。コントローラー、業務システム、リーダーとコントローラー間の通信規格(OSDPなど)は対象外です。
* パソコンへのログインなど、物理的な入場以外の認証。
* 鍵の共有と監査記録。これらは将来のバージョンで扱う予定とされています。

つまりAliroは、扉に対して何かを命令する規格ではありません。誰が来たかを確実に示すだけで、その後の処理は扉のコントローラーと鍵の発行者に委ねられます。このため、扉の側の設計の自由度が保たれます。ここでいう鍵の発行者とは、誰に鍵を発行し、いつ失効させるかを決めて記録する主体のことです。

== 扉の側から見た利点

物理的な鍵を完全に廃止するには、代わりとなる手段が一つでは不十分です。Aliroは、その手段を複数にするための基盤になります。

* 通信方式が三つあるため、一つが使えなくても別の方式で解錠できます。
* スマートフォンとスマートウォッチの両方に同じ鍵を入れられます。
* iPhoneは、バッテリー切れで電源が落ちた後も数時間はWalletの鍵をNFCで使えます。
* 複数の発行者の鍵を、同じリーダーで受け付けられます。管理者の鍵、保守作業者の鍵、一時的な来客の鍵を、それぞれ別の発行者が出せます。

これらはいずれもインターネットに依存しません。クラウドに依存する認証手段は、何本用意してもサーバー障害で同時に止まるため、冗長化になりません。Aliroが冗長化に使えるのは、リーダー内で認証を完結させることを規格で定めているからです。

== 課題

スマートフォンのWalletに鍵を入れるには、AppleおよびGoogleとの契約が必要です。リーダー側の実装は自由でも、鍵を発行する側はこの契約を経由することになります。これは鍵の発行事業を始める際の参入障壁であり、Aliroそのものの価値を下げるものではありませんが、事前に把握しておく必要があります。

リーダーを開発する側には参照設計があります。Espressif、Nordic Semiconductor、STMicroelectronicsが、Aliro対応リーダーの開発キットとソフトウェアを提供しています。リーダーは既製品として調達できるようになりつつあり、扉メーカーが自社開発する必要はありません。

== まとめ

Aliroリーダーから得られる「認証成功、誰であるか」という結果を、扉のコントローラーの入力の一つとして扱います。カメラによる顔認証、マイクによる音声、ドアの開閉センサーも同じ形式の入力として扱い、それらを組み合わせた判断は扉の側で行います。リーダーはいつでも別の製品に交換できる設計にしておくことが重要です。

== 出典

= スマートドアに求められる条件

ここでいうスマートドアとは、電子錠、リーダー、コントローラーを備え、鍵の発行と失効をソフトウェアで管理できる扉のことです。製品は数多くありますが、本当に必要な条件は多くありません。この記事では条件を六つに整理し、最後に、リーダーの有力候補と見られるAppleのドアホンについて、報道内容をその条件に照らして確認します。

== 1. ローカルで動作すること

インターネットに接続していなくても、解錠、施錠、記録ができることです。これができない電子錠は信頼できないため、利用者は外側のシリンダー錠を残し、物理鍵を持ち歩き続けます。結果として電子錠は追加の機器になり、費用も鍵の管理も増えます。現在の後付け型スマートロックの多くがサムターンに被せる形なのは、このためです。

ローカルで完結する電子錠であれば、物理鍵の代わりになります。外側のシリンダーをなくせば、ピッキングの対象がなくなり、合鍵の複製も不要になり、扉の開口部の規格を一つにできます。これは扉メーカーにしかできない変更です。残す必要があるのは、避難のための内側からの機械的な解錠と、非常用の給電口だけです。

== 2. 錠を交換できること

扉と錠を交換せずに、リーダーや鍵の発行者を変更できることです。錠と専用アプリを一体で提供する製品は、共通規格が普及した時点で優位性を失います。扉の側が接続仕様を定め、錠の側がそれに合わせる形が望ましい構造です。錠の通信規格としてのlink:/guide/matter/[Matter]は家庭用には十分ですが、業務用の扉には不足があります。その理由は別の記事で説明しています。

== 3. リーダーを交換できること

来訪者を識別する機器は、顔はカメラ、鍵はスマートフォンのWallet、声はマイクで読み取ります。玄関でこの役割を担うのはドアホンであり、Apple、Google、Amazonが競争している分野です。競争の成果は利用者側に還元されます。扉の側はリーダーを自社開発せず、「誰が来たか」という結果を受け取るインターフェースを用意して待つのが合理的です。

== 4. 記録を手元に置くこと

扉の記録は、誰が何時に出入りしたか、来客は誰か、休日に誰が出勤したか、という人事・営業に関わる情報です。これが個人向けアカウントを通じて外部のサーバーに保存される構造は、企業では受け入れにくいものです。記録は自社の管理下に置き、外部に送信する範囲と内容は事業者が決められるようにします。

== 5. 認証を一社に依存しないこと

一社のサーバーが認証を握る構造では、障害、事業撤退、情報漏えい、値上げ、差し押さえといったリスクが、その一点に集中します。扉が自ら認証を判断し、鍵の発行者は署名付きの資格情報を渡すだけで、解錠のたびに呼び出されない形が望ましい構造です。監査記録は扉側と管理台帳側の二か所に別々に保存します。

== 6. 認証手段を複数持つこと

物理鍵を廃止するには、代わりの手段が一つでは足りません。スマートフォンの鍵、スマートウォッチの鍵、顔認証、暗証番号、非常手段。どの手段もインターネットに依存しないことが条件です。クラウドに依存する手段は、何本あってもサーバー障害で同時に止まります。link:/guide/aliro/[Aliro]がこの用途に適しているのは、リーダー内で認証を完結させることを規格で定めているからです。

== リーダーの有力候補: Appleの顔認証ドアホン

Appleが、顔認証で玄関の錠を解錠するドアホンを開発しているという報道が、2024年末から続いています。上記の条件に照らして、事実と未確認情報を分けて整理します。

=== 報道の内容

最初の報道は、BloombergのMark Gurman記者が2024年12月22日に書いた記事です。内容は次のとおりです。

* 玄関に立った人の顔を認識し、登録された住人であれば錠を自動的に解錠するドアホン。iPhoneのFace IDと同じ発想。
* 錠はApple製ではなく、HomeKit対応の既存のデッドボルト錠と無線で接続する。特定の錠メーカーと提携して公式の組み合わせを提供する可能性もある。
* Appleが独自に設計した無線チップ「Proxima」を使う可能性がある。顔認証の処理は機器内で行う。
* 開発は初期段階で、発売は早くても2026年。
* Appleが自社で製造せず、LogitechやBelkinなどの他社を通じて技術を提供する可能性もある。

2026年2月の9to5Macの記事も、この報道を「2026年中に発売される可能性がある」と伝えた内容で、新しい事実は加わっていません。

=== 2026年9月時点の状況

9月9日の発表会で発表されたのは、iPhone 18 Pro、iPhone Duo、Apple Watch、AirPodsでした。ドアホンやその他のスマートホーム製品は発表されていません。

スマートホーム製品については、7インチディスプレイを備えたホームハブと室内用カメラが「2026年後半から2027年初め」に発売されると報じられています。ホームハブが顔認証で利用者を識別する機能を持つことは、2026年8月にmacOS 26.7のリリース候補版のコードから確認されました。ドアホンは報道の中でもホームハブとカメラの後に位置づけられており、2026年3月の製品予想記事には含まれていません。

つまり、「開発中」であることは一社の報道として事実ですが、「発売される」ことはまだ確定していません。Apple自身は一度も言及していません。

=== 有力候補と見る理由

報道されている製品の特徴は、リーダーに求められる条件のうち三つを満たしています。

*顔認証の処理を機器内で完結させる。* クラウドに顔データを送らないリーダーは、ローカルで動作する扉と同じ側に立ちます。企業で使う場合、従業員の出退勤記録が外部サーバーに送られないことが条件になります。三社の中でこの方針を製品の特徴として打ち出しているのはAppleだけです。

*錠は他社の既存製品を使う。* 自社の錠とアプリで囲い込まず、HomeKit対応の錠であれば接続できます。扉メーカーから見ると、錠を交換できる扉の前提と一致します。リーダーが変わっても、扉と錠を交換する必要がありません。

*スマートフォンとWalletの鍵を持つ企業が、顔認証も提供する。* 鍵と顔と声を一台で読み取るリーダーの姿を、最も揃えて持っているのがAppleです。iPhoneはバッテリー切れの後も数時間はWalletの鍵をNFCで使えます。物理鍵を廃止するための冗長化が、同じ企業の製品群の中で完結します。

=== 未確認の点

* Walletの鍵(NFC、UWB)をドアホン側で読み取るかどうかは、報道に含まれていません。UWBによる近接解錠は、現在も錠側のリーダーで実現されています。
* 日本での発売時期。
* 集合住宅の住戸玄関に対応するかどうか。これは機器の問題ではなく建物側の問題です。

=== 扉の側で準備すべきこと

リーダーは自社開発せず、ドアホンから送られる「誰が来たか」という情報を受け取るインターフェースを扉の側に用意します。Aliroリーダーからの認証結果と同じ形式の入力として扱えば、Appleのドアホンが発売された時点でそのまま接続できます。

火災や停電時の動作、記録、二人同時認証が必要な部屋の判断は、リーダーではなく扉の側が担います。リーダーはいつでも別の製品に交換できる設計にしておくことが、有力候補を待つ側の準備です。

=== 今後の見通し

= 玄関まわりの技術を層に分けて見る

玄関まわりの技術は、扉そのものから、それを管理する人まで、いくつもの層が重なってできています。Apple、Google、Amazonがドアホンや鍵の分野に参入した後の姿を前提に、各層で誰が残り、どのような経済になるかを整理します。並びは下から上へ、物から人への順です。

== 一覧表

|===
| 層 | 残る事業者 | 経済の形

| 扉の製造
| 扉メーカー。電子錠を埋め込む開口部、扉内部の配線経路、その性能等級を持つ
| 防火認定と等級が参入障壁。数量は新築着工数ではなく、既存の建物の戸数に比例する

| 電子錠
| 競争を経て少数の優良メーカーが残る。電動部は標準的な錠として購入する部品になる。認定や物理的な要件がある特殊な錠は残る
| 汎用品は価格が下がり続ける。特殊品は認定によって少数が高い利幅で残る

| 扉のコントローラ
| 扉側の専用コントローラ。火災・停電・避難時の判断、監査記録、二人同時認証と強要検知、配線の自己診断、複数の入力の組み合わせを扉の中で処理する。インターネットに接続しなくても動作する。仕様は公開し、実装は各社が工夫する
| これまで設備工事会社(SIer)が独自の制御盤で担っていた部分。公開仕様に置き換わると、独自仕様による価格は消え、工夫の差が扉の中に残る

| Apple、Google、Amazon。顔、NFC、UWB、音声を1台で読み取る。消防連動や過酷な環境が要件の特殊なリーダーは残る
| 汎用品は本体を1回販売し、囲い込みは月額の映像サービスで行う。特殊品は認定と物理要件で残る

| スマートフォン
| Apple、Google。Walletの鍵と本人確認の手段
| 鍵自体には課金しない。囲い込みは端末で行う

| 周辺機器
| スピーカー、火災報知器、センサー、室内カメラ。各社
| 購入する部品。足りない機能は1台追加する

| 通信規格
| 公開規格。Aliro、OSDP、ONVIF、そして扉のAPI(公開仕様)。Matterは周辺機器を接続する口の一つ
| 無料。誰も所有しない

| 鍵の発行
| 発行者。誰に鍵を出し、いつ失効させ、本人であることを確認して記録する
| *収益が出る。* 1戸あたり月額。限界費用はほぼゼロ

| 業務システムとの連携
| 機器で起きた出来事を、予約、名簿、鍵の台帳、スケジュールに結びつける
| *収益が出る。* 事業者ごとに責任者と様式が異なるため、汎用のSaaSにはならない

| 業務システム
| 予約、名簿、会計、報告
| 無料に向かう。作らずに既存の物を配る

| 管理者とAI
| 事業者本人。判定はAIが行い、判断に迷う件だけ本人が確認する
| 外部の人員は原則ゼロ

== 表の読み方

扉の製造から周辺機器までは、購入する部品です。通信規格は無料の公開規格で、誰の所有物でもありません。収益が出るのは「鍵の発行」と「業務システムとの連携」の二つの層だけで、業務システムは無料で配布し、最上位に管理者が一人います。

この二つの層は、機器と人の間に位置します。下は購入する部品、上は本人の責任です。その間で、機器の出来事を人の責任に翻訳する仕事だけが、汎用の商品になりません。安全に責任を持つ仕事だからです。

== 扉のコントローラの層

コントローラは、これまで表に現れなかった層です。設備工事会社(SIer)の独自の制御盤の中に隠れていたためです。入退室管理システム一式の仕様、価格、保守を握っていたのは、錠でも扉でもリーダーでもなく、制御盤でした。リーダー側はAliroが、機器側はMatterが、リーダーと制御盤の間はOSDPが公開規格にした後、火災・停電時の判断、監査記録、二人同時認証、建物設備との連動だけが独自仕様のまま残っています。これを扉側の専用コントローラとして公開仕様で実装するのが、扉メーカーの新しい役割です。

この層はインターネットに接続しなくても完全に動作します。通信が切れても解錠・施錠・記録ができるため、物理鍵を廃止でき、電子錠は追加の機器ではなく標準の錠になります。外側のシリンダーが不要になり、開口部の規格が一つになります。

この層は、カメラ、マイク、センサー、Aliroリーダーの情報を扉の中で統合します。配線が物理的に集まる場所が扉だからです。扉メーカーが利用者に提供できる機能は、たとえば次のようなものです。手ぶらで入れる、鍵を落としても他人は入れない、後ろから付いてきた人がいれば通知する、脅されて開けたときは通報する、重要な部屋は二人で開ける、配達員は音声で用件を伝えれば通す、家族や来客ごとに開け方を選べる。

== 三社が競争する領域

Apple、Google、Amazonが競争するのは、リーダー、スマートフォン、周辺機器です。これらは汎用品の領域であり、だからそれ以外の層は残ります。三社が参入しない特殊な錠とリーダーは、認定と物理要件によって汎用品の競争の外で残ります。競争の場所はリーダーの製造ではありません。リーダーとは来訪者を識別する機器であり、玄関でその役割を担うのはドアホンです。製造は台湾などの産業機器メーカーに移り、競争の成果は購入する側に還元されます。したがって、扉の側でリーダーを自社開発する必要はありません。

== 需要は減らない

全体として需要は減りません。減るのは1台あたりの価格と、中間に立っていた事業者です。

汎用品の層は安くなりますが、安くなった分だけ数量が出ます。スマートフォンの鍵がWalletの標準機能になれば、リーダーは一部の高級仕様ではなく、全戸の要件になります。特殊品の側は認定と物理要件で残り、少数が高い利幅で残ります。鍵の発行と業務システムとの連携は新しく生まれた層で、以前は存在しなかった需要です。

減ったように見えるのは、独自の錠と独自のアプリで囲い込んでいた会社の売上と、画面を受託開発していた会社の売上です。それは需要が消えたのではなく、囲い込みが外れて、需要が層ごとに配り直されたということです。

= 扉のコントローラの仕様と試験の道具を公開する

このサイトを運営するaiseedは、扉側のコントローラの仕様と、それを確かめるための試験の道具を公開しています。この記事では、何を公開するか、どのような性格の物か、仕様の中核に何を置くかを説明します。

== 公開する物

* 仕様。何を満たすかだけを、番号を付けて書いた文書です。本文は https://github.com/aiseed-dev/digitaldoor/blob/main/docs/扉コントローラ仕様書.md[扉コントローラ仕様書]にあります。
* 疑似の扉と試験の道具。Pythonで動作するコードです。扉の判断、監査記録、HTTP APIを含みます。同じリポジトリの https://github.com/aiseed-dev/digitaldoor/tree/main/controller[controller/] に、ほかのコードとは別に Apache-2.0 で公開しています。製品に組み込んで、閉じたまま配ることもできます。認定を受けた製品ではなく、仕様を確かめ、読取機や管理ソフトを作る人が実機なしで相手にするための物です。
* テスト。「この入力に対してこの出力」という形式で書かれています。テストが通れば、仕様を満たしていると言えます。

日本語を優先し、英語版は後から用意します。日本の扉メーカー、錠メーカー、電気工事の技術者、学生が、同じ言葉で開発できるようにするためです。

== どのような性格の物か

Matterと同じ位置づけで、Matterが対象としていない業務用の扉を対象にします。現在の業務用の入退室管理システムは高価で、ソフトウェアの使い勝手も良くありません。発注するのは総務や設備部門で、使うのは現場であり、仕様は制御盤メーカーの独自形式で、修正のたびに見積もりが必要だからです。公開仕様と動作する参照実装があれば、価格は下がり、ソフトウェアは直せる物になります。

認証制度ではなく、実用のための仕様です。認証の仕組み、会費、商標は設けません。満たしているかどうかは、公開されたテストを自分で実行すれば分かります。プログラミング言語のPythonが広まったのと同じ形で、無料で、読める形で、動く物とともに置き、使う人が追加していく方式です。

責任を負う文書ではありません。利用者の要望を整理して扉メーカーに伝える要望書です。責任は、扉に組み込んで認定を取る扉メーカー、鍵を発行する事業者、その建物を運営する管理者が持ちます。したがって、扉メーカーからは料金を取りません。aiseedの収益は、鍵の発行と業務システムとの連携から得ます。

仕様は「何を満たすか」だけを書き、今後も追加していきます。追加するときは、要求ごとに理由、テスト手順、日付を添えます。既存の番号は変えません。仕様を満たす側は、どの番号を満たすかを申告します。「どう作るか」は書かないため、扉メーカーは仕様の中で自由に工夫できます。

== 仕様の中核

*セキュリティを含めて自由に使えるAPI。* 業務システムから、プラットフォーム企業のアカウントを経由せずに扉へ直接アクセスできること。呼び出し側は認証され、権限で区切られること。扉で起きたことはすべて署名付きで記録され、改ざんを検出できること。火災や停電時の動作は扉が持ち、外部からの呼び出しで上書きできないこと。

*ローカルで動作すること。* 認証の判定、施錠と解錠、火災・停電・避難時の動作、監査記録、失効の適用、非常手段は、外部との通信がなくても動作します。通信が切れても、扉は最後に受け取った資格情報と失効リストで判定を続けます。扉の出来事は構内で完結し、外部に送信する範囲は事業者が決めます。これがなければ物理鍵は廃止できず、電子錠は追加の機器のままです。

*認証を一社に集中させないこと。* 一社のサーバーが認証を握る構造では、障害、撤退、侵害、値上げ、差し押さえのリスクがその一点に集まります。扉が自ら判定し、発行者は署名付きの資格情報を渡すだけで、解錠のたびに呼び出されない形にします。監査記録は扉側と台帳側の二か所に別々に残します。

*複数の認証手段。* 扉は互いに独立した二つ以上の経路で資格情報を受け取ります。Aliroはこの冗長化に適しています。

将来は、カメラ、マイク、センサー、Aliroリーダーの情報を扉の中で組み合わせて判断できるようにします。組み合わせの規則は事業者が決めます。

== 扉メーカーとの関係

扉メーカーは仕様を書く側ではなく、仕様に適合する側です。扉と認定に専念でき、囲い込みの疑いを受けません。公開仕様の中で工夫できる部分は、防火戸への組み込み方、標準錠との組み合わせでの認定、配線経路の自己診断の測定値、接点の信頼性、価格と納期です。

| Associate | 無料 | 他の会員が認証した製品を自社の名前で売ることだけ
|===

確定した仕様は、会員でなくても CSA の頁から無料でダウンロードできます。2026年10月の時点で、Matter 1.4〜1.6.1、Aliro 1.0、製品のセキュリティの仕様が並んでいます。一方、仕様を決める作業部会に加わり、草案を読むには、Participant 以上の会員になる必要があります。仕様が決まる過程は、外からは見えません。

Matter は、2025年11月の1.5でカメラと開閉機器(シャッター、門、ガレージの扉)を加え、2026年6月17日の1.6でNFCによる設定と、複数のエコシステムによる一台の共同管理を加えました。錠(Door Lock)は1.0から機器の種類として定まっています。

Aliro 1.0 は2026年2月26日に公開されました。NFC、Bluetooth LE、Bluetooth LE と UWB の組み合わせで、スマートフォンやウォッチを鍵にする規格です。CSA の発表では、Apple、Google、Samsung がウォレットでの対応を表明し、220社を超える会員が開発に関わりました。認証は、CSA が認めた試験所で行います。CSA の認証製品の一覧には、2026年3月27日付けで Aliro 1.0 の錠が載っています(ULTRALOQ)。同社は2026年9月に、Aliro の認証を受けた錠を三機種まとめて発表しました。どれが最初かは、同社の発表の言い方であって、CSA は述べていません。

開かれている所もあります。Matter の SDK(connectedhomeip)は Apache-2.0 で GitHub にあり、誰でも CLA に署名すれば修正を送れます。ただし GitHub の Discussions は使っておらず、話し合いは Issue で行います。仕様そのものを変えるには、作業部会への参加が要ります。Aliro には、CSA の公開の置き場(aliro-access-control)があり、認証の試験の道具と、読取機と利用者の端末を模擬する道具が Apache-2.0 で公開されています。開発者の会合は、2026年8月27日に深圳で Matter Developer Conference が開かれ、Aliro と入退室管理も議題でした。

=== 読取機と制御盤の間

業務用の入退室管理では、読取機と制御盤の間に OSDP が使われます。SIA の規格で、2020年に IEC 60839-11-5 として国際規格になったと報じられています(Security Sales)。SIA の適合確認(OSDP Verified)を受けた機種は、2026年7月に32社の222機種になったと報じられています(SecurityInfoWatch、2026年7月28日、SIA の発表に基づく)。適合確認には SIA の会員であることが要ります。オープンソースの実装として libosdp(Apache-2.0)があります。

ONVIF には、扉の監視と制御の Profile C(2014年)と、資格情報と規則の Profile A があります。

== 制度

製品の安全を求める制度は、作る人が必ず通る場です。錠に関わるものを並べます。

|===
| 制度 | 時期 | 錠に関わる所

| JC-STAR(日本) | 2025年3月に申請の受付開始 | IoT 製品のセキュリティの適合ラベル。詳しくは日本の記事
| 無線機器指令の委任規則(2022/30)と EN 18031(EU) | 2025年8月1日から義務 | 無線でつながる機器に、パスワード、更新、データ保護の要件
| サイバーレジリエンス法、CRA(EU) | 報告の義務は2026年9月11日から、全面の適用は2027年12月11日 | スマートドアロックは、セキュリティ機能を持つスマートホーム製品として、重要な製品の区分に入る(法律事務所等の解説による)
| PSTI 法(英国) | 2024年4月29日 | 共通の初期パスワードの禁止、脆弱性の連絡先と更新期間の公開
| Cyber Trust Mark(米国) | 2025年に中断。FCC は2026年4月13日に新しい運営者を選んだ | 再開の状況は確かめられなかった
|===

どの制度も、脆弱性の連絡先と更新の期間を公開することを求める方向です。製造者と研究者をつなぐ窓口が、制度として要るようになりました。

== 各社の開発者向けの窓口

|===
| 会社と製品 | 窓口 | 条件

| Nuki | Bluetooth、ブリッジ、Web、MQTT の各 API、Matter。公開の開発者フォーラム | 公開
| SwitchBot | Open API v1.1(GitHub で文書を公開) | アプリでトークンを発行。個人利用で、商用は問い合わせ
| CANDY HOUSE の SESAME | SesameSDK(iOS、Android、ESP32 向け。MIT ライセンス)と Web API | 公開
| Allegion の Schlage | 開発者ポータル | 事業者だけ。審査の後に鍵を発行。趣味の開発は対象外と明記
| U-tec の ULTRALOQ | U Home OpenAPI | 登録の条件は確かめられなかった
| Brivo | 入退室管理の API | アプリを登録し、本番の鍵を申請
| Avigilon Alta | 入退室管理の REST API、技術提携の制度 | 提携

錠の会社(Nuki から U-tec まで)は電子錠の層を、Brivo と Avigilon Alta は扉のコントローラと鍵の発行の層を、Seam は鍵の発行と業務システムとの連携の層を扱います。窓口の形と条件は会社ごとに違います。複数の会社の錠を一つの口で扱いたい事業者には、Seam のような商用のサービスがまとめ役を担っています。Seam は、民泊、ホテル、集合住宅、ジム、コワーキング、トランクルームを用途に挙げています。

== オープンソース

* Matter の SDK(project-chip/connectedhomeip)。Apache-2.0。2026年10月17日の時点で、星は約8,970、貢献者は約779。最新は v1.6.1.0(2026年9月25日)。錠の例(examples/lock-app)が、ESP32、Linux、Nordic、Silicon Labs、NXP 等の向けにあります。
* Home Assistant。錠を扱う連携は53あります(2026年10月17日、開発版)。2026年4月の版で、Matter の錠の利用者と暗証番号を管理する画面が加わりました。SESAME の連携は古いクラウドの方式のままで、保守する人がいません。
* openHAB、ESPHome、Zigbee2MQTT も錠を扱います。Zigbee2MQTT と openHAB は GitHub の Discussions で話しています。
* 有志のファームウェア。Nuki の錠を家のネットワークにつなぐ ESP32 の中継器(nuki_hub)、RFID と Wiegand の入退室管理(esp-rfid、2017年から)、Apple のホームキーを ESP32 で読む実装(HomeKey-ESP32)。
* Aliro。Espressif が2026年6月に、ESP32 向けの Aliro の SDK(esp-aliro、Apache-2.0)を公開しました。有志による研究用の実装もあります。

広く使われている、開かれた扉のコントローラのハードウェアは見つかりませんでした。近い物は、ESP32 を使う有志のファームウェアです。

== 研究者

錠の脆弱性を調べる研究者も、一つの集まりです。会議と脆弱性の公開の場で集まり、製造者とは事案ごとにつながります。

* 2024年3月。ホテルの RFID 錠(dormakaba の Saflok)で、偽の親鍵のカードで扉が開く問題が公開されました。報道では、131か国のホテルと集合住宅の13,000を超える施設で、300万を超える錠が対象とされています(SecurityWeek、2024年3月22日)。製造者への連絡は2022年で、公開まで1年半ほどかかりました。
* 2024年3月7日。CERT/CC が、Sciener のファームウェアを使う錠と TTLock のアプリ等の問題を公開しました(VU#949046)。CERT/CC は、ソフトウェアによる修正の手段は無いとしています。
* 2026年10月9日。SwitchBot の Lock の系列の Bluetooth で暗号の使い方の誤りが、CVE-2026-8374 として公開されました(CVSS v4 で8.5)。

== 層ごとに見る

場ごとに見た物を、層ごとに並べ直します。

|===
| 層 | 仕様を決める場 | 実装と話し合いの場

| 扉の製造 | 国ごとの防犯と防火の制度、業界団体 | 見つからない
| 電子錠 | CSA(Matter の Door Lock、Aliro) | connectedhomeip の錠の例、Home Assistant、各社の SDK。各社と Home Assistant のフォーラム
| 扉のコントローラ | SIA(OSDP)と ONVIF。ただし読取機との間の通信だけ | libosdp。話し合いの場は見つからない
| ドアホン(読取機) | CSA(Aliro、Matter 1.5 のカメラ)、ONVIF | esp-aliro、有志の実装。話し合いの場は見つからない
| 通信規格 | CSA、FiRa、NFC Forum | 各規格の SDK。connectedhomeip の Issue
| 鍵の発行 | Aliro(資格情報の形) | 商用のまとめ役。開かれた場は見つからない
| 業務システムとの連携 | 見つからない | 各社の API と商用のまとめ役。開かれた場は見つからない
|===

== 足りない物

調べた範囲で、次の物が見つかりませんでした。

. *層をまたいで話す開かれた場。* 扉メーカー、錠メーカー、読取機のメーカー、設備工事会社、建物の運営者が一緒に話す公開の場はありません。近い物は、会員制の団体と展示会です。
. *仕様を決める過程の公開。* 確定した仕様は無料で読めますが、決める席は会員制で、草案に触れるには年21,500ドル以上(CSA)が要ります。
. *扉のコントローラの層の仕様と試験。* 火災、停電、避難のときの挙動と、改ざんの分かる監査記録を扱う公開の仕様と試験はありません。Matter と Aliro は錠と読取機まで、OSDP は読取機と制御盤の間までです。
. *事業者が使える共通の口。* 各社の API は形も条件も違い、まとめる役は商用のサービスが担っています。業務システムとの連携の層に、公開の仕様はありません。
. *使う人の声が仕様に届く道。* 建物の運営者や住む人の困りごとは、各社のサポートと利用者のフォーラムに散っていて、要求として仕様の席に届く公開の道は見つかりませんでした。

このサイトは、扉のコントローラの link:/guide/open-specification/[仕様と参照実装] と、使う人の困りごとを要求の番号に結ぶ道を、誰でも読める形で置いています。上の空いた所を、開かれた場で埋めるためです。

=== 防犯性能の高い建物部品(CP部品)

警察庁、国土交通省、経済産業省と民間の16団体が、2002年11月25日に官民合同会議を設けました。侵入までに5分以上かかる建物部品を試験で確かめて目録に載せ、CP マークを付けます。2026年3月末の時点で、17種類、3,545品目です。電気錠も錠の区分に入っています(日本サッシ協会の目録)。

== 制度

=== JC-STAR

JC-STAR は、IoT 製品のセキュリティの適合ラベルの制度です。経済産業省の監督のもとで IPA が運営し、2025年3月に★1の申請の受付が始まりました。★1は、IoT 製品に共通する最低限の脅威への備えです。

美和ロックは2025年10月7日に、住宅の玄関扉用の電気錠「iEL Zero smart シリーズ」で★1を取得し、錠メーカーとして初めてだと発表しました。IPA の一覧では、ラベルの付与は2025年9月11日、期限は2027年9月10日です。扉の周りでは、パナソニックのドアホン「外でもドアホン」(2026年2月6日)や、Axis の入退室管理とインターホンを含む製品(2025年5月12日)もラベルを受けています。後付けのスマートロックは、確かめた範囲の一覧には見当たりませんでした。

=== 置き配とオートロック

国土交通大臣は2025年9月16日の会見で、宅配の業者がオートロックを自由に開けられる仕組みを国が作るという話は事実ではないと述べました。あわせて、民間の各社が開発した解錠の仕組みが、既に2万棟を超えるマンションに入っていること、配達員の本人確認と解錠の記録、事前に登録した荷物だけの一時的な解錠、管理組合の合意という条件で使われていることを説明しました。令和8年度の予算要求には、配送会社をまたいだ伝票番号と配送データの標準化を支える事業が入っています。

事業者の例として、美和ロックと PacPort は2026年1月13日に、ヤマト運輸の「EAZY」の配達でオートロックを解錠する仕組みを2026年春から始めると発表しました。

=== 火災と避難

建築基準法施行令第125条の2は、屋外への出口などの施錠装置を、屋内から鍵を使わずに開けられる構造にすることを定めています。火災の信号による解錠、非常時の解錠、予備の電源の扱いは、各地の火災予防条例と消防の基準で決まります。例えば名古屋市の「電気錠の指導基準」は、電気錠を通電時に施錠する型など四つの型に分け、避難に要る出入口では、防災センター等からの遠隔の解錠と、自動火災報知設備に連動した解錠を、型に応じて求めています。国としてまとめた電気錠の通知は見つけられませんでした。

経済産業省の「スマートホームの安心・安全に向けたサイバー・フィジカル・セキュリティ対策ガイドライン」(2021年4月)は、スマートホーム全体を扱い、錠に絞った章はありません。

== 足りない物

. *スマートロックを扱う業界団体。* 錠の業界団体は物理の防犯の試験の窓口で、公開の仕様は見当たりません。
. *扉、錠、業務システムの間の公開の接続仕様。* ECHONET Lite の電気錠の種類と、始まったばかりの Matter と Aliro だけです。建物の現場で使われる JEM-A は本文が公開されていません。
. *火災と避難のときの電気錠の挙動の、全国で同じ前提。* 決まりは各地の基準にあり、国としてまとめた公開の文書は見つかりません。扉のコントローラを作る人が、全国で同じ前提を持てません。
. *事業者が公開の条件で使える開発者の窓口。* 個人向けと営業経由に分かれています。
. *業界と開発者が会員制でなく会う場。* 両者が同じ場にいるのは CSA 日本支部で、Adopter(年7,500ドル)以上の会員制です。
. *置き配の解錠の条件を確かめる公開の試験。* 2万棟を超える建物で動いていますが、本人確認、解錠の記録、管理組合の合意という条件を確かめる公開の仕様と試験は見つけられませんでした。

このサイトの link:/guide/open-specification/[扉のコントローラの仕様] は、3 と 6 にある火災と停電のときの挙動と、改ざんの分かる解錠の記録を、番号の付いた要求と公開のテストで扱っています。

= 日本のスマートロックのアプリの現状と課題

日本で使われているスマートロックのうち、Akerun(フォトシンス)、ビットキー、RemoteLOCK、美和ロック、ゴール、Qrio の六社のアプリを、2026年10月18日に調べました。錠そのものではなく、利用者が毎日触るアプリの側を見ます。

数字は Google Play と App Store の日本の頁から取りました。利用者の声は、ストアのレビューを読んで自分の言葉で要約し、個人は特定しません。会社が発表したことと、報道されたことと、利用者が書いたことは、分けて書きます。レビューは、困った人ほど書くものです。評価の低さは不満の多さを示しますが、使っている人全体の満足度とは違います。

== 見方

アプリごとに、次の六つを見ます。

* アプリの役割(住む人、働く人、管理する人、施工する人)
* ストアの数字(評価、件数、ダウンロード数、最終更新日)
* 利用者の多い不満
* 会社の答え方(レビューへの返信、更新の説明)
* 会社の発表と報道(障害、提供の終了)
* 網やクラウドが止まったときの動き

== 一覧

評価は、Google Play / App Store の順です。件数が少ないと Google Play は評価を表示しません。

|===
| アプリ(会社) | 評価(件数) | 最終更新

| Akerun App(フォトシンス) | 2.4(58) / 2.39(93) | 2026年7月
| homehub(ビットキー) | 2.3(312) / 2.1(350) | 2026年10月
| workhub(ビットキー) | 3.9(47) / 3.47(121) | 2026年10月
| RemoteLock(米国の RemoteLock 社。日本は構造計画研究所) | 日本の頁に表示なし / 2.0(8) | 2026年10月
| MIWA Support(美和ロック) | 表示なし / 3.4(15) | 2026年5月
| KEYMO NEO(美和ロック) | 1.3(7) / 1.39(36) | 2024年10月
| LaresIA ON(ゴール) | 表示なし / 2.43(7) | iOS は2021年5月、Android は2025年10月
| Qrio Lock(ソニーネットワークコミュニケーションズ) | 2.2(1,130) / 2.19(1,109) | 2026年9月

利用者の多いアプリ(10万ダウンロード以上)は、Akerun App、homehub、Qrio Lock の三つで、評価はどれも2点台です。

== 会社ごとに見る

=== Akerun(フォトシンス)

Akerun App は、会社、ジム、スタジオ、賃貸住宅で、利用者が錠を開けるアプリです。Google Play で10万ダウンロードを超えています。

*利用者の多い不満。* 一番多いのは、Bluetooth でつながらず、何度押しても開かないという声です。2025年から2026年にかけて、十回以上押した、家に入るのに十分以上かかった、同じ扉で IC カードはすぐ開くのにアプリでは開かない、という声が続いています。ジムやスタジオの会員が、入れなかったと書く例が目立ちます。ほかに、招待した鍵が届かない、機種を替えたらつながらない、ログインで締め出される、という声があります。

*会社の答え方。* Google Play の文章つきのレビュー(2022年〜2026年の24件)に、会社の返信はありませんでした。更新の説明は「不具合を修正しました」が中心です。

*会社の発表と報道。* 日経クロステックは2025年6月10日に、5月27日の午前から Akerun のアプリで解錠できないなどの障害が起き、約半日後に完全に復旧したと報じました。会社の告知は、サポートの頁が自動の取得を断るため確かめられませんでした。

*止まったとき。* 会社の説明は見つかりませんでした。利用者の声では、アプリで開かないときも IC カードでは開いています。

=== ビットキー(homehub、workhub)

homehub は住む人のアプリで、賃貸住宅の管理会社が錠と一緒に入れる形が中心です。同社の発表では、レオパレス21 の物件で2024年4月末までに25万戸に設置しました。workhub は会社で働く人と管理者のアプリです。

*利用者の多い不満(homehub)。*

* 2026年8月19日の版(3.34.0)で、開閉のボタンが「再読み込み」のまま進まず、Bluetooth はつながっているのに開け閉めできないという声が集中しました。二日後の版で直りましたが、その説明は「軽微な不具合を修正しました」でした。
* 建物の入口で「未接続」になる、遅いという声が、2024年から2026年まで続いています。
* 錠の状態や履歴がアプリと合わない、夜中に自動で解錠された、電池を替えても残量の警告が消えない、急にログアウトされた、古い機種が使えなくなった、という声があります。
* 管理会社が入れたので選べなかった、という声が多くあります。

*会社の答え方。* homehub の Google Play のレビューには、ほぼすべてに1〜3日で返信しています(2025年以降の文章つき58件中57件)。返信は、お詫びと問い合わせ窓口への案内の定型が中心です。workhub の Google Play のレビューには返信がありません。workhub の iOS の更新の説明は、何を直したかが具体的です。

*会社の発表。* 2026年3月1日に iOS 15 以前と Android 10 以前の対応を終え、次の終了(iOS 16 以前、Android 12 以前)は2026年10月31日に延ばしています。旧アプリ bitlock の提供は2026年5月30日で終わり、homehub への移行を求めました。2026年8月の不具合の告知は、ニュースの頁には見当たりませんでした。

*止まったとき。* アプリがクラウドが止まっても開けるかの説明は見つかりませんでした。遠隔の操作と状態の確認は、網の中継器を通ると説明しています。

=== RemoteLOCK(構造計画研究所)

RemoteLOCK は米国の RemoteLock 社の製品で、日本では構造計画研究所が提供しています。管理はおもにウェブの画面で行い、アプリは管理者向けと、機種ごとの設定用に分かれています。

*利用者の多い不満。* 管理者向けのアプリが開かない、すぐ落ちる、という声が2024年から2025年に続き、ウェブ版を使っているという声があります。

*会社の答え方。* ストアのレビューへの返信は見当たりませんでした。一方で、構造計画研究所はサポートの頁に「障害情報」をまとめ、2024年1月から2026年9月までの障害を、起きた時刻、影響、対応とともに載せています。例えば2025年1月7日の障害では、新しい利用者と来訪者が解錠できず、登録済みの暗証番号か物理鍵を使うよう案内しました。2026年9月1日から2日の障害では、障害の間に受けた発行の要求を後で送り直したと書いています。

*止まったとき。* 停電と通信の障害のときの動きを、機種の電源の取り方ごとに表で説明しています。本体に登録済みの暗証番号は網が切れても使え、クラウドで作った番号は次に網につながったときに本体に届き、遠隔の解錠は網が無いと使えません。

=== 美和ロック

美和ロックは、電気錠と住宅の玄関の錠の大手です。アプリは用途ごとに分かれています。MIWA Support は住む人と施工の人の設定用で、スマートフォンを鍵にする機能は有料のサービスです。KEYMO NEO は、集合住宅の錠をスマートフォンで開けるアプリです。

*利用者の多い不満。*

* MIWA Support では、Android で利用規約の同意の欄に印が付けられず登録できないという声(2025年4月、8月)があります。
* KEYMO NEO は評価が1点台で、最後の更新は2024年10月です。2026年9月17日と10月15日の二件のレビューは、iOS の更新の後に使えなくなったと書いています。一件は、物理鍵をたまたま持っていたので入れたと書いています。ほかに、ペアリングに時間がかかる、解錠のたびに操作が多い、鍵を家族のスマートフォンに渡せない、という声があります。
* FeliCa の鍵をスマートフォンに移すアプリ(KEYMO)では、料金を払った後で、管理会社が持つカードでの登録も要ると分かった、という声があります。

*会社の答え方。* ストアのレビューへの返信は見当たりませんでした。KEYMO NEO の紹介の頁に、iOS の更新についての告知は見当たりませんでした(2026年10月18日)。

*会社の発表。* ニュースの頁に、アプリの障害や提供の終了の告知は見当たりませんでした。2025年10月7日に、住宅用の電気錠で JC-STAR の★1を取得したと発表しています。

*止まったとき。* 明確な説明は見つかりませんでした。錠に登録した ID キーやカードを併せて使う前提の作りです。

=== ゴール

ゴールは錠のメーカーで、スマートフォンで開けるための自社のアプリを持っていません。電池式の電気錠 LaresIA の設定アプリ(LaresIA ON)は、ストアの説明で「本アプリで施解錠操作はできません」としています。iOS 版の最後の更新は2021年5月です。

賃貸住宅向けの LaresIA+ は、2023年2月27日の同社の発表で、住む人は Qrio の「Qrio Lock」アプリで開け閉めし、管理は Qrio の管理システムで行うとしています。つまり、この製品のスマートフォンの使い心地は、Qrio Lock のアプリに左右されます。

2025年11月に発表したホテルと民泊向けの Arc LINK Room は、本体で照合する設定なら、網が切れても登録済みの鍵が使えると説明しています。ストアの頁とニュースの頁に、アプリの障害や終了の告知は見当たりませんでした。

=== Qrio

Qrio Lock は、後付けのスマートロックの代表的な製品の一つです。ストアの提供元はソニーネットワークコミュニケーションズです。

*製品の今。* 同社のサポートの頁は2026年3月23日に、Qrio Lock(Q-SL2)の販売を終えたこと、サービスとサポートを終える予定は無いことを告知しました。2026年4月21日には、Nature 社が Qrio Lock の設計と技術を使った Nature Lock を発表しましたが、Qrio Lock のアプリとは使えません。前の機種の Qrio Smart Lock(Q-SL1)は、2026年7月15日にアプリでの解錠ができなくなり、物理鍵に切り替えるよう案内されました。

*利用者の多い不満。*

* 近づくと開くハンズフリー解錠が働かない、遅い、という声が一番多くあります。
* 反対に、家にいるのに解錠された、寝ている間に開いた、という声があります。
* 2026年1月の更新の後に Apple Watch のアプリが落ちる、強制のログアウトの後に再ログインできず締め出された、合鍵の受け取りの案内がループする、消せない広告が出る、という声があります。
* 販売の終了の後、先行きを心配する声と、他社の製品に移るという声が増えています。

*会社の答え方。* Google Play のレビューへの返信は、ここ三年は見当たりませんでした。更新の説明は「安定性を向上しました」が中心です。一方、サポートの頁では、障害、提供の終了、必要な版を告知しています。2025年6月10日17時から翌朝7時30分ごろまでの障害では、遠隔の操作、ログイン、履歴、合鍵の発行が使えず、原因はクラウドの基盤の電力の障害としました。2026年2月の告知は、アプリには定期的な再ログインが要ること、古い版では錠と通信できず開けられなくなるおそれがあることを書き、物理鍵を持つよう勧めています。

*止まったとき。* サーバーの保守の告知で、手元にある鍵での Bluetooth の解錠は使えると説明しています。止まるのは、ログイン、遠隔の操作、履歴、鍵の発行です。

== 共通する課題

. *近くで開ける無線が不安定。* 六社のうち、利用者の多いアプリの不満の一番は、どれも Bluetooth でつながらない、遅い、勝手に開く、です。スマートフォンの機種や OS の更新で動きが変わり、KEYMO NEO のように OS の更新の後に開かなくなったという声も出ています。
. *クラウドとアカウントに頼る所が大きい。* ログインが切れる、再ログインを求められる、クラウドが止まると新しい鍵が届かない、という場面で締め出しが起きています。錠の本体に登録した暗証番号、カード、手元に持っている鍵は、止まっても使えると説明している会社(RemoteLOCK、Qrio)があります。説明の無い会社もあります。
. *アプリの寿命が錠より短い。* 錠は十年単位で扉に付いていますが、アプリは毎年の OS の更新に追われます。Qrio の前の機種はアプリでの解錠が終わって物理鍵に戻り、ビットキーは旧アプリの提供を終え、古い機種のスマートフォンの対応を順に切っています。美和ロックの KEYMO NEO は二年、ゴールの設定アプリの iOS 版は五年、更新がありません。
. *使う人がアプリを選べない。* 賃貸住宅の住む人、ジムの会員、会社で働く人は、管理する側が選んだアプリを使います。低い評価の多くはこの人たちのものです。合わないと思っても、他のアプリに替えられません。
. *直したことが伝わらない。* 開け閉めができなくなった不具合を直した版の説明が「軽微な不具合を修正しました」だった例があります。ストアのレビューに返信しない会社が多く、返信しても定型です。
. *止まったときの説明に差がある。* 障害の記録と、停電と通信の障害のときの動きを具体的に公開しているのは RemoteLOCK(構造計画研究所)で、Qrio もサポートの頁で障害と必要な版を告知しています。他の会社は、確かめた範囲では、止まったときに何が使えるかを書いていません。

== 層で見る

不満の多くは、錠そのものではなく、アプリとクラウドの層で起きています。錠の本体が持つ暗証番号やカードは、アプリやクラウドが止まっても使えています。スマートフォンを鍵にするなら、判定は錠の側が持ち、アプリやクラウドが止まっても、OS が変わっても、手元の鍵で開けられる作りが要ります。link:/guide/what-a-smart-door-needs/[スマートドアに求められる条件] の「ローカルで動作すること」と「認証手段を複数持つこと」は、この課題への答えです。スマートフォンの鍵を各社のアプリではなく端末のウォレットに置く link:/guide/aliro/[Aliro] は、アプリの寿命の課題を軽くする道の一つです。

= 業者に預けた鍵と権限

2026年10月の一週間に、業者に預けた鍵や権限から多くの顧客に被害が及ぶ件が、続けて公表されました。2025年にも同じ形の件があります。この記事では五つの件を同じ項目で並べ、共通する形を取り出し、扉の鍵に当てはめます。調べたのは2026年10月18日です。会社と団体が発表したことと、報道や分析で伝えられたことは分けて書きます。どの件も、調べた時点で調査が続いています。

== 見方

件を二つの型に分けます。

* *預かり型。* 業者が、多くの顧客の鍵や権限を預かって常に持っている形です。顧客は、連携の手間を省くために、業者のサービスに自分の環境へ入る権限や、他社のサービスの鍵を渡しています。
* *相乗り型。* 他人と同じ機械の上で、自分の仕組みを動かしている形です。クラウド、VPS、レンタルサーバーが当たります。

それぞれの件について、預けていた物、起きたこと、顧客の側で防げたか、業者がどう止めたかを見ます。

== 一覧

|===
| 件(時期) | 型と、預けていた物 | 起きたこと

| ConnectWise Cloud Backup(2026年10月) | 預かり型。Microsoft 365 のメール、OneDrive、SharePoint、Teams を読み書きできる、バックアップのアプリの権限 | 業者の側にあるアプリの認証情報で、多くの顧客のテナントにサインインされた
| OpenCode Console(2026年10月) | 預かり型。利用者が保存した、AI の事業者(OpenAI、Anthropic、Google など)の鍵 | 廃止の途中の古い仕組みへの不正なアクセスで、保存された鍵が漏れたおそれ
| CVE-2026-99999、PwnEscape(2026年10月) | 相乗り型。同じ機械の上の仮想マシン | 仮想マシンから、その機械(ホスト)のメモリを読み書きできる不具合
| Commvault Metallic(2025年5月) | 預かり型。Microsoft 365 のバックアップのアプリの秘密情報 | 顧客の環境に入るための秘密情報が盗まれた
| Salesloft Drift(2025年8月) | 預かり型。Salesforce につなぐ連携のトークン | 多くの会社の Salesforce のデータが持ち出された
|===

== 件ごとに見る

=== ConnectWise Cloud Backup(旧 SkyKick)

*発表。* ConnectWise は、Cloud Backup の環境で「アプリケーションの ID への不正なアクセス」を見つけたと発表しました。対策として、提携先と顧客の Cloud Backup のアプリのアクセスを止め、バックアップのサービスは再開の見通しが示されないまま止まりました(2026年10月17日。BleepingComputer の報道による)。バックアップのデータが見られた兆しは無いとしています。原因は公表していません。Microsoft は、活動中のサプライチェーン攻撃と判断しました。

*分析。* セキュリティ会社の Huntress の分析(2026年10月16日公開、17日更新)では、盗まれたのはバックアップのアプリの認証情報で、業者のテナントの中にありました。顧客の環境の中で何をしても防げない物です。不正なサインインは10月16日の時点で162のテナントで確かめられ、17日の更新では、約1,000のテナントで試みがあり、300を超えて成功しています。一つのテナントでは、別の ConnectWise のアプリが自分に全体管理者の権限を与え、他のアプリに秘密の鍵を足していました。データが持ち出されたかは確定していません。

=== OpenCode Console

*発表。* AI のコーディングの道具を提供する OpenCode は、2026年10月17日に自社の X のアカウントで、前夜にセキュリティの侵害があったと公表しました。大規模な蒸留攻撃に関連し、コンソールの利用者の1.4%に影響があり、メールを受け取っていない人は影響を受けていない、としています。Anthropic、OpenAI、Google と協力して対応していて、調査が続いているため詳細は出せないとしています。

*利用者へのメール(報道による)。* 廃止の途中だった古い仕組みへの不正なアクセスを見つけ、作業場所に保存された外部の事業者の鍵(OpenAI、Anthropic など)が漏れたおそれがあるとして、鍵を取り消して作り直すよう求めています(OfficeChai、DEV Community、2026年10月17日〜18日)。

*報道。* 利用者が、身に覚えの無い利用の請求を受けたという声が伝えられています(Crypto Briefing、2026年10月17日)。金額は利用者の報告で、確かめられていません。蒸留攻撃は、一般に、他人のモデルを大量に呼び出し、その答えで別のモデルを育てる使い方を指します。盗んだ鍵がそう使われたのかを、OpenCode は説明していません。鍵がどう保存されていたかも公表されていません。

=== CVE-2026-99999(PwnEscape)

*発表。* Linux カーネルの IPv4 の処理の不具合で、CVE の記録は2026年10月15日に公開されました。Red Hat と Linux のカーネルの CVE チームは Critical としています。

*研究者の説明。* 仮想マシンが細工したパケットを送ると、ホストのカーネルのメモリを読み、書き換えられます。研究者は、自分の KVM の実験環境で、ホストの root での実行まで示しました。各社の本番の環境で root を取ったとは主張していません。

*告知。* AlmaLinux の告知(2026年10月16日)は、最も危ないのは他人の仮想マシンを動かす機械、つまりクラウド、VPS の事業者、コードを動かすサンドボックスだとしています。Vercel が本番のサンドボックスでメモリの漏れを示し、他の事業者に知らせたとも書いています。回避の手段は無く、直したカーネルに替えるしかありません。ホストの再起動は、その上の全部の仮想マシンを止めます。

=== Commvault Metallic

*発表。* 米国の CISA は2025年5月22日に、Commvault の Microsoft 365 のバックアップのサービス(Metallic、Azure の上で動く)の秘密情報が盗まれたおそれがあると警告しました。既定の設定と強い権限を持つ SaaS を狙う、より広い攻撃の一部と見ています。Commvault は、影響を受けたのは少数の顧客で、バックアップのデータは見られておらず、該当の顧客の秘密情報を作り直したとしています(The Record、2025年5月23日)。

=== Salesloft Drift

*分析。* Google の脅威情報の部門と Mandiant は、2025年8月8日から18日に、Salesloft のチャットの道具 Drift が Salesforce につなぐためのトークンが盗まれ、多くの会社の Salesforce からデータが持ち出されたと公表しました。攻撃者は、データの中から AWS の鍵やパスワードなどの秘密を探していました。Salesloft は8月20日に、Drift と Salesforce の連携を全部切りました(Security Affairs、2025年8月28日)。

== 共通する形

. *預けた物が一か所に集まる。* 一社が、多くの顧客の環境に入る権限や、他社の鍵をまとめて持っています。そこを一度破れば、全部の顧客に届きます。
. *顧客の側では防げない。* ConnectWise の認証情報は業者のテナントにあり、OpenCode の鍵は業者のサービスに保存され、PwnEscape を直せるのは機械を持つ事業者です。顧客にできるのは、知らされた後の対応だけです。
. *止める手段が大きい。* 業者はサービスごと止める(ConnectWise のバックアップの停止)か、全員に鍵の作り直しを頼みます(OpenCode、Commvault)。相乗り型では、直すための再起動で全部の仮想マシンが止まります。
. *預けた権限は、用途より広い。* バックアップのためにメールの全部を読む権限を、連携のために顧客の記録を読むトークンを、便利さのために請求の起きる鍵を、業者に渡しています。

== 扉に当てはめると

* *クラウド型のスマートロックは、預かり型そのもの。* 業者のクラウドが、全部の顧客の扉に鍵を出し、遠隔で開ける権限を常に持っています(link:/guide/japanese-smart-lock-apps/[日本のスマートロックのアプリの現状と課題])。業者が破られると、メールや請求ではなく、多くの建物の扉が開きえます。業者が被害を止めるためにサービスを止めれば、アプリで開ける扉が全部止まります。
* *判定が扉の中で完結しても、発行者の鍵が一か所に集まれば同じ。* link:/guide/aliro/[Aliro] のように、スマートフォンと読取機だけで判定する方式でも、鍵を作る発行者の秘密鍵を一つの業者が全顧客の分まとめて持てば、その鍵一つで全部の扉の鍵が作れます。
* *鍵の台帳を共有の機械に置くと、相乗り型の危険を負う。* 発行者の秘密鍵や鍵の台帳を VPS やレンタルサーバーに置くと、隣の仮想マシンから抜かれうる不具合の影響を受けます。
* *分譲マンションでは、住戸の錠の鍵を出すのは区分所有者。* 法律上の持ち主と、鍵を出す実際の力を持つ業者がずれると、預かり型の危険が住戸にまで及びます。

== このサイトの要求仕様

この形を避けるため、要求仕様に次を書いています(2026年10月18日に追加)。

|===
| 番号 | 要求 | 対応する形

| R-AC-09 | 一つの発行者の鍵が届く扉は、その発行者が管理する扉に限る。業者が多くの顧客の発行を引き受けても、顧客ごとに別の鍵にする | 一か所に集まる
| R-AC-10 | 業者と連携先に、扉を開ける常の権限を持たせない。遠隔の解錠は一回ごとに、発行者の一時の資格情報を錠が自分で確かめる。業者のサービスが止まっても、登録済みの資格情報で開く | 一か所に集まる、止める手段が大きい
| R-AC-11 | 発行者の秘密鍵は取り出せない場所に置き、他人と同じ機械を共有する環境に置かない | 相乗り型
| R-AC-12 | 錠と読取機が信頼する発行者の変更は、管理者の認証済みの操作だけで行い、記録に残す | 顧客の側で防げない
| R-AP-38、R-AP-39 | 住戸の錠の発行者は区分所有者とし、管理会社と管理組合の発行者の鍵では住戸の錠を開けられない | 一か所に集まる
|===

扉のコントローラの側では、発行者が署名した資格情報を、扉が網も発行者のサーバーも使わずに自分で確かめる形を、link:/guide/open-specification/[扉コントローラ仕様書] の 5.2a に書きました。仕様を確かめる疑似の扉(digitaldoor-controller)で、この形の試験が通っています。

== 使う人ができること

* 業者に預けている鍵と権限を一覧にします。どの業者に、何への、どれだけの権限を渡しているかです。
* 渡す権限を用途に要る分だけにし、期限を付けられる物は付けます。
* 業者が止まったとき、止めたときにも使える手段を手元に残します。扉なら、錠に登録した暗証番号、カード、物理鍵です。
* 預けた鍵を作り直す手順を、事前に決めておきます。
* 秘密鍵を、他人と共有する機械に置きません。

= 自分で持つべき人と物

デジタルの扉は、売ったら終わりの物ではありません。鍵の発行と失効、更新、脆弱性への対応を、扉が付いている何十年もの間、続けます。この仕事を業者に預け切ると、link:/guide/vendor-held-keys/[業者に預けた鍵と権限] で見た「預かり型」の危険を、自分の扉で抱えることになります。この記事では、扉を作る製造者と、扉を使う運営者(民泊、貸家、事業所)が、自分で持つべき人と物を整理します。

== なぜ自分で持つのか

* *売って終わりではない。* 錠は十年単位で扉に付いていますが、スマートフォンの OS と暗号は毎年変わります。更新を出し続ける人がいなければ、link:/guide/japanese-smart-lock-apps/[日本のスマートロックのアプリ] で見たように、アプリが錠より先に使えなくなります。
* *預けた所は、顧客の側で防げない。* 業者が持つ鍵や権限が破られると、顧客は知らされた後に対応するしかありません。
* *法が求め始めた。* EU のサイバーレジリエンス法(規則 2024/2847)は、製造者に、利用者が脆弱性を知らせる一つの窓口を設けることを求め、悪用されている脆弱性を知ったら24時間以内に早期の届け出をする義務を、2026年9月11日から適用しています。全体の適用は2027年12月11日からです。英国の PSTI 法は2024年4月29日から、脆弱性の連絡先と、更新を出す期間の公開を求めています。

== 扉の製造者が手放せない役

コードを全部自分で書く必要はありません。外の会社や AI に作らせてよい所はあります。ただ、次の役は社内に置きます。

|===
| 役 | すること | 手放せない理由

| 仕様とテストを読める人 | 外の会社や AI が作った物が、仕様のどの要求を満たしているかを、テストで確かめる | 確かめられないと、作った物を信じるしかなくなる
| 鍵の持ち主 | 発行者の鍵、更新の署名の鍵、記録の署名の鍵を、どこに置き、誰が触れ、どう作り直すかを決める | 鍵を業者が持てば、業者が扉の持ち主になる
| 脆弱性の窓口 | 研究者や利用者からの報告を受け、直す期間を決め、公表し、法の求める届け出をする | 報告の先が無ければ、弱点は直されないまま広まる
| 更新を出し続ける人 | 扉が付いている間、OS と暗号の変化に合わせて、更新を作り、試し、署名して出す | 更新が止まると、扉が物理鍵に戻るか、弱いまま残る
| 預けている物の目録係 | どの業者に、どの権限と鍵を渡しているかを一覧で持ち、漏れたときに作り直す順番を決める | 一覧が無ければ、何を作り直せばよいかが分からない
|===

== 運営者が自分で持つ物

民泊や貸家の運営者は、技術者でなくてよいです。ただ、次は人に預けず、自分で持ちます。

* *鍵を出す判断と、取り消す判断。* 誰に、いつからいつまで出すかを決めるのは運営者です。発行の作業は仕組みと AI に任せられます。
* *記録を手元に。* 誰がいつ出入りしたかの記録を、業者のクラウドではなく手元に置き、問題が起きたときに自分で読めること。
* *業者が止まったときの手段。* 錠に登録した暗証番号、カード、物理鍵の置き場と、客への伝え方。
* *預けている物の一覧と、作り直す手順。* 予約サイト、錠の業者、清掃の業者に何を渡しているかと、漏れたときに鍵を作り直す順番。

== AI に任せられる所と、人がする所

|===
| 仕事 | AI に任せられる所 | 人がする所

| 実装とテスト | 仕様からテストを書き、別のセッションで実装し、わざと壊して確かめる | どの要求を満たすか。テストが仕様に合っているか
| 鍵の発行 | 予約に合わせて出し、期限で切る | 誰に出すか。例外を認めるか
| 記録 | 読み、いつもと違う出入りを拾う | 拾った件にどう対応するか
| 脆弱性の報告 | 受け付け、仕分け、原因の候補と直し方の案を出す | 直す期間、公表の時期、届け出
| 更新 | 作り、試験を回し、影響をまとめる | 出すかどうか。署名するのは人
| 据付と試験 | 手順書と確かめる項目の案を作る | 現場で置き、つなぎ、火災と停電の挙動を実機で確かめる
| 攻撃と事故 | 記録を読み、原因と手当ての案を出す | 現場で線を抜き、区画を止め、予備に入れ替えて戻す
|===

AI は休まずに読み、作り、確かめます。少人数でも続けられるのはそのためです。ただ、署名する手と、決める頭と、現場で物に触れる手は、人の側に残します。人が決めた記録が残ることが、後で説明できる理由になります。網が止まった建物で頼れるのは、その場にいる人です(link:/guide/on-site/[人に残るのは現場])。

== 機械の置き方

鍵と記録を置く機械も、自分で持つ物です。

* *サーバーを借りない。* クラウドの仮想マシン、VPS、レンタルサーバーは、他人と同じ機械の上で動きます。2026年10月に公開された CVE-2026-99999 のように、隣の仮想マシンから機械ごと乗っ取れる不具合が出ると、直すのは事業者で、借りた側は待つしかありません。
* *自社でも、性質の違う物を同居させない。* 危ないのは仮想化そのものより、外の網に向いたウェブや予約の連携と、鍵の発行者の秘密鍵や扉の判断を、同じ機械や同じ仮想化の基盤に置くことです。外から破られた所から、鍵まで届きます。
* *役割ごとに小さな機械に分け、台数を増やす。* 扉ごとのコントローラ、建物ごとのミニサーバー、鍵はセキュアエレメントに分ければ、一台が破られても止まっても、ほかの扉は動き続けます。
* *台数を増やす代わりに、要る物がある。* 同じ形の予備の機械を置き、イメージから一つの手順で元に戻せるようにし、更新を全部の機械に回す仕組みを持ちます。誰がやっても同じ手順で戻せることが、台数を増やしても続けられる条件です。

== 育て方

学ぶ物の重みが変わりました。コードを書くことは、AI が担えるようになったので、深く学ばなくてもかまいません。代わりに、セキュリティを学び、仕組みを実際に動かせることが要ります。知識として知っているだけでは、鍵が漏れた夜や、業者が止まった朝に、手が動きません。

|===
| 学ぶ物 | どこまで | 理由

| コードを書くこと | 浅くてよい。AI に書かせ、テストで確かめる | 書く手間は AI が担う
| テストを読むこと | 深く。何を、どの入力で、何を期待して確かめているかを言える | AI の出した物を確かめる唯一の手段
| セキュリティ | 深く。鍵と署名、権限の範囲、更新、脆弱性の扱い、攻撃の手口 | 何を守り、何を預けてはいけないかを決めるのは人
| 実際に動かすこと | 手で。下の訓練を、自分の手で一通り行える | 事故の時に、手順書を初めて読むのでは間に合わない
|===

動かせることを確かめる訓練は、次のとおりです。

* *疑似の扉を自分で動かす。* 疑似の扉(digitaldoor-controller)を起動し、署名つき資格情報を出して開け、期限で切れるのを見て、記録を伝票として出し、公開鍵で検べる。テストを読み、実装をわざと壊して、テストが落ちるのを見る。
* *鍵を作り直す。* 年に一度、預けている鍵の一つを実際に作り直し、手順どおりに戻ることを確かめる。
* *予備の機械に戻す。* 予備の機械に、イメージから一つの手順で戻し、扉の判断と記録が続くことを確かめる。
* *止まったときに開ける。* 錠の業者のサービスが止まった想定で、暗証番号やカードで開くことを、客を迎える前に確かめる。
* *記録から見つける。* 記録を読み、いつもと違う出入りや、知らない発行者からの資格情報の拒否を見つける。AI が拾った件を、自分で確かめて判断する。
* *報告から知らせるまでを通す。* 脆弱性の報告を受けた想定で、直す期間を決め、利用者に知らせ、届け出るまでを、期限の内に通す。

このサイトの仕様と、開発用のスキル、疑似の扉は、そのまま教材になります。

= AI の時代に、委託をやめて自社で育てる

結論を先に書きます。一般の会社は、自社の鍵と判断を委託先に預けるのをやめ、自社で持てる人を育てるしかありません。そして今は、AI があるので、それが自社でできます。この記事では、その理由を一つずつ順に説明します。

== 論の筋

=== 1. AI は、攻撃の手間を減らす

攻撃には、下調べ、弱点の探索、侵入、内部での移動、情報の持ち出しという手間がかかります。これまでは人が一つずつ行っていました。

Anthropic は、2025年9月中旬に、国家が背後にいるとみられる集団が、同社の AI(Claude Code)を使って約30の組織を狙った攻撃を検知し、止めたと報告しています。報告書によれば、作戦の実行の80〜90%を AI が自分で行い、人には不可能な速さ(一秒に何回もの要求)で動いていました。人が決めたのは、狙う先と要所の判断だけでした。侵入に成功したのは数件でした。

手間が減れば、同じ人数で、より多く、より速く攻撃できます。攻撃は、数も速さも増える方向にあります。

=== 2. 狙われるのは、一度で多く取れる所

攻撃が安くなると、攻める側は、一度で多く取れる所を選びます。それは、多くの顧客の鍵と権限を預かっている委託先です。

link:/guide/vendor-held-keys/[業者に預けた鍵と権限] で見たとおり、2025年から2026年に、この形の件が続きました。

* ConnectWise Cloud Backup(2026年10月)では、バックアップの業者の一つの認証情報から、300を超える顧客の Microsoft 365 にサインインされました(Huntress の分析)。
* OpenCode Console(2026年10月)では、利用者が預けた AI の事業者の鍵が漏れたおそれがあり、同社は「大規模な蒸留攻撃」に関連すると説明しました。AI を動かすための鍵そのものが、狙う価値のある物になっています。
* Commvault(2025年5月)と Salesloft Drift(2025年8月)でも、業者が預かっていた秘密情報やトークンから、多くの顧客に届きました。

=== 3. 預けた側は、防げない

委託先が破られたとき、預けた側にできることはほとんどありません。ConnectWise の件では、盗まれた認証情報は業者の環境の中にあり、顧客の環境で何をしても防げませんでした。顧客にできたのは、知らされた後に権限を止め、鍵を作り直すことだけでした。業者は被害を止めるためにサービスごと止め、顧客はバックアップを失いました。

=== 4. まとめて守る、という委託の前提が崩れる

委託の利点は、「専門家がまとめて守るほうが、各社が自分で守るより強く、安い」ことでした。

しかし、まとめるほど、一度に取れる量が増え、狙う価値が上がります。攻撃が安くなるほど、強い攻撃者がそこに集まります。業者がどれほど強くても、破られたときの被害は全部の顧客に及びます。まとめて守ることが、まとめて失うことに変わります。AI で攻撃の手間が減るほど、この逆の効果は強くなります。

=== 5. AI は、守る側の手間も減らす

それでも多くの会社が委託してきたのは、自社で持つには人と手間がかかりすぎたからです。

AI は、守る側の手間も同じように減らします。仕様を読み、テストを書き、実装し、わざと壊して確かめる。記録を読み、いつもと違う動きを拾う。脆弱性の報告を受け付け、仕分け、直し方の案を出す。更新を作り、試す。これらを AI が休まずに行えます。少人数の会社でも、自社で持てるようになりました。委託する理由だった「手間」が、AI によって小さくなったのです。

=== 6. ただし、AI に任せ切らない

AI に全部を任せると、委託先を AI に替えただけになります。AI も間違えます。先の Anthropic の報告書でも、攻撃に使われた AI は、見つけた物を大きく言ったり、無い物を作り出したりしていました。守る側の AI も同じです。

だから、AI の出した物を確かめて決める人が、自社に要ります。コードを書けなくても、テストを読んで「何を、どの入力で、何を期待して確かめているか」を言え、わざと壊して落ちるかを確かめられる人です。署名する手と、決める頭と、現場で物に触れる手は、人の側に残します。この人を、自社で育てます。育てるときに重みを置くのは、コードを書く力ではありません。セキュリティを学び、鍵を作り直す、予備の機械に戻す、止まったときに開ける、といった仕組みを、自分の手で実際に動かせることです(link:/guide/people-and-keys-to-keep/[自分で持つべき人と物] の「育て方」)。

=== 7. 結論:自社で持つ範囲と、任せてよい範囲

|===
| 区分 | 中身 | 理由

| 自社で持つ | 鍵(発行者の鍵、署名の鍵)、誰に何を許すかの判断、記録、脆弱性の窓口、止まったときの手段、現場で置き、確かめ、止め、戻す人 | 預ければ、業者が持ち主になり、破られたときに防げない
| AI に任せる | 実装、テスト、記録を読むこと、報告の仕分け、更新の準備 | 手間がかかるが、確かめられる形で出せる
| 外に頼んでよい | 部品、機械、決まった作業、一時的な専門家の助け | 鍵と常の権限を渡さなければ、破られても全顧客には届かない
|===

委託を全部やめるのではありません。やめるのは、鍵と判断を預け切ることです。

== 防御は集中できない。共有する

ここまでの話をまとめると、防御は一か所に集められない、ということになります。

* *鍵と常の権限は集められない。* 集めた所が一番狙う価値のある所になり、破られれば全員が一度に失います。
* *その場の判断は集められない。* 遠くの一か所が扉を開けるかを決めると、そこが止まれば全部が止まり、乗っ取られれば全部が開きます。
* *責任は集められない。* 預けた側は、破られた後に対応するしかありません。

ただし、分散するだけでは足りません。AI は、一か所を破る手間だけでなく、多くの小さな相手を一つずつ破る手間も減らします。これまで小さな会社は「狙われにくさ」で守られていましたが、攻撃を大量にまわせるようになると、その守りは消えます。初期のパスワードのまま、更新が止まったまま、という弱い所が、まとめて刈り取られます。分散した一つひとつが最低限の強さを自分で持っていないと、分散は「弱い所がたくさんある」だけになります。

だから、集めずに、共有します。

|===
| 一か所に集めない物 | みんなで共有する物 | 扉では

| 鍵、署名の鍵 | 何を満たすべきかの仕様 | 要求仕様と扉コントローラ仕様書
| 常の権限(遠隔で開ける力) | 満たしているかの確かめ方 | 試験の対と、疑似の扉
| その場の判断 | 脆弱性の情報と直し方 | 製造者の窓口と更新(R-RS-01、02)
| 記録の持ち主 | 攻撃の手口の情報 | 業者に預けた鍵と権限の件の整理
|===

扉の言葉にすると、町の全部の扉を開ける合鍵は作らない、けれども、良い錠の作り方と確かめ方は全員に配る、ということです。

避けられない集中もあります。OS、半導体、スマートフォンのウォレットは、少数の会社に集まっています。この場合の線引きは、作ることと配ることは集まってもよいが、動いているときに扉を開ける権限は持たせない、です。link:/guide/aliro/[Aliro] が判定を読取機の中で完結させているのは、この線に沿っています。

== 委託の代わりは AI。本来の仕事が戻ってきただけ

委託していたのは、作業だけではありませんでした。鍵を持つこと、誰に何を許すかを決めること、記録を読むこと、脆弱性に答えることといった、本来は自分で持つべき物まで、作業と一緒に預けていました。人と手間が足りなかったからです。

AI が作業を引き受けるようになり、預ける理由が無くなりました。新しい仕事が増えたのではありません。元からあった仕事を、元の持ち主がやるようになっただけです。

ただし、委託の代わりの AI そのものを、新しい委託先にしてはいけません。link:/guide/vendor-held-keys/[業者に預けた鍵と権限] の OpenCode の件は、AI の道具のサービスが利用者の鍵を預かっていて漏れた件でした。AI にはコードとテストと記録を扱わせ、鍵と権限は渡しません。秘密は手元とセキュアエレメントに置きます。ここを守らないと、業者に預けていた物を、AI の業者に預け替えるだけになります。

IT の仕事の側がどう変わるか(委託のモデルが成り立たなくなる理由、各社が自分で作り動かす人を雇う時代、AI に任せる範囲の決め方)は、aiseed.dev の連載 https://aiseed.dev/ai-native-software/[AI ネイティブなソフトウェア開発] に書いています。特に https://aiseed.dev/ai-native-software/sier-uneconomic/[SIer 委託モデルの構造的不経済]、https://aiseed.dev/ai-native-software/hiring-builders/[各社がビルダーを雇用する時代]、https://aiseed.dev/ai-native-software/ai-delegation/[AI に任せる範囲を決める] が、この記事と対になります。

== よくある反論と答え

|===
| 反論 | 答え | 根拠

| 中小の会社には人がいない | 自社で持つ範囲を、鍵、判断、記録、窓口に絞る。作業は AI が担う。一人から始められる | 5、7
| 専門の業者の方が強い | 強い業者も破られた。問題は強さではなく、多くの顧客が一か所に集まること | 2、4
| 全部を自前にするのは非効率 | 自前にするのは持ち主の役だけ。作業は AI と部品に任せる | 7
| AI そのものが危ない | 鍵は人とセキュアエレメントが持ち、AI の出した物はテストで確かめてから使う | 6
|===

== 何から始めるか

. *預けている物の一覧を作る。* どの業者に、何への、どれだけの権限と鍵を渡しているか。
. *鍵の持ち主を決める。* 鍵ごとに、置き場、触れる人、作り直す手順を決める。
. *止まったときの手段を持つ。* 業者が止まっても、自分で開けられる、動かせる手段。
. *確かめる人を一人育てる。* AI と一緒に、仕様を読み、テストを読み、壊して確かめる練習をする。
. *機械を借りず、分ける。* 鍵と判断を、他人や外向きのサービスと同じ機械に置かない。

扉については、link:/guide/people-and-keys-to-keep/[自分で持つべき人と物] に、製造者と運営者が持つべき役と物、機械の置き方、育て方を書いています。要求仕様では、R-RS-01〜06(自分で持つべき人と物)、R-AC-09〜13(鍵の範囲、常の権限、置き場所、機械の分け方)にあたります。

= 植物の守り方に学ぶ

link:/guide/ai-and-in-house/[AI の時代に、委託をやめて自社で育てる] で、防御は一か所に集められない、集めずに共有する、と書きました。この形は、植物がずっと前から行っている守り方とよく似ています。この記事では、植物の守り方を研究の総説で確かめ、扉と情報システムの守りに当てはめます。例えは例えなので、似ていない所も書きます。

== 植物には、守りの司令塔が無い

動物の多くは、体をめぐって敵を探す免疫の細胞と、出会った敵を覚える仕組み(獲得免疫)を持っています。植物は、どちらも持っていません。植物の病気の総説は、植物は動きまわる守りの細胞も獲得免疫も持たず、前もって備えた壁と、局所と全身の信号で調整される細胞の反応で守る、と説明しています(Guest、2012年)。別の総説は、植物は専門の免疫の細胞を持たず、どの細胞も自分で有効な免疫の反応を起こせると考えられている、としています(Spoel と Dong、2012年)。

細胞ごとの免疫は二段になっています。一段目は、多くの微生物に共通する印を見分けて反応します。二段目は、病原体が持ち込む、病気を起こすための物質に反応します(Jones と Dangl、2006年)。

扉の言葉にすると、判断を遠くのサーバーに預けず、扉のコントローラが一つひとつ自分で判断する形です。

== 対応表

|===
| 植物の守り | 中身 | 扉とシステムでは

| 細胞ごとの免疫 | どの細胞も、自分で敵を見分けて反応する | 各扉が自分で判断する。判断を一か所に集めない(R-AC-10)
| 前もって備えた壁 | 表面と細胞の壁で、入られる前に防ぐ | 初期のパスワードを持たない、外に向いた口を絞る
| 過敏感反応 | 感染した所の細胞が自ら死に、病原体を閉じ込める | 役割ごとに小さな機械に分け、破られた所で止める(R-AC-13)
| 全身獲得抵抗性 | 一か所が攻撃されると、信号が全身に伝わり、他の部分が備える | 鍵は渡さず、攻撃の知らせだけを社内で伝える
| 隣の植物への警報 | 食べられた植物が出す揮発性の物質で、隣の植物が守りを固める | 脆弱性と手口の情報を、会社をまたいで共有する(R-RS-01、02)
|===

== 一つずつ見る

=== 破られた所で止める(過敏感反応)

病原体を見分けた細胞は、その場で自ら死に、病原体が広がるのを止めます。これを過敏感反応と呼びます(Gao ほか、2015年)。全体を守るために、破られた一部を切り離す動きです。

システムでは、役割ごとに小さな機械に分けておけば、破られた一台を切り離しても、ほかの扉は動き続けます。一つの大きな機械に全部を載せていると、切り離す所がありません。

=== 鍵は渡さず、知らせだけを伝える(全身獲得抵抗性)

一か所が攻撃されると、その知らせが師管を通って、まだ感染していない遠くの葉に伝わり、植物全体が長い間、広い種類の病原体に強くなります。これを全身獲得抵抗性と呼び、サリチル酸という物質が中心の役を担います(Gao ほか、2015年)。

伝わるのは「攻撃が来た」という知らせで、守りの力そのものを一か所から配っているわけではありません。どの部分も、知らせを受けて自分で備えます。システムでも、共有するのは攻撃の手口と脆弱性の情報で、鍵や権限ではありません。

=== 会社をまたいで知らせる(隣の植物への警報)

虫に食べられた木が空気中に物質を出し、近くの木が守りの物質を作り始める、という報告が1983年に出ました。初めの研究は統計や実験の作りを批判されましたが、その後、実験室と野外で繰り返し確かめられてきました(Quanta Magazine、2013年)。食べられた植物が隣に知らせようとしているのか、隣が勝手に聞き取っているのかは、まだ分かっていません。

システムでは、脆弱性の窓口と公表、攻撃の手口の共有がこれにあたります。

== 単一栽培の弱さ

植物の守りで一番大事な教えは、個体の守りより、集団の多様さにあります。

輸出用のバナナは、かつてグロスミシェルという品種でした。パナマ病と呼ばれる土の中の病気がこの品種を襲い、各地の輸出用の農園の生産が成り立たなくなりました。病気に強いキャベンディッシュの品種群が見つかり、輸出の取引はこれに置き換わりました。ところが、キャベンディッシュの品種群も互いに近い株の集まりで、遺伝的な幅は狭いままです。今は、キャベンディッシュを枯らす新しい型の病原体(TR4)が、東半球で大きく広がっています。同じ総説は、いろいろな品種を他の作物と混ぜて植える畑では被害はほどほどで済むが、弱い品種だけの単一栽培はたいてい壊滅する、と書いています(Ploetz、2015年)。

全員が同じ業者に鍵を預け、同じクラウドで同じ製品を動かす状態は、単一栽培と同じ形です。一つの破れ目が、全部に届きます(link:/guide/vendor-held-keys/[業者に預けた鍵と権限])。公開の仕様に沿って、各社が別々に実装し、各自が自分で鍵を持つことは、畑に多様な品種を植えることにあたります。

== 似ていない所

* *植物は、意図して共有しない。* 植物の信号は、自分の体の中か、たまたま近くにいる個体に届くだけです。人の社会で情報を共有するには、窓口、公開の仕様、試験の対といった仕組みを、意図して作る必要があります。このサイトが置いている物は、植物なら自然に持っている仕組みを、人の側で作っている物です。
* *扉は、自分を犠牲にしてはいけない。* 植物の細胞は全体のために自ら死にますが、扉は、破られたときにも人を閉じ込めてはいけません。火災と停電のときの挙動と、内側から機械的に開ける手段は、どの切り離しよりも先に守ります(扉コントローラ仕様書 第3章)。
* *植物の守りは、長い時間をかけて選ばれてきた物。* 情報システムでは、その時間がありません。仕様を書き、試験で確かめ、足りない物を仕様に戻す、という手順で、短い時間で同じことを行います。

== まとめ

植物から取り出せる守りの形は、五つです。

. 司令塔を持たない。どの部分も自分で守る。
. 入られる前の壁を、前もって備える。
. 破られた所で止める。全部を一か所に載せない。
. 鍵ではなく、知らせを伝える。
. 同じ物ばかりを植えない。

= ルーターは全部の前にある

扉の判断を扉に置き、機械を役割ごとに分けても、その全部の前に、一台のルーターがあります。扉のコントローラ、ミニサーバー、読取機、カメラ、事業所のサーバーは、どれもルーターを通って外とつながります。ルーターが乗っ取られると、通信は覗かれ、書き換えられ、外への攻撃の足場にされます。この記事では、ルーターの何が問題かを、公的な機関の発表で確かめて整理し、扉の側で求めることを示します。調べたのは2026年10月18日です。

== 何が起きてきたか

|===
| 件 | 発表した所 | 起きたこと

| KV ボットネット(2024年1月) | 米国の司法省 | 国家が背後にいるとされる集団が、米国の家庭と小さな事業所の数百台のルーターを乗っ取り、重要インフラへの攻撃の出どころを隠す中継に使っていた。多くは更新の止まった機種だった
| 中継のための乗っ取り(2025年5月) | 米国の FBI | 犯罪者が、更新の止まったルーターにマルウェアを入れ、犯罪の出どころを隠す中継として売っていた。遠隔の管理が有効な機種が狙われた
| 家庭用ルーターの不正な利用(2023年3月) | 警視庁 | 一般家庭のルーターが外から操作され、VPN などの機能を有効にされて、サイバー攻撃に使われていた。一度設定を変えられると、従来の対策だけでは元に戻らない
| 事業者の遠隔の管理の口(2016年11月) | 報道 | ドイツの通信事業者のルーター約90万台が、事業者が遠隔で設定と更新を行うための口を狙われ、つながらなくなった
|===

=== KV ボットネット

米国の司法省は、2023年12月に裁判所の許可を得て行った作戦で、米国の家庭と小さな事業所の数百台のルーターから構成されたボットネットを止めたと発表しました(2024年1月31日)。国家が背後にいるとされる集団(民間では Volt Typhoon と呼ばれる)が、このルーターを中継にして、重要インフラへの攻撃の出どころを隠していました。ルーターの多くは、メーカーの更新が止まった Cisco と NETGEAR の機種でした。作戦によるマルウェアの除去は一時的な物で、持ち主が再起動すると元に戻ります。FBI は、更新の止まったルーターを替えるよう勧めています。

=== 中継のための乗っ取り

FBI は2025年5月7日に、更新の止まったルーター(メーカーが売るのも支えるのもやめた機種)が、TheMoon というマルウェアの系統で乗っ取られ、犯罪の出どころを隠す中継として使われていると注意を出しました。新しい型は、遠隔の管理が有効なルーターで見つかっています。2010年以前のルーターは、更新を受けていない可能性が高いとしています。勧めているのは、替えること、更新を全部当てること、遠隔の管理を切って再起動すること、長いパスワードにすることです。

=== 家庭用ルーターの不正な利用

警視庁は2023年3月に、捜査の中で、一般家庭のルーターがサイバー攻撃に悪用されていることが分かったと注意を出しました。攻撃者は外からルーターを操作して機能を有効にし、一度設定を変えると、従来の対策だけでは不正な状態が解けず、使われ続けるおそれがあるとしています。従来の対策(初期のパスワードを変える、ファームウェアを最新にする、サポートの終わったルーターは替える)に加えて、見覚えのない VPN、DDNS、外からの管理画面の接続の設定や、VPN の見覚えのないアカウントが無いかを、定期的に確かめるよう求めています。

=== 事業者の遠隔の管理の口

2016年11月、ドイツの通信事業者 Deutsche Telekom の利用者約90万人の回線がつながらなくなりました。報道によれば、Mirai という乗っ取りのマルウェアの一種が、通信事業者がルーターの設定と更新を遠隔で行うための口(TR-069)を狙っていました。回線の事業者が貸すルーターに入っている遠隔の管理の仕組みは、事業者が全部の利用者のルーターに常の権限を持つ形で、link:/guide/vendor-held-keys/[業者に預けた鍵と権限] の預かり型と同じ構造です。

== 日本の決まり

日本では、端末設備等規則に IoT の機器のセキュリティの基準(第34条の10)が新しく設けられ、2020年4月から、インターネットにつながる機器の認証の対象になりました。設定を変えるためのアクセス制御の機能、初めに決められたパスワードの変更を促す機能、ソフトウェアを更新する機能、電源が切れても設定と更新を保つ機能を求めています(総務省の資料)。ただし、決まりは新しく認証を受ける機器に掛かる物で、すでに家や事業所にある古いルーターには届きません。

== ルーターの何が問題か

. *全部の前にある。* 扉、サーバー、カメラを分けても、ルーターは一台で全部の前にいます。ルーターを取られると、その後ろの全部の通信が通り道で見られます。
. *寿命が短く、終わっても使われ続ける。* ルーターの更新の期間は、扉より短いのが普通です。メーカーが支えるのをやめても、つながっている限り使われ続け、誰も替えません。
. *外からの口が開いていることがある。* 遠隔の管理、VPN、DDNS、外からの管理画面が有効だと、外から直接操作されます。警視庁の注意のとおり、勝手に有効にされることもあります。
. *回線の事業者が常の権限を持つことがある。* 貸し出されるルーターの遠隔の管理の仕組みは、事業者の側が破られると、全部の利用者のルーターに届きます。
. *持ち主がいない。* 家では誰の物でもなく、集合住宅では管理組合か管理会社か回線の事業者かがはっきりせず、事業所では「つながっているから触らない」物になりがちです。更新と確認をする人が決まっていません。

== 扉の側で求めること

ルーターを強くすることと、ルーターを信用しない作りにすることの、両方が要ります。

* *ルーターを信用しない。* 扉の系統の通信は、ルーターが乗っ取られても読まれず書き換えられないよう、端から端まで暗号化し、相手を確かめます。ルーターが止まっても、扉の判断と記録は扉の側で続きます。
* *扉の系統を、ほかの機器と網の上で分ける。* 錠、扉のコントローラ、ミニサーバー、読取機を、来客用の Wi-Fi、家電、ほかのカメラとは別の区画に置き、外から扉の系統へ直接入る口を開けません。
* *更新の期間を確かめて選び、終わる前に替える。* ルーターも、扉と同じく、更新を出す期間を公開している物を選びます。
* *外からの口は、使うときだけ。* 遠隔の管理、VPN、DDNS、外からの管理画面、回線の事業者の遠隔の設定は、要るときだけ有効にし、見覚えのない設定が無いかを点検のたびに確かめます。
* *持ち主を決める。* 誰がルーターの更新と確認と交換をするかを決めます。集合住宅では管理組合が決め、点検の項目に入れます。

要求仕様には、共通コアに R-NW-01〜05(ルーターと網)、集合住宅に R-AP-40(ルーターの持ち主と点検)を書きました。

= 人に残るのは現場

AI の時代に人に残るのは、何を作るかを決めることと、出来た物が正しいかを見て判断すること。そう言われてきましたし、このサイトの link:/guide/people-and-keys-to-keep/[自分で持つべき人と物] と link:/guide/ai-and-in-house/[AI の時代に、委託をやめて自社で育てる] も、初めはそう書きました。この言い方は外れていました。画面の中の仕事しか数えていなかったからです。

== 何が起きるか

AIで作るのが安くなると、作られる物の数が増えます。その一つ一つを、会社や家や建物の中に入れて動かす人が要ります。機械を置き、配線し、つなぎ、その場で動くことを確かめる仕事です。これはAIだけではできません。

攻撃する側もAIを使うので、攻撃の数も増えます。攻撃を受けたとき、線を抜く、区画を止める、戻すといった作業は現場でやるしかありません。網が止まっていれば、外からAIで直すこともできません。

画面の中で作る仕事は減り、物と場所に触れる仕事が増える。ソフトウェア開発者は、現場に出ることになります。

== 前の言い方の何が外れていたか

. *作る物の数を考えていなかった。* 作る費用が下がるほど、作った物を現実の場所に入れて動かす仕事の割合は大きくなります。作るのは一度で済みますが、入れて動かすのは、置く場所の数だけ要ります。
. *攻撃と事故の場所を考えていなかった。* 攻撃が増えれば、受けたときの手当ても増えます。手当ての多くは、機械のある場所でしかできません。
. *判断を、画面の中の物だと思っていた。* 残る判断は、画面の上の正しさではなく、その場の物で確かめる判断です。扉が本当に閉まっているか。火災の信号で開くか。ルーターの見覚えのない設定は何か。どの線を抜けば被害が止まるか。決めることも判断することも残りますが、場所と手を離れては成り立ちません。

== 人に残る仕事

|===
| 仕事 | 中身 | 扉の現場では

| 置く、配線する、つなぐ | 機械を据え、電源と線を引き、網につなぐ | 錠、扉のコントローラ、読取機、ミニサーバー、ルーターを据え、扉の系統の区画を分けてつなぐ
| その場で確かめる | 図面と仕様のとおりに、現実の物が動くかを試す | 火災の信号で開くか、停電で設定どおりか、内側から機械で開くかを、実機で試す
| 点検する | 決めた周期で、見て、触って、記録する | ルーターの更新と外からの口、錠の電池、記録の連鎖を確かめる
| 止める | 攻撃や事故のときに、被害が広がる所を切り離す | 扉の系統の線を抜く、区画を止める。扉は内側から開けられる状態を保つ
| 戻す | 予備に入れ替え、元の状態に戻し、動くことを確かめる | 予備のミニサーバーにイメージから戻し、鍵を作り直し、扉の判断と記録が続くことを確かめる
|===

AI は、手順書と確かめる項目の案を作り、記録を読んで原因と手当ての案を出せます。その案を、現場で物に当てて実行し、結果を確かめるのは人です。ロボットが現場の作業を担う日が来るかもしれません。それでも、建物の中の配線を変えたり、扉の安全を実機で確かめたりする仕事を任せられるのは、まだ先です。

== 網が止まったとき

外の AI も、業者のクラウドも、網を通ってしか届きません。網が止まった建物で頼れるのは、その場にある物と、その場にいる人です。

* 扉は、網が無くても自分で判断し、記録を続けます(link:/guide/open-specification/[扉のコントローラの仕様])。
* 人は、手元の手順書と予備の部品で、切り離し、入れ替え、戻します。
* 連絡の手段も、網が止まっても使える形で持っておきます。

== ソフトウェア開発者は現場に出る

コードを書く仕事は AI が引き受けます。開発者に残るのは、作った物を現実の場所で動かし、守り、直す仕事です。扉なら、据付、受入れ試験、点検、事故の手当てです。

育て方も変わります。link:/guide/people-and-keys-to-keep/[自分で持つべき人と物] の「育て方」に書いたとおり、学ぶ重みはセキュリティと、仕組みを自分の手で実際に動かせることにあります。そこに、現場で物に触れることが加わります。疑似の扉で手順を覚え、実機で据付と試験をし、予備への入れ替えと切り離しを練習します。
